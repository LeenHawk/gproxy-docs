This page shows how to call GPROXY in each supported protocol, with and without streaming, and what the common error codes mean. It assumes you finished the [Quick start](/getting-started/quick-start) and have a model route named `fast` and a gateway API key. The examples use the default address `http://127.0.0.1:8787`; change it if you changed the port.

```sh
export GPROXY_KEY='your-gproxy-api-key'
```

## Sending the key

GPROXY reads the gateway key from `Authorization: Bearer <key>`, `x-api-key` or `x-goog-api-key`, so each protocol's usual header works. If a request carries more than one, `Authorization` is used first, then `x-api-key`, then `x-goog-api-key`. The CLI and container host also accept Gemini's `?key=` query parameter; a header always takes precedence over it.

Always send a gateway key here. Upstream credentials are stored in providers and are not accepted by the gateway.

## OpenAI Chat Completions

```sh
curl -sS http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'content-type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"Say hello."}]}'
```

## OpenAI Responses

```sh
curl -sS http://127.0.0.1:8787/v1/responses \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'content-type: application/json' \
  -d '{"model":"fast","input":"Say hello."}'
```

## Claude Messages

```sh
curl -sS http://127.0.0.1:8787/v1/messages \
  -H "x-api-key: $GPROXY_KEY" \
  -H 'anthropic-version: 2026-10-21' \
  -H 'content-type: application/json' \
  -d '{"model":"fast","max_tokens":256,
       "messages":[{"role":"user","content":"Say hello."}]}'
```

## Gemini GenerateContent

Gemini puts the model name in the path rather than in the body:

```sh
curl -sS "http://127.0.0.1:8787/v1beta/models/fast:generateContent" \
  -H "x-goog-api-key: $GPROXY_KEY" \
  -H 'content-type: application/json' \
  -d '{"contents":[{"parts":[{"text":"Say hello."}]}]}'
```

## Streaming

For OpenAI and Claude, set `"stream":true` in the body. Pass `-N` to curl so it prints events as they arrive instead of buffering them:

```sh
curl -sSN http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'content-type: application/json' \
  -d '{"model":"fast","stream":true,
       "messages":[{"role":"user","content":"Count to three."}]}'
```

Gemini uses a separate method, `streamGenerateContent`, with `alt=sse` for server-sent events:

```sh
curl -sSN "http://127.0.0.1:8787/v1beta/models/fast:streamGenerateContent?alt=sse" \
  -H "x-goog-api-key: $GPROXY_KEY" \
  -H 'content-type: application/json' \
  -d '{"contents":[{"parts":[{"text":"Count to three."}]}]}'
```

## Which protocol to use

The `fast` route works with all of the examples above, whatever protocol its upstream uses. GPROXY answers in the protocol the client sent and converts to and from the upstream's format in between.

Conversion does not add features. Whether a request succeeds still depends on the route's members, what the upstream supports, and whether that particular conversion is supported. A feature the upstream lacks stays unavailable when you call it through a different endpoint.

## Listing models

The console's model catalog lists the gateway model names you have configured. To get the catalog visible to the caller through the API:

```sh
curl -sS http://127.0.0.1:8787/portal/api/models \
  -H "Authorization: Bearer $GPROXY_KEY"
```

Each entry has a `permitted` field that says whether this caller may use it. Application does not serve `/portal/api` over HTTP; use the catalog in the app instead.

`GET /v1/models` is a different thing: it forwards the model list of the selected upstream, not the gateway catalog.

## Selecting a provider or namespace

The URL prefix and the model name together pick the target:

| URL | Model in request | Target |
| --- | --- | --- |
| `/v1/chat/completions` | `fast` | The `fast` route |
| `/openai-main/v1/chat/completions` | Upstream model ID | The `openai-main` provider |
| `/acme/v1/chat/completions` | `fast` | The `acme/fast` route |

The naming rules are in [Models and routes](/guides/models).

## Common errors

| Status | Meaning |
| --- | --- |
| `400` | Invalid request or configuration value |
| `401` | Missing, invalid, disabled, or expired key |
| `403` | Insufficient permissions or OAuth scope |
| `404` | Unknown model, route, or resource |
| `429` | A rate or quota limit applies |
| `5xx` | Gateway or upstream failure; inspect the logs |

Each request appears in the console's usage and request records. Whether the request and response bodies are kept depends on the logging settings; see [Usage, logs and audit](/guides/observability).
