本頁列出實例提供的全部 HTTP 路由，以及請求路徑的解析順序。需要確認某個 URL 對應哪個操作、供應商或命名空間前綴會帶來什麼變化、請求如何在供應商之間失敗轉移時，可以查閱本頁。原生宿主和 Workers 宿主掛載的是同一張路由表。`gproxy-protocol` 本身不宣告任何路徑，URL 與操作的對應關係由本頁所述的入站層決定。

各路由完整的請求與回應結構見 [HTTP API 參考](/zh-tw/reference/http-api)。

## 閘道自身的路由

閘道自己只有少數幾條路由，其餘路徑全部交給資料面處理。這與常見做法相反：閘道自身的路由是一份固定的短清單，其他路徑都是實例要轉發的上游 API，因此支援新的上游介面時不需要在這裡增加路由。

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| `GET` | `/healthz` | 存活檢查及已發布的設定 revision；無需認證 |
| `GET` | `/info` | 實例名稱、版本和建置 hash |
| `GET` | `/robots.txt` | 禁止所有爬蟲 |
| `GET` | `/publications/{id}` | 已發布的內容。id 本身就是憑據，因此不需要 key |
| — | `/admin/api/…` | 管理 API |
| — | `/portal/api/…` | 終端使用者自己的 API |
| — | 其餘路徑 | 入站處理（OAuth issuer、廠商服務、資料面、控制台） |

```sh
curl -s http://127.0.0.1:8787/healthz
```

```json
{"revision":2,"status":"ok"}
```

`/healthz` 只讀取已發布的快照，不存取資料庫，也不存取 cache，負載均衡器頻繁輪詢也不會給兩者增加壓力。

所有回應都帶有 `x-robots-tag: noindex, nofollow`。

## 請求處理順序

不屬於閘道自身路由的請求按以下順序處理：

1. CORS 與客戶端位址。CORS 預檢請求在這一步直接應答，不會轉發，因為它詢問的是本實例接受什麼。客戶端位址按[可信代理規則](/zh-tw/reference/configuration#可信代理)解析，之後才會寫入任何日誌。
2. 掛載點：路徑開頭哪一部分屬於本閘道，見[掛載點](#掛載點)。
3. OAuth issuer，路徑為 `{mount}/v1/oauth/…`。這些路徑屬於本實例而不是某個上游，並且使用 OAuth 的錯誤格式應答，所以排在資料面之前匹配。
4. 渠道的廠商服務路由，例如 Codex 的 `/backend-api/…`、Claude Code 的 `/api/…`。只在供應商或命名空間掛載點上匹配：匹配它需要確定渠道，而聚合掛載點不指定渠道。
5. [資料面](#資料面端點)。
6. 控制台（啟用時），帶 SPA 回退。

以上都不匹配的請求傳回 404。

### 共用路徑的方言判斷

`/v1/models`、`/v1/models/{id}` 和 `/v1/files` 在 OpenAI、Claude 和 Gemini 的 v1 API 中寫法完全相同。方言決定轉換時使用哪一套協定型別，判斷錯誤會讓客戶端收到無法解析的回應。

閘道根據客戶端自己的認證請求標頭判斷：有 `x-goog-api-key` 時按 Gemini 處理，有 `anthropic-version` 或 `x-api-key` 時按 Claude 處理。這些請求標頭由廠商 SDK 每次都會發送。兩者都沒有時，按表中的第一行即 OpenAI 處理。

### 檔案與影片的歸屬

檔案和影片的 id 由上游分配，而一個上游憑證通常由許多呼叫方共用，所以閘道自己記錄每個資源由誰建立。上傳或建立影片成功後，閘道把它記在呼叫方名下，同時記下處理該請求的憑證。同一使用者的所有金鑰和控制台工作階段算作同一個呼叫方，每個 OAuth 授權各算一個呼叫方。

- 取得、下載、輪詢或刪除某個 id 時，除非該呼叫方是經閘道建立的，否則一律傳回 404。屬於他人的 id 與不存在的 id 得到相同的答覆。請求會發往持有該資源的憑證。
- 列表只顯示呼叫方自己的條目。分頁游標（`has_more`、`last_id`、`nextPageToken`）原樣直接傳遞，因此一頁的條目可能少於 `limit`，甚至在還有後續頁時為空。請持續翻頁，直到上游表示沒有更多。
- 在這項檢查出現之前建立的檔案和影片，以及直接在上游建立的，都無法透過閘道存取。
- Gemini 的可續傳上傳（google-genai SDK 的預設方式）照常可用。start 請求傳回的 `x-goog-upload-url` 是繫結到呼叫方的閘道 URL，資料在同一憑證上轉發到上游工作階段，上傳完成的檔案歸該呼叫方所有。其他呼叫方使用這個 URL 會得到 404。部署在代理之後時，請設定 `public_base_url`（或轉發 `Host` 和受信任的 `X-Forwarded-Proto`），讓該 URL 指向客戶端能存取的位址。
- 其他請求中引用的檔案同樣適用這條規則：Chat、Responses 或 Claude 訊息中的 `file_id`（包括 code interpreter 容器的 `file_ids`）、指向 Files API 檔案的 Gemini `fileData.fileUri`、影片的 `input_reference`。引用的檔案不是該呼叫方上傳的，會在發出任何請求之前傳回 404；請求在持有這些檔案的憑證上執行。分別上傳到兩個不同憑證的檔案不能在同一個請求中使用（400）。multipart 表單也按同樣方式檢查（`file_id`、`file_ids[]`、`input_reference[file_id]` 欄位）。
- 在 Responses WebSocket 上，新的 response 會在持有其引用檔案的憑證上建立上游連線。續接（`previous_response_id`）留在原帳號上，引用其他憑證上的檔案會收到 `error` 事件；需要使用這些檔案時，請開始一個新的 response。
- 在 Realtime 或 Gemini Live 連線上，如果客戶端訊息引用了呼叫方在該連線憑證上並不擁有的檔案，訊息不會轉發：Realtime 傳回 `error` 事件（`file_not_found`），Gemini Live 以代碼 `1008` 關閉連線。

### Realtime 與 WebSocket 工作階段

標準 Realtime 與 GPT-Live 的協定和帳號權限不同。舊版 `/v1/live` 路由為相容而保留。新的 Live 路由和自訂音色建立需要 OpenAI API Key；Codex 渠道支援標準 Realtime、臨時憑據（client secret）和顯式結束通話。工作階段建立傳回 201 只表示請求已被接受，不代表工作階段一定能執行。

臨時憑據是可直連上游的 bearer 憑據。相關介面的正文不會被封包擷取，客戶端之後直接發往上游的請求也不經過閘道的准入和計量。顯式結束通話和控制連線沿用建立者的權限範圍和原憑證，並在准入之前恢復原來繫結的模型，重新檢查目前的模型權限。

`POST /v1/realtime/calls` 是攜帶 SDP offer 的 HTTP multipart 請求，後續的 WebSocket 握手不帶請求體。兩者靠 call id 關聯，call id 位於路徑中或 `?call_id=` 參數中。引擎據此把連線固定到應答該 offer 的憑證上，因此查詢字串會原樣轉發。

Realtime 工作階段不做方言轉換，只支援同方言直通。客戶端可以在回應進行中繼續傳送內容，這種互動在半雙工方言中沒有對應的形式。

Realtime 請求在升級連線之前完成准入。順序是：認證、驗證握手、准入、上游握手，最後才傳回 `101`。因此每一種拒絕都是客戶端能讀取的普通 HTTP 回應；如果先接受連線再立即關閉，客戶端既拿不到狀態碼，也拿不到回應體或錯誤碼。上游拒絕握手時，其回應原樣轉發：廠商傳回的 `429 {"error":{"code":"insufficient_quota"}}` 比閘道自己產生的 502 更有參考價值。

Realtime 連線會一直佔用並行名額直到關閉，而不是在發出 `101` 後就釋放。執行一小時的工作階段會佔用名額一小時。

Responses 的 HTTP POST 與 WebSocket GET 共用 `/v1/responses` 路徑。握手時認證呼叫方；之後每條 `response.create` 提供的模型用於權限檢查、選路和產生限流。不同的 `stream_id` 可以並行。新的回應鏈可以重新選擇目標，帶 `previous_response_id` 的續接保持原來的目標。空閒的 Responses 連線不佔用產生並行名額。

原生 Responses WebSocket 會轉發上游的控制事件。橋接到 HTTP Responses、Chat、Claude 和 Gemini 時，支援本機上下文預熱、中斷、steering 後繼，以及在 HTTP 產生段之間注入輸入。本機預熱不會預填充上游快取。`store:false` 的歷史只在客戶端連線期間保留；持久化的續接會儲存隔離後的歷史和目標繫結。已經開始或結果不確定的產生不會換目標重放。

### Codex 專用路由

Codex 專有操作只在使用 Codex 渠道的供應商掛載點下提供。假設供應商名為 `codex`，呼叫路徑為 `POST /codex/v1/memories/trace_summarize`。這些路由同樣經過正常的操作准入、模型路由和結算；聚合的 `/v1` 不提供這些路徑。標準的 `/v1/moderations` 仍使用自己的 `create_moderation` JSON 契約。

帳號服務也可以在 `/codex/v1` 下呼叫，包括 `usage/thread_usage/query_v2`（POST）、`usage/plan_limit_history`，以及每日 token、積分、工作區、外掛和技能統計（GET）。原生寫法 `/codex/api/codex/**`、`/codex/backend-api/**`、`/codex/ps/**` 同樣可用。管理員可以透過 `x-gproxy-view: credential:<id>` 讀取指定憑證的上游報表。在預設的呼叫方檢視和池檢視中，無法從本機記錄重建的歷史額度和廠商積分會標記為不可用，金額為 `null`，不會借用其他帳號的資料，也不會顯示為零。

## 掛載點

同一個實例在三種掛載點上提供相同的上游 API：

| 路徑 | 掛載點 | 解析範圍 |
| --- | --- | --- |
| `/v1/messages` | 聚合 | 不限制 |
| `/acme/v1/messages` | 命名空間 `acme` | `acme/` 下的公開名稱 |
| `/openai-prod/v1/messages` | 供應商 `openai-prod` | 該供應商 |

命名空間是帶斜線的公開模型名的第一段：公開 `acme/fast` 即產生命名空間 `acme`。供應商掛載點使用供應商的 `name`，即你自己起的名稱，而不是行 id，因為沒有人會把自動產生的 id 寫進客戶端的 Base URL。命名空間與供應商同名時，命名空間優先。

只有去掉前綴後剩餘的路徑也是閘道提供的路由時，前綴才會被去掉。如果不做這項檢查，名為 `backend-api` 的供應商就會吞掉 `/backend-api/codex/responses` 這條真實存在的 Codex 路徑，把一次資料面呼叫變成一個並不存在的掛載點。當第一段與某個命名空間或供應商同名、但剩餘部分不是已知路由時，路徑保持原樣，按聚合掛載點處理。漏認一個掛載點會得到一個看得見的 404；錯認則會把請求發給錯誤的上游。

掛載點透過給模型名加前綴來限制解析範圍，這正是解析器表示供應商或路由的語法：`/acme/v1/messages` 加上 `{"model":"fast"}` 會解析 `acme/fast`。已經帶有該前綴的名稱保持不變，所以客戶端兩種寫法都可以。供應商掛載點也會把不帶模型的操作（例如檔案操作）限制在該供應商上。

在命名空間掛載點上呼叫廠商服務路由時，由該命名空間中渠道提供此路由的那一個供應商處理。如果有多個供應商都提供，請求傳回 409，請改用對應供應商自己的掛載點。

## OAuth issuer

issuer 端點相對於掛載點前綴（`""`、`/acme`、`/openai-prod`）：

```text
GET  {prefix}/v1/oauth/authorize    同意頁交接（瀏覽器則 302 到 `/console/authorize`）
POST {prefix}/v1/oauth/authorize    使用者的決定
POST {prefix}/v1/oauth/token        code、refresh 與裝置授權
POST {prefix}/v1/oauth/device/code
POST {prefix}/v1/oauth/revoke
GET  {prefix}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{prefix}/v1   （RFC 8414 §3.1）
```

issuer 識別碼為 `{origin}{prefix}/v1`，所以聚合掛載點的 issuer 是 `https://host/v1` 而不是 `https://host`。這樣一條規則就能覆蓋三種掛載點。RFC 8414 要求該識別碼與客戶端取得元資料的位址一致，而只有宿主知道請求來自哪個掛載點，因此由宿主傳入。

這些端點使用 OAuth 規定的錯誤格式（RFC 6749 §5.2，`error` 為字串），而不是閘道通常的錯誤結構。裝置授權的批准頁面本身屬於使用者入口操作，即 `/portal/api/oauth/device`，由控制台的 `/console/device` 頁面呼叫。

v3 把這些端點放在根路徑下。移到 `/v1` 之下後，它們與 `/v1/messages` 遵循同一條前綴規則。v3 從未實現發現端點，客戶端原本就是硬編碼位址，所以這次調整幾乎沒有遷移成本。

## 管理 API

每個管理資源族都有相同的六條路由：

```text
GET    /admin/api/{family}           列表（分頁與過濾在 query 裡）
POST   /admin/api/{family}           建立
GET    /admin/api/{family}/{id}      讀取
PATCH  /admin/api/{family}/{id}      更新
DELETE /admin/api/{family}/{id}      刪除    → 204
POST   /admin/api/{family}/batch     批次
       [{"create": …}, {"update": {"id": …, "patch": …}}, {"delete": "id"}]
```

這些路由由同一份宣告產生，因此不會有哪個資源族缺少其中一條。一次批次操作無論包含多少行，都是一個 revision 提交：要麼全部寫入，要麼全部不寫入。

身份類資源族：`users`、`api-keys`、`organizations`、`teams`、`permissions`、`rate-limits` 和 `oauth-clients`。組織和團隊成員透過各自的成員介面管理（`organizations/{id}/members`、`teams/{id}/members`）。以下資源族與六條路由有所不同：

- `oauth-clients` 用 `POST …/{id}/retire` 代替刪除，因為客戶端簽發過的授權仍然引用它。在它的批次操作中，delete 項表示停用；含停用的批次只能全部是 delete，因為停用在單獨的交易中執行，不能與建立、修改放進同一個提交。已停用的 `client_id` 可以重新註冊，新註冊沿用原來的行，停用時撤銷的授權仍保持撤銷狀態。
- `api-keys` 的批次操作不接受建立：建立 key 時會傳回明文，而批次操作沒有地方傳回它。
- 會導致實例不再有任何啟用中管理員的 `users` 批次操作整體被拒絕。

設定類資源族：`providers`、`credentials`、`models`、`provider-models`、`routes`、`route-members`、`connection-profiles`、`rule-sets`、`rules`、`provider-rule-sets`、`operation-rules`、`operation-endpoints`、`quotas`、`price-rules`、`price-rates`、`price-tiers`。

其他管理端點：

- 實例：`settings`、`export`、`import`、`connectivity/test`、`audit`、`session`、`sessions`、`context`，以及 `update`（宿主支援自更新時）。
- 憑證：`credentials/{id}/…` 下的 `reveal`、`status`、`refresh`、`quota`、`quota-probe`、`quota-reset`、`quota-reset-credits`、`quota-diagnostics`、`quota-observations`、`health-reset`、`limits`、`models/discover` 和 `models/test`；`credentials/owners`、`credentials/providers`；以及 `credential-login/…` 下的授權碼和裝置碼登入流程。
- 模型與路由：`models/discover`、`models/discover/apply`、`models/test`、`model-names`、`operation-keys`、`providers/{id}/routing`、`providers/{id}/routing-defaults/reset`、`providers/{id}/default-rule-set`。
- 規則：`rule-sets/{id}/rules`、`rule-sets/{id}/rule-presets/{preset}`、`rule-presets`。
- 配額：`quotas/status`、`quotas/{id}/reset`、`quotas/{id}/limit-reset`。
- 目錄：`channels`、`tls-presets`、`default-model-catalog`、`default-model-catalog/apply-prices`。
- 詞表：`tokenizer-vocabs`、`tokenizer-auth`。
- 使用者：`users/{id}/password`、`users/{id}/sessions`、`users/{id}/allowlist`；API key：`api-keys/{id}/rotate`、`api-keys/{id}/secret`。
- 歷史記錄：`usage`、`usage/records`、`logs/downstream`、`logs/upstream`、`logs/captures/{id}`，見[用量、日誌與稽核](/zh-tw/guides/observability)。

完整列表及參數見 [HTTP API 參考](/zh-tw/reference/http-api)。v4 的管理請求與資料結構已有變化，舊腳本請對照該參考重新核對。

每個管理請求都經過同一個中介軟體：認證（以 cookie 認證的非安全方法還要做同源驗證）→ 確定呼叫方的管理範圍 → 執行操作 → 寫入稽核記錄。每個請求都會記錄稽核，被拒絕的請求也不例外。該中介軟體是 route layer，因此未知的 `/admin/api/…` 路徑直接傳回 404，不會存取資料庫。管理請求體上限為 50 MiB，足夠容納一次設定匯入。

## 使用者入口 API

```text
POST   /portal/api/login             使用者名稱 + 密碼 → 工作階段 cookie 與令牌
POST   /portal/api/logout
GET    /portal/api/context           呼叫方、他們的成員關係、他們的特性開關
GET    /portal/api/models            全部公開名稱，各自標註 `permitted`
GET    /portal/api/usage             他們自己的花費
GET    /portal/api/quota             他們自己的預算視窗
GET    /portal/api/requests          他們的近期請求（若已啟用）
GET    /portal/api/sessions
GET    /portal/api/keys              （+ POST、DELETE …/{id}、POST …/{id}/rotate、GET …/{id}/secret）
GET    /portal/api/oauth-sessions    （+ DELETE …/{id}）
POST   /portal/api/password
GET    /portal/api/oauth/device      查詢待批准的裝置碼（?userCode=），供 `/console/device` 使用
POST   /portal/api/oauth/device      批准或拒絕；需要登入工作階段或帶管理權限的 key
```

使用者入口路由只要求呼叫方已認證，不做其他檢查。不需要角色檢查，因為每個入口操作都只作用於發起請求的呼叫方本人，而且沒有任何一個接收使用者 id。漏寫的權限檢查可能成為漏洞，而根本不存在的參數無從濫用。

`login` 和 `logout` 不經過這項檢查。`login` 在呼叫方確定之前執行；`logout` 必須對已經過期的工作階段也能生效，否則瀏覽器會留下一個永遠無法清除的 cookie。

## 解析與失敗轉移

模型名的四種形式及其嘗試順序見[模型與路由](/zh-tw/guides/models)。失敗轉移預算的規則如下：

- 預算是路由自己的 `maxAttempts`，上限為 `settings.maxAttempts`。
- 預算在各目標之間共享。每個目標最多獲得與其憑證數量相同的嘗試次數，且不超過剩餘預算，因此一次請求計劃的上游呼叫次數不會超過預算。
- 只有換一個供應商可能成功的失敗才會轉移到下一個供應商：沒有可用憑證、憑證失效、續接固定在其他位置、任何渠道或傳輸錯誤，或者上游傳回 401、403、429、5xx。
- 預算耗盡、請求被禁止、請求被取消、轉換失敗，以及 store 或 cache 故障，都會就地停止。
- 沒有可轉移的目標時，最後一個應答原樣傳回。最後一個供應商傳回的 429 就是呼叫方收到的 429，不會被替換成閘道產生的錯誤。

請求體只緩衝一次，以便在其他目標上重放。超過 `maxRequestBodyBytes` 的串流請求體保持串流傳輸，請求計劃隨之縮減為單個目標：為了失敗轉移而把大檔案全部讀入記憶體並不划算。
