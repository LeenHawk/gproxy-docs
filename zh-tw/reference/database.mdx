GPROXY 的儲存分三部分，各自獨立設定：資料庫、快取，以及可選的檔案儲存。本頁介紹每部分有哪些後端、如何選擇，以及執行多個執行個體或規劃備份時需要注意什麼。

## 資料庫

資料庫儲存全部設定、身份、用量和日誌。原生程式（`gproxy`）可以開啟 SQLite、PostgreSQL 或 MySQL；Cloudflare Workers 宿主可以開啟 D1 或 libSQL。

| 後端 | 連線方式 | 適用範圍 |
| --- | --- | --- |
| SQLite（預設） | `<data-dir>/gproxy.db`，或 `--dsn` 中的檔案路徑、`sqlite://` URL | 原生程式，始終編譯在內 |
| PostgreSQL | `--dsn` 中的 `postgres://…` | 原生程式，`postgres` feature（預設開啟） |
| MySQL | `--dsn` 中的 `mysql://…` | 原生程式，`mysql` feature（預設開啟） |
| D1 | Worker 的 D1 binding（預設名為 `DB`） | Workers 宿主 |
| libSQL / Turso | `GPROXY_DATABASE_URL` 中的 `libsql://` 或 `https://` URL，權杖放在 `GPROXY_LIBSQL_TOKEN` | Workers 宿主 |

MySQL 需要 8.0.13 或更新版本，這是第一個支援 JSON 預設值表示式的版本。PostgreSQL 和 MySQL 驅動均帶 TLS 支援。

### 選擇後端

對原生程式，通常只需設定 `--dsn`（`GPROXY_DSN`）：沒有設定 `--persistence`（`GPROXY_PERSISTENCE`）時，由 URL 的 scheme 決定後端。

```sh
gproxy serve --dsn 'postgres://gproxy:…@db.internal:5432/gproxy'
```

`GPROXY_PERSISTENCE` 可取 `sqlite`、`postgres` 或 `mysql`。v2、v3 部署遺留的 `sqlite://` DSN 仍然接受，程式取其中的檔案路徑。`:memory:` 會被拒絕：資料庫隨處理程序消失的執行個體會照常初始化管理員、服務流量，然後把這些全部丟掉。

本次構建不包含的後端會在啟動時被拒絕，錯誤資訊會指出提供該後端的 feature。問題在處理程序啟動時就會暴露，而不是等到第一個請求。原生程式同樣拒絕 D1 和 libSQL，這兩種只能由 Workers 宿主開啟，相關 binding 見 [Cloudflare Workers](/zh-tw/deployment/edge)。在 Workers 宿主中，`GPROXY_DATABASE_URL` 優先於 D1 binding。libSQL 透過 HTTP 存取資料庫，使用的是 Worker 呼叫上游時用的同一個 fetch 傳輸。

### 表結構同步

```text
$ gproxy migrate --data-dir ./data
INFO gproxy::instance: schema is up to date warnings=0
```

表結構從實體定義推導，而不是靠一串編號的遷移指令碼。一份註冊表描述所有表。同步時，在新資料庫上建立缺失的表；在已有資料庫上，在後端支援的範圍內補上缺失的欄位和索引。重複執行不會丟失資料。

`gproxy serve` 啟動時也會同步表結構。`gproxy migrate` 用於把同步作為獨立步驟、由單一寫入者在所有執行個體啟動前執行的部署。多個執行個體共用一個資料庫時應當這樣做，以免多個執行個體同時修改表結構。

同步不會做以下事情：

- 建立預設設定或管理員；
- 執行版本化遷移；
- 修改欄位的型別、轉換欄位中的資料，或修改已有的外部索引鍵。

這些變更需要顯式遷移，而且 GPROXY 不保證遷移在每個原生後端上都在單個交易中完成。

同步報告會列出警告，例如 D1 上的型別差異。警告列表為空並不能證明所有變更都已應用。在確認啟動完成之前，請閱讀日誌中的診斷資訊。

### Store API 與批處理

原生 SeaORM 連線和 Cloudflare D1 透過同一套 store API 存取。所有實體存取器都經過同一個泛型倉儲，普通 CRUD 不需要按表手寫，每個方法作為一個原子批執行。建立 store 不會開啟資料庫，也不會修改表結構。

呼叫方可以依賴以下行為：

- 讀取結果與輸入順序一致，保留重複項，缺失的 id 對應 `None`，呼叫方可以把結果逐一對應到請求。
- 鍵謂詞會被拆分，使每條語句都不超過 D1 的 100 個繫結參數上限，拆分後的語句仍在同一個批中執行。呼叫方自己寫的 SQL 不會被拆分，資料庫本身的請求數和大小限制仍然適用。
- SQL 錯誤會回滾交易性寫入。條件寫入影響 0 行時回傳衝突，不會回滾同一批中的其他語句。
- 不會自動重試。提交結果不確定時（例如連線中斷），請先檢查已儲存的狀態，再決定是否重新寫入。

### 精確金額

金額和限額以縮放後的整數儲存，不使用浮點數。最小單位是 `0.000000001`，可表示範圍約為 ±92 億。

SQL 欄位型別為 `BIGINT`。實體以文字形式在 D1 的 JavaScript 邊界上傳遞這些值，使比較、排序和加法在資料庫內仍按數值進行；JSON 中使用十進位字串也是出於同樣的原因。

計算使用 decimal 型別，並且只對整次結算舍入一次，採用四捨六入五成雙（ties to even）。遞增計數器之前，結算會檢查負值和有符號溢位。

## 快取

快取儲存短期狀態：帶 TTL 的值、精確計數器、許可與租約，以及失效通知 topic。快取不儲存業務實體，也不儲存持久帳本；需要長期保留的資料都寫入資料庫。

| 後端 | 選擇方式 | 共享範圍 |
| --- | --- | --- |
| 記憶體 | 原生程式的預設值（`memory` feature） | 不共享，僅一個處理程序 |
| Redis / Valkey | `GPROXY_REDIS_URL`；程式需帶 `redis` feature 構建 | 使用同一 Redis 的所有執行個體 |
| 資料庫 | Workers 宿主的預設值 | 使用同一資料庫的所有 isolate |

原生程式在啟動時連線 Redis，連不上就退出。限流計數儲存在快取裡，連不上 Redis 的執行個體即使接受了流量，也只能把受限流的請求逐個拒絕。資料庫快取只用於 Workers 宿主，原生程式會拒絕這種設定。發布版程式使用預設 feature 集，其中不含 `redis` 和 `s3`；需要它們的部署請自行構建（見[構建](/zh-tw/development/building)）。

### 操作

| 操作 | 行為 |
| --- | --- |
| `get` / `put` / `delete` | 不透明位元組；必須提供正的 TTL；每次 put 產生新版本 |
| `compare_exchange` | 當前版本與預期一致（或鍵不存在）時替換或刪除 |
| `counter` / `increment` / `decrement` | 精確的非負整數，帶原子上限檢查 |
| `acquire_permit` | 最多 N 個存活持有者，各自有 TTL |
| `acquire_lease` | 上限為 1 的許可，用作重新整理租約 |
| `publish` / `subscribe` | 失效提示，不保證送達 |

每個操作只對單個鍵保證原子性，跨鍵不保證。鍵值、計數器、許可和 topic 是相互獨立的名稱空間，同一個名字可以在每個名稱空間中各自存在。

計數器使用固定時間窗，只有建立計數器的那次呼叫設定 TTL，因此每個執行個體只憑時鐘就能算出時間窗邊界。許可沒有時間窗：它統計的是在途請求，時間窗邊界無法切分在途請求。許可的 TTL 只決定請求異常退出、沒有釋放許可時，快取等多久才把許可收回。

### 快取故障

Redis 出故障時，GPROXY 不會改用處理程序內快取。如果兩個執行個體各自退回本機狀態，它們會持有相互衝突的鎖，並分別統計同一個限額，這比直接報錯更糟。

受限流約束的請求，如果快取無法完成判斷，會以 `429` 拒絕，且不帶 `Retry-After`。如果放行這類請求，一次快取故障就會悄無聲息地關閉執行個體上的所有限流，而維運人員察覺不到。

### 部署多個執行個體

多個執行個體需要共享快取：原生執行個體使用 Redis，Workers 上使用資料庫快取。如果每個程序各用自己的快取，每個執行個體會各自統計限流、各自重新整理同一個 OAuth 權杖，也收不到其他執行個體發出的設定失效通知。

登入工作階段同樣儲存在快取中，所以在一個執行個體上發起的登入可以在另一個執行個體上完成。在負載均衡後面，這是常見情況。

多個部署或多套環境共用一台 Redis 時，請為每個部署設定獨立的 namespace（預設為 `gproxy`）。通知 channel 名中包含資料庫編號，因為 Redis Pub/Sub 會忽略 `SELECT`。

### 資料庫快取

Workers isolate 沒有常駐處理程序，也沒有 Redis，因此 Workers 宿主把快取放在 D1 或 libSQL 資料庫的三張表中。過期時間在 SQL 中比較，同一資料庫上的所有 isolate 對哪些條目仍然有效的判斷一致。

這種後端沒有通知傳輸。訂閱只會收到最初的 resync 提示，此後再無訊息。Workers 宿主改為在每個請求開始時讀取一次設定 revision，這就是它全部的同步機制。

## 設定同步

一次設定寫入經過以下步驟：

```text
commit_revision([語句…, config_revision += 1, 讀回])   一個交易
      ↓
reload   本執行個體的快照
      ↓
publish  ConfigurationChanged { revision, scopes }
```

資料行和 revision 遞增在同一個交易中寫入。如果分開寫，其他執行個體可能在資料行寫入之前就讀到新的 revision。

其他執行個體透過兩種方式得知變更，兩者缺一不可：

| 機制 | 傳遞的內容 | 失效方式 |
| --- | --- | --- |
| 共享快取上的失效通知 | 毫秒級的“重新檢查” | 訊息可能丟失 |
| 輪詢 `settings.config_revision` | 持久化的 revision，每 30 秒一次 | 較慢 |

通知從不攜帶設定內容，只說明存在哪個 revision；只有當該 revision 比執行個體正在使用的更新時，執行個體才重新載入。無法解析的通知載荷一律觸發重新載入。

快取中的計數器不能代替資料庫中的 revision。Redis 重啟或淘汰可能丟失這個計數器；先提交資料庫、再向 topic 發布，仍然是兩次獨立的操作，不構成一個交易。

重新載入依序執行，且只向前推進：舊 revision 不會覆蓋新 revision；重新載入失敗時，上一份快照繼續提供服務。

## 檔案儲存

檔案儲存是可選的，設定後端之前處於關閉狀態。

| 後端 | 選擇方式 | 原生程式 | Workers 宿主 |
| --- | --- | --- | --- |
| 本機檔案系統 | `--file-storage-dir`（`fs` feature，預設開啟） | 支援 | 不支援 |
| S3 相容儲存，含 R2 | `[file_storage]` 設定塊（`s3` feature） | 支援 | 支援 |

檔案儲存儲存發布內容的正文（`/publications/{id}` 提供的位元組）和下載的 tokenizer 詞表。檔案元資料和歸屬儲存在資料庫中，儲存後端只儲存內容。

沒有檔案儲存時，發布和詞表下載都回傳“不支援”，因為沒有地方存放這些位元組。

發布連結還需要 `GPROXY_PUBLIC_BASE_URL`。沒有設定時，發布會在寫入任何正文之前失敗，並提示呼叫方改為直接內聯獲取位元組。GPROXY 不會用請求的 `Host` 標頭拼接連結，因為這個標頭由用戶端決定：上游會接受答覆，位元組會被存下，交出去的 URL 卻可能指向一個回傳 404 的主機。

## 備份

- SQLite：停止處理程序後複製 `<data-dir>/gproxy.db`，或使用 SQLite 的線上備份。請把主密鑰和副本儲存在一起，沒有主密鑰就無法讀取加密資料庫中的憑證密鑰。
- PostgreSQL 和 MySQL：使用資料庫自帶的匯出工具。
- D1 和 libSQL / Turso：使用平台提供的快照。
- 邏輯匯出：`gproxy export --out config.json --include-secrets`。匯出內容是設定而非歷史資料，不包含身份、用量和 capture。見[設定](/zh-tw/reference/configuration#匯出與匯入設定)。

每個加密密鑰都繫結到所在行的 id，把某一行的密鑰恢復到另一行上是行不通的。這樣可以防止密鑰在行之間被調換，對整庫恢復沒有影響。
