本頁說明 GPROXY 如何根據價格表計算一次交換的費用，以及如何編輯這些表。錄入價格、排查費用異常或設定費用預算時會用到。

## 概述

引擎在結算時為每次交換計價，依據是供應商、上游模型，以及渠道從回應中提取出的歸一化用量。預算和觀察者讀取的是同一個計算結果。（v3 中引擎把用量交給應用層，由應用層再算一遍，結果出現了兩套模型匹配邏輯，對“模型沒有價格”也有兩種不同的處理。v4 只在一處計價。）

價格存放在三張表中：

- `price_rules`：每行選中一個模型，可以限定某個供應商和某個操作。
- `price_rates`：該規則下每個指標的基礎價。
- `price_tiers`：按提示長度和服務檔位覆蓋該規則的 token 價格。

所有價格和結算金額均以 USD 計。

## 規則選擇

一條規則同時滿足以下條件時適用於某次交換：

- 規則的供應商就是這次交換的供應商，或者規則沒有指定供應商（全域規則）；
- 規則的 `modelPattern` glob 匹配上游模型名；
- 規則的 `operation` 與請求的操作相同，或者沒有指定（覆蓋全部操作）。

供應商規則先於全域規則匹配。同一組內 `(priority, id)` 最小的規則勝出。

| 欄位 | 含義 |
| --- | --- |
| `providerId` | `null` 表示全域規則 |
| `modelPattern` | 匹配上游模型名的 `*` / `?` glob |
| `operation` | `null` 覆蓋所匹配模型的全部操作 |
| `priority` | 越小越先匹配，相同時按 id 排序 |
| `currency` | 必須為 `USD` |
| `enabled` | 停用的規則不參與匹配 |

幣種不是 `USD`、pattern 不是合法 glob 或操作名未知的規則，會在裝配快照時被跳過（見[無效行](#無效行)）。

如果一次交換的用量按嘗試（attempt）分別報告，每個可計費的嘗試按其自身模型對應的規則計價，再把金額相加。標記為不可計費的嘗試不計入。

### 沒有匹配規則的交換

沒有任何規則匹配時，這次交換不計價：費用為零，照常結算，用量中帶有以下維度：

```json
{"dimensions": {"unpriced": "true"}}
```

請求不會因此被拒絕。缺少價格屬於設定遺漏，靠這個維度可以找出正在免費提供的模型，而不必在有人錄入價格之前拒絕流量。

## 費率列

一個費率列是某條規則下某個指標的基礎價。

| 欄位 | 含義 |
| --- | --- |
| `metric` | 內建指標鍵，或渠道產出的任意自訂鍵 |
| `unit` | `token`、`count`、`second` 或 `character` |
| `unitQuantity` | 正數分母：1 000 000 個 token、1 張圖、60 秒 |
| `value` | `unitQuantity` 個單位的非負價格，單位 USD |
| `conditions` | `null` 表示兜底行；否則是“維度名 → 純量值”的非空物件，所有條件都必須匹配 |
| `priority` | 同一指標的多行中，越小越先嘗試 |

對每個指標，帶條件的行按 `(priority, id)` 順序嘗試，第一個所有條件都與結算維度匹配的行生效；都不匹配時使用兜底行。命中的條件行取代兜底價，而不是與它疊加。

```json
[{"metric":"input_tokens",  "unit":"token","unitQuantity":"1000000","value":"0.40"},
 {"metric":"output_tokens", "unit":"token","unitQuantity":"1000000","value":"1.60"},
 {"metric":"image_outputs", "unit":"count","unitQuantity":"1","value":"0.04",
  "conditions":{"quality":"hd","size":"1024x1024"},"priority":0}]
```

### 避免重複計費

每個費率計價的數量不能與其他費率重疊。具體來說：

- 命中快取的 input 與普通 input 分開計數。
- 已經包含在某個彙總項中計費的 reasoning 或媒體 token 子集，不能再單獨計價一次。
- 按圖計費和按 token 計費的輸出價格二選一。只有廠商確實兩樣都收時才同時填寫。
- 通用的 `tool_calls` 行和具體的 `web_searches` 行不能對同一次呼叫重複計費。
- 用戶端在請求中宣告工具不等於伺服器端執行了工具，不應計費。

## 指標

token 指標習慣上按每百萬 token 定價：

```text
input_tokens          output_tokens           cached_input_tokens
cache_creation_tokens
reasoning_tokens      image_input_tokens      image_output_tokens
audio_input_tokens    cached_audio_input_tokens  audio_output_tokens
video_input_tokens    video_tokens
```

計數、時長與字元指標：

```text
image_outputs   video_outputs   audio_seconds   video_seconds   audio_characters
search_units    web_searches    web_fetches     file_searches
code_interpreter_sessions       tool_calls      requests
```

以上只是內建鍵的列表，並不限制可用的指標：不在列表中的指標，只要有費率列引用，同樣會被計價。

非 token 類指標的費用為

```text
amount × value / unitQuantity
```

服務檔位的乘數不作用於這些指標。

`requests` 是按請求收取的費用，每個被計價的交換計一次請求。

### 快取寫入

快取寫入統一計為 `cache_creation_tokens`。用量中可能有多個保留時長不同的寫入桶，每個桶分別計價。要為某個保留時長單獨定價，新增帶 `ttl_seconds` 條件的費率列：`{"ttl_seconds":43200}` 匹配 12 小時寫入；不帶該條件的行是預設價格。

在檔位中，寫入價格以列表形式給出，`ttlSeconds: null` 是預設項：

```text
cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]
```

價格按每百萬 token 計。保留時長只用於選擇價格，不參與乘法。

快取讀取是單一的 `cached_input_tokens` 計數，沒有 TTL。

## 分層

`price_tiers` 行只覆蓋 token 價格，並且一律按每百萬 token 計。

| 欄位 | 含義 |
| --- | --- |
| `serviceTier` | `null` 表示上下文檔位；否則是服務檔位，如 `standard`、`priority`、`flex`、`batch` |
| `minPromptTokens` | 非負閾值，包含端點；預設 0 |
| `multiplier` | 僅用於服務檔位：繼承價格要乘的係數。上下文檔位不設定 |
| `*_per_million` | 某一類 token 的顯式價格 |

顯式價格列有 `input`、`output`、`cache_read`、`cache_creation`、`reasoning`、`image_input`、`image_output`、`audio_input`、`cached_audio_input`、`audio_output`、`video_input` 和 `video`，均帶 `_per_million` 字尾。`cache_creation_per_million` 是[快取寫入](#快取寫入)一節所述的列表。

判斷閾值時，提示長度等於 input token、快取讀取與快取寫入之和，每項只計一次。

### token 價格的計算順序

每類 token 的價格分三步確定：

1. 基礎費率：該指標的 `price_rates` 行，帶條件的行先嘗試。
2. 上下文檔位：在沒有服務檔位的行中，取提示長度已達到的最高 `minPromptTokens` 那一行。該行設定了哪些類的顯式價格，就替換哪些類的基礎價。
3. 服務檔位：在服務檔位等於實際服務檔位的行中，取已達到的最高閾值那一行。該行有顯式價格時直接使用；否則把上一步得到的價格乘以該行的 `multiplier`（預設 1）。

閾值相同時，`(priority, id)` 較小的行勝出。價格為 `null` 表示沿用上一步的結果；`0` 表示該類免費。

<Warning>
服務檔位的顯式價格會取代它下面的整條階梯，包括上下文檔位。設基礎 input 價為 1，上下文台階為 `≥ 200 000 → 2`，提示長度為 300 000 個 token：

| `batch` 行 | 實際 input 費率 |
| --- | --- |
| `{"serviceTier":"batch","multiplier":"0.5"}` | `2 × 0.5 = 1` |
| `{"serviceTier":"batch","inputPerMillion":"0.5"}` | `0.5`（200k 台階失效） |
| `{"serviceTier":"batch","minPromptTokens":200000,"inputPerMillion":"1"}` | `1` |

要麼在需要覆蓋的每個閾值上重複寫出顯式檔位價，要麼改用乘數。
</Warning>

### reasoning token 與快取讀取

reasoning token 是 output token 的子集。規則有 reasoning 價格時，reasoning token 從 `output_tokens` 中扣除，按 reasoning 價格單獨計費；沒有時，它們留在 output 中，按 output 價格計一次。

沒有單獨價格的快取讀取沿用 input 價格；其他沒有價格的 token 類一律免費。快取讀取本來就是 input token，沿用 input 價格是穩妥的預設值。而音訊或影片缺少價格屬於設定遺漏，按零計價能讓這個遺漏在費用裡直接顯現出來。

### 請求的服務檔位與實際服務檔位

計價使用回應中報告的服務檔位，而不是請求中要求的檔位。廠商把 `priority` 請求降級處理時，按降級後的檔位行結算。服務檔位名比較時不區分大小寫。

## 編輯價格

每張表都有對應的管理 API：

```sh
curl -s http://127.0.0.1:8787/admin/api/price-rules  -H "Authorization: Bearer $GPROXY_KEY"
curl -s http://127.0.0.1:8787/admin/api/price-rates  -H "Authorization: Bearer $GPROXY_KEY"
curl -s http://127.0.0.1:8787/admin/api/price-tiers  -H "Authorization: Bearer $GPROXY_KEY"
```

每組都有通常的五個路由和一個批次路由。一次批次操作無論包含多少行，都作為一個 revision 提交。在控制台中，全域價格在“模型”頁編輯，供應商價格在供應商的“模型”標籤中編輯，見[控制台](/zh-tw/guides/console#配額與價格)。

### 應用內建目錄價格

內建模型目錄收錄了發布時已知模型的價格。從目錄建立規則：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

不帶 `providerId` 時，規則使用目錄自帶的 glob 和優先順序，一條全域規則即可為所有提供該模型的供應商計價。帶 `providerId` 時，模型名原樣作為 pattern，優先順序為 0。

使用 `"overwrite": false` 可以隨時重複應用目錄：已經存在的規則（例如你修改過的規則）保持不變，在回應中計入跳過數。

### 無效行

無法使用的計價行（幣種不是 USD 的規則、非法 pattern、未知操作、`unitQuantity` 不為正數的費率、不是“非空純量物件”的條件）會在裝配設定快照時被丟棄並記錄 warn 日誌。快照的其餘部分照常載入，一個輸錯的數值不會讓正在服務流量的執行個體停下來。修改價格後請檢查日誌中是否有這類警告。

## 費用預算

費用預算是一行 metric 為 `cost`、以 USD 計的 `quotas`。准入階段，引擎拿到呼叫方鏈 `[api_key?, user, team?, org?]`，鏈上每個歸屬者的每個已啟用預算都對該請求生效。

費用在上游呼叫回傳後才結算，因此在途請求和併發請求可能使預算超出上限。預算的歸屬和檢查方式見[權限、限流與費用預算](/zh-tw/guides/permissions)。

## token 估算

可計費的回應完全沒有用量時，引擎自行統計 token，並把記錄標記為 `estimated = true`。統計使用本機詞表，按以下順序選擇：

1. GPT 系列模型使用 tiktoken 編碼；
2. 模型目錄行指定的詞表；
3. 內建的 DeepSeek 詞表。

列出已儲存的詞表，或從 Hugging Face 下載詞表並指定給某個模型和執行個體預設值：

```sh
curl -s http://127.0.0.1:8787/admin/api/tokenizer-vocabs -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/tokenizer-vocabs \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"repo":"…","filename":"tokenizer.json","modelId":"…","setAsDefault":true}'
```

下載的檔案先寫入已設定的檔案儲存，然後在一次 revision 提交中寫入詞表行、模型指標和預設指標。順序不能顛倒：指向從未寫入的檔案的行會讓之後每次重新載入都失敗，而沒有對應行的檔案只是浪費一點空間。

詞表依賴檔案儲存。沒有設定檔案儲存時，所有詞表路由都回傳“不支援”。見[檔案儲存](/zh-tw/reference/database#檔案儲存)。
