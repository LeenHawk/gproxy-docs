本文供管理員將 v3 部署升級到 v4 時參考。v4 啟動時會辨識 v3 資料庫並原地轉換，支援 SQLite、PostgreSQL、MySQL 和 D1。資料目錄或連線字串、`GPROXY_MASTER_KEY` 都沿用原值，不需要匯出資料，也不需要重設密碼。

## 變更內容

資料庫 schema 整體更換。v4 讀取 v3 的資料表，寫入新的 v4 資料表，全部完成後才開始處理請求。各類資料的處理方式如下：

- 供應商與憑證：轉換已知的渠道名稱及其設定，憑證以目前的主金鑰重新加密。
- 模型路由與成員：路由原有的公開模型名稱成為路由名稱；其餘每個名稱展開為一條獨立路由，並複製成員。
- 使用者、密碼、API key、組織與團隊：全部遷移。密碼雜湊（Argon2）和 API key 摘要原樣保留，原有的使用者名稱、密碼和金鑰繼續可用。
- 價格與預算：換算為 v4 的單位。v4 金額保留 9 位小數，超出部分依「四捨六入五成雙」捨入，並在報告中列出。
- 權限、限流與改寫規則：遷移支援的寫法；含義有變化或無法對應的內容在報告中列出。
- 團隊和組織權限：展開為每位已遷移成員（包括已停用使用者）各自的使用者規則。規則依升級時的成員關係產生，之後成員異動不會同步。沒有已遷移成員的群組在報告中記為略過。早期版本升級時沒有展開這類權限，已經升級過的執行個體遺失的權限不會由後續版本補回。
- 歷史用量：分批次匯入原始 token 數、歸屬和已結算費用，不重新計價，也不重新結算配額。v4 沒有對應欄位的 v3 欄位保存在 `metrics.v3` 中。
- 封包擷取、請求日誌、工作階段和稽核歷史：不轉換，保留在 v3 備份中。所有人都需要重新登入控制台。

渠道或設定無法轉換的供應商會連同依賴它的資料列一起略過，並在報告中註明。略過只針對無法轉換的內容；資料庫讀寫錯誤或主金鑰不正確時，升級仍會中止。

原有的 v3 啟動參數繼續有效，v4 仍接受 `--persistence db` 和 `sqlite://` 形式的 DSN。Docker 映像檔的目錄結構與 v3 相同（資料在 `/app/data`，使用者為 `65532:65532`），但 v3 標籤執行的仍是 v3，需要換成 v4 標籤。

## 準備工作

1. 確認 `GPROXY_MASTER_KEY` 設定在哪裡（`.env` 檔案、服務單元或容器環境變數），並另存一份。v4 必須用同一把金鑰解開憑證；金鑰不正確時，升級會在變更任何資料之前停止。
2. 保留 v3 執行檔，或記下 v3 映像檔標籤，回復時需要。
3. 安排停止所有 v3 執行個體。升級期間只能有一個處理程序寫入資料庫。如果 v3 和 v4 分別使用不同的資料庫同時執行，不要讓它們共用同一份 OAuth 憑證，否則雙方更新 token 時會讓對方的 token 失效。
4. CLI 部署使用 PostgreSQL 或 MySQL 時，確認 v4 建置包含對應的資料庫驅動程式。

然後在 v3 停止的狀態下備份資料庫：

<Tabs>
  <Tab title="SQLite">
    複製整個資料目錄。目錄中有 `gproxy.db`，可能還有 `gproxy.db-wal` 和 `gproxy.db-shm`；WAL 檔案裡可能有尚未寫回 `gproxy.db` 的已提交資料，三個檔案要一起複製。

    ```sh
    cp -a data data.v3-backup
    ```

    升級過程中 v4 還會在資料庫旁邊另寫一份備份（見下文），因此要預留相當於兩份資料庫大小的可用空間：一份備份，一份轉換後的新資料庫。
  </Tab>
  <Tab title="PostgreSQL">
    ```sh
    pg_dump --format=custom --file=gproxy-v3.dump "$GPROXY_DSN"
    ```
  </Tab>
  <Tab title="MySQL">
    ```sh
    mysqldump --single-transaction --databases gproxy > gproxy-v3.sql
    ```
  </Tab>
  <Tab title="D1">
    ```sh
    wrangler d1 export gproxy --remote --output=gproxy-v3.sql
    ```
  </Tab>
</Tabs>

## 升級步驟

1. 停止所有 v3 執行個體。
2. 以 v4 執行檔取代 v3，或將容器映像檔換成 v4 標籤。Workers 部署則以原有的 D1 binding 和 Secrets 部署 v4 Worker。
3. 以原來的資料目錄或連線字串、原來的 `GPROXY_MASTER_KEY` 啟動 v4。也可以先單獨執行 `gproxy migrate`，它走同樣的升級流程，完成後結束。
4. 觀察日誌。SQLite 部署依序會看到 `migrating v3 database to v4`、每張資料表一行 `migrated`、帶有列數、捨棄數和警告數的 `v3 import complete`，最後是帶有備份路徑的 `v3 migration complete`。含義發生變化的內容列在 `Changed on the way in` 下，沒有 v4 對應形式的資料列列在 `NOT migrated` 下。
5. 日誌顯示服務開始監聽後，登入控制台。

Worker 在部署後的第一個請求中轉換資料庫。轉換未完成的執行個體不處理請求，也不會建立新的管理員，因此轉換結束前請求都會失敗。

## 遷移過程

### SQLite

在開啟 HTTP 連接埠之前，v4 先用 `VACUUM INTO` 產生 v3 資料庫的一致快照（包含 WAL 中已提交的內容），以 `gproxy.db.v3-*.bak` 儲存在資料庫旁邊。隨後在原資料庫旁的暫存目錄中將這份快照轉換成新資料庫，以現有主金鑰解密憑證。只有匯入成功後，才將新資料庫重新命名到原路徑上。

轉換失敗時原檔案保持不變，依日誌指出的原因修正（例如還原原來的主金鑰）後重新啟動即可。如果在重新命名之前中斷，原路徑上仍是 v3 資料庫，下次啟動會重新嘗試；重新命名之後，原路徑上是 v4 資料庫，其遷移帳本表明它已是目前版本，之後的啟動都是一般的 v4 啟動，不會重複匯入。

### PostgreSQL、MySQL 與 D1

v4 先讀取並檢查 v3 資料，包括主金鑰能否解開憑證，確認無誤後才將每張 v3 資料表重新命名為 `gproxy_v3_<原表名>`，並以原來的資料表名稱建立 v4 資料表。設定、身分資料和歷史用量從重新命名後的資料表中轉換，最後一步完成後執行個體才開始處理請求。

進度記錄在 `gproxy_v3_upgrade` 資料表中，其 `report_json` 欄位保存略過的資料列和含義變化的警告。身分資料和用量分批次寫入，每批次之後記錄檢查點；升級中斷後，下次啟動（Workers 上是下一個請求）會從中斷處繼續。

各資料庫以不同方式防止第二個處理程序同時遷移：

- PostgreSQL 在整個升級期間持有工作階段層級的 advisory lock，並在一個交易中完成所有 v3 資料表的重新命名。
- MySQL 持有工作階段鎖（`GET_LOCK`），鎖在 DDL 陳述式隱含提交後依然有效；所有 v3 資料表以一條 `RENAME TABLE` 陳述式重新命名。
- D1 以交易性 batch 重新命名。遷移租約在每批次寫入時都會檢查，防止另一個 isolate 同時寫入；升級中斷後，租約最多 60 秒後失效。

第二個 PostgreSQL 或 MySQL 執行個體取不到鎖時，會以 `another instance is migrating this database; retry after it finishes` 結束。Workers 上的提示則是等租約釋放後重試。

失敗後，v3 資料仍在封存資料表中，v4 資料表裡可能已有部分匯入的資料。修正報告的錯誤後重新啟動，升級會繼續進行。升級完成之前，不要刪除 `gproxy_v3_upgrade`，也不要重新命名封存資料表。

## 檢查升級結果

1. 閱讀遷移報告：SQLite 在啟動日誌中，其他資料庫在 `gproxy_v3_upgrade.report_json` 中。重點查看被略過的供應商和權限變化。
2. 執行 `gproxy migrate --status`。它列出本版本的每個 schema 遷移以及資料庫是否已套用，只讀不寫，也不會執行 v3 升級。
3. 在控制台中確認供應商、憑證、模型路由、使用者和 API key 都在，用量統計中的歷史總數與原來一致。
4. 以一個原有的 API key 傳送請求，參照[第一個請求](/zh-tw/getting-started/first-request)。

確認無誤後，可以刪除 `gproxy.db.v3-*.bak`（SQLite），或刪除 `gproxy_v3_<表名>` 封存資料表（其他資料庫）。如需保留報告，請留下 `gproxy_v3_upgrade`。此後 v4 的 schema 變更記錄在 SeaORM 的 `seaql_migrations` 資料表中。

## 回復

v3 無法讀取 v4 資料庫，轉換到一半的資料庫兩個版本都無法使用，所以回復只能還原 v3 資料。升級之後寫入的內容（新用量、設定修改）都會遺失。

<Tabs>
  <Tab title="SQLite">
    1. 停止 v4。
    2. 將 `gproxy.db` 以及可能存在的 `gproxy.db-wal`、`gproxy.db-shm` 移到別處。
    3. 將 `gproxy.db.v3-*.bak`（或自己備份中的 `gproxy.db`）複製為 `gproxy.db`。
    4. 重新安裝 v3 執行檔或換回 v3 映像檔標籤，以原來的參數和主金鑰啟動。
  </Tab>
  <Tab title="PostgreSQL、MySQL 與 D1">
    1. 停止所有執行個體。
    2. 將升級前的備份還原到一個空資料庫中。
    3. 以原來的主金鑰讓 v3 連線還原後的資料庫並啟動。

    不要讓 v3 連線已部分或全部轉換過的資料庫。
  </Tab>
</Tabs>

## 匯入到另一個執行個體

上面的流程是原地轉換。如果要將 v3 資料庫或匯出檔案匯入另一個 v4 執行個體，請使用 `import --from-v3`：

```sh
gproxy --data-dir ./other-instance migrate
gproxy --data-dir ./other-instance import --from-v3 /path/to/v3-backup.db
```

目標必須為空，或者只包含同一匯入先前未完成的那次執行。來源資料中的金鑰已加密時，以 `--source-master-key` 或 `GPROXY_IMPORT_SOURCE_MASTER_KEY` 提供 v3 的主金鑰。加上 `--skip-unmappable-providers` 會像自動升級一樣略過無法轉換的供應商；不加時，遇到這樣的供應商匯入會停止。

輸入也可以是 v3 `POST /admin/api/export` 匯出的 JSON，匯出時需帶上 `{"include_secrets": true}`。這種匯出不含密碼雜湊、權限、限流和供應商模型，而 SQLite 資料庫中都有。匯入不含雜湊的匯出檔案時，以 `--admin-password` 設定控制台密碼；匯入 SQLite 不需要。
