## 廠商服務路由

有些廠商 CLI 需要的不只是推論端點。它們還會從廠商控制面取得帳號資料、用量視窗、外掛、任務和檔案，這些請求失敗時 CLI 就無法正常運作。

因此渠道可以宣告一張服務路由表，列出它認識的控制面路徑以及每條路徑回傳的內容。宿主在轉發到資料面之前，先用這張表比對進來的路徑。

控制面路徑因廠商而異，所以只在供應商或 namespace 掛載點上比對。聚合掛載點不指定渠道，沒有渠道也就沒有路由表可查：

```text
https://gproxy.example/codex/backend-api/wham/profiles/me
                       ^^^^^ 名為 "codex" 的供應商（或 namespace）
```

表中沒有的路徑回傳 `404`，檢視為 `credential:{id}` 時除外（見下文）。

### 選擇檢視

請求頭 `x-gproxy-view` 指定呼叫方想要的結果。不帶此請求頭時檢視為 `caller`，一般成員也只能使用 `caller`。

| 請求頭 | 回傳內容 |
| --- | --- |
| `x-gproxy-view: caller` | 呼叫方自己的資料：其用量視窗、預算鏈，以及其自身呼叫建立的資源。身分、用量和設定類請求不會存取廠商。 |
| `x-gproxy-view: pool` | 同上，但在目標中的所有憑證上彙總。 |
| `x-gproxy-view: credential:{id}` | 原樣轉發。用指定憑證自己的鑑權存取上游，廠商的回應不做修改直接回傳。 |

能使用哪種檢視取決於憑證歸屬。目標是呼叫方在該供應商上可見的憑證集合，與同一把 key 發起模型呼叫時可用的憑證相同。只有實例管理員，或者擁有該集合中全部憑證的組織或團隊的 `Admin` 成員，才是這個目標的管理員。其他人都是成員，只能使用 `caller`；請求 `pool` 或 `credential:{id}` 會回傳 `403`。

要求「全部憑證」是為了保證管理一個組織時，不會看到混有其他組織憑證的池。沒有歸屬的憑證也就沒有人能是它的管理員，所以在憑證全部共享的單租戶實例上，只有實例管理員能使用 `pool` 和 `credential`。

任何檢視下都拒絕簽發 key。共享訂閱上的長期 API key，正是共享閘道要避免發放出去的憑據。

### 計量與取消

廠商服務呼叫不占用限流租約，否則一次資料查詢就會消耗呼叫方留給付費流量的額度。服務呼叫也不寫 capture 記錄：引擎不為服務呼叫寫上游記錄，下游記錄便無從關聯，看起來會像一個沒有到達任何上游的請求。

服務呼叫仍然經過預算鏈，因為 `caller` 檢視要據此顯示呼叫方自己的額度視窗。查詢額度不會消耗額度。

服務呼叫與模型請求使用同一個取消權杖。取消會中止憑證準備、上游呼叫和 HTTP 回應的串流讀取。對 WebSocket 服務，權杖涵蓋握手階段，連線建立後由宿主管理。服務呼叫同樣不占用限流租約，也不產生模型用量。

## Codex CLI

`codex` 渠道宣告了 CLI 在 Responses 之外向 ChatGPT 後端發起的呼叫。介面細節以 `samples/codex` 下 CLI 自己的原始碼為準。

| 類別 | 路徑 |
| --- | --- |
| 外掛與 MCP | `/backend-api/ps/**` |
| 帳號、設定、用量、任務、環境、遠端控制 | `/backend-api/wham/**` |
| 上傳 | `/backend-api/files/**` |
| 工作區外掛共享 | `/backend-api/public/plugins/**` |
| 啟動時的身分探測 | `GET /v1/user-auth-credential/whoami` |

CLI 有兩種方式存取同一批端點：ChatGPT 主機上使用 `/backend-api/wham/**`，Codex API 主機上使用 `/api/codex/**`。這兩種寫法，以及裸的 `/codex/**` 和 `/ps/**` 掛載，在查表前都會統一為 `/backend-api/**`，所以用戶端設定成哪種主機風格都可以。

`/backend-api/wham/remote/control/server` 是 WebSocket，也是唯一需要協定升級的服務路由。Codex 不接受合成檢視，因此只能由該憑證的管理員傳送 `x-gproxy-view: credential:{id}` 來存取。

表中沒有歸類的路徑落入 `/backend-api/{*path}` 前綴規則，原樣轉發，非 2xx 回應也一樣。

## Claude Code

`claudecode` 渠道宣告了 CLI 在 Messages 之外發起的 OAuth 範圍內 `/api/**` 呼叫：profile、validate、roles、bootstrap、用量、政策限額、帳號設定、檔案上傳與下載、組織連接器、外掛與 skill、新手引導與計費控制、桌面端更新跳轉，以及 Claude Design 介面。

這些呼叫全部送往 `api.anthropic.com`。`claude.ai` 只用於憑證的 cookie 初始化，所以渠道在處理這些呼叫時不會存取它。

在 `caller` 和 `pool` 檢視下，身分、用量和設定類回應由本實例已知的資訊合成，其中的 id 是供應商與呼叫方身分的穩定雜湊。CLI 顯示的帳號、組織和方案都是 GPROXY 產生的值；不會捏造任何關於共享上游帳號的資訊，也不會洩漏它。

## GPROXY 作為 OAuth 授權伺服器

使用 OAuth 登入的 CLI 可以登入到本 GPROXY 實例，而不是登入到廠商。這與 SDK 的 `login()` 是兩回事：在 `login()` 中，GPROXY 是別家授權伺服器的 OAuth 用戶端。

```text
  Claude Code ──authorize/token──▶ gproxy   （授權伺服器）
                                     │
                                     └──login()──▶ OpenAI   （用戶端）
```

每個掛載點下都有這組端點，用戶端探索到的就是它所存取的掛載點對應的授權伺服器：

```text
GET  {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/token
POST {mount}/v1/oauth/device/code
POST {mount}/v1/oauth/revoke
GET  {mount}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{mount}/v1
```

```sh
curl -s http://127.0.0.1:8787/v1/.well-known/oauth-authorization-server
```

```json
{"issuer":"http://127.0.0.1:8787/v1",
 "authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/authorize",
 "token_endpoint":"http://127.0.0.1:8787/v1/oauth/token",
 "device_authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/device/code",
 "revocation_endpoint":"http://127.0.0.1:8787/v1/oauth/revoke",
 "response_types_supported":["code"],
 "grant_types_supported":["authorization_code","refresh_token",
   "urn:ietf:params:oauth:grant-type:device_code"],
 "code_challenge_methods_supported":["S256"]}
```

v3 把這些端點放在根路徑；v4 把它們移到 `/v1` 之下，與 `/v1/messages` 遵循同一條前綴規則，共用一份實作。

### 授權伺服器的安全規則

- 必須使用 PKCE S256。`plain` 會被拒絕，不帶 challenge 也會被拒絕。所有註冊的用戶端都是 public 用戶端，沒有 secret 可以證明身分，能阻止外洩的授權碼換取令牌的只有 verifier。
- redirect URI 必須精確比對，不接受前綴、萬用字元或「同源」。任何更寬鬆的規則都會放行某個攻擊者控制的 URL。
- 授權碼、refresh token 和裝置碼都只能使用一次。每次都在一個原子批次中消耗並替換，因此無論兩次兌換如何交錯，都不可能同時成功。
- 重放授權碼或 refresh token 會撤銷整個令牌族：該授權、它的內部 key，以及它簽發過的所有令牌。回應遺失和憑據被竊無法區分，所以一律按外洩處理。合法用戶端重新登入即可，竊取者則不能。裝置碼流程例外，因為輪詢用戶端本來就會重複傳送裝置碼。

### OAuth 呼叫方的權限

access token 是使用者交給別人的程式使用的憑據。除非用戶端列在實例的 `oauth.cliClientIds` 中，否則該令牌只能列出模型、查詢模型、計算 token、生成、串流生成和壓縮，其他操作一律回傳 `403`。實例管理員的帳號也受此限制，管理員帳號恰恰最不應該讓第三方令牌取得管理權限。

把用戶端寫進 `cliClientIds`，代表維運者認可它在整個 API 上代表使用者操作。不過令牌仍受使用者授權的 scope 約束：每個操作都要求授權中包含對應的 `gproxy:{operation}` scope，列入名單的用戶端也不例外。

OAuth 呼叫方也不能簽發、輪換、檢視或刪除 key，不能修改帳號密碼。

## 工作階段親和性

多輪對話的 CLI 最好讓一個對話始終使用同一把憑證。GPROXY 按實際發出請求的用戶端的格式讀取對話識別碼，而不是按它將被轉發到的上游：轉發到其他渠道的 Claude Code 請求，讀取的仍是 Claude Code 的欄位。

按以下順序取第一個非空值：

1. 閘道自己的請求頭 `x-gproxy-session-id`。
2. 各用戶端的原生請求頭，依序為 `x-opencode-session`、`thread-id`、`session-id`、`x-claude-code-session-id`、`x-conversation-id`、`x-grok-session-id`、`x-session-id`、`x-session-affinity`、`session_id`。
3. 傳入請求本文格式自帶的工作階段欄位：Responses 的 `client_metadata.thread_id` 或 `session_id`；Claude 在 JSON 編碼的 `metadata.user_id` 內部的 `session_id`；Gemini 的 `request.session_id` 或 `request.sessionId`。Chat Completions 沒有這類欄位。
4. 對話穩定前綴的 sha256 指紋。
5. 請求 id，記錄為備援值，而不是當作工作階段。

只讀取上述欄位，不會在任意 JSON 中遞迴尋找名為 `session_id` 的欄位。請求級、輪次級和快取級識別碼，如 `x-grok-req-id`、`user_prompt_id`、`prompt_cache_key`、`previous_response_id`，都不會被當作工作階段。

閘道請求頭不會轉發給上游，用戶端傳來的也一樣：用戶端不能透過傳送閘道用來標識工作階段的請求頭，去選中其他呼叫方的對話。沒有任何工作階段請求頭的請求也不會被拒絕。
