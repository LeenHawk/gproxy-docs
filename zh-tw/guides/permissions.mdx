本頁說明 GPROXY 在把請求送往上游之前所做的幾項檢查：權限規則決定呼叫方能用什麼，限流決定能多頻繁地用，費用預算決定還能花多少錢。三者分開設定、分開檢查，無法互相取代。

## 檢查順序

金鑰驗證通過後，請求依以下順序准入：

1. OAuth scope 與 OAuth 操作基線，僅適用於使用 OAuth 存取權杖的請求。
2. 權限規則，得出呼叫方在目前的模型和操作上可以使用的供應商集合。
3. 憑證可見範圍，得出呼叫方可以使用的憑證集合。
4. 確定適用的費用預算。
5. 限流。

限流放在最後，因為只有這一步會消耗額度。前面任何一步拒絕的請求都不會計數，沒有權限的呼叫方也就無法耗盡別人仰賴的額度。在動用任何憑證之前，還會再檢查一次費用預算，並在上游呼叫結束後扣抵。

## 權限規則

權限規則可以指定使用者、API Key 或兩者都指定；兩者都不指定時，規則對所有使用者和 API Key 生效；兩者都指定時，只在該使用者使用這把 API Key 時生效。規則可以限定供應商、模型模式和操作，動作為 `allow` 或 `deny`。模型模式支援 `*` 與 `?`，因此要限制個別模型時，不必為它們另外建立供應商。

對每個供應商，規則依優先順序由高到低、同一優先順序再依 ID 排序逐條檢查，第一條適用的規則決定結果。需要例外時，請給例外規則較高的優先順序：優先順序 0 的 `allow *` 加上優先順序 10 的 `deny gpt-4*`，表示除了 `gpt-4*` 以外全部允許；優先順序 0 的 `deny *` 加上優先順序 10 的 `allow gpt-4o`，表示只允許 `gpt-4o`。若同一優先順序上有兩條適用但結論相反的規則，會依 ID 決定，結果固定但沒有實際意義，因此彼此重疊的規則應設為不同的優先順序。

沒有預設授權。一般使用者必須有適用的 `allow` 規則；對該模型沒有任何允許的供應商時，請求在路由之前就會以 `403` 拒絕。要把某個供應商開放給所有人，請建立一條不指定使用者和 API Key、只指定該供應商的 `allow` 規則。

執行個體管理員不受權限規則限制，可以存取所有供應商，這樣一條設錯的 `deny` 規則就不會把管理員擋在自己的執行個體之外。不過管理員同樣受下文的 OAuth 限制。

| API 欄位 | 意義 |
| --- | --- |
| `userId` / `apiKeyId` | 規則主體，皆為選填；都省略時對所有人生效 |
| `providerId` | 選填，省略時符合所有供應商 |
| `modelPattern` | 模型模式，預設 `*` |
| `operation` | 選填，省略時符合所有操作 |
| `action` | `allow` 或 `deny` |
| `priority` | 數值越大越先比對 |

模型目錄中的 `permitted` 欄位表示目前呼叫方能否使用該項目。無權使用的模型仍可能出現在目錄中。

### 供應商服務路由

供應商服務路由是渠道宣告的帳戶、用量等非模型端點。它們沒有模型，也沒有操作，因此只有涵蓋整個供應商的規則（任意模型、不限操作）才能允許或拒絕它們。

## OAuth 存取權杖

OAuth 存取權杖是使用者交給其他程式使用的憑據，因此 GPROXY 會在使用者本身的權限之外，對它另加限制。

預設情況下，權杖只能使用一組固定的基線操作：列出和讀取模型目錄、token 計數、生成、串流生成和壓縮。嵌入、圖像、音訊、檔案、影片、Realtime 等其他操作一律拒絕。把用戶端加入 `oauth.cli_client_ids`，即可為該用戶端解除基線限制。供應商服務路由不在基線內，同樣要求用戶端列在這份清單中。

此外，每個操作都要求權杖帶有對應的 `gproxy:<operation>` scope，operation 使用 snake_case 操作 ID，例如 `gproxy:list_models`、`gproxy:generate_content` 和 `gproxy:stream_generate_content`。供應商服務需要 `gproxy:services`。空 scope、`openid` 和 `profile` 不授予任何資源存取權；舊的用戶端需要請求所需的 scope 並重新授權。

這些檢查對所有權杖都有效。不論是執行個體管理員授權的權杖，還是列在 `oauth.cli_client_ids` 中的用戶端，都無法略過 scope 檢查；scope 也無法略過操作基線或一般的權限規則。

## 憑證可見範圍

只有模型權限還不夠，呼叫方還需要有一份可以使用的憑證。憑證歸屬於使用者、組織或團隊。一個請求能選用哪些憑證，取決於這次呼叫所用金鑰的綁定，而不是使用者的所有成員關係：同時屬於兩個組織的使用者，可以持有只綁定其中一個組織的金鑰，這把金鑰無法使用另一個組織的憑證。綁定團隊的金鑰也可以使用該團隊所屬組織的憑證。執行個體管理員可以選用所有憑證。

管理範圍、模型權限和憑證歸屬是三項獨立的設定。模型有權限、但沒有可見的憑證能處理時，請求會回傳 `503`（`no_usable_target`），而不是 `403`。

## 請求限流

限流規則可以指定使用者、API Key、兩者都指定或都不指定，含義與權限規則相同。規則包含指標、上限、週期秒數、選填的模型模式、計數方式和啟用狀態。

計數方式決定規則涵蓋的呼叫方如何分配這個上限：`shared` 表示整條規則共用一個計數器，`user` 表示每位使用者單獨計數，`key` 表示每把 API Key 單獨計數；沒有 API Key 的呼叫方（例如主控台工作階段）按使用者計數。對所有人生效、計數方式為 `user` 的規則會分別限制每位使用者；同樣的規則改為 `shared` 時，限制的是所有使用者的總和。

兩類指標的行為不同：

- `concurrency` 計算正在處理中的請求數。請求在回應完全送出之前會一直占用名額；串流回應在請求開始後可能占用很長一段時間。
- `requests` 以及其他任何指標名稱，計算目前週期內發出的請求數，每個請求計 1，與指標名稱無關。token 數要等上游回傳後才知道，所以需要限制 token 用量或花費時，請改用費用預算。

計數器儲存在快取後端。多執行個體部署必須共用快取，否則每個執行個體都會各自套用完整的額度。快取無法使用時，受限流約束的請求會被拒絕，而不是略過檢查直接放行。

請求被拒絕時，請依回傳的錯誤和日誌，判斷是呼叫方限流還是上游憑證的額度限制。

## 費用預算

費用預算可以設定在使用者、API Key、組織和團隊上，以 USD 計。請求會檢查金鑰和使用者的預算，以及金鑰實際綁定的組織、團隊的預算。綁定團隊的金鑰不會計入該團隊所屬組織的預算；若兩者都要計入，請把金鑰同時綁定到組織和團隊。

所有適用且已啟用的預算都必須還有餘額。週期和模型範圍在控制台中設定。

實際費用要等上游呼叫結束才能確定，並在那時結算。因此進行中的請求和並行請求可能使總額超過上限。預算用盡後會拒絕新請求，但並不是上游消費的硬性上限。

價格缺漏會同時影響費用統計和預算消耗，請一併檢查[價格設定](/zh-tw/reference/pricing)。API 中的預算金額以十進位字串傳輸。

## 供應商與憑證限額

供應商的預設限額會分別套用到每一份憑證，而不是由所有憑證共用一個額度池。憑證上已啟用的同名規則會覆寫供應商的預設規則；還原為繼承會刪除憑證自己的規則。

這些都是本地限額，與上游帳戶的額度無關。重設本地規則不會重設上游餘額或額度時段。詳見[供應商與憑證](/zh-tw/guides/providers)和[控制台](/zh-tw/guides/console)。

## 排查拒絕

- `401`：檢查金鑰及其使用者是否存在、已啟用且未過期。
- `403`：檢查權限規則、OAuth scope 和 OAuth 操作基線。
- `429`：檢查呼叫方限流、費用預算、憑證本地限額和上游額度。
- `503` 且錯誤為 `no_usable_target`：檢查呼叫方能否看到可處理該模型且已啟用的憑證。

先在控制台查看相關的使用者、金鑰和憑證，再依日誌中的具體錯誤，找出拒絕請求的規則。
