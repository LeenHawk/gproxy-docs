本章寫給負責把 GPROXY 接到上游的管理員，內容包括選擇渠道、建立供應商、新增和維護憑證，以及對外連線的設定。

**渠道**（channel）是編譯進二進位檔的上游轉接器，每個渠道對應一族上游。**供應商**（provider）是某個渠道上儲存的一條連線，由名稱、選填的 base URL、渠道自己的 `config` JSON 和一個憑證池組成。一個渠道下可以建立任意多個供應商，例如 `openai-main` 和 `openai-eu` 都可以使用 `openai` 渠道。

## 選擇渠道

### 接入相容服務

如果某個服務與標準 API 的差別只在服務位址和請求頭，就不需要專用渠道。用 `custom` 渠道建立供應商，填寫服務位址和它支援的協定即可：

```json
{ "name": "example-vendor", "channel": "custom",
  "baseUrl": "https://api.example-vendor.com",
  "config": { "dialects": ["openai_chat"] } }
```

只有在一行供應商設定無法表達某個服務的需求時，才會為它撰寫專用渠道。NVIDIA NIM、Vercel AI Gateway 和 Cloudflare AI Gateway 過去都用 `custom` 接入，現在各有專用渠道，提供各自的認證和餘額查詢，應優先使用。

## 建立供應商

在控制台開啟 **供應商**，點選 **新增供應商**，選擇渠道，填寫名稱和該渠道表單中的欄位，然後 **儲存**。接著新增憑證（見[憑證](#憑證)），先測試一把憑證，再把供應商加入模型路由。

也可以透過管理 API 建立：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/providers \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"example-vendor","channel":"custom",
       "baseUrl":"https://api.example-vendor.com",
       "config":{"dialects":["openai_chat"]}}'
```

修改不需要重新啟動。供應商和憑證的每次寫入都與設定版本號的遞增放在同一個交易裡提交；實例先重新載入自身設定，再通知其他實例，因此下一個請求就能用上新設定。

## 供應商設定

| 欄位 | 含義 |
| --- | --- |
| `name` | 管理員取的名稱，必須唯一。它同時是供應商掛載點（`/{name}/...`），也是 `provider/model` 寫法中的前半部分。 |
| `channel` | 上表中的某個渠道 id。 |
| `baseUrl` | 上游的來源位址，僅對接受 base URL 的渠道有效。 |
| `config` | 渠道自己的 JSON。每個渠道宣告自己讀取哪些鍵，`GET /admin/api/channels` 會列出。 |
| `connectionProfileId` | 該供應商對外呼叫使用的連線設定（代理、TLS 模擬），見[連線設定](#連線設定)。 |
| `enabled` | 停用的供應商不參與解析。 |

`custom` 的 `config` 包含 `dialects`（端點支援的協定格式）、靜態 `headers`、`allowed_headers` 和兩個 magic cache 開關。模擬廠商 CLI 的渠道會自行設定身分請求頭，用戶端無法覆寫。

以下各節說明個別渠道的專屬選項。

### Claude 模型 fallback

`fallback_mode` 可取 `off`（預設）、`default` 或 `models`；`fallback_models` 是按順序排列的上游模型 ID 列表。控制台根據渠道描述呈現這兩個欄位。列表中的空值、重複項和主模型會被略過，最多使用三個 fallback 模型。

不同渠道的執行方式不同：

- Claude API、Claude Code 和自訂 Claude 端點：傳送 Anthropic 的 `fallbacks` 欄位及對應的 beta 頭。`default` 模式由 Anthropic 選擇 fallback 模型。
- OpenRouter：Claude Messages 請求傳送 `fallbacks`，Chat Completions 請求傳送 `models`，由 OpenRouter 執行 fallback。這不影響 `provider.allow_fallbacks`，後者控制的是同一模型在不同供應方之間的路由。用戶端已經帶了 `fallbacks` 或 `models` 時以用戶端的值為準。Responses 請求不加 fallback 參數，因為 OpenRouter 沒有為它提供公開參數。
- Vercel、Azure、Vertex 和 AWS Bedrock：由 GPROXY 自己在同一憑證上用下一個設定的模型重試 Claude `refusal`，每次重新準備請求並重新簽章。`default` 模式選擇主模型命名空間下的 `claude-opus-4-8`。雲端廠商專用的模型 ID 請按該上游接受的完整 ID 設定。

閘道 fallback 對從其他協定轉換為 Claude 的請求同樣生效。它只處理 refusal，不重試任意 HTTP 錯誤。串流內容到達即下發；一旦已經有輸出，只有上游簽發了帶 prefill 宣告的 credit 才能繼續，沒有可兌現的 credit 時絕不重放伺服器端工具。每次實際嘗試分別記錄，並按各自的模型計價；回報零輸出的 refusal 不計費。最終回應保留最後一次嘗試的頂層 usage。

### Claude Code 額度續用模式

`claudecode` 渠道有兩個開關，決定訂閱額度用盡時的行為，預設都是 `false`。

- `low_priority: true`：5 小時額度被拒絕後，接受伺服器端給出的低優先權方案。此後同一工作階段傳送 `anthropic-usage-limit: slow`，直到該視窗重設或伺服器端結束這個模式。週額度和單獨的低優先權額度仍然有效。
- `extended_usage: true`：在未確認已開通付費額外用量時，為工具結果續輪傳送 `anthropic-usage-limit: extended`。是否給予寬限由伺服器端決定，訂閱額度不會因此重設。

即使兩個開關都關閉，用戶端自己傳送的 `slow` 或 `extended` 也會保留，兩者互斥。CountTokens 和控制類請求不帶這個請求頭。對 Claude Code 以外的用戶端，以工具結果訊息判斷續輪；官方 CLI 內部的任務深度和實驗開關，閘道拿不到。

傳送 `slow` 期間，GPROXY 遇到 `429 slot_busy` 和過載回應時會等待，然後在同一憑證上重試緩衝好的原始請求。與 CLI 2.1.302 一致，預設間隔 20 秒，隨機浮動 30%，預設最長等待 20 分鐘；伺服器端給出的提示值被限制在每次 5–600 秒、總計 1–360 分鐘之內。宿主的截止時間或取消訊號可以提前結束等待。預算耗盡、週額度耗盡和資格拒絕直接回傳，不做這種重試；已經開始的回應串流、無法重放的請求本文和不透明的 fallback credit 兌換請求都不會重放。

額度檢視還會記錄伺服器端回報的低優先權額度和寬限額度，這些額度不會攔截一般請求。顯式模式只對當前請求放行它所適用的訂閱視窗；本機預算、模型專屬額度以及上游失敗或限流的冷卻仍然生效。

### Claude Code 用戶端身分

`client_identity` 決定 `claudecode` 渠道以哪個官方用戶端的身分發出請求。兩種身分都是同一個 CLI 二進位檔、同一個 OAuth 令牌。

- `cli`（預設）：互動式 CLI，`claude-cli/2.1.318 (external, cli)`。用戶端自帶的合法 CLI User-Agent 和計費區塊中的 `cc_entrypoint` 會保留。
- `agent_sdk`：Claude Agent SDK 0.3.318，`claude-cli/2.1.318 (external, sdk-ts, agent-sdk/0.3.318)`。只保留用戶端自帶的 Agent SDK User-Agent（`sdk-ts` 或 `sdk-py` 且帶 `agent-sdk/…`），其他一律替換。計費區塊的 `cc_entrypoint` 跟隨 User-Agent，回合按 SDK 回合填寫（`cc_turn_origin=sdk`、`cc_prompt_index=0`）。

`identity_system_block: true`（預設 `false`）會在計費區塊之後緊接著放入與計費 `cc_entrypoint` 對應的身分 system 區塊：`cli` 使用 `You are Claude Code, Anthropic's official CLI for Claude.`，`sdk-*` 使用 `You are a Claude agent, built on Anthropic's Claude Agent SDK.`。用戶端自帶的 SDK 身分（包括 `running within the Claude Agent SDK` 變體）會保留；另一類身分區塊會被改寫；用戶端沒有傳送時則插入一個。關閉此開關時，用戶端的 system 區塊原樣保留。

計費校驗和（`cch`）、`cc_version` 後綴和 `metadata.user_id` 在兩種身分下的計算方式相同。Anthropic 可能對訂閱下的 Agent SDK 流量與互動式使用分開計量，區分依據就是 entrypoint。

### 按操作覆寫 URL

`operation_endpoints` 為某個供應商的某個 `(操作, 方言, 傳輸)` 整體替換方法 URL。URL 按原樣使用，不會在後面再拼接渠道的預設路徑；渠道自己的路徑參數由該方法解析：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/operation-endpoints \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","operation":"generate_content","dialect":"openai_chat",
       "url":"https://elsewhere.example/v1/chat/completions"}'
```

對於把模型名寫在路徑裡的介面，URL 中的 `{model}` 會被替換成上游模型名，並作為單一路徑段做百分號編碼，例如 `https://relay.example/v1beta/models/{model}:generateContent`。

`operation_rules` 則按供應商覆寫渠道對某個操作的處理方式。渠道預設值保留在程式碼裡，不會複製到每個新建立的供應商中，所以沒有覆寫項的供應商會跟隨預設值的後續變化。`POST /admin/api/providers/{id}/routing-defaults/reset` 在一次提交中清除這兩類覆寫。

### Gemini Interactions

`aistudio` 渠道支援兩種 Gemini 協定：`gemini`（GenerateContent）和 `gemini_interactions`（Interactions API）。兩者都對應 `generate_content` 和 `stream_generate_content` 操作，但 Interactions 有自己的請求格式、步驟事件和回應類型。

用戶端請求 `POST /v1beta/interactions` 或 `POST /v1/interactions`，前面可以加上供應商掛載前綴。設定 `stream: true` 即為原生 SSE。`GET /interactions/{id}`、`POST /interactions/{id}/cancel` 和 `DELETE /interactions/{id}` 使用相同的版本前綴；`stream`、`last_event_id` 等查詢參數會原樣轉送，用戶端可以據此讀取或續傳。Interaction 的 id 以及引用它的 `previous_interaction_id` 只對建立它的閘道呼叫方有效，並且一直使用建立時的那份憑證。`agent` 目標和模型名稱一樣經過路由與權限檢查，轉送給上游時保留 `agent` 欄位。

Responses、Chat Completions 和 Claude Messages 都可以與 Interactions 直接互相轉換，不依賴保存的狀態。使用方式是在供應商的操作對應裡把目標協定設為 `gemini_interactions`，或者建立一個只支援 Interactions 的 `custom` 供應商：

```json
{ "channel": "custom", "baseUrl": "https://generativelanguage.googleapis.com",
  "config": { "dialects": ["gemini_interactions"] } }
```

轉換涵蓋函式呼叫與結果、帶簽章的思考歷史、內嵌圖片，以及文字和 JSON 輸出 schema。Interactions 的步驟簽章與 GenerateContent 的簽章分開保存。無法轉換的選用欄位會記入轉換診斷。檔案 id 需要事先換成內嵌資料或 URL。

以下功能需要原生支援 Interactions 的上游：agent、背景執行、續接保存在其他協定中的對話，以及明確的 `store: true`。把 Interactions 用戶端轉換到其他協定的上游時，請送出完整歷史並設定 `store: false`；這時取得的回應 id 並不對應上游保存的 Interaction。

原生串流是增量回傳的。跨協定的串流請求會先從上游收齊完整結果，再依用戶端協定重新產生事件，因此不會縮短第一個 token 的等待時間。輪詢和續傳讀取不會重複計費累計用量；建立回應中沒有用量資訊的背景工作，閘道不會回報其用量。

### GLM

`glm` 使用按量計費 API，`glmcode` 使用 GLM Coding Plan，兩者都填寫 `api_key` 憑證。預設位址是中國大陸的 `https://open.bigmodel.cn`；國際帳號把 `baseUrl` 設為 `https://api.z.ai`。`glmcode` 使用 Coding Plan 專用的 Chat、Claude Messages 和 Responses 入口，額度用盡後不會改用一般付費 API。

兩個渠道的模型列表都取自 ZCode 官方動態目錄：先請求 `/api/v1/client/configs`，下載回傳的 `builtin_provider_config_json`，再選取對應地區的一般 API 或 Coding Plan 範本。沒有內建的固定模型名單，下載失敗時也不會退回舊名單。這份目錄是官方的產品列表，不代表某個 Key 對其中每個模型都有權限。

`glmcode` 透過 `/api/monitor/usage/quota/limit` 讀取伺服器端回報的用量百分比、各個獨立視窗及其重設時間。一般 `glm` 尚未接入帳戶餘額查詢。

### MiniMax

`minimax` 預設位址為 `https://api.minimax.io`；中國大陸平台的帳號按平台文件填寫對應的 API 位址。OpenAI Chat 和 Claude Messages 均可使用 Subscription Key（Coding Plan / Token Plan）或按量計費 API Key，都填入 `api_key`。模型列表和模型詳情使用官方的 `/v1/models` 與 `/v1/models/{id}`。兩類 Key 可以放在不同的供應商中，分別為訂閱文字和付費影片設定路由。

額度查詢沿用官方 CLI 的做法，按 Key 類型讀取 `/v1/token_plan/remains` 或 `/account/query_balance`。這些讀數（以及 `glmcode` 的讀數）目前只用於顯示，憑證是否耗盡仍以上游的請求結果為準。

影片支援 H3 V2（`MiniMax-H3`、`MiniMax-H3-Max`），需要按量計費 API Key。向 `/v1/videos` 提交 GPROXY 的 OpenAI 影片擴充 JSON：

```json
{
  "model": "MiniMax-H3",
  "prompt": "一只猫在花园里奔跑",
  "duration": 5,
  "resolution": "2K",
  "aspect_ratio": "16:9"
}
```

用回傳的 `id` 查詢 `/v1/videos/{id}`，完成後從 `/v1/videos/{id}/content` 下載。`frame_images` 用於指定首尾影格，`input_references` 用於提供影像、影片和音訊參考；也可以直接傳 MiniMax 原生的 `content`。不支援 Sora multipart、`seconds` 和 `size` 參數，也不支援舊版 Hailuo 2.x V1 介面。

列表使用 `page_num` 和 `page_size`（`limit` 對應到 `page_size`），不支援 `after`、`order` 游標。刪除介面回傳上游的 `action`：`cancelled` 表示取消了排隊中的任務，`deleted` 表示刪除了任務記錄。渠道不會自動輪詢，也不儲存影片檔案。

介面依據：[ZCode 動態目錄實作](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/packages/provider-node/src/zcode-builtin-download.ts)、[MiniMax 官方 CLI](https://github.com/MiniMax-AI/cli)、[GLM Coding Plan](https://docs.bigmodel.cn/cn/coding-plan/tool/others)、[MiniMax 文字](https://platform.minimax.io/docs/api-reference/text-anthropic-api)、[MiniMax H3 V2](https://platform.minimax.io/docs/api-reference/video-generation-v2-create)。

### OrcaTerm

`orcaterm` 使用桌面端的 LightAI 協定，支援圖文對話和模型專屬的思考參數。建立供應商後，透過瀏覽器 OAuth 登入或匯入 OAuth 憑證。國際站設定 `international=true`，帳號位址為 `https://orcaterm.ai`，LightAI 位址為 `https://lightai.tencentcloud.com`。

圖片以 Base64 data URL 傳送（PNG、JPEG、WebP 或 GIF），歷史訊息中的圖片和只含圖片的使用者訊息都支援。過大的靜態圖片在上傳前自動縮放和壓縮；同一張圖片在預覽連結有效期內重複使用該憑證下已有的上傳結果。可用模型和思考檔位來自動態模型目錄。上游不支援的請求選項會被忽略。token 數量是本機按字元估算的，在計量中標記為估算值和不完整用量；帳號額度回傳的是 AI 問答次數。

GPROXY 能辨識的用戶端終端機、檔案和網頁擷取工具會對應到 OrcaTerm 原生的 review/reportToolResult 協定，每次呼叫仍由原用戶端按自己的權限規則執行。工具續輪使用同一個供應商、憑證和模型；不支援註冊任意函式。正文和工具參數在 Agent 完成回應修訂後才輸出。Codex 的獨立網路請求使用 OrcaTerm 伺服器端的搜尋和擷取工具，回傳的是真實結果。

### 火山方舟

`volcengine_agent`（Agent Plan）和 `volcengine_coding`（Coding Plan）共用一套實作，分別走各自產品的路徑（`/api/plan` 和 `/api/coding`），不會退回按量計費的 `/api/v3` 介面。Agent Plan 需要其專用 API Key；Coding Plan 個人版使用已開通 Coding Plan 的平台 API Key，企業版使用席位專用 API Key。

只做推論時，憑證只需要 `{"api_key"}`。模型探索、額度和方案資訊還需要在同一份 secret 中填寫 IAM 金鑰對（`access_key_id`、`secret_access_key`，臨時憑證可加 `session_token`）。金鑰對只送往控制面，API Key 只送往推論介面。沒有金鑰對時，推論照常可用，模型需手動設定。

`config.edition` 取 `personal`（預設）或 `enterprise`；企業版額度需要在憑證 metadata 中設定 `seat_id`。各個來源位址可以覆寫：供應商的 base URL（預設 `https://ark.cn-beijing.volces.com`）、`config.control_base_url`（預設 `https://ark.cn-beijing.volcengineapi.com`），以及 Agent Plan 語音使用的 `config.speech_base_url`（預設 `https://openspeech.bytedance.com`）。帳號在上游開通了後付費用量時，Agent 憑證可以在 metadata 中設定 `allow_paid_usage: true`，讓訂閱視窗用盡後繼續路由到該憑證。

## 憑證

憑證是供應商憑證池中的一份密鑰：API key、一組 OAuth 令牌或一個瀏覽器工作階段。在控制台中開啟供應商，進入 **憑證** 分頁管理；透過 API 時，`POST /admin/api/credentials` 建立一條，批次介面可一次建立多條。

| 欄位 | 含義 |
| --- | --- |
| `label` | 選填。透過登入建立時，根據渠道和帳號自動產生。 |
| `authKind` | `api_key`、`oauth` 或 `cookie`，表示儲存的憑證類型，與取得方式無關。 |
| `secret` | 渠道宣告的欄位。永遠不會回傳；列表中只顯示 `hasSecret`。 |
| `organizationId` / `teamId` / `userId` | 歸屬者：三者恰好填一個，或都不填（共享憑證）。 |
| `connectionProfileId` | 覆寫供應商的連線設定。 |
| `expiresAtMs` | 密鑰需要重新整理的時間。 |
| `status` | `active` 或 `dead`。`dead` 的憑證不再被使用。 |
| `version` | 重新整理寫回時使用的 CAS 版本號。 |

密鑰用主金鑰以 AES-256-GCM 加密封裝，並且封裝與該行自己的 id 綁定，所以把密文複製到另一行上是解不開的。讀取明文需要單獨呼叫，並會記入稽核：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/reveal \
  -H "Authorization: Bearer $GPROXY_KEY"
```

沒有設定主金鑰時，密鑰以明文儲存。這是受支援的部署方式，程式會在啟動時提示一次。

### 憑證可見性

憑證在以下情況對呼叫方可見：憑證沒有歸屬者，或者歸屬者與呼叫方所用 key 的綁定一致，即該 key 的使用者、團隊或有效組織。

判斷依據是 key 的綁定，而不是使用者的成員關係，因為一個使用者可以屬於兩個組織，而一把 key 只屬於一個。如果按成員關係判斷，多組織使用者的每一把 key 都能用到所有這些組織的訂閱，也就不可能有比持有人權限更窄的 key。

可見性只會從可用憑證中排除一部分，不會增加憑證。

## 透過登入取得憑證

持有帳號而不是 key 的渠道，可以透過登入上游來建立憑證。

1. 開啟供應商的 **憑證** 分頁，選擇 **登入新增憑證**。
2. 瀏覽器授權（授權碼）方式：開啟授權連結並登入，然後把瀏覽器網址列中完整的回呼 URL 貼回對話框。
3. 裝置碼方式：在廠商頁面輸入顯示的驗證碼，控制台會自動輪詢，直到登入完成。

完成後新憑證會出現在列表中。另見[控制台管理](/zh-tw/guides/console#憑證與上游登入)。

每個渠道提供下面一種或兩種流程，在 `GET /admin/api/channels` 中以 `loginModes` 列出。請求渠道未提供的方式會被拒絕。

| 流程 | 步驟 | 適用情境 |
| --- | --- | --- |
| 授權碼 | start → complete | 帶 PKCE 的瀏覽器跳轉 |
| 裝置碼 | start → 反覆 poll | 在另一台裝置上輸入驗證碼 |

四個 POST 操作位於 `/admin/api/credential-login` 下。待完成的登入工作階段與發起它的使用者及其管理範圍綁定。

### 匯入既有憑證

已經有令牌或 cookie 時，用 `POST /admin/api/credentials`（或批次介面）匯入，再呼叫 `POST /admin/api/credentials/{id}/refresh` 完成初始化。控制台儲存後會自動重新整理待初始化的記錄；初始化失敗時已儲存的記錄仍然保留，可以在詳情中重試。Claude Web 使用 `authKind: "cookie"`；Claude Code 和 OrcaTerm 使用 `authKind: "oauth"`，以 `secret: {"cookie": "..."}` 形式匯入時也一樣。舊的類型標籤仍可讀取。初始化和重新整理會把 secret、到期時間和選填的公開 metadata 一起按版本號 CAS 儲存，不需要資料庫遷移或歷史資料回填。

### 登入的安全措施

凡是不屬於上游的環節都由 GPROXY 自己產生和校驗。PKCE verifier 是本機產生的 32 個隨機位元組，從不外傳，只有它的 S256 摘要會寫進授權 URL，因此授權碼即使被截取也無法使用。CSRF state 同樣在本機產生和比對；state 不符時請求被拒絕，同時銷毀該登入工作階段，攻擊者無法反覆重放直到成功。

待完成的工作階段儲存在共享快取中，而不是行程記憶體裡。因此一個實例發起的登入可以由另一個實例完成（在負載平衡後面這是常態）；放棄的登入也不會留下任何東西：快取鍵到期後，與從未簽發過的 id 沒有差別。

裝置碼輪詢每次只執行一步就回傳，伺服器端不會休眠或迴圈，輪詢由呼叫方負責。每次回應都帶有下次輪詢前應等待的間隔，上游回傳 `slow_down` 時會調大這個間隔，並對之後的所有輪詢生效。

登入成功後，憑證的寫入與一般管理寫入走同一條提交路徑。密鑰在建構 SQL 陳述式之前就已加密封裝，渠道到資料庫之間的任何環節都看不到明文，回應中也只有新憑證的 id。

### 重新整理憑證

持有 OAuth 令牌的渠道會宣告密鑰何時到期。重新整理回傳一份完整的新密鑰，而不是需要合併的部分更新。宿主以 `version` 做 CAS 寫回，並發布憑證變更通知。手動重新整理：

```sh
curl -s -X POST 'http://127.0.0.1:8787/admin/api/credentials/{id}/refresh?force=true' \
  -H "Authorization: Bearer $GPROXY_KEY"
```

上游明確拒絕憑證時（`invalid_grant`、令牌已撤銷），憑證被標記為 `dead`。暫時的傳輸錯誤或 5xx 不會讓憑證失效，只作為傳輸錯誤回報，宿主稍後重試。

使用版本號校驗是因為 Claude 每次重新整理都會輪換 refresh token。如果兩次重新整理並行而遺失了其中一次寫入，資料庫裡儲存的 refresh token 就已經失效了。

## 憑證健康與額度視窗

解析請求時，已停用、已退役和 `dead` 的憑證直接排除。被上游限流的憑證處於封鎖狀態：只要該供應商還有未封鎖的憑證，它就被排除；如果供應商的憑證全部被封鎖，則保留這些憑證，但該供應商排在所有健康供應商之後，只在沒有其他選擇時才會被使用。

管理 API 可以按憑證查詢和重設這些狀態：

```sh
# 檢視上游記錄的這份憑證的額度視窗
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/quota -H "Authorization: Bearer $GPROXY_KEY"
# 立即向上游查詢
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-probe -H "Authorization: Bearer $GPROXY_KEY"
# 兌換一次額度重置（僅限提供此服務的廠商）
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-reset -H "Authorization: Bearer $GPROXY_KEY"
# 清除已記錄的健康狀態
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/health-reset -H "Authorization: Bearer $GPROXY_KEY"
# 檢視適用於這份憑證的維運限額
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/limits -H "Authorization: Bearer $GPROXY_KEY"
```

`POST /admin/api/credentials/{id}/status` 可以手動設為 `active` 或 `dead`，需附上原因。

## 連線設定

連線設定是一次呼叫使用的對外連線堆疊：代理，以及對外呈現的 TLS 和 HTTP/2 指紋。選擇順序依次是憑證、供應商、渠道自己的預設值，最後是實例預設值。

身分預設集可以直接儲存為連線設定的 `emulation`：

```sh
curl -s http://127.0.0.1:8787/admin/api/tls-presets -H "Authorization: Bearer $GPROXY_KEY"
```

其中六個預設集模擬廠商 CLI：

```text
claude / Claude CLI    codex / Codex CLI       gemini / Gemini CLI
antigravity            kiro / Kiro CLI         copilot / GitHub Copilot CLI
```

列表中還包含模擬函式庫自帶的每個瀏覽器和 HTTP 用戶端指紋（Chrome、Edge、Firefox、Safari、Opera、OkHttp），id 形如 `wreq:{profile}`。

只有 `wreq` 傳輸會呈現模擬指紋。模擬 CLI 的渠道會提供自己的預設連線設定；憑證或供應商上明確指定的設定仍然優先。

## 測試供應商

管理呼叫中只有兩類會存取行程外部：連通性測試，以及模型測試與探索。

### 連通性測試

連通性測試經由 scope 指定的用戶端鏈路存取 Cloudflare 的 trace 端點，查看本部署從外部看起來是什麼樣子：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/connectivity/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"scope":"global"}'
```

```json
{"ok":true,"latencyMs":803,"ip":"223.166.167.192","colo":"LAX","error":null}
```

scope 可以是 `global`、`{"scope":"provider","provider_id":"…"}`、`{"scope":"credential","credential_id":"…"}`（與該憑證的呼叫使用同一條傳輸），或 `{"scope":"proxy","url":"…"}`，用於測試尚未設定到任何地方的代理。網路不通時回傳 `ok: false` 和原因，而不是 HTTP 錯誤，因為「上游無法連線」本身就是測試的有效結果。

### 模型測試與探索

模型測試和模型探索與呼叫方的請求一樣完整地經過引擎：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","model":"gpt-4o-mini"}'

curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

<Warning>
這兩個呼叫使用真實憑證：會消耗上游額度，計入該憑證適用的預算，並寫入一條用量記錄。沒有 dry run 模式，因為不真正呼叫上游的測試什麼也測不出來。
</Warning>

模型探索使用供應商自己的協定查詢，所以回傳的是上游的模型名。每個結果都會標明該供應商是否已有這個模型，以及內建目錄能否為它定價。`POST /admin/api/models/discover/apply` 插入你選中的模型，已存在的會略過。

## 請求頭白名單

預設情況下，用戶端的請求頭不會轉發給上游。全域請求頭白名單在「設定 → 網路」中設定，每個供應商還可以透過 `config.allowed_headers` 追加。最終生效的集合是全域白名單、供應商白名單和渠道預設頭的聯集，另外始終保留 `content-type`。未設定或為空的列表不增加任何項目。

原始鑑權頭和逐跳頭即使列入白名單也會被移除。渠道注入的鑑權資訊和 `config` 中的靜態 `headers` 不受此規則影響。修改在下一次設定重新載入時生效，合併結果不會寫回供應商儲存的列表。

## 遷移設定

```sh
gproxy export --out config.json --include-secrets
gproxy import --in  config.json --mode merge --source-master-key '…'
```

匯出內容是部署本身的設定：連線設定、供應商、憑證、模型目錄、路由、操作覆寫、改寫規則、配額、價格和 settings 行。身分資料不匯出（使用者、key、組織、團隊、權限和訂閱屬於產品層），用量和 capture 也不匯出，否則目標實例上會出現它從未產生過的歷史。主金鑰相關規則見[設定](/zh-tw/reference/configuration#匯出與匯入設定)。
