本頁說明 GPROXY 如何把用戶端請求中的 `model` 解析成供應商、憑證和上游模型名，以及如何設定決定這一過程的路由和模型目錄。如果要修改請求參數而不是請求的去向，請使用[重寫規則](/zh-tw/guides/rules)。

## 模型名解析

用戶端填寫的模型名通常不是上游模型 id。GPROXY 在請求進入引擎之前完成解析，引擎拿到的始終是已經選定的目標：

```text
請求裡的 model
  → 第一條命中的形式：路由名 · 供應商名/模型
  → 候選按渠道、允許的供應商、允許的憑證收窄
  → 按 (tier, 健康度, 權重倒序, 穩定 id) 排序
  → 首段按路由策略均衡
  → 每次嘗試得到一個 (供應商, 憑證, 上游模型)
```

模型名按下表順序比對，採用第一條命中的形式：

| 名字 | 解析為 | 嘗試預算 |
| --- | --- | --- |
| 沒有模型 | 全部啟用的供應商，無上游模型 | `settings.max_attempts` |
| 模型路由名稱 | 該路由啟用的成員 | 路由自己的 |
| `供應商名/模型` | 那一個供應商 | `settings.max_attempts` |
| 其他 | `404 unknown_model` | — |

路由名精確比對，並且優先於前綴形式。已停用的路由不參與比對，請求會繼續嘗試後面的形式。`供應商名/模型` 中的前綴始終是供應商名，而不是渠道 id：名為 `openai`、渠道為 `codex` 的供應商透過 `openai/…` 呼叫，與其專屬入口 `/openai/v1` 一致。

比對到的候選隨後按入口掛載點的渠道、呼叫方 Key 允許的供應商和允許使用的憑證收窄。名字能夠解析、但收窄後沒有可用目標時，回傳 `503 no_usable_target`。這屬於設定問題（沒有啟用的成員、沒有可用憑證，或者 Key 無權使用其中任何一個），因此與未知模型分開回報。

實際使用中，應把路由名交給用戶端作為模型名。

## 建立路由

路由是一個公開的模型名，包含若干供應商／上游模型成員、一個均衡策略和一個嘗試預算。建立名為 `main` 的路由後，用戶端即可請求 `model: "main"`。

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/routes \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"main","strategy":"round_robin","maxAttempts":6}'
```

```json
{"id":"33a88261f571347c7f0408c3bd2e2164","name":"main","strategy":"round_robin",
 "maxAttempts":6,"enabled":true}
```

| 欄位 | 含義 |
| --- | --- |
| `name` | 全域唯一，用戶端在 `model` 中直接填寫此名稱。 |
| `sessionAffinity` | 工作階段優先重用成功的供應商／模型目標，預設關閉；內部憑證選擇仍由供應商負責。 |
| `strategy` | `round_robin`、`weighted` 或 `failover`。 |
| `maxAttempts` | 含首次呼叫在內的總嘗試預算，必須為正數。執行時以 `settings.maxAttempts`（預設 6）為硬上限。 |

控制台中，路由位於「模型路由」頁面。

## 新增成員

每個成員把流量送往一個供應商，並指定上游模型名：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/route-members \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"routeId":"…","providerId":"…","upstreamModel":"gpt-4o-mini",
       "tier":0,"weight":100}'
```

| 欄位 | 含義 |
| --- | --- |
| `providerId`、`upstreamModel` | 成員把流量送往哪裡。模型名是明確的字串，不是模型目錄的外鍵。 |
| `tier` | 越小越優先。tier 0 用盡之前，tier 1 不會收到任何流量。 |
| `weight` | 正數，預設 100。用於同一 tier 內分流，也決定容錯移轉候選的順序。 |
| `enabled` | 停用的成員不進入執行計畫。 |

所屬供應商已停用或已刪除的成員會被略過。如果 `upstreamModel` 與該供應商某個已啟用模型的變體名相同，請求會改用該模型的上游名稱送出。

成員不指定憑證。引擎在選中的供應商內部挑選憑證，並且先在該供應商的憑證之間容錯移轉，然後才轉到下一個成員。

## 排序與均衡策略

候選按 `(tier, 健康度, 權重倒序, 穩定 id)` 排序。穩定 id 是成員 id，因此兩個候選不會相等，每次請求的排序結果一致。

tier 是嚴格的優先順序，後面的 tier 不會與前面的 tier 一起均衡。只有首段（與第一個候選 tier 和健康度都相同的那些候選）會按路由策略重新排列：

- `round_robin`：用每個路由各自的計數器輪替首段。
- `weighted`：把平滑加權輪詢選出的候選移到最前。一個完整週期內，每個成員被選中的次數與權重成正比，並且分散出現，不會連續集中。
- `failover`：保持排序結果不變。

輪替使用計數器而不是亂數，因此原生版本與 wasm 版本行為一致，順序也可以重現。計數器保存在行程記憶體中，多個執行個體之間不共享；重新啟動後從第一個候選重新開始。

健康度取決於供應商的憑證。已停用、已退役和已失效（dead）的憑證直接排除。被封鎖的憑證（例如觸發限流後）在該供應商仍有未封鎖憑證時排除；如果某個供應商的憑證全部被封鎖，該供應商仍保留在計畫中，但排在所有健康供應商之後。這樣，被限流的供應商會作為最後的選擇，而不是被當作無法使用。

開啟 `sessionAffinity` 後，工作階段上一次成功的目標會被優先使用，但只限於同一個首段（相同 tier 和健康度）之內。

## 路由名稱與 namespace

用戶端使用的模型名直接在路由上建立和修改，不需要另外設定公開名稱對應。

### namespace

名稱中帶 `/` 的路由會在執行時形成一個 namespace。建立路由 `acme/fast` 後，`acme` 就成為一個掛載點，向 `/acme/v1/chat/completions` 傳送 `{"model":"fast"}` 會解析到 `acme/fast`：

```sh
curl -s http://127.0.0.1:8787/acme/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"hi"}]}'
```

namespace 只是路由名的索引。它不單獨儲存，不對路由分組，也不擁有路由；出現新的 namespace 時不會建立任何物件。

### 保留的首段

如果路由名的首段與現有供應商名相同（不區分大小寫），管理介面會拒絕寫入，因為 `名稱/…` 已經表示該供應商的 `供應商名/模型` 形式：

```json
{"error":{"code":"invalid_request","message":"invalid request: `codex/` is reserved:
 a first segment naming a provider already means `provider/model` narrowing;
 choose a distinct model route name"}}
```

其他首段都可以使用，例如 `coding/fast`。

## 呼叫方看到的模型列表

`GET /v1/models` 回傳已設定的模型名，包括路由名和 `供應商名/模型`，並且只列出呼叫方有權使用的名字。它不會代理某一家上游的模型目錄。新增或匯入供應商模型後，它們會以供應商名為前綴出現在列表中。

下面兩種呼叫方式等價：API 位址用 `/供應商A/v1`、模型填 `gpt-5`；或者位址用 `/v1`、模型填 `供應商A/gpt-5`。`GET /供應商A/v1/models` 只查詢供應商 A，並保留上游模型原名。

前綴使用供應商的顯示名稱。供應商改名後，對應的模型前綴和 API 位址也會隨之改變。

使用者入口的模型列表還會顯示呼叫方無權使用的名字，並用 `permitted` 標註：

```sh
curl -s http://127.0.0.1:8787/portal/api/models -H "Authorization: Bearer $GPROXY_KEY"
```

```json
[{"name":"provider-A/gpt-4o-mini","providerCount":1,"channelIds":["custom"],"permitted":true},
 {"name":"fast","providerCount":1,"channelIds":["custom"],"permitted":true}]
```

呼叫方規則涵蓋不到的名字仍會出現在列表中，標記為 `permitted: false`。v3 會去掉這些列；v4 保留它們，因為靜默省略會讓「模型回傳 404」和「沒有權限使用該模型」看起來一樣，而且這些名字本來就是維運者對外公開的執行個體設定。

列表不顯示名字背後的供應商 id，只給出供應商數量和渠道 id。呼叫方可以據此判斷一個名字有多少備援，但看不到具體是哪些供應商。

## 模型目錄

模型目錄由兩張表組成，路由不依賴其中任何一張：路由成員以普通字串指定上游模型，因此兩張表裡都沒有的名字也能正常路由。目錄資料用於模型列表、文件、詮釋資料和計價。

- `provider_models` 記錄每個供應商提供哪些上游模型名，模型探索的結果寫入這裡。
- `models` 是全域目錄，`provider_models` 的列可以指向其中一筆。每筆記錄包含一個名字、它的詮釋資料，以及 token 估算應使用的詞表。

手動新增一個供應商模型：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/provider-models \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","upstreamName":"gpt-4o-mini"}'
```

```json
{"id":"f32df0bb6378c03e70f7c3aa6315a3b8","providerId":"5a45fd807be0…",
 "upstreamName":"gpt-4o-mini","modelId":null,"metadata":{},"enabled":true}
```

### 從上游探索模型

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

模型探索使用供應商自己的協定向上游查詢，不做任何轉換，回傳的就是上游的模型名。每一項都會註明該供應商是否已有對應記錄，以及內建目錄能否為它定價。`POST /admin/api/models/discover/apply` 插入你指定的條目並略過已有條目，所以同一次探索結果套用兩次與套用一次效果相同。

補全詮釋資料時，先按完整模型 ID 比對，再嘗試唯一的末段名稱；有歧義的名字不補預設值。合併順序為：內建預設值，上游的非空欄位，本機覆寫值。在控制台向已有的供應商模型匯入時，只補充缺少的欄位。

<Warning>
模型探索和 `POST /admin/api/models/test` 都會使用真實憑證，並寫入真實的用量記錄。參見[測試供應商](/zh-tw/guides/providers#測試供應商)。
</Warning>

### 內建模型目錄

每個版本都內建一份模型目錄，包含模型名、上下文視窗和預設價格。它是產生該資源時的快照，不是即時目錄：

```sh
curl -s http://127.0.0.1:8787/admin/api/default-model-catalog -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

設定 `overwrite: false` 後可以放心重複套用：維運者修改過的規則保留修改，並在結果中標記為略過。

內建模型 ID 使用 `claude-sonnet-4` 這樣不帶來源前綴的名字，而不是 `anthropic/claude-sonnet-4`；來源 URL 和原始報價仍然保留。帶前綴的上游名稱仍可按末段名稱比對。比對預設價格時優先選擇最長的比對模型片段；從供應商匯入價格時，規則模式使用該供應商實際的上游名稱。

預設價格是 OpenRouter 的報價快照，不代表每個供應商的實際合約價格。套用預設價格會產生全域計費規則，已有同模式的規則不會被取代。供應商專屬規則優先於全域規則。價格在全域模型和供應商模型的編輯對話框中修改，價格編輯器支援費率、上下文分段和服務等級。參見[價格與分層](/zh-tw/reference/pricing)。

### 「模型」頁面

控制台的「模型」頁面（`/console/model-catalog`）列出資料庫中儲存的模型。它與權限選擇框使用同一個 `/admin/api/models` 介面；資料庫為空時列表為空。頁面顯示已儲存的能力和上限、關聯的供應商，以及能比對到的內建參考價格。

「載入預設模型」把你選中的內建條目寫入資料庫，已有模型保持不變。載入模型詮釋資料不會修改計價規則。也可以手動新增模型。刪除的模型會從列表中移除，讀取列表時不會從內建資料中補回。

詮釋資料在匯入時複製。之後編輯全域模型，不會改變此前已經從它匯入的供應商模型。

### 更新內建目錄

用以下指令重新產生內建資源：

```sh
node scripts/update-openrouter-model-catalog.mjs
```

加上 `--input response.json` 可以用儲存好的回應離線產生。公開的模型介面不需要 Key；選用的憑證只從 `OPENROUTER_API_KEY` 環境變數讀取。產生器保留原始的 `source_pricing` 供核查，只對應它支援的計費單位。單位換算後，計費價格捨入到 9 位小數（就近捨入，中點取偶），匯入預設價格時使用同樣的規則。

價格缺少或為動態價格，並不表示免費。從官方價格頁補充價格之前，先確認模型版本、地區、單位和門檻，不要猜測缺少的費率。
