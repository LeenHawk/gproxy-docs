本頁介紹 GPROXY 如何為 Claude 和 OpenAI 上游放置提示快取標記（透過快取斷點規則，或透過寫在提示中的魔法字串），以及快取 token 如何記錄和計價。

快取本身由上游提供，能否命中取決於模型、提示前綴和有效期（TTL）。新增標記不保證命中，也不能讓不支援快取的上游獲得快取能力。

## 快取斷點規則

在供應商的「重寫規則」頁面新增「快取斷點」規則，選擇上游協定和位置。位置包括全域、系統和訊息，Claude 還支援工具。局部位置可以填寫索引：正數從 1 開始，負數從末尾倒數，留空則選擇最後一個可用位置。

Claude 可選預設、5 分鐘或 1 小時 TTL；OpenAI 局部斷點可選預設、30 分鐘或 12 小時，OpenAI 全域規則可選預設或 30 分鐘。TTL 實際如何生效由上游決定。規則中的協定指轉換後的上游協定。Gemini 不支援這種規則。

透過 API 設定時，使用 `action: "cache_breakpoint"`，並在 `replacement` 中填寫設定物件的 JSON 字串，例如：

```json
{"dialect":"claude","target":"message","index":-1,"ttl":"5m"}
```

```json
{"dialect":"openai","target":"message","index":-1,"ttl":"12h"}
```

這條規則作用於請求正文，與其他[重寫規則](/zh-tw/guides/rules)按同一順序執行。正文中已有四個標記時，規則不再新增，這與下文魔法字串的上限相同。能夠自行設定原生快取欄位的用戶端，也可以直接傳送上游支援的欄位。

## 魔法字串

無法設定快取欄位的用戶端，可以在提示文字中寫入以下字串之一。供應商為目標協定開啟 magic cache 選項後，GPROXY 會去掉該字串，並在原位置放置一個斷點。

```text
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_7D9ASD7A98SD7A9S8D79ASC98A7FNKJBVV80SCMSHDSIUCH
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_49VA1S5V19GR4G89W2V695G9W9GV52W95V198WV5W2FC9DF
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_1FAS5GV9R5H29T5Y2J9584K6O95M2NBVW52C95CX984FRJY
```

| 字串 | Claude 目標 | OpenAI 目標 |
| --- | --- | --- |
| …`7D9ASD…` | `cache_control`，使用 API 預設 TTL | 明確斷點 |
| …`49VA1S…` | `cache_control`，`"ttl": "5m"` | `prompt_cache_breakpoint` (`"ttl": "30m"`) |
| …`1FAS5G…` | `cache_control`，`"ttl": "1h"` | `prompt_cache_breakpoint` (`"ttl": "12h"`) |

同一個字串按目標協定選擇短期或長期快取：Claude 的 `5m`、`1h` 分別對應 OpenAI 的 `30m`、`12h`，預設字串不設定 TTL。TTL 寫在斷點本身上，不修改整個請求的快取選項。

這些字串屬於用戶端與 GPROXY 之間的協定，不會隨版本變化。

### 開啟 magic cache

供應商 `config` 中有兩個開關，每個協定族一個：

```json
{ "config": { "enable_claude_magic_cache": true,
              "enable_openai_magic_cache": true } }
```

| 開關 | 提供該開關的渠道 |
| --- | --- |
| `enable_claude_magic_cache` | `aws_bedrock`、`azure`、`claudeapi`、`claudecode`、`custom`、`opencodego`、`opencodezen`、`openrouter`、`vercel` |
| `enable_openai_magic_cache` | `aws_bedrock`、`azure`、`openai`、`codex`、`custom`、`opencodego`、`opencodezen`、`openrouter`、`vercel` |

控制台中這兩個開關顯示為「Claude 魔法快取」和「OpenAI 魔法快取」。

起作用的是目標協定對應的開關，而不是用戶端協定的開關。OpenAI 格式的用戶端請求路由到 Claude 供應商時，會先轉換為 Claude Messages，因此由 Claude 開關決定，寫入的標記是 `cache_control`。用戶端收到的回應仍是它自己的格式。

### 字串的移除

上表中的渠道無論是否開啟 magic cache，都會移除這些字串，因為殘留在提示中的標記對上游沒有任何用處。

開關只決定是否在字串原來的位置放置斷點。magic cache 關閉時，只移除字串，其他內容都不變：用戶端自己的 `cache_control` 或 `prompt_cache_breakpoint` 原樣保留；不含字串的正文按原位元組轉送，不解析，也不重新序列化。

`claudeweb` 渠道同樣只移除字串而不放置斷點，因為瀏覽器工作階段沒有快取控制。

## 標記的位置

開啟 magic cache 後，魔法字串對應的標記按目標協定放置在以下位置。

### Claude Messages

先對正文做正規化：字串形式的 content 轉為區塊陣列，空文字區塊被刪除，刪除的區塊上若帶有 `cache_control`，會移到最近的可快取區塊上。因此，單獨佔一行的字串也能正常生效。thinking 區塊只在 assistant 輪次中保留。

隨後先處理 `system`，再處理 `messages`，斷點名額因此按提示順序分配，而不是按 JSON 鍵的順序。每個包含字串的文字區塊都會加上標記：

```json
{ "cache_control": { "type": "ephemeral", "ttl": "1h" } }
```

已經帶有 `cache_control` 的區塊保持不變。

### OpenAI Chat Completions

除 `function` 角色以外的訊息都可以加標記。純字串的 `content` 會拆成一個帶標記的 `text` part，因為標記必須放在某個 part 上；陣列形式的 content 則直接在原有 part 上加標記。

```json
{ "type": "text", "text": "…", "prompt_cache_breakpoint": { "mode": "explicit" } }
```

### OpenAI Responses

依次在三個位置放置標記：

1. `instructions`。其中的字串被移除，並在 `input` 開頭插入一則帶標記的 developer 訊息，因為 `instructions` 是純字串，無法攜帶標記。
2. `prompt.variables`，標記方式與 Chat 的 part 相同。
3. `input`。裸字串會變成一則帶標記的 user 訊息；如果是 item 陣列，則用 `input_text` 和 `output_text` 類型標記其中的 `content` 與 `output`。

### Gemini

Gemini 沒有斷點。字串被移除，不做其他處理。

## 四個斷點的上限

離開代理的斷點最多四個，用戶端自己設定的也計算在內。可用名額等於四減去正文中已有的標記數，所以用戶端已經放了三個時，只剩一個名額。

超出上限的字串仍會被移除，只是不再變成標記。

## 協定轉換中的原生快取欄位

在 Claude 與 OpenAI Chat/Responses 之間轉換時，原生快取欄位按同樣的 TTL 對應關係雙向對應。帶標記的系統提示、訊息、圖片/文件和工具結果區塊保留各自的邊界。Claude 的自動快取策略會轉換為對應末尾區塊上的明確斷點，前提是該區塊在目標協定中有對應表示。沒有 OpenAI 對應欄位的工具定義級標記會列在轉換報告中。

從 OpenAI 轉換到 Claude 時，只有明確傳入 `prompt_cache_options.mode: "implicit"` 才會產生頂層 `cache_control`。省略整個選項物件或省略 `mode`（包括空物件、只傳 TTL）都不會開啟 Claude 自動快取。區塊上的明確標記不受此影響，單獨轉換。

OpenAI Responses 和 Chat 的明確斷點支援 `prompt_cache_breakpoint: {"mode":"explicit","ttl":"12h"}`（也支援 `"30m"`），Chat 與 Responses 互相轉換時保留這個 TTL。目前的[官方 OpenAPI](https://github.com/openai/openai-openapi/blob/master/openapi.json) 中，請求級的 `prompt_cache_options.ttl` 仍只允許 `"30m"`；`prompt_cache_retention` 是另一套較早的策略。

## 用量與計價

快取 token 作為獨立的指標記錄，並按你設定的費率列計價：

| 上游回報的內容 | 指標 |
| --- | --- |
| 快取讀取 | `cached_input_tokens` |
| 快取寫入，按 TTL 分桶 | `cache_creation_tokens` + `ttl_seconds` |
| 快取寫入，TTL 未知 | `cache_creation_tokens` |

快取寫入統一使用 `cache_creation_tokens`。費率條件 `{"ttl_seconds":43200}` 比對 12 小時寫入的價格，不帶該條件的費率作為預設價格；上游回報的每個寫入桶分別計費。快取讀取是單一的 `cached_input_tokens` 計數，沒有 TTL。階梯價格使用 `cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]`，其中 `ttlSeconds: null` 的條目是預設價格。價格按每百萬 token 計，不再乘以 TTL。

OpenAI 單次呼叫的 usage 只回報 `cache_write_tokens` 總量，因此 GPROXY 把這些寫入的 TTL 記為未知，不去猜測它們在不同 TTL 的斷點之間如何分配。

`cached_input_tokens` 以 `input_tokens` 為上限。未命中的部分按輸入價格計費，命中的部分按快取讀取價格計費；沒有設定快取讀取價格時按輸入價格計費。沒有單獨費率的快取寫入不計費。參見[價格與分層](/zh-tw/reference/pricing)。

用量記錄中的各項 token 數可以為空，因為上游沒有回報某個欄位，不代表它測得的是 0。合計值則總是普通數值，因為對「沒有回報」的欄位求和，結果就是 0。

## 避免快取未命中

重寫規則在協定轉換之後、渠道傳送之前執行，因此修改提示文字的規則可能把本應命中的請求變成未命中。把穩定的內容放在最前面，標記放在它後面，每次請求都會變化的內容放在標記之後。同時檢查是否有 `paths` 範圍過寬的重寫規則改動了快取前綴。
