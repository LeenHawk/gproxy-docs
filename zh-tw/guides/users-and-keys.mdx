本頁介紹使用 GPROXY 的帳戶，以及呼叫模型所用的閘道 API Key：第一位管理員、使用者、組織與團隊，以及金鑰的建立、傳遞、輪替和撤銷。

<VideoTutorial topic="users" locale="zh-TW" title="使用者與金鑰影片教學" />

GPROXY 有兩種身分憑據。登入控制台使用使用者名稱和密碼，用戶端呼叫模型使用閘道 API Key。上游憑證屬於供應商，只用來存取上游，不能用來登入 GPROXY。

## 第一位管理員

Application 會在首次設定精靈中建立管理員。

CLI 在空的執行個體上啟動時會建立管理員，並顯示產生的密碼和 API Key。如果想自行指定，請在首次啟動前設定以下變數：

```sh
export GPROXY_ADMIN_USER='admin'
export GPROXY_ADMIN_PASSWORD='your-initial-password'
export GPROXY_BOOTSTRAP_ADMIN_API_KEY='your-initial-gateway-key'
./gproxy serve
```

在新的執行個體上，密碼和金鑰變數都可以省略，省略的值由程式產生。`GPROXY_BOOTSTRAP_ADMIN_API_KEY` 只在首次初始化時讀取。

<Warning>
`GPROXY_ADMIN_PASSWORD` 在每次啟動時都會生效，不限於首次。若存在名為 `GPROXY_ADMIN_USER` 的使用者，會把該使用者的密碼設為此值；若沒有同名使用者，則還原內建的 0 號管理員：改為該名稱、重新啟用並設為 `admin` 角色、設定此密碼，同時結束其現有的控制台工作階段。不再需要時請移除這個變數，否則在控制台改過的密碼會在重新啟動後被覆寫。
</Warning>

供應商需要在控制台中新增。舊的 `GPROXY_BOOTSTRAP_CHANNELS` 變數已不會再建立供應商。

CLI 與容器部署的登入入口是 `/console/`。個人頁面和管理頁面共用同一個登入工作階段，儲存在名為 `gproxy_session` 的 HTTP Cookie 中，有效期限由 `session_ttl_secs` 設定。Application 使用應用程式內的控制台。

## 使用者、組織與團隊

執行個體管理員在 **成員與組織 → 使用者** 中建立使用者。使用者角色為 `admin` 或 `user`。沒有設定密碼的使用者無法登入控制台，但仍可在權限範圍內使用簽發給自己的 API Key。

組織和團隊透過成員關係把使用者分組，每筆成員關係都帶有該使用者在群組內的角色。組織管理員和團隊管理員只能管理所屬範圍內開放的功能，並不是執行個體管理員。各範圍可以管理的內容見[控制台與範圍管理](/zh-tw/guides/console)。

API Key 可以綁定一個組織或團隊。綁定決定金鑰能使用哪些共用憑證，以及要計入哪些群組的費用預算。綁定關係儲存在金鑰上，用戶端無法透過傳送組織或團隊請求標頭來變更。

## 建立金鑰

使用者在控制台 **個人** 檢視的 **我的金鑰** 中管理自己的金鑰。執行個體管理員可以在 **存取控制 → 使用者金鑰** 中管理所有使用者的金鑰。

金鑰包含以下設定：

- **名稱**：用來區分使用這把金鑰的應用程式或裝置。
- 歸屬：所屬使用者，以及可選擇綁定的組織或團隊。
- **到期時間** 與 **啟用**：已過期或已停用的金鑰無法發出新請求。
- **管理權限**：允許金鑰呼叫管理 API，但仍受所屬使用者和範圍的權限限制。預設關閉，由管理員在 **使用者金鑰** 中設定。
- **保留金鑰原文**：儲存完整金鑰，以便日後再次查看。預設關閉，只能在建立時選擇。
- **費用預算**：管理員可以為金鑰設定金額、週期和模型範圍。

建立後頁面會顯示完整金鑰，請立即複製。未保留原文的金鑰無法再次顯示，從其他執行個體僅以摘要匯入的金鑰也一樣。查看已保留的金鑰同樣需要相應的權限。

新金鑰會和初始預算一起儲存。預算驗證失敗時，金鑰也不會建立。

## 傳遞金鑰

```text
Authorization: Bearer <gateway-key>
x-api-key: <gateway-key>
x-goog-api-key: <gateway-key>
```

使用用戶端協定慣用的請求標頭，而且只傳一把金鑰。同時存在多個時，依序優先讀取 `Authorization`、`x-api-key`、`x-goog-api-key`。

呼叫管理 API 需要已啟用管理權限的金鑰。一般的推論金鑰不會因為所屬使用者是管理員，就自動取得管理權限。

## 輪替與撤銷

輪替會取代金鑰的值，舊值立即失效，所有使用它的用戶端都要更新設定。如果想逐一遷移用戶端，可以改為建立第二把金鑰，等用戶端全部切換後，再停用或刪除舊金鑰。

管理 API 中的對應操作：

- `POST /admin/api/api-keys/{id}/rotate`：輪替。
- `GET /admin/api/api-keys/{id}/secret`：查看已保留的金鑰。
- 個人 API 使用 `/portal/api/keys/{id}/rotate` 和 `/portal/api/keys/{id}/secret`。

撤銷在執行寫入的執行個體上立即生效。多執行個體部署中，其他執行個體依據記憶體快照回應認證，要重新載入後才會拒絕該金鑰：通常透過共用快取的失效通知，在毫秒內完成；通知遺失時，最晚在每 30 秒一次的修訂號輪詢後完成。參見[架構](/zh-tw/development/architecture)。

把成員移出組織或團隊時，會在同一筆交易中停用該使用者綁定到該組織或團隊的金鑰，包括 OAuth 內部金鑰。

## OAuth 工作階段

GPROXY 可以作為 OAuth 授權伺服器：用戶端請求使用者授權，然後取得存取權杖。每次授權背後都有一把內部金鑰。內部金鑰不同於一般使用者金鑰，無法手動建立、無法顯示，也不能當作 Bearer Key 使用。

使用者可以在 **帳號 → 已授權的程式** 中查看和撤銷已授權的程式。在 **存取控制 → OAuth 用戶端** 中註銷某個用戶端，會撤銷它的所有授權和權杖。

用戶端設定和授權流程見[CLI 用戶端](/zh-tw/guides/cli-clients)。OAuth 權杖可以使用哪些 scope 和操作，見[權限、限流與費用預算](/zh-tw/guides/permissions#oauth-存取權杖)。
