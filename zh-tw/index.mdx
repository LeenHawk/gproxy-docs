GPROXY 是一個自行部署的大型語言模型 API 閘道。上游帳號（API Key、Codex 或 Claude Code 這類 OAuth 登入、瀏覽器 Cookie）交給 GPROXY 保管，用戶端只需要一個閘道位址、一個 GPROXY API Key，以及你自己定義的模型名稱。

每個請求到達後，GPROXY 依模型名稱選出供應商和憑證；用戶端與上游的格式不同時，在 OpenAI、Claude、Gemini 三種格式之間轉換；檢查呼叫者的權限、限流和預算；最後記錄 token 用量和費用。某個憑證或供應商失敗時，請求會換到下一個繼續嘗試。

GPROXY 不執行模型，推論由上游服務完成。它也無法替上游補上缺少的能力：把請求轉換成另一種格式，並不會讓一個不支援工具呼叫或圖片輸入的模型變得支援。

它可以作為附 Web 控制台的原生服務（CLI 或容器）執行，也可以作為內建控制台的桌面或手機應用程式使用，或者搭配託管資料庫部署在 Cloudflare Workers、Netlify 和 Vercel 上。Rust 程式也可以把它當作函式庫嵌入。

## 一個例子

假設有一個名為 `openai-main` 的供應商，裡面存放了 OpenAI API Key；再建立一個名為 `fast` 的模型路由，指向它的 `gpt-4o-mini`。用戶端這樣請求：

```sh
curl http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"你好"}]}'
```

用戶端始終接觸不到 OpenAI 的 Key。之後替 `fast` 再加一個供應商，或者換掉背後的模型，用戶端都不必修改。同一個路由也可以用 Claude 格式請求 `/v1/messages`，或用 Gemini 格式請求 `/v1beta/models/fast:generateContent`。
