GPROXY has three storage components, each configured on its own: the
database, the cache, and optional file storage. This page describes the
backends for each, how they are selected, and what you need when you run more
than one instance or plan backups.

## Database

The database holds all configuration, identities, usage and logs. The native
binary (`gproxy`) opens SQLite, PostgreSQL or MySQL; the Cloudflare Workers
host opens D1 or libSQL.

| Backend | Connection | Availability |
| --- | --- | --- |
| SQLite (default) | `<data-dir>/gproxy.db`, or a file path or `sqlite://` URL in `--dsn` | native binary, always compiled in |
| PostgreSQL | `postgres://…` in `--dsn` | native binary, `postgres` feature (on by default) |
| MySQL | `mysql://…` in `--dsn` | native binary, `mysql` feature (on by default) |
| D1 | the Worker's D1 binding (`DB` by default) | Workers host |
| libSQL / Turso | a `libsql://` or `https://` URL in `GPROXY_DATABASE_URL`, token in `GPROXY_LIBSQL_TOKEN` | Workers host |

MySQL must be 8.0.13 or later, which is the first version that accepts JSON
default expressions. The PostgreSQL and MySQL drivers are built with TLS
support.

### Selecting a backend

For the native binary, `--dsn` (`GPROXY_DSN`) is usually enough: when
`--persistence` (`GPROXY_PERSISTENCE`) is not set, the URL scheme selects the
backend.

```sh
gproxy serve --dsn 'postgres://gproxy:…@db.internal:5432/gproxy'
```

`GPROXY_PERSISTENCE` accepts `sqlite`, `postgres` or `mysql`. A `sqlite://`
DSN left over from a v2 or v3 deployment is accepted, and the file path inside
it is used. `:memory:` is refused, because an instance whose database
disappears with the process would bootstrap an administrator, serve traffic
and then lose all of it.

A backend that the build does not include is refused at startup, with an
error that names the feature that provides it. You find out when the process
starts, not at the first request. The native binary also refuses D1 and
libSQL, which only the Workers host can open; see
[Cloudflare Workers](/deployment/edge) for its bindings. In the Workers host,
`GPROXY_DATABASE_URL` takes precedence over the D1 binding. libSQL reaches the
database over HTTP with the same fetch transport the Worker uses for upstream
calls.

### Schema synchronization

```text
$ gproxy migrate --data-dir ./data
INFO gproxy::instance: schema is up to date warnings=0
```

The schema is derived from the entity definitions rather than from a numbered
series of migrations. One registry describes the tables. Synchronization
creates the missing tables on a new database and, on an existing one, adds
missing columns and indexes where the backend supports that. Running it again
keeps all rows.

`gproxy serve` synchronizes the schema at startup as well. `gproxy migrate`
exists for deployments that run it as a separate step, with a single writer,
before any instance starts. Do it that way when several instances share one
database, so that they do not all alter the schema at once.

Synchronization does not:

- create default settings or administrators;
- run versioned migrations;
- change a column's type, convert its data, or change an existing foreign key.

Those changes need an explicit migration, and GPROXY does not guarantee that a
migration runs in a single transaction on every native backend.

The synchronization report lists warnings, for example type differences on
D1. An empty list does not prove that every change was applied. Read the
diagnostics in the log before you treat a startup as complete.

### Store API and batches

Native SeaORM connections and Cloudflare D1 are accessed through the same
store API. Every entity accessor goes through one generic repository, so
ordinary CRUD is not written per table, and each method runs as one atomic
batch. Creating the store does not open a database or change the schema.

Some properties of this API that callers rely on:

- Reads return results in input order, keep duplicates, and return `None` for
  a missing id, so a caller can match each result to its request.
- A key predicate is split so that each statement stays under D1's limit of
  100 bound parameters. The parts still run in the same batch. SQL written by a
  caller is not split, and the database's own request and size limits still
  apply.
- An SQL error rolls back a transactional write. A conditional write that
  affects zero rows returns a conflict and does not roll back the rest of its
  batch.
- Nothing is retried automatically. If the result of a commit is unknown (for
  example the connection dropped), check the stored state before you repeat
  the write.

### Exact amounts

Money and limits are stored as scaled integers, not floating point. One unit
is `0.000000001`, and the representable range is about ±9.2 billion.

The SQL columns are `BIGINT`. The entities pass these values across D1's
JavaScript boundary as text, so that comparison, ordering and addition stay
numeric inside the database; JSON uses decimal strings for the same reason.

Arithmetic is done in a decimal type and rounded once, on the complete
settlement, with ties rounded to even. Before a counter is incremented,
settlement checks for negative values and signed overflow.

## The cache

The cache holds short-lived state: values with a TTL, exact counters, permits
and leases, and the invalidation topic. It holds no business entities and no
durable ledger; anything that must survive goes to the database.

| Backend | Selected by | Shared between |
| --- | --- | --- |
| Memory | default in the native binary (`memory` feature) | nothing; one process |
| Redis / Valkey | `GPROXY_REDIS_URL`; the binary must be built with the `redis` feature | all instances using the same Redis |
| Database | default in the Workers host | all isolates using the same database |

The native binary connects to Redis at startup and exits if it cannot. Rate
limits are counted in the cache, so an instance that cannot reach Redis would
otherwise accept traffic only to reject each rate-limited request. The
database-backed cache is only for the Workers host; the native binary refuses
it. The default feature set, which release binaries use, does not include
`redis` or `s3`; a deployment that needs either builds its own binary (see
[Building](/development/building)).

### Operations

| Operation | Behaviour |
| --- | --- |
| `get` / `put` / `delete` | opaque bytes; a positive TTL is required; every put creates a new version |
| `compare_exchange` | replace or delete if the current version matches, or if the key is absent |
| `counter` / `increment` / `decrement` | exact non-negative integers, with an atomic ceiling check |
| `acquire_permit` | at most N live holders, each with its own TTL |
| `acquire_lease` | a permit with a limit of 1, used as a refresh lease |
| `publish` / `subscribe` | invalidation hints; delivery is not guaranteed |

Each operation is atomic for one key; nothing is atomic across keys.
Key/value entries, counters, permits and topics are separate namespaces, so
the same name can exist in each.

A counter uses a fixed window. Only the call that creates it sets its TTL, so
every instance can compute the window boundary from the clock alone. A permit
has no window: it counts requests in flight, which a window boundary does not
divide. Its TTL only bounds how long the cache waits before reclaiming a
permit from a request that died without releasing it.

### Cache failures

If Redis fails, GPROXY does not switch to an in-process cache. Two instances
that each fell back to local state would hold conflicting locks and each count
the same limit separately, which is worse than returning an error.

A request subject to a rate limit that the cache cannot evaluate is refused
with `429`, without a `Retry-After` hint. If such requests were let through,
a cache outage would silently turn off every rate limit on the instance, and
the operator would not see it.

### Running more than one instance

Several instances need a shared cache: Redis for native instances, or the
database-backed cache on Workers. With a per-process cache each instance
counts its own rate limits, each refreshes the same OAuth token, and none of
them sees the others' configuration invalidations.

Sign-in sessions are also kept in the cache, so a login started on one
instance can be completed on another. Behind a load balancer this is the usual
case.

If several deployments or environments use one Redis server, give each its
own namespace (the default is `gproxy`). The notification channel name
includes the database number, because Redis Pub/Sub ignores `SELECT`.

### Database-backed cache

A Workers isolate has no long-lived process and no Redis, so the Workers host
keeps the cache in three tables of its D1 or libSQL database. Expiry is
compared in SQL, so all isolates on one database agree on which entries are
live.

This backend has no notification transport. A subscription yields the initial
resync hint and nothing after it. Instead, the Workers host reads the
configuration revision at the start of every request; that is its whole
synchronization mechanism.

## Configuration synchronization

A configuration write goes through these steps:

```text
commit_revision([statements…, config_revision += 1, read back])   one transaction
      ↓
reload   this instance's snapshot
      ↓
publish  ConfigurationChanged { revision, scopes }
```

The rows and the revision increment are written in one transaction. If they
were separate, another instance could read the new revision before the rows
exist.

Other instances learn about the change in two ways, and both are needed:

| Mechanism | What it carries | How it fails |
| --- | --- | --- |
| an invalidation on the shared cache | "check again", within milliseconds | messages can be lost |
| polling `settings.config_revision` | the durable revision, every 30 seconds | it is slow |

A notification never carries configuration. It names a revision, and an
instance reloads only if that revision is newer than the one it is serving.
A payload that cannot be parsed triggers a reload.

A counter kept in the cache cannot replace the revision in the database. A
Redis restart or eviction can lose it, and a commit to the database followed
by a publish to the topic are still two separate operations, not one
transaction.

Reloads run one at a time and only move forward: an older revision never
replaces a newer one, and if a reload fails, the previous snapshot keeps
serving.

## File storage

File storage is optional and disabled until you configure a backend.

| Backend | Selected by | Native binary | Workers host |
| --- | --- | --- | --- |
| Local filesystem | `--file-storage-dir` (`fs` feature, on by default) | yes | no |
| S3-compatible, including R2 | the `[file_storage]` block (`s3` feature) | yes | yes |

It stores the bodies of publications (the bytes served at
`/publications/{id}`) and downloaded tokenizer vocabularies. File metadata and
ownership are kept in the database; the storage backend holds only content.

Without file storage, publishing and vocabulary downloads answer
"unsupported", because there is nowhere to put the bytes.

A publication link also needs `GPROXY_PUBLIC_BASE_URL`. Without it, the
publish fails before any body is written, and the caller is told to request
the bytes inline. GPROXY does not build the link from the request's `Host`
header, because the client chooses that header: the upstream would accept the
answer, the bytes would be stored, and the URL handed out could point to a
host where it returns 404.

## Backups

- SQLite: stop the process and copy `<data-dir>/gproxy.db`, or use SQLite's
  online backup. Keep the master key together with the copy; credential
  secrets in a sealed database cannot be read without it.
- PostgreSQL and MySQL: use the database's own dump tools.
- D1 and libSQL / Turso: use the platform's snapshots.
- Logical export: `gproxy export --out config.json --include-secrets`. The
  export contains configuration, not history; identities, usage and captures
  are not included. See
  [Configuration](/reference/configuration#moving-a-configuration).

Each sealed secret is bound to the id of its row. Restoring one row's secret
onto a different row does not work. This protects against secrets being
swapped between rows and does not affect restoring a whole database.
