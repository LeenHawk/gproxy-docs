This page lists every HTTP route an instance serves and the order in which a
request path is interpreted. Use it when you need to know which URL reaches
which operation, how a provider or namespace prefix changes that, and how a
request fails over between providers. The native host and the Workers host
mount the same table. `gproxy-protocol` itself declares no paths; which URL
serves an operation is decided by the ingress layer described here.

For the full request and response schemas of each route, see the
[HTTP API reference](/reference/http-api).

## Gateway routes

The gateway has only a few routes of its own. Every other path falls through
to the data plane. This is the reverse of the usual arrangement: the gateway's
own routes are a short, fixed list, and everything else is an upstream API that
the instance forwards, so supporting a new upstream surface does not require a
new route here.

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/healthz` | liveness and the published configuration revision; no authentication |
| `GET` | `/info` | instance name, version and build hash |
| `GET` | `/robots.txt` | disallows all crawlers |
| `GET` | `/publications/{id}` | a published body. The id is the credential, so no key is required |
| — | `/admin/api/…` | the management API |
| — | `/portal/api/…` | the end user's own API |
| — | everything else | ingress (OAuth issuer, vendor services, data plane, console) |

```sh
curl -s http://127.0.0.1:8787/healthz
```

```json
{"revision":2,"status":"ok"}
```

`/healthz` reads the published snapshot and touches neither the database nor
the cache, so a load balancer polling it does not add load to either.

Every response carries `x-robots-tag: noindex, nofollow`.

## Request processing order

A request that is not one of the gateway routes is interpreted in this order:

1. CORS and the client address. A CORS preflight is answered here and never
   forwarded, because it asks what this instance accepts. The client address is
   resolved under the [trusted-proxy rule](/reference/configuration#trusted-proxies)
   before anything logs it.
2. The mount: which leading part of the path belongs to this gateway (see
   [Mounts](#mounts)).
3. The OAuth issuer, at `{mount}/v1/oauth/…`. These paths belong to this
   instance rather than to an upstream, and they answer in the OAuth error
   format, so they are matched before the data plane.
4. A channel's vendor service route, such as Codex's `/backend-api/…` or Claude
   Code's `/api/…`. Only on a provider or namespace mount, because matching one
   needs a channel and the aggregated mount names none.
5. The [data plane](#data-plane-endpoints).
6. The console, with an SPA fallback, if it is enabled.

A request that matches none of these gets a 404.

## Data plane endpoints

Before anything else happens, including authentication, a request body is
limited to `settings.maxRequestBodyBytes` (128 MiB by default), or
`maxUploadBodyBytes` (512 MiB) for a file upload.

### Dialect selection on shared paths

`/v1/models`, `/v1/models/{id}` and `/v1/files` are spelled the same by OpenAI,
Claude and Gemini's v1 API. The dialect decides which wire types a conversion
produces, so a wrong guess gives the client a body it cannot parse.

The gateway decides from the client's own authentication headers:
`x-goog-api-key` selects Gemini, and `anthropic-version` or `x-api-key` selects
Claude. These are headers the vendor's SDK always sends. With neither present,
the first row in the table wins, which is OpenAI.

### File and video ownership

File and video ids are the upstream's own, and one upstream credential is
usually shared by many callers, so the gateway records who created what. A
successful upload or video creation is recorded against the caller and against
the credential that served it. All keys and console sessions of one user count
as one caller; each OAuth grant is a caller of its own.

- Retrieving, downloading, polling or deleting an id returns 404 unless that
  caller created it through the gateway. The answer is the same whether the id
  belongs to someone else or does not exist. The request is sent on the
  credential that holds the resource.
- A list shows only the caller's own items. Paging cursors (`has_more`,
  `last_id`, `nextPageToken`) are passed through unchanged, so a page can hold
  fewer items than `limit`, or none while more pages remain. Keep paging until
  the upstream says there are no more.
- Files and videos created before this check existed, or created directly at
  the upstream, are not reachable through the gateway.
- A Gemini resumable upload (the default in the google-genai SDKs) works as
  usual. The `x-goog-upload-url` returned by the start request is a gateway URL
  bound to the caller; the bytes are relayed to the upstream session on the
  same credential, and the finished file belongs to the caller. Another caller
  presenting that URL gets 404. Behind a proxy, set `public_base_url` (or
  forward `Host` and a trusted `X-Forwarded-Proto`) so the URL names the address
  clients reach.
- The same rule covers files referenced inside other requests: a `file_id` in a
  Chat, Responses or Claude message (including a code-interpreter container's
  `file_ids`), a Gemini `fileData.fileUri` naming a Files API file, and a video
  `input_reference`. A file the caller did not upload returns 404 before
  anything is sent, and the request runs on the credential holding the files.
  Files uploaded on two different credentials cannot be used in one request
  (400). Multipart forms are checked the same way (`file_id`, `file_ids[]` and
  `input_reference[file_id]` fields).
- On a Responses WebSocket, a new response opens its upstream connection on the
  credential holding the files it references. A continuation
  (`previous_response_id`) stays on its account, so files uploaded elsewhere are
  refused with an `error` event; start a new response to use them.
- On a Realtime or Gemini Live socket, a client message naming a file the
  caller does not own on the socket's credential is not forwarded. Realtime
  answers with an `error` event (`file_not_found`); Gemini Live closes with
  code `1008`.

### Realtime and WebSocket sessions

Standard Realtime and GPT-Live use different protocols and different account
entitlements. The legacy `/v1/live` routes remain for compatibility. The new
Live routes and custom voice creation are available with an OpenAI API key;
the Codex channel supports standard Realtime, client secrets and explicit
hangup. A 201 from session creation only means the request was accepted, not
that the session can run.

Client secrets are upstream bearer credentials for direct connections. Their
bodies are never captured, and requests a client then makes directly to the
upstream bypass gateway admission and metering. Explicit hangup and sidebands
use the scope of the caller that created the call and its original credential.
Their bound model is recovered before admission, and current model permissions
are checked again.

`POST /v1/realtime/calls` is an HTTP multipart request carrying an SDP offer.
The WebSocket handshake that continues it carries no body. What links the two
is the call id, in the path or in `?call_id=`. The engine looks it up to pin the
socket to the credential that answered the offer, which is why the query string
is forwarded unchanged.

A realtime session is never converted between dialects; only same-dialect
passthrough is supported. A client that can keep talking while a response is in
progress has no equivalent in a half-duplex dialect.

A realtime request is admitted before the connection is upgraded. The order is
authentication, handshake validation, admission, the upstream handshake, and
only then the `101` response. Every refusal is therefore an ordinary HTTP
response the client can read; a socket that is accepted and then closed
immediately would carry no status, body or code. If the upstream refuses the
handshake, its answer is relayed as it is: a vendor's
`429 {"error":{"code":"insufficient_quota"}}` tells the client more than a
gateway 502 would.

A realtime socket holds its concurrency slot until it closes, not just until
the `101` is sent. A session that runs for an hour holds its slot for that hour.

Responses uses the same `/v1/responses` path for HTTP POST and WebSocket GET.
The handshake authenticates the caller; each `response.create` then supplies
the model used for permissions, routing and generation limits. Independent
`stream_id` lanes can run concurrently. A new response chain can choose a new
target, while `previous_response_id` continuations keep their original target.
Idle Responses connections do not hold generation concurrency permits.

Native Responses sockets forward upstream control events. Bridges from the
socket to HTTP Responses, Chat, Claude and Gemini support local context
warmup, interruption, steering successors, and injected inputs between HTTP
generation segments. Local warmup does not prefill an upstream cache.
`store:false` history lasts only as long as the client connection; stored
continuations keep scoped history and target bindings. A generation that has
started, or whose outcome is uncertain, is not replayed on another target.

### Codex routes

Private Codex operations are available only on the mount of a provider that
uses the Codex channel. For a provider named `codex`, use
`POST /codex/v1/memories/trace_summarize`. These routes go through normal
operation admission, model routing and settlement; the aggregated `/v1` surface
does not expose them. The standard `/v1/moderations` route keeps its own
`create_moderation` JSON contract.

Account services are also available under `/codex/v1`, including
`usage/thread_usage/query_v2` (POST), `usage/plan_limit_history`, and daily
token, credit, workspace, plugin and skill reports (GET). The native spellings
under `/codex/api/codex/**`, `/codex/backend-api/**` and `/codex/ps/**` also
work. An administrator can read a specific account's upstream reports with
`x-gproxy-view: credential:<id>`. In the default caller and pool views,
historical allowances and vendor credits that cannot be rebuilt from local
records are marked unavailable, with null amounts, rather than borrowed from
another account or reported as zero.

## Mounts

One instance serves the same upstream API at three kinds of mount:

| Path | Mount | Narrows resolution to |
| --- | --- | --- |
| `/v1/messages` | aggregated | nothing |
| `/acme/v1/messages` | namespace `acme` | the exposed names under `acme/` |
| `/openai-prod/v1/messages` | provider `openai-prod` | that provider |

A namespace is the first segment of an exposed model name that contains a
slash: exposing `acme/fast` creates the namespace `acme`. A provider mount uses
the provider's `name`, the label you chose, not the row id, because nobody
types a generated id into a client's base URL. If a namespace and a provider
have the same name, the namespace wins.

A prefix is stripped only when the rest of the path is also a route the gateway
serves. Without this check, a provider named `backend-api` would swallow
`/backend-api/codex/responses`, which is a real Codex path, and turn a
data-plane call into a mount that does not exist. When the first segment names
a namespace or provider but the rest is not a known route, the path is left
whole and treated as aggregated. A missed mount produces a 404 you can see; a
wrongly taken mount would send the request to the wrong upstream.

A mount narrows resolution by prefixing the model name, which is the resolver's
own syntax for a provider or route: `/acme/v1/messages` with
`{"model":"fast"}` resolves `acme/fast`. A name that already carries the prefix
is left alone, so clients may write it either way. A provider mount also
restricts operations that name no model, such as file operations, to that
provider.

A vendor service route on a namespace mount is served by the one provider in
that namespace whose channel offers the route. If more than one does, the
request is refused with 409; call it on that provider's own mount instead.

## OAuth issuer

The issuer endpoints are relative to a mount prefix (`""`, `/acme`,
`/openai-prod`):

```text
GET  {prefix}/v1/oauth/authorize    consent handoff (302 to `/console/authorize` for a browser)
POST {prefix}/v1/oauth/authorize    the person's decision
POST {prefix}/v1/oauth/token        code, refresh and device grants
POST {prefix}/v1/oauth/device/code
POST {prefix}/v1/oauth/revoke
GET  {prefix}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{prefix}/v1   (RFC 8414 §3.1)
```

The issuer identifier is `{origin}{prefix}/v1`, so the aggregated issuer is
`https://host/v1`, not `https://host`. This way one rule covers all three
kinds of mount. RFC 8414 requires the identifier to match the location the
client fetched the metadata from, and only the host knows which mount a request
arrived on, so the host passes it in.

These endpoints answer errors in the OAuth format (RFC 6749 §5.2, `error` as a
string), not in the gateway's usual error envelope. The device approval page
itself is a portal operation, `/portal/api/oauth/device`, used by the console's
`/console/device` page.

v3 served these endpoints at the root. Moving them under `/v1` lets them follow
the same prefix rule as `/v1/messages`. v3 never implemented the discovery
endpoint, so clients were hard-coding the addresses anyway.

## Management API

Every management family has the same six routes:

```text
GET    /admin/api/{family}           list      (page and filters in the query)
POST   /admin/api/{family}           create
GET    /admin/api/{family}/{id}      get
PATCH  /admin/api/{family}/{id}      update
DELETE /admin/api/{family}/{id}      delete    → 204
POST   /admin/api/{family}/batch     batch
       [{"create": …}, {"update": {"id": …, "patch": …}}, {"delete": "id"}]
```

The routes are generated from one declaration, so no family can be missing one
of them. A batch is one revision commit however many rows it names: either
every item is stored or none is.

Identity families: `users`, `api-keys`, `organizations`, `teams`,
`permissions`, `rate-limits` and `oauth-clients`. Organization and team
memberships have their own endpoints
(`organizations/{id}/members`, `teams/{id}/members`). Some families differ
from the six routes:

- `oauth-clients` has `POST …/{id}/retire` instead of a delete, because the
  grants a client issued still refer to it. In its batch, a delete item
  retires the client, and a batch that retires may contain only deletes:
  retirement runs in its own transaction, so it cannot share a commit with
  creates or updates. A retired `client_id` can be registered again; the new
  registration reuses the row, and grants revoked at retirement stay revoked.
- The `api-keys` batch refuses creates, because creating a key returns its
  plaintext and a batch has no way to return it.
- A `users` batch that would leave no enabled administrator is refused as a
  whole.

Configuration families: `providers`, `credentials`, `models`,
`provider-models`, `routes`, `route-members`, `connection-profiles`,
`rule-sets`, `rules`, `provider-rule-sets`, `operation-rules`,
`operation-endpoints`, `quotas`, `price-rules`, `price-rates`, `price-tiers`.

Other management endpoints:

- Instance: `settings`, `export`, `import`, `connectivity/test`, `audit`,
  `session`, `sessions`, `context`, and `update` (where the host supports
  self-update).
- Credentials: `credentials/{id}/…` with `reveal`, `status`, `refresh`,
  `quota`, `quota-probe`, `quota-reset`, `quota-reset-credits`,
  `quota-diagnostics`, `quota-observations`, `health-reset`, `limits`,
  `models/discover` and `models/test`; `credentials/owners`,
  `credentials/providers`, and the `credential-login/…` authorization-code and
  device flows.
- Models and routing: `models/discover`, `models/discover/apply`,
  `models/test`, `model-names`, `operation-keys`,
  `providers/{id}/routing`, `providers/{id}/routing-defaults/reset`,
  `providers/{id}/default-rule-set`.
- Rules: `rule-sets/{id}/rules`, `rule-sets/{id}/rule-presets/{preset}`,
  `rule-presets`.
- Quotas: `quotas/status`, `quotas/{id}/reset`, `quotas/{id}/limit-reset`.
- Catalogues: `channels`, `tls-presets`, `default-model-catalog`,
  `default-model-catalog/apply-prices`.
- Tokenizer: `tokenizer-vocabs`, `tokenizer-auth`.
- Users: `users/{id}/password`, `users/{id}/sessions`, `users/{id}/allowlist`;
  API keys: `api-keys/{id}/rotate`, `api-keys/{id}/secret`.
- History: `usage`, `usage/records`, `logs/downstream`, `logs/upstream`,
  `logs/captures/{id}`; see [Usage, logs, and audit](/guides/observability).

The [HTTP API reference](/reference/http-api) has the full list with
parameters. Management payloads changed in v4, so check older scripts against
it.

Each management request goes through one middleware: authentication (an unsafe
method authenticated by a cookie is also checked for same origin), then
resolution of the caller's management scope, then the operation, then an audit
entry. Every request is audited, including refused ones. The middleware is a
route layer, so an unknown `/admin/api/…` path is a 404 that never touches the
database. A management request body is limited to 50 MiB, which is enough for
a configuration import.

## Portal API

```text
POST   /portal/api/login             name + password → session cookie and token
POST   /portal/api/logout
GET    /portal/api/context           the caller, their memberships, their features
GET    /portal/api/models            every exposed name, each marked `permitted`
GET    /portal/api/usage             their own spend
GET    /portal/api/quota             their own budget windows
GET    /portal/api/requests          their recent requests, if enabled
GET    /portal/api/sessions
GET    /portal/api/keys              (+ POST, DELETE …/{id}, POST …/{id}/rotate, GET …/{id}/secret)
GET    /portal/api/oauth-sessions    (+ DELETE …/{id})
POST   /portal/api/password
GET    /portal/api/oauth/device      a pending device code (?userCode=), for `/console/device`
POST   /portal/api/oauth/device      approve or deny it; a session or a management key
```

The portal routes require an authenticated caller and nothing else. There is no
role check because every portal operation is scoped to the caller who made the
request, and none of them takes a user id. A missing role check could be a
bug; a parameter that does not exist cannot be misused.

`login` and `logout` are outside that check. `login` runs before there is a
caller, and `logout` has to work for a session that has already expired;
otherwise the browser would keep a cookie it could never clear.

## Resolution and failover

The four forms of model name and the order in which they are tried are
described in [Models, Routes & Exposed Names](/guides/models). The failover
budget works as follows:

- The budget is the route's own `maxAttempts`, capped by
  `settings.maxAttempts`.
- The budget is shared across targets. Each target gets at most as many
  attempts as it has credentials, and never more than what is left, so a plan
  cannot make more upstream calls than its budget.
- A failure moves on to the next provider only if another provider could serve
  the request: no usable credential, a dead credential, a continuation pinned
  elsewhere, any channel or transport error, or a 401, 403, 429 or 5xx answer.
- A spent budget, a forbidden request, a cancellation, a failed conversion, and
  a store or cache failure stop the call where it is.
- When no target is left, the last answer is returned unchanged. A 429 from the
  final provider reaches the caller as that 429, not as a synthesized error.

The request body is buffered once so it can be replayed on another target. A
streaming body larger than `maxRequestBodyBytes` is kept as a stream, and the
plan is cut to a single target: reading a large upload into memory is not worth
it for the sake of failover.
