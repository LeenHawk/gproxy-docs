本页说明 GPROXY 如何根据价格表计算一次交换的费用，以及如何编辑这些表。录入价格、排查费用异常或配置费用预算时会用到。

## 概述

引擎在结算时为每次交换计价，依据是供应商、上游模型，以及渠道从响应中提取出的归一化用量。预算和观察者读取的是同一个计算结果。（v3 中引擎把用量交给应用层，由应用层再算一遍，结果出现了两套模型匹配逻辑，对“模型没有价格”也有两种不同的处理。v4 只在一处计价。）

价格存放在三张表中：

- `price_rules`：每行选中一个模型，可以限定某个供应商和某个操作。
- `price_rates`：该规则下每个指标的基础价。
- `price_tiers`：按提示长度和服务档位覆盖该规则的 token 价格。

所有价格和结算金额均以 USD 计。

## 规则选择

一条规则同时满足以下条件时适用于某次交换：

- 规则的供应商就是这次交换的供应商，或者规则没有指定供应商（全局规则）；
- 规则的 `modelPattern` glob 匹配上游模型名；
- 规则的 `operation` 与请求的操作相同，或者没有指定（覆盖全部操作）。

供应商规则先于全局规则匹配。同一组内 `(priority, id)` 最小的规则胜出。

| 字段 | 含义 |
| --- | --- |
| `providerId` | `null` 表示全局规则 |
| `modelPattern` | 匹配上游模型名的 `*` / `?` glob |
| `operation` | `null` 覆盖所匹配模型的全部操作 |
| `priority` | 越小越先匹配，相同时按 id 排序 |
| `currency` | 必须为 `USD` |
| `enabled` | 停用的规则不参与匹配 |

币种不是 `USD`、pattern 不是合法 glob 或操作名未知的规则，会在装配快照时被跳过（见[无效行](#无效行)）。

如果一次交换的用量按尝试（attempt）分别报告，每个可计费的尝试按其自身模型对应的规则计价，再把金额相加。标记为不可计费的尝试不计入。

### 没有匹配规则的交换

没有任何规则匹配时，这次交换不计价：费用为零，照常结算，用量中带有以下维度：

```json
{"dimensions": {"unpriced": "true"}}
```

请求不会因此被拒绝。缺少价格属于配置遗漏，靠这个维度可以找出正在免费提供的模型，而不必在有人录入价格之前拒绝流量。

## 费率行

一个费率行是某条规则下某个指标的基础价。

| 字段 | 含义 |
| --- | --- |
| `metric` | 内置指标键，或渠道产出的任意自定义键 |
| `unit` | `token`、`count`、`second` 或 `character` |
| `unitQuantity` | 正数分母：1 000 000 个 token、1 张图、60 秒 |
| `value` | `unitQuantity` 个单位的非负价格，单位 USD |
| `conditions` | `null` 表示兜底行；否则是“维度名 → 标量值”的非空对象，所有条件都必须匹配 |
| `priority` | 同一指标的多行中，越小越先尝试 |

对每个指标，带条件的行按 `(priority, id)` 顺序尝试，第一个所有条件都与结算维度匹配的行生效；都不匹配时使用兜底行。命中的条件行取代兜底价，而不是与它叠加。

```json
[{"metric":"input_tokens",  "unit":"token","unitQuantity":"1000000","value":"0.40"},
 {"metric":"output_tokens", "unit":"token","unitQuantity":"1000000","value":"1.60"},
 {"metric":"image_outputs", "unit":"count","unitQuantity":"1","value":"0.04",
  "conditions":{"quality":"hd","size":"1024x1024"},"priority":0}]
```

### 避免重复计费

每个费率计价的数量不能与其他费率重叠。具体来说：

- 命中缓存的 input 与普通 input 分开计数。
- 已经包含在某个汇总项中计费的 reasoning 或媒体 token 子集，不能再单独计价一次。
- 按图计费和按 token 计费的输出价格二选一。只有厂商确实两样都收时才同时填写。
- 通用的 `tool_calls` 行和具体的 `web_searches` 行不能对同一次调用重复计费。
- 客户端在请求中声明工具不等于服务端执行了工具，不应计费。

## 指标

token 指标习惯上按每百万 token 定价：

```text
input_tokens          output_tokens           cached_input_tokens
cache_creation_tokens
reasoning_tokens      image_input_tokens      image_output_tokens
audio_input_tokens    cached_audio_input_tokens  audio_output_tokens
video_input_tokens    video_tokens
```

计数、时长与字符指标：

```text
image_outputs   video_outputs   audio_seconds   video_seconds   audio_characters
search_units    web_searches    web_fetches     file_searches
code_interpreter_sessions       tool_calls      requests
```

以上只是内置键的列表，并不限制可用的指标：不在列表中的指标，只要有费率行引用，同样会被计价。

非 token 类指标的费用为

```text
amount × value / unitQuantity
```

服务档位的乘数不作用于这些指标。

`requests` 是按请求收取的费用，每个被计价的交换计一次请求。

### 缓存写入

缓存写入统一计为 `cache_creation_tokens`。用量中可能有多个保留时长不同的写入桶，每个桶分别计价。要为某个保留时长单独定价，添加带 `ttl_seconds` 条件的费率行：`{"ttl_seconds":43200}` 匹配 12 小时写入；不带该条件的行是默认价格。

在档位中，写入价格以列表形式给出，`ttlSeconds: null` 是默认项：

```text
cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]
```

价格按每百万 token 计。保留时长只用于选择价格，不参与乘法。

缓存读取是单一的 `cached_input_tokens` 计数，没有 TTL。

## 分层

`price_tiers` 行只覆盖 token 价格，并且一律按每百万 token 计。

| 字段 | 含义 |
| --- | --- |
| `serviceTier` | `null` 表示上下文档位；否则是服务档位，如 `standard`、`priority`、`flex`、`batch` |
| `minPromptTokens` | 非负阈值，包含端点；默认 0 |
| `multiplier` | 仅用于服务档位：继承价格要乘的系数。上下文档位不设置 |
| `*_per_million` | 某一类 token 的显式价格 |

显式价格列有 `input`、`output`、`cache_read`、`cache_creation`、`reasoning`、`image_input`、`image_output`、`audio_input`、`cached_audio_input`、`audio_output`、`video_input` 和 `video`，均带 `_per_million` 后缀。`cache_creation_per_million` 是[缓存写入](#缓存写入)一节所述的列表。

判断阈值时，提示长度等于 input token、缓存读取与缓存写入之和，每项只计一次。

### token 价格的计算顺序

每类 token 的价格分三步确定：

1. 基础费率：该指标的 `price_rates` 行，带条件的行先尝试。
2. 上下文档位：在没有服务档位的行中，取提示长度已达到的最高 `minPromptTokens` 那一行。该行设置了哪些类的显式价格，就替换哪些类的基础价。
3. 服务档位：在服务档位等于实际服务档位的行中，取已达到的最高阈值那一行。该行有显式价格时直接使用；否则把上一步得到的价格乘以该行的 `multiplier`（默认 1）。

阈值相同时，`(priority, id)` 较小的行胜出。价格为 `null` 表示沿用上一步的结果；`0` 表示该类免费。

<Warning>
服务档位的显式价格会取代它下面的整条阶梯，包括上下文档位。设基础 input 价为 1，上下文台阶为 `≥ 200 000 → 2`，提示长度为 300 000 个 token：

| `batch` 行 | 实际 input 费率 |
| --- | --- |
| `{"serviceTier":"batch","multiplier":"0.5"}` | `2 × 0.5 = 1` |
| `{"serviceTier":"batch","inputPerMillion":"0.5"}` | `0.5`（200k 台阶失效） |
| `{"serviceTier":"batch","minPromptTokens":200000,"inputPerMillion":"1"}` | `1` |

要么在需要覆盖的每个阈值上重复写出显式档位价，要么改用乘数。
</Warning>

### reasoning token 与缓存读取

reasoning token 是 output token 的子集。规则有 reasoning 价格时，reasoning token 从 `output_tokens` 中扣除，按 reasoning 价格单独计费；没有时，它们留在 output 中，按 output 价格计一次。

没有单独价格的缓存读取沿用 input 价格；其他没有价格的 token 类一律免费。缓存读取本来就是 input token，沿用 input 价格是稳妥的默认值。而音频或视频缺少价格属于配置遗漏，按零计价能让这个遗漏在费用里直接显现出来。

### 请求的服务档位与实际服务档位

计价使用响应中报告的服务档位，而不是请求中要求的档位。厂商把 `priority` 请求降级处理时，按降级后的档位行结算。服务档位名比较时不区分大小写。

## 编辑价格

每张表都有对应的管理 API：

```sh
curl -s http://127.0.0.1:8787/admin/api/price-rules  -H "Authorization: Bearer $GPROXY_KEY"
curl -s http://127.0.0.1:8787/admin/api/price-rates  -H "Authorization: Bearer $GPROXY_KEY"
curl -s http://127.0.0.1:8787/admin/api/price-tiers  -H "Authorization: Bearer $GPROXY_KEY"
```

每组都有通常的五个路由和一个批量路由。一次批量操作无论包含多少行，都作为一个 revision 提交。在控制台中，全局价格在“模型”页编辑，供应商价格在供应商的“模型”标签中编辑，见[控制台](/zh-cn/guides/console#配额与价格)。

### 应用内置目录价格

内置模型目录收录了发布时已知模型的价格。从目录创建规则：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

不带 `providerId` 时，规则使用目录自带的 glob 和优先级，一条全局规则即可为所有提供该模型的供应商计价。带 `providerId` 时，模型名原样作为 pattern，优先级为 0。

使用 `"overwrite": false` 可以随时重复应用目录：已经存在的规则（例如你修改过的规则）保持不变，在响应中计入跳过数。

### 无效行

无法使用的计价行（币种不是 USD 的规则、非法 pattern、未知操作、`unitQuantity` 不为正数的费率、不是“非空标量对象”的条件）会在装配配置快照时被丢弃并记录 warn 日志。快照的其余部分照常加载，一个输错的数值不会让正在服务流量的实例停下来。修改价格后请检查日志中是否有这类警告。

## 费用预算

费用预算是一行 metric 为 `cost`、以 USD 计的 `quotas`。准入阶段，引擎拿到调用方链 `[api_key?, user, team?, org?]`，链上每个归属者的每个已启用预算都对该请求生效。

费用在上游调用返回后才结算，因此在途请求和并发请求可能使预算超出上限。预算的归属和检查方式见[权限、限流与费用预算](/zh-cn/guides/permissions)。

## token 估算

可计费的响应完全没有用量时，引擎自行统计 token，并把记录标记为 `estimated = true`。统计使用本地词表，按以下顺序选择：

1. GPT 系列模型使用 tiktoken 编码；
2. 模型目录行指定的词表；
3. 内置的 DeepSeek 词表。

列出已存储的词表，或从 Hugging Face 下载词表并指定给某个模型和实例默认值：

```sh
curl -s http://127.0.0.1:8787/admin/api/tokenizer-vocabs -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/tokenizer-vocabs \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"repo":"…","filename":"tokenizer.json","modelId":"…","setAsDefault":true}'
```

下载的文件先写入已配置的文件存储，然后在一次 revision 提交中写入词表行、模型指针和默认指针。顺序不能颠倒：指向从未写入的文件的行会让之后每次重载都失败，而没有对应行的文件只是浪费一点空间。

词表依赖文件存储。没有配置文件存储时，所有词表路由都返回“不支持”。见[文件存储](/zh-cn/reference/database#文件存储)。
