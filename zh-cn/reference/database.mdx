GPROXY 的存储分三部分，各自独立配置：数据库、缓存，以及可选的文件存储。本页介绍每部分有哪些后端、如何选择，以及运行多个实例或规划备份时需要注意什么。

## 数据库

数据库保存全部配置、身份、用量和日志。原生程序（`gproxy`）可以打开 SQLite、PostgreSQL 或 MySQL；Cloudflare Workers 宿主可以打开 D1 或 libSQL。

| 后端 | 连接方式 | 适用范围 |
| --- | --- | --- |
| SQLite（默认） | `<data-dir>/gproxy.db`，或 `--dsn` 中的文件路径、`sqlite://` URL | 原生程序，始终编译在内 |
| PostgreSQL | `--dsn` 中的 `postgres://…` | 原生程序，`postgres` feature（默认开启） |
| MySQL | `--dsn` 中的 `mysql://…` | 原生程序，`mysql` feature（默认开启） |
| D1 | Worker 的 D1 binding（默认名为 `DB`） | Workers 宿主 |
| libSQL / Turso | `GPROXY_DATABASE_URL` 中的 `libsql://` 或 `https://` URL，令牌放在 `GPROXY_LIBSQL_TOKEN` | Workers 宿主 |

MySQL 需要 8.0.13 或更新版本，这是第一个支持 JSON 默认值表达式的版本。PostgreSQL 和 MySQL 驱动均带 TLS 支持。

### 选择后端

对原生程序，通常只需设置 `--dsn`（`GPROXY_DSN`）：没有设置 `--persistence`（`GPROXY_PERSISTENCE`）时，由 URL 的 scheme 决定后端。

```sh
gproxy serve --dsn 'postgres://gproxy:…@db.internal:5432/gproxy'
```

`GPROXY_PERSISTENCE` 可取 `sqlite`、`postgres` 或 `mysql`。v2、v3 部署遗留的 `sqlite://` DSN 仍然接受，程序取其中的文件路径。`:memory:` 会被拒绝：数据库随进程消失的实例会照常初始化管理员、服务流量，然后把这些全部丢掉。

本次构建不包含的后端会在启动时被拒绝，错误信息会指出提供该后端的 feature。问题在进程启动时就会暴露，而不是等到第一个请求。原生程序同样拒绝 D1 和 libSQL，这两种只能由 Workers 宿主打开，相关 binding 见 [Cloudflare Workers](/zh-cn/deployment/edge)。在 Workers 宿主中，`GPROXY_DATABASE_URL` 优先于 D1 binding。libSQL 通过 HTTP 访问数据库，使用的是 Worker 调用上游时用的同一个 fetch 传输。

### 表结构同步

```text
$ gproxy migrate --data-dir ./data
INFO gproxy::instance: schema is up to date warnings=0
```

表结构从实体定义推导，而不是靠一串编号的迁移脚本。一份注册表描述所有表。同步时，在新数据库上创建缺失的表；在已有数据库上，在后端支持的范围内补上缺失的列和索引。重复执行不会丢失数据。

`gproxy serve` 启动时也会同步表结构。`gproxy migrate` 用于把同步作为独立步骤、由单一写入者在所有实例启动前执行的部署。多个实例共用一个数据库时应当这样做，以免多个实例同时修改表结构。

同步不会做以下事情：

- 创建默认设置或管理员；
- 执行版本化迁移；
- 修改列的类型、转换列中的数据，或修改已有的外键。

这些变更需要显式迁移，而且 GPROXY 不保证迁移在每个原生后端上都在单个事务中完成。

同步报告会列出警告，例如 D1 上的类型差异。警告列表为空并不能证明所有变更都已应用。在确认启动完成之前，请阅读日志中的诊断信息。

### Store API 与批处理

原生 SeaORM 连接和 Cloudflare D1 通过同一套 store API 访问。所有实体访问器都经过同一个泛型仓储，普通 CRUD 不需要按表手写，每个方法作为一个原子批执行。创建 store 不会打开数据库，也不会修改表结构。

调用方可以依赖以下行为：

- 读取结果与输入顺序一致，保留重复项，缺失的 id 对应 `None`，调用方可以把结果逐一对应到请求。
- 键谓词会被拆分，使每条语句都不超过 D1 的 100 个绑定参数上限，拆分后的语句仍在同一个批中执行。调用方自己写的 SQL 不会被拆分，数据库本身的请求数和大小限制仍然适用。
- SQL 错误会回滚事务性写入。条件写入影响 0 行时返回冲突，不会回滚同一批中的其他语句。
- 不会自动重试。提交结果不确定时（例如连接中断），请先检查已存储的状态，再决定是否重新写入。

### 精确金额

金额和限额以缩放后的整数存储，不使用浮点数。最小单位是 `0.000000001`，可表示范围约为 ±92 亿。

SQL 列类型为 `BIGINT`。实体以文本形式在 D1 的 JavaScript 边界上传递这些值，使比较、排序和加法在数据库内仍按数值进行；JSON 中使用十进制字符串也是出于同样的原因。

计算使用 decimal 类型，并且只对整次结算舍入一次，采用四舍六入五成双（ties to even）。递增计数器之前，结算会检查负值和有符号溢出。

## 缓存

缓存保存短期状态：带 TTL 的值、精确计数器、许可与租约，以及失效通知 topic。缓存不保存业务实体，也不保存持久账本；需要长期保留的数据都写入数据库。

| 后端 | 选择方式 | 共享范围 |
| --- | --- | --- |
| 内存 | 原生程序的默认值（`memory` feature） | 不共享，仅一个进程 |
| Redis / Valkey | `GPROXY_REDIS_URL`；程序需带 `redis` feature 构建 | 使用同一 Redis 的所有实例 |
| 数据库 | Workers 宿主的默认值 | 使用同一数据库的所有 isolate |

原生程序在启动时连接 Redis，连不上就退出。限流计数保存在缓存里，连不上 Redis 的实例即使接受了流量，也只能把受限流的请求逐个拒绝。数据库缓存只用于 Workers 宿主，原生程序会拒绝这种配置。发布版程序使用默认 feature 集，其中不含 `redis` 和 `s3`；需要它们的部署请自行构建（见[构建](/zh-cn/development/building)）。

### 操作

| 操作 | 行为 |
| --- | --- |
| `get` / `put` / `delete` | 不透明字节；必须提供正的 TTL；每次 put 产生新版本 |
| `compare_exchange` | 当前版本与预期一致（或键不存在）时替换或删除 |
| `counter` / `increment` / `decrement` | 精确的非负整数，带原子上限检查 |
| `acquire_permit` | 最多 N 个存活持有者，各自有 TTL |
| `acquire_lease` | 上限为 1 的许可，用作刷新租约 |
| `publish` / `subscribe` | 失效提示，不保证送达 |

每个操作只对单个键保证原子性，跨键不保证。键值、计数器、许可和 topic 是相互独立的命名空间，同一个名字可以在每个命名空间中各自存在。

计数器使用固定窗口，只有创建计数器的那次调用设置 TTL，因此每个实例只凭时钟就能算出窗口边界。许可没有窗口：它统计的是在途请求，窗口边界无法切分在途请求。许可的 TTL 只决定请求异常退出、没有释放许可时，缓存等多久才把许可收回。

### 缓存故障

Redis 出故障时，GPROXY 不会改用进程内缓存。如果两个实例各自退回本地状态，它们会持有相互冲突的锁，并分别统计同一个限额，这比直接报错更糟。

受限流约束的请求，如果缓存无法完成判断，会以 `429` 拒绝，且不带 `Retry-After`。如果放行这类请求，一次缓存故障就会悄无声息地关闭实例上的所有限流，而运维人员察觉不到。

### 运行多个实例

多个实例需要共享缓存：原生实例使用 Redis，Workers 上使用数据库缓存。如果每个进程各用自己的缓存，每个实例会各自统计限流、各自刷新同一个 OAuth 令牌，也收不到其他实例发出的配置失效通知。

登录会话同样保存在缓存中，所以在一个实例上发起的登录可以在另一个实例上完成。在负载均衡后面，这是常见情况。

多个部署或多套环境共用一台 Redis 时，请为每个部署设置独立的 namespace（默认为 `gproxy`）。通知 channel 名中包含数据库编号，因为 Redis Pub/Sub 会忽略 `SELECT`。

### 数据库缓存

Workers isolate 没有常驻进程，也没有 Redis，因此 Workers 宿主把缓存放在 D1 或 libSQL 数据库的三张表中。过期时间在 SQL 中比较，同一数据库上的所有 isolate 对哪些条目仍然有效的判断一致。

这种后端没有通知传输。订阅只会收到最初的 resync 提示，此后再无消息。Workers 宿主改为在每个请求开始时读取一次配置 revision，这就是它全部的同步机制。

## 配置同步

一次配置写入经过以下步骤：

```text
commit_revision([语句…, config_revision += 1, 读回])   一个事务
      ↓
reload   本实例的快照
      ↓
publish  ConfigurationChanged { revision, scopes }
```

数据行和 revision 递增在同一个事务中写入。如果分开写，其他实例可能在数据行写入之前就读到新的 revision。

其他实例通过两种方式得知变更，两者缺一不可：

| 机制 | 传递的内容 | 失效方式 |
| --- | --- | --- |
| 共享缓存上的失效通知 | 毫秒级的“重新检查” | 消息可能丢失 |
| 轮询 `settings.config_revision` | 持久化的 revision，每 30 秒一次 | 较慢 |

通知从不携带配置内容，只说明存在哪个 revision；只有当该 revision 比实例正在使用的更新时，实例才重新加载。无法解析的通知载荷一律触发重新加载。

缓存中的计数器不能代替数据库中的 revision。Redis 重启或淘汰可能丢失这个计数器；先提交数据库、再向 topic 发布，仍然是两次独立的操作，不构成一个事务。

重新加载串行执行，且只向前推进：旧 revision 不会覆盖新 revision；重新加载失败时，上一份快照继续提供服务。

## 文件存储

文件存储是可选的，配置后端之前处于关闭状态。

| 后端 | 选择方式 | 原生程序 | Workers 宿主 |
| --- | --- | --- | --- |
| 本地文件系统 | `--file-storage-dir`（`fs` feature，默认开启） | 支持 | 不支持 |
| S3 兼容存储，含 R2 | `[file_storage]` 配置块（`s3` feature） | 支持 | 支持 |

文件存储保存发布内容的正文（`/publications/{id}` 提供的字节）和下载的 tokenizer 词表。文件元数据和归属保存在数据库中，存储后端只保存内容。

没有文件存储时，发布和词表下载都返回“不支持”，因为没有地方存放这些字节。

发布链接还需要 `GPROXY_PUBLIC_BASE_URL`。没有配置时，发布会在写入任何正文之前失败，并提示调用方改为直接内联获取字节。GPROXY 不会用请求的 `Host` 头拼接链接，因为这个头由客户端决定：上游会接受答复，字节会被存下，交出去的 URL 却可能指向一个返回 404 的主机。

## 备份

- SQLite：停止进程后复制 `<data-dir>/gproxy.db`，或使用 SQLite 的在线备份。请把主密钥和副本保存在一起，没有主密钥就无法读取加密数据库中的凭证密钥。
- PostgreSQL 和 MySQL：使用数据库自带的导出工具。
- D1 和 libSQL / Turso：使用平台提供的快照。
- 逻辑导出：`gproxy export --out config.json --include-secrets`。导出内容是配置而非历史数据，不包含身份、用量和 capture。见[配置](/zh-cn/reference/configuration#导出与导入配置)。

每个加密密钥都绑定到所在行的 id，把某一行的密钥恢复到另一行上是行不通的。这样可以防止密钥在行之间被调换，对整库恢复没有影响。
