GPROXY 是一个自行部署的大模型 API 网关。上游账户（API Key、Codex 或 Claude Code 这类 OAuth 登录、浏览器 Cookie）交给 GPROXY 保管，客户端只需要一个网关地址、一个 GPROXY API Key 和你自己定义的模型名。

每个请求到达后，GPROXY 根据模型名选出供应商和凭证；客户端与上游的格式不同时，在 OpenAI、Claude、Gemini 三种格式之间转换；检查调用者的权限、限流和预算；最后记录 token 用量和费用。某个凭证或供应商失败时，请求会换到下一个继续尝试。

GPROXY 不运行模型，推理由上游服务完成。它也不能替上游补上缺失的能力：把请求转换成另一种格式，并不会让一个不支持工具调用或图像输入的模型变得支持。

它可以作为带 Web 控制台的原生服务（CLI 或容器）运行，也可以作为内置控制台的桌面或手机应用使用，或者配合托管数据库部署在 Cloudflare Workers、Netlify 和 Vercel 上。Rust 程序还可以把它当作库嵌入。

## 一个例子

假设有一个名为 `openai-main` 的供应商，里面保存了 OpenAI API Key；再建一个名为 `fast` 的模型路由，指向它的 `gpt-4o-mini`。客户端这样请求：

```sh
curl http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"你好"}]}'
```

客户端始终接触不到 OpenAI 的 Key。以后给 `fast` 再加一个供应商，或者换掉背后的模型，客户端都不用改。同一个路由也可以用 Claude 格式请求 `/v1/messages`，或用 Gemini 格式请求 `/v1beta/models/fast:generateContent`。
