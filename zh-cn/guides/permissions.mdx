本页说明 GPROXY 在把请求发往上游之前做的几项检查：权限规则决定调用方能用什么，限流决定能多频繁地用，费用预算决定还能花多少钱。三者分别配置、分别检查，不能互相替代。

## 检查顺序

密钥验证通过后，请求按以下顺序准入：

1. OAuth scope 与 OAuth 操作基线，仅针对使用 OAuth 访问令牌的请求。
2. 权限规则，得出调用方对当前模型和操作可以使用的供应商集合。
3. 凭证可见范围，得出调用方可以使用的凭证集合。
4. 确定适用的费用预算。
5. 限流。

限流放在最后，因为只有这一步会消耗额度。前面任何一步拒绝的请求都不会计数，没有权限的调用方也就无法耗尽别人依赖的限额。费用预算在动用任何凭证之前还会再检查一次，并在上游调用结束后扣减。

## 权限规则

权限规则属于某个用户或某一把 API Key，可以限定供应商、模型模式和操作，动作为 `allow` 或 `deny`。模型模式支持 `*` 与 `?`，因此限制个别模型时不必为它们另建供应商。

对每个供应商，规则按优先级从高到低、同优先级按 ID 排序依次检查，第一条适用的规则决定结果。需要例外时，给例外规则更高的优先级：优先级 0 的 `allow *` 加上优先级 10 的 `deny gpt-4*`，表示除 `gpt-4*` 外全部允许；优先级 0 的 `deny *` 加上优先级 10 的 `allow gpt-4o`，表示只允许 `gpt-4o`。同一优先级上有两条适用但结论相反的规则时按 ID 决定，结果固定但没有实际含义，因此相互重叠的规则应设为不同的优先级。

没有默认授权。普通用户必须有适用的 `allow` 规则；对该模型没有任何允许的供应商时，请求在路由之前就以 `403` 拒绝。

实例管理员不受权限规则限制，可以访问所有供应商，这样一条配错的 `deny` 规则不会把管理员挡在自己的实例之外。但管理员同样受下文的 OAuth 限制。

| API 字段 | 含义 |
| --- | --- |
| `userId` / `apiKeyId` | 二选一，指定规则主体 |
| `providerId` | 可选，省略时匹配所有供应商 |
| `modelPattern` | 模型模式，默认 `*` |
| `operation` | 可选，省略时匹配所有操作 |
| `action` | `allow` 或 `deny` |
| `priority` | 数值越大越先匹配 |

模型目录中的 `permitted` 字段表示当前调用方能否使用该条目。无权使用的模型仍可能出现在目录中。

### 供应商服务路由

供应商服务路由是渠道声明的账户、用量等非模型端点。它们没有模型，也没有操作，因此只有覆盖整个供应商的规则（任意模型、不限操作）才能允许或拒绝它们。

## OAuth 访问令牌

OAuth 访问令牌是用户交给其他程序使用的凭据，因此 GPROXY 在用户自身权限之外对它另加限制。

默认情况下，令牌只能使用一组固定的基线操作：列出和读取模型目录、token 计数、生成、流式生成和压缩。嵌入、图像、音频、文件、视频、Realtime 等其他操作一律拒绝。把客户端加入 `oauth.cli_client_ids` 可以为该客户端解除基线限制。供应商服务路由不在基线内，同样要求客户端在该列表中。

此外，每个操作都要求令牌带有对应的 `gproxy:<operation>` scope，operation 使用 snake_case 操作 ID，例如 `gproxy:list_models`、`gproxy:generate_content` 和 `gproxy:stream_generate_content`。供应商服务需要 `gproxy:services`。空 scope、`openid` 和 `profile` 不授予任何资源访问；旧客户端需要请求所需的 scope 并重新授权。

这些检查对所有令牌生效。无论是实例管理员授权的令牌，还是列在 `oauth.cli_client_ids` 中的客户端，都不能绕过 scope 检查；scope 也不能绕过操作基线或普通权限规则。

## 凭证可见范围

有模型权限还不够，调用方还需要有一份可以使用的凭证。凭证归属于用户、组织或团队。一个请求能选用哪些凭证，取决于调用所用密钥的绑定，而不是用户的全部成员关系：同时属于两个组织的用户可以持有只绑定其中一个组织的密钥，这把密钥无法使用另一个组织的凭证。绑定团队的密钥还可以使用该团队所属组织的凭证。实例管理员可以选用所有凭证。

管理范围、模型权限和凭证归属是三项独立的设置。模型有权限、但没有可见凭证能够处理时，请求返回 `503`（`no_usable_target`），而不是 `403`。

## 请求限流

限流规则属于用户或 API Key，包含指标、上限、周期秒数、可选的模型模式和启用状态。两类指标的行为不同：

- `concurrency` 统计正在处理的请求数。请求在响应完全发送之前一直占用名额；流式响应会在请求开始后占用很长时间。
- `requests` 以及其他任何指标名，统计当前周期内发起的请求数，每个请求计 1，与指标名称无关。token 数要等上游返回后才知道，所以需要限制 token 用量或花费时，请改用费用预算。

计数器保存在缓存后端。多实例部署必须共享缓存，否则每个实例都会各自执行完整的限额。缓存不可用时，受限流约束的请求会被拒绝，而不是跳过检查放行。

被拒绝时，根据返回的错误和日志区分是调用方限流还是上游凭证的限额。

## 费用预算

费用预算可以设置在用户、API Key、组织和团队上，以 USD 计。请求会检查密钥和用户的预算，以及密钥实际绑定的组织、团队的预算。绑定团队的密钥不会计入该团队所属组织的预算；两者都要计入时，请把密钥同时绑定到组织和团队。

所有适用且启用的预算都必须还有余量。周期和模型范围在控制台中设置。

实际费用要等上游调用结束才能确定，并在此时结算。因此在途请求和并发请求可能使总额超过上限。预算耗尽后会拒绝新请求，但不是上游消费的硬性封顶。

价格缺失会同时影响费用统计和预算消耗，请一并检查[价格配置](/zh-cn/reference/pricing)。API 中的预算金额以十进制字符串传输。

## 供应商与凭证限额

供应商的默认限额分别作用于每一份凭证，而不是由所有凭证共用一个额度池。凭证上启用的同名规则会覆盖供应商默认规则；恢复继承会删除凭证自己的规则。

这些都是本地限额，与上游账户的额度无关。重置本地规则不会重置上游余额或额度窗口。详见[供应商与凭证](/zh-cn/guides/providers)和[控制台](/zh-cn/guides/console)。

## 排查拒绝

- `401`：检查密钥及其用户是否存在、已启用且未过期。
- `403`：检查权限规则、OAuth scope 和 OAuth 操作基线。
- `429`：检查调用方限流、费用预算、凭证本地限额和上游额度。
- `503` 且错误为 `no_usable_target`：检查调用方能否看到可处理该模型的已启用凭证。

先在控制台查看相关的用户、密钥和凭证，再根据日志中的具体错误找到拒绝请求的规则。
