## 厂商服务路由

有些厂商 CLI 需要的不只是推理端点。它们还会从厂商控制面获取账号资料、用量窗口、插件、任务和文件，这些请求失败时 CLI 就无法正常工作。

因此渠道可以声明一张服务路由表，列出它认识的控制面路径以及每条路径返回的内容。宿主在转发到数据面之前，先用这张表匹配进来的路径。

控制面路径因厂商而异，所以只在供应商或 namespace 挂载点上匹配。聚合挂载点不指定渠道，没有渠道也就没有路由表可查：

```text
https://gproxy.example/codex/backend-api/wham/profiles/me
                       ^^^^^ 名为 "codex" 的供应商（或 namespace）
```

表中没有的路径返回 `404`，视图为 `credential:{id}` 时除外（见下文）。

### 选择视图

请求头 `x-gproxy-view` 指定调用方想要的结果。不带此请求头时视图为 `caller`，普通成员也只能使用 `caller`。

| 请求头 | 返回内容 |
| --- | --- |
| `x-gproxy-view: caller` | 调用方自己的数据：其用量窗口、预算链，以及其自身调用创建的资源。身份、用量和设置类请求不会访问厂商。 |
| `x-gproxy-view: pool` | 同上，但在目标中的所有凭证上汇总。 |
| `x-gproxy-view: credential:{id}` | 原样转发。用指定凭证自己的鉴权访问上游，厂商的应答不做修改直接返回。 |

能使用哪种视图取决于凭证归属。目标是调用方在该供应商上可见的凭证集合，与同一把 key 发起模型调用时可用的凭证相同。只有实例管理员，或者拥有该集合中全部凭证的组织或团队的 `Admin` 成员，才是这个目标的管理员。其他人都是成员，只能使用 `caller`；请求 `pool` 或 `credential:{id}` 会返回 `403`。

要求“全部凭证”是为了保证管理一个组织时，不会看到混有其他组织凭证的池。没有归属的凭证也就没有人能是它的管理员，所以在凭证全部共享的单租户实例上，只有实例管理员能使用 `pool` 和 `credential`。

任何视图下都拒绝签发 key。共享订阅上的长期 API key，正是共享网关要避免发放出去的凭据。

### 计量与取消

厂商服务调用不占用限流租约，否则一次资料查询就会消耗调用方留给付费流量的额度。服务调用也不写 capture 记录：引擎不为服务调用写上游记录，下游记录便无从关联，看上去会像一个没有到达任何上游的请求。

服务调用仍然经过预算链，因为 `caller` 视图要据此展示调用方自己的额度窗口。查询额度不会消耗额度。

服务调用与模型请求使用同一个取消令牌。取消会中止凭证准备、上游调用和 HTTP 响应的流式读取。对 WebSocket 服务，令牌覆盖握手阶段，连接建立后由宿主管理。服务调用同样不占用限流租约，也不产生模型用量。

## Codex CLI

`codex` 渠道声明了 CLI 在 Responses 之外向 ChatGPT 后端发起的调用。接口细节以 `samples/codex` 下 CLI 自己的源码为准。

| 类别 | 路径 |
| --- | --- |
| 插件与 MCP | `/backend-api/ps/**` |
| 账号、设置、用量、任务、环境、远程控制 | `/backend-api/wham/**` |
| 上传 | `/backend-api/files/**` |
| 工作区插件共享 | `/backend-api/public/plugins/**` |
| 启动时的身份探测 | `GET /v1/user-auth-credential/whoami` |

CLI 有两种方式访问同一批端点：ChatGPT 主机上使用 `/backend-api/wham/**`，Codex API 主机上使用 `/api/codex/**`。这两种写法，以及裸的 `/codex/**` 和 `/ps/**` 挂载，在查表前都会统一为 `/backend-api/**`，所以客户端配置成哪种主机风格都可以。

`/backend-api/wham/remote/control/server` 是 WebSocket，也是唯一需要协议升级的服务路由。Codex 不接受合成视图，因此只能由该凭证的管理员发送 `x-gproxy-view: credential:{id}` 来访问。

表中没有归类的路径落入 `/backend-api/{*path}` 前缀规则，原样转发，非 2xx 应答也一样。

## Claude Code

`claudecode` 渠道声明了 CLI 在 Messages 之外发起的 OAuth 作用域内 `/api/**` 调用：profile、validate、roles、bootstrap、用量、策略限额、账号设置、文件上传与下载、组织连接器、插件与 skill、引导与计费控制、桌面端更新跳转，以及 Claude Design 接口。

这些调用全部发往 `api.anthropic.com`。`claude.ai` 只用于凭证的 cookie 初始化，所以渠道在处理这些调用时不会访问它。

在 `caller` 和 `pool` 视图下，身份、用量和设置类应答由本实例已知的信息合成，其中的 id 是供应商与调用方身份的稳定哈希。CLI 显示的账号、组织和套餐都是 GPROXY 生成的值；不会编造任何关于共享上游账号的信息，也不会泄露它。

## GPROXY 作为 OAuth 授权服务器

使用 OAuth 登录的 CLI 可以登录到本 GPROXY 实例，而不是登录到厂商。这与 SDK 的 `login()` 是两回事：在 `login()` 中，GPROXY 是别家授权服务器的 OAuth 客户端。

```text
  Claude Code ──authorize/token──▶ gproxy   （授权服务器）
                                     │
                                     └──login()──▶ OpenAI   （客户端）
```

每个挂载点下都有这组端点，客户端发现的就是它所访问的挂载点对应的授权服务器：

```text
GET  {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/token
POST {mount}/v1/oauth/device/code
POST {mount}/v1/oauth/revoke
GET  {mount}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{mount}/v1
```

```sh
curl -s http://127.0.0.1:8787/v1/.well-known/oauth-authorization-server
```

```json
{"issuer":"http://127.0.0.1:8787/v1",
 "authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/authorize",
 "token_endpoint":"http://127.0.0.1:8787/v1/oauth/token",
 "device_authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/device/code",
 "revocation_endpoint":"http://127.0.0.1:8787/v1/oauth/revoke",
 "response_types_supported":["code"],
 "grant_types_supported":["authorization_code","refresh_token",
   "urn:ietf:params:oauth:grant-type:device_code"],
 "code_challenge_methods_supported":["S256"]}
```

v3 把这些端点放在根路径；v4 把它们移到 `/v1` 之下，与 `/v1/messages` 遵循同一条前缀规则，共用一份实现。

### 授权服务器的安全规则

- 必须使用 PKCE S256。`plain` 会被拒绝，不带 challenge 也会被拒绝。所有注册的客户端都是 public 客户端，没有 secret 可以证明身份，能阻止泄露的授权码换取令牌的只有 verifier。
- redirect URI 必须精确匹配，不接受前缀、通配符或“同源”。任何更宽松的规则都会放行某个攻击者控制的 URL。
- 授权码、refresh token 和设备码都只能使用一次。每次都在一个原子批次中消费并替换，因此无论两次兑换如何交错，都不可能同时成功。
- 重放授权码或 refresh token 会撤销整个令牌族：该授权、它的内部 key，以及它签发过的所有令牌。应答丢失和凭据被盗无法区分，所以一律按泄露处理。合法客户端重新登录即可，盗用者则不能。设备码流程例外，因为轮询客户端本来就会重复发送设备码。

### OAuth 调用方的权限

access token 是用户交给别人的程序使用的凭据。除非客户端列在实例的 `oauth.cliClientIds` 中，否则该令牌只能列出模型、查询模型、计算 token、生成、流式生成和压缩，其他操作一律返回 `403`。实例管理员的账号也受此限制，管理员账号恰恰最不应该让第三方令牌获得管理权限。

把客户端写进 `cliClientIds`，意味着运维者认可它在整个 API 上代表用户操作。不过令牌仍受用户授权的 scope 约束：每个操作都要求授权中包含对应的 `gproxy:{operation}` scope，列入名单的客户端也不例外。

OAuth 调用方也不能签发、轮换、查看或删除 key，不能修改账号密码。

## 会话亲和性

多轮对话的 CLI 最好让一个对话始终使用同一把凭证。GPROXY 按实际发出请求的客户端的格式读取对话标识，而不是按它将被转发到的上游：转发到其他渠道的 Claude Code 请求，读取的仍是 Claude Code 的字段。

按以下顺序取第一个非空值：

1. 网关自己的请求头 `x-gproxy-session-id`。
2. 各客户端的原生请求头，依次为 `x-opencode-session`、`thread-id`、`session-id`、`x-claude-code-session-id`、`x-conversation-id`、`x-grok-session-id`、`x-session-id`、`x-session-affinity`、`session_id`。
3. 入站请求体格式自带的会话字段：Responses 的 `client_metadata.thread_id` 或 `session_id`；Claude 在 JSON 编码的 `metadata.user_id` 内部的 `session_id`；Gemini 的 `request.session_id` 或 `request.sessionId`。Chat Completions 没有这类字段。
4. 对话稳定前缀的 sha256 指纹。
5. 请求 id，记录为兜底值，而不是当作会话。

只读取上述字段，不会在任意 JSON 中递归查找名为 `session_id` 的字段。请求级、轮次级和缓存级标识，如 `x-grok-req-id`、`user_prompt_id`、`prompt_cache_key`、`previous_response_id`，都不会被当作会话。

网关请求头不会转发给上游，客户端发来的也一样：客户端不能通过发送网关用来标识会话的请求头，去选中其他调用方的对话。没有任何会话请求头的请求也不会被拒绝。
