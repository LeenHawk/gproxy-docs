本页说明 GPROXY 如何把客户端请求中的 `model` 解析成供应商、凭证和上游模型名，以及如何配置决定这一过程的路由和模型目录。如果要修改请求参数而不是请求的去向，请使用[重写规则](/zh-cn/guides/rules)。

## 模型名解析

客户端填写的模型名通常不是上游模型 id。GPROXY 在请求进入引擎之前完成解析，引擎拿到的始终是已经选定的目标：

```text
请求里的 model
  → 第一条命中的形式：路由名 · 供应商名/模型
  → 候选按渠道、允许的供应商、允许的凭证收窄
  → 按 (tier, 健康度, 权重倒序, 稳定 id) 排序
  → 首段按路由策略均衡
  → 每次尝试得到一个 (供应商, 凭证, 上游模型)
```

模型名按下表顺序匹配，采用第一条命中的形式：

| 名字 | 解析为 | 尝试预算 |
| --- | --- | --- |
| 没有模型 | 全部启用的供应商，无上游模型 | `settings.max_attempts` |
| 模型路由名称 | 该路由启用的成员 | 路由自己的 |
| `供应商名/模型` | 那一个供应商 | `settings.max_attempts` |
| 其他 | `404 unknown_model` | — |

路由名精确匹配，并且优先于前缀形式。已禁用的路由不参与匹配，请求会继续尝试后面的形式。`供应商名/模型` 中的前缀始终是供应商名，而不是渠道 id：名为 `openai`、渠道为 `codex` 的供应商通过 `openai/…` 调用，与其专属入口 `/openai/v1` 一致。

匹配到的候选随后按入口挂载点的渠道、调用方 Key 允许的供应商和允许使用的凭证收窄。名字能够解析、但收窄后没有可用目标时，返回 `503 no_usable_target`。这属于配置问题（没有启用的成员、没有可用凭证，或者 Key 无权使用其中任何一个），因此与未知模型分开报告。

实际使用中，应把路由名交给客户端作为模型名。

## 创建路由

路由是一个公开的模型名，包含若干供应商／上游模型成员、一个均衡策略和一个尝试预算。创建名为 `main` 的路由后，客户端即可请求 `model: "main"`。

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/routes \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"main","strategy":"round_robin","maxAttempts":6}'
```

```json
{"id":"33a88261f571347c7f0408c3bd2e2164","name":"main","strategy":"round_robin",
 "maxAttempts":6,"enabled":true}
```

| 字段 | 含义 |
| --- | --- |
| `name` | 全局唯一，客户端在 `model` 中直接填写此名称。 |
| `sessionAffinity` | 会话优先复用成功的供应商／模型目标，默认关闭；内部凭证选择仍由供应商负责。 |
| `strategy` | `round_robin`、`weighted` 或 `failover`。 |
| `maxAttempts` | 含首次调用在内的总尝试预算，必须为正数。执行时以 `settings.maxAttempts`（默认 6）为硬上限。 |

控制台中，路由位于“模型路由”页面。

## 添加成员

每个成员把流量发往一个供应商，并指定上游模型名：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/route-members \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"routeId":"…","providerId":"…","upstreamModel":"gpt-4o-mini",
       "tier":0,"weight":100}'
```

| 字段 | 含义 |
| --- | --- |
| `providerId`、`upstreamModel` | 成员把流量发往哪里。模型名是显式字符串，不是模型目录的外键。 |
| `tier` | 越小越优先。tier 0 用尽之前，tier 1 不会收到任何流量。 |
| `weight` | 正数，默认 100。用于同一 tier 内分流，也决定故障转移候选的顺序。 |
| `enabled` | 禁用的成员不进入执行计划。 |

所属供应商已禁用或已删除的成员会被跳过。如果 `upstreamModel` 与该供应商某个已启用模型的变体名相同，请求会改用该模型的上游名称发出。

成员不指定凭证。引擎在选中的供应商内部挑选凭证，并且先在该供应商的凭证之间故障转移，然后才转到下一个成员。

## 排序与均衡策略

候选按 `(tier, 健康度, 权重倒序, 稳定 id)` 排序。稳定 id 是成员 id，因此两个候选不会相等，每次请求的排序结果一致。

tier 是严格的优先级，后面的 tier 不会与前面的 tier 一起均衡。只有首段（与第一个候选 tier 和健康度都相同的那些候选）会按路由策略重新排列：

- `round_robin`：用每个路由各自的计数器轮转首段。
- `weighted`：把平滑加权轮询选出的候选移到最前。一个完整周期内，每个成员被选中的次数与权重成正比，并且分散出现，不会连续集中。
- `failover`：保持排序结果不变。

轮转使用计数器而不是随机数，因此原生版本与 wasm 版本行为一致，顺序也可以复现。计数器保存在进程内存中，多个实例之间不共享；重启后从第一个候选重新开始。

健康度取决于供应商的凭证。已禁用、已退役和已失效（dead）的凭证直接排除。被封禁的凭证（例如触发限流后）在该供应商仍有未封禁凭证时排除；如果某个供应商的凭证全部被封禁，该供应商仍保留在计划中，但排在所有健康供应商之后。这样，被限流的供应商会作为最后的选择，而不是被当作不可用。

开启 `sessionAffinity` 后，会话上一次成功的目标会被优先使用，但只限于同一个首段（相同 tier 和健康度）之内。

## 路由名称与 namespace

客户端使用的模型名直接在路由上创建和修改，不需要另外配置公开名称映射。

### namespace

名称中带 `/` 的路由会在运行时形成一个 namespace。创建路由 `acme/fast` 后，`acme` 就成为一个挂载点，向 `/acme/v1/chat/completions` 发送 `{"model":"fast"}` 会解析到 `acme/fast`：

```sh
curl -s http://127.0.0.1:8787/acme/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"hi"}]}'
```

namespace 只是路由名的索引。它不单独存储，不对路由分组，也不拥有路由；出现新的 namespace 时不会创建任何对象。

### 保留的首段

如果路由名的首段与现有供应商名相同（不区分大小写），管理接口会拒绝写入，因为 `名称/…` 已经表示该供应商的 `供应商名/模型` 形式：

```json
{"error":{"code":"invalid_request","message":"invalid request: `codex/` is reserved:
 a first segment naming a provider already means `provider/model` narrowing;
 choose a distinct model route name"}}
```

其他首段都可以使用，例如 `coding/fast`。

## 调用方看到的模型列表

`GET /v1/models` 返回已配置的模型名，包括路由名和 `供应商名/模型`，并且只列出调用方有权使用的名字。它不会代理某一家上游的模型目录。新增或导入供应商模型后，它们会以供应商名为前缀出现在列表中。

下面两种调用方式等价：API 地址用 `/供应商A/v1`、模型填 `gpt-5`；或者地址用 `/v1`、模型填 `供应商A/gpt-5`。`GET /供应商A/v1/models` 只查询供应商 A，并保留上游模型原名。

前缀使用供应商的显示名称。供应商改名后，对应的模型前缀和 API 地址也会随之改变。

用户门户的模型列表还会显示调用方无权使用的名字，并用 `permitted` 标注：

```sh
curl -s http://127.0.0.1:8787/portal/api/models -H "Authorization: Bearer $GPROXY_KEY"
```

```json
[{"name":"provider-A/gpt-4o-mini","providerCount":1,"channelIds":["custom"],"permitted":true},
 {"name":"fast","providerCount":1,"channelIds":["custom"],"permitted":true}]
```

调用方规则覆盖不到的名字仍会出现在列表中，标记为 `permitted: false`。v3 会去掉这些行；v4 保留它们，因为静默省略会让“模型返回 404”和“没有权限使用该模型”看起来一样，而且这些名字本来就是运维者对外公开的实例配置。

列表不显示名字背后的供应商 id，只给出供应商数量和渠道 id。调用方可以据此判断一个名字有多少冗余，但看不到具体是哪些供应商。

## 模型目录

模型目录由两张表组成，路由不依赖其中任何一张：路由成员以普通字符串指定上游模型，因此两张表里都没有的名字也能正常路由。目录数据用于模型列表、文档、元数据和计价。

- `provider_models` 记录每个供应商提供哪些上游模型名，模型发现的结果写入这里。
- `models` 是全局目录，`provider_models` 的行可以指向其中一条。每条记录包含一个名字、它的元数据，以及 token 估算应使用的词表。

手动添加一个供应商模型：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/provider-models \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","upstreamName":"gpt-4o-mini"}'
```

```json
{"id":"f32df0bb6378c03e70f7c3aa6315a3b8","providerId":"5a45fd807be0…",
 "upstreamName":"gpt-4o-mini","modelId":null,"metadata":{},"enabled":true}
```

### 从上游发现模型

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

模型发现使用供应商自己的协议向上游查询，不做任何转换，返回的就是上游的模型名。每一项都会注明该供应商是否已有对应记录，以及内置目录能否为它定价。`POST /admin/api/models/discover/apply` 插入你指定的条目并跳过已有条目，所以同一次发现结果应用两次与应用一次效果相同。

补全元数据时，先按完整模型 ID 匹配，再尝试唯一的末段名称；有歧义的名字不补默认值。合并顺序为：内置默认值，上游的非空字段，本地覆盖值。在控制台向已有的供应商模型导入时，只补充缺失的字段。

<Warning>
模型发现和 `POST /admin/api/models/test` 都会使用真实凭证，并写入真实的用量记录。参见[测试供应商](/zh-cn/guides/providers#测试供应商)。
</Warning>

### 内置模型目录

每个版本都内置一份模型目录，包含模型名、上下文窗口和默认价格。它是生成该资源时的快照，不是实时目录：

```sh
curl -s http://127.0.0.1:8787/admin/api/default-model-catalog -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

设置 `overwrite: false` 后可以放心重复应用：运维者修改过的规则保留修改，并在结果中标记为跳过。

内置模型 ID 使用 `claude-sonnet-4` 这样不带来源前缀的名字，而不是 `anthropic/claude-sonnet-4`；来源 URL 和原始报价仍然保留。带前缀的上游名称仍可按末段名称匹配。匹配默认价格时优先选择最长的匹配模型片段；从供应商导入价格时，规则模式使用该供应商实际的上游名称。

默认价格是 OpenRouter 的报价快照，不代表每个供应商的实际合同价格。应用默认价格会生成全局计费规则，已有同模式的规则不会被替换。供应商专属规则优先于全局规则。价格在全局模型和供应商模型的编辑弹窗中修改，价格编辑器支持费率、上下文分段和服务等级。参见[价格与分层](/zh-cn/reference/pricing)。

### “模型”页面

控制台的“模型”页面（`/console/model-catalog`）列出数据库中保存的模型。它与权限选择框使用同一个 `/admin/api/models` 接口；数据库为空时列表为空。页面显示已保存的能力和上限、关联的供应商，以及能匹配到的内置参考价格。

“加载默认模型”把你选中的内置条目写入数据库，已有模型保持不变。加载模型元数据不会修改计价规则。也可以手动新增模型。删除的模型会从列表中移除，读取列表时不会从内置数据中补回。

元数据在导入时复制。之后编辑全局模型，不会改变此前已经从它导入的供应商模型。

### 更新内置目录

用以下命令重新生成内置资源：

```sh
node scripts/update-openrouter-model-catalog.mjs
```

加上 `--input response.json` 可以用保存好的响应离线生成。公开的模型接口不需要 Key；可选的凭证只从 `OPENROUTER_API_KEY` 环境变量读取。生成器保留原始的 `source_pricing` 供核查，只映射它支持的计费单位。单位换算后，计费价格舍入到 9 位小数（就近舍入，中点取偶），导入默认价格时使用同样的规则。

价格缺失或为动态价格，并不表示免费。从官方价格页补充价格之前，先确认模型版本、地区、单位和阈值，不要猜测缺失的费率。
