重写规则在请求发往上游、或响应返回客户端的途中修改内容：添加系统文本、放置缓存断点、修改 JSON 字段、替换文本以及设置请求头。本页最后一节介绍协议与端点覆盖，用于决定供应商在某个操作上使用哪种上游协议和 URL。

## 添加规则

打开供应商的“重写规则”页面，新增规则，选择类型并填写内容。新建供应商时会自动创建并绑定一个同名的默认规则集，只有一个供应商时无需手动管理绑定。多个供应商需要共用一组规则时，再使用高级绑定设置。

| 界面类型 | 用途 | API `action` |
| --- | --- | --- |
| 系统文本 | 在现有系统指令前或后添加文本 | `system_text` |
| 缓存断点 | 按协议为全局、系统、消息或工具添加缓存标记 | `cache_breakpoint` |
| 重写 | 设置、删除字段，或合并 JSON 对象 | `set`、`delete`、`merge` |
| 变换 | 对正文、请求头或查询参数做正则替换 | `replace` |
| 请求头 | 设置值，或合并逗号分隔的值 | `header_set`、`header_merge` |

系统文本支持 Claude、OpenAI Chat、Responses（含 WebSocket）和 Gemini。缓存断点支持 Claude 与 OpenAI 协议，具体位置和有效期见[提示缓存](/zh-cn/guides/claude-caching)。

每条规则都有 `phase`（`request`、`response` 或 `both`）和 `target`（`body`、`header` 或 `query`）。

## 执行顺序

请求先转换为上游协议，然后执行请求规则，最后由渠道发出。响应先执行响应规则，再转换回客户端协议。因此，规则中的字段路径要按上游格式填写。例如，OpenAI Chat 请求路由到 Claude 供应商后，请求规则看到的已经是 Claude 的 `system` 和 `messages` 字段。

已启用的规则集绑定按 `sortOrder`、再按 ID 排序执行，集内已启用的规则也按同样方式排序。每条规则都基于前一条的结果执行。系统文本和缓存断点规则与其他规则遵循同一顺序。

## 路径、正则与请求头

JSON 改写需要填写路径，例如 `temperature` 或 `messages.*.content`，路径中的 `*` 表示所有元素。`set` 的值可以是任意合法 JSON，`merge` 的值必须是 JSON 对象，`delete` 不需要值。

变换使用 Rust 正则语法，支持 `(?i)`、`(?s)`，替换内容中可以使用 `$1` 和 `${name}`。填写正文路径时，只在选中的 JSON 字符串值内替换；不填路径时对整段正文文本替换，此时要注意替换后仍是合法 JSON。

请求头和查询参数规则需要填写 `targetName`。`header_set` 替换请求头的值；`header_merge` 合并逗号分隔的值并去重。不要把上游密钥写进与其他供应商共用的规则。

## 过滤条件

过滤条件限制规则在什么情况下执行。所有已设置的条件都满足时规则才会执行，未设置的条件不做限制。

| 条件 | API 字段 | 匹配内容 |
| --- | --- | --- |
| 操作与协议 | `filterOperationKeys` | 转换后在供应商上执行的操作 |
| 模型 | `filterModelPattern` | 上游模型名或客户端请求的模型名，支持 `*`、`?` |
| 请求头 | `filterHeaderPattern` | 正则表达式，逐个匹配 `name: value` 形式的入站请求头 |
| 流事件 | `filterEventPattern` | SSE 事件名或 JSON `type`，用于正文规则 |

为某个客户端添加兼容规则时，应加上请求头过滤，以免影响其他客户端。

模型过滤的候选项只来自已保存的供应商模型及其变体。在供应商页面中只显示该供应商的模型；在独立的规则集页面中显示所关联供应商模型的并集。未关联供应商的规则集没有候选项，但仍可手动填写模型名或 `gpt-*` 这类匹配模式。候选列表不会请求上游的模型目录。

## 正文与请求头条件

`filterBody` 和 `filterHeader` 让规则只在某个正文字段或请求头取特定值时执行。两者可以单独使用，也可以同时使用，并且要与其他过滤条件同时满足：

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "service_tier"
  ],
  "pattern": "",
  "replacement": "\"priority\"",
  "filterBody": {
    "path": "reasoning.effort",
    "op": "eq",
    "value": "high"
  },
  "filterHeader": {
    "name": "x-client-mode",
    "op": "eq",
    "value": "fast"
  }
}
```

`filterBody` 判断当前的 JSON 正文，能看到前面规则所做的修改，只能用于正文目标。路径由点分隔的键和数组下标组成，例如 `reasoning.effort`、`messages.0.role`，不支持 `*`。相等比较区分 JSON 类型，`"1"` 不等于 `1`；字段缺失与值为 `null` 是两种情况。非 JSON 正文不满足任何正文条件，`not_exists` 也不例外。

`filterHeader` 判断原始的入站请求头，可用于任何目标和阶段。请求头名称不区分大小写；值按区分大小写的完整字符串比较，不按逗号拆分。同名请求头出现多次时，`eq` 只要有一个值相等即命中；`ne` 要求请求头存在且所有值都不相等。

比较方式有 `eq`、`ne`、`exists` 和 `not_exists`。`eq` 和 `ne` 必须提供 `value`，`exists` 和 `not_exists` 不能提供。字段缺失时不满足 `ne`。

在流式传输中，条件对每个完整的 SSE 事件、NDJSON 记录、JSON 数组元素或 WebSocket 消息单独判断，不在它们之间保留状态；普通 HTTP 正文按整体判断。要移除条件，在表单中清空对应的路径或名称，或者把 API 字段设为 `null`。PATCH 请求中省略该字段则保留原有条件。

### JMESPath 表达式

`filterBody` 也可以是一个 JMESPath 表达式字符串。表达式针对当前正文求值，只有结果为布尔值 `true` 时才执行动作；类型错误、未知函数、其他求值错误以及非布尔结果都视为不匹配。保存规则时会校验表达式语法。原有的 `{ "path", "op", "value" }` 对象形式仍然可用。

下面的规则只在最后一条消息的某个文本块包含 keepalive 标记时把 `max_tokens` 设为 0，历史消息中的标记不会触发：

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "max_tokens"
  ],
  "replacement": "0",
  "filterBody": "length(messages[-1].content[?type(text) == 'string' && contains(text, '[cache-keepalive]')]) > `0`"
}
```

负索引 `[-1]`、投影、`contains()`、比较运算和逻辑组合都遵循 [JMESPath 规范](https://jmespath.org/specification.html)。缺失的字段求值为 `null`，可以在表达式中显式判断；非 JSON 正文始终不匹配。动作的 `paths` 仍使用上文的点路径语法，与表达式无关。

表达式只编译一次。正文没有变化时，所有表达式共用同一份转换后的 JMESPath 数据；前面的规则确实修改了正文时，会重新转换，避免读到过期的值。不使用表达式的规则不会产生这份额外副本。流中的每个单元单独求值；需要遍历整个文档的查询，耗时仍随文档大小增长。

## 流式响应

正文重写以完整事件为单位执行，例如一个 SSE 事件或一个 JSON 数组元素，而不是网络数据块。单个事件超过 `settings.maxStreamEventBytes` 时请求失败。可以用事件过滤只改写特定类型的事件。

## 以 JSON 编辑规则

在规则集中，或在供应商的“重写规则”页面中新建或编辑规则时，切换到“高级 JSON”即可粘贴一个 v4 规则对象。表单与 JSON 可以相互切换，JSON 可以格式化。输入有误时内容会保留在编辑器中并显示错误，保存时还会校验规则能否执行。

例如，将正文中的 `"type":"function"}` 替换为 `"type":"function","strict":false}`：

```json
{
  "action": "replace",
  "phase": "request",
  "target": "body",
  "pattern": "\"type\":\"function\"\\}",
  "replacement": "\"type\":\"function\",\"strict\":false}"
}
```

请使用 v4 的 `action`、`pattern`、`replacement` 字段。规则集、ID 和顺序由页面管理，不要写进 JSON。可选的过滤条件和 `enabled` 可以一并填写；省略过滤条件表示不限制，省略 `enabled` 表示启用。编辑器一次只接受一个规则对象，不接受数组。

## 通过 API 管理

下面的示例把选中字符串中的 `widget` 替换为 `gadget`。请换成你自己的规则集 ID。

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"ruleSetId":"your-rule-set-id","action":"replace",
       "phase":"request","target":"body","paths":["messages.*.content"],
       "pattern":"(?i)\\bwidget\\b","replacement":"gadget",
       "filterOperationKeys":[{"operation":"generate_content","dialect":"openai_chat"}]}'
```

`PUT /admin/api/rule-sets/{id}/rules` 一次替换规则集中的全部规则。系统文本和缓存断点规则的 `replacement` 是 JSON 编码的配置字符串，控制台会自动生成，无需手工拼接。

## 兼容预设

`GET /admin/api/rule-presets` 返回内置的 OpenCode、pi-mono、Aider、Cline、Continue 和 Cursor 兼容预设。每个预设包含哪些规则，以接口的返回为准。

<Warning>
`POST /admin/api/rule-sets/{id}/rule-presets/{preset}` 会替换规则集中的全部已有规则。需要保留原有规则时，先读取或导出，合并后再保存。
</Warning>

## 协议与端点覆盖

供应商的“路由规则”决定它在某个操作上使用哪种上游协议。它与选择供应商的“模型路由”是两项不同的配置。

- `operation_rules` 覆盖供应商在某个操作上的协议列表。客户端协议在列表中时直接透传，否则转换为列表中的第一个协议。
- `operation_endpoints` 覆盖某个操作、协议和传输方式对应的完整端点 URL。

例如，修改生成操作使用的协议：

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/operation-rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"providerId":"your-provider-id","operation":"generate_content",
       "action":"dialects","target":["claude","openai_chat"]}'
```

没有覆盖时使用渠道的默认值。`POST /admin/api/providers/{id}/routing-defaults/reset` 清除该供应商的操作规则和端点覆盖。

`custom` 渠道还需要在供应商配置中声明 `dialects`，例如 `["openai_chat", "openai"]`。某个操作调用失败时，先确认上游是否支持该操作，再检查这个列表和操作覆盖。
