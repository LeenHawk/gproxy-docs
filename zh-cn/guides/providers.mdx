本章面向负责把 GPROXY 接到上游的管理员，内容包括选择渠道、创建供应商、添加和维护凭证，以及出站连接的设置。

**渠道**（channel）是编译进二进制的上游适配器，每个渠道对应一族上游。**供应商**（provider）是某个渠道上保存的一条连接，由名称、可选的 base URL、渠道自己的 `config` JSON 和一个凭证池组成。一个渠道下可以建任意多个供应商，例如 `openai-main` 和 `openai-eu` 都可以使用 `openai` 渠道。

## 选择渠道

### 接入兼容服务

如果某个服务与标准 API 的区别只在服务地址和请求头，就不需要专用渠道。用 `custom` 渠道建供应商，填写服务地址和它支持的协议即可：

```json
{ "name": "example-vendor", "channel": "custom",
  "baseUrl": "https://api.example-vendor.com",
  "config": { "dialects": ["openai_chat"] } }
```

只有在一行供应商配置无法表达某个服务的需求时，才会为它编写专用渠道。NVIDIA NIM、Vercel AI Gateway 和 Cloudflare AI Gateway 过去都用 `custom` 接入，现在各有专用渠道，提供各自的认证和余额查询，应优先使用。

## 创建供应商

在控制台打开 **供应商**，点击 **新建供应商**，选择渠道，填写名称和该渠道表单中的字段，然后 **保存**。接着添加凭证（见[凭证](#凭证)），先测试一把凭证，再把供应商加入模型路由。

也可以通过管理 API 创建：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/providers \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"example-vendor","channel":"custom",
       "baseUrl":"https://api.example-vendor.com",
       "config":{"dialects":["openai_chat"]}}'
```

修改不需要重启。供应商和凭证的每次写入都与配置版本号的递增放在同一个事务里提交；实例先重新加载自身配置，再通知其他实例，因此下一个请求就能用上新配置。

## 供应商配置

| 字段 | 含义 |
| --- | --- |
| `name` | 管理员取的名称，必须唯一。它同时是供应商挂载点（`/{name}/...`），也是 `provider/model` 写法中的前半部分。 |
| `channel` | 上表中的某个渠道 id。 |
| `baseUrl` | 上游的源地址，仅对接受 base URL 的渠道有效。 |
| `config` | 渠道自己的 JSON。每个渠道声明自己读取哪些键，`GET /admin/api/channels` 会列出。 |
| `connectionProfileId` | 该供应商出站调用使用的连接配置（代理、TLS 模拟），见[连接配置](#连接配置)。 |
| `enabled` | 禁用的供应商不参与解析。 |

`custom` 的 `config` 包含 `dialects`（端点支持的协议格式）、静态 `headers`、`allowed_headers` 和两个 magic cache 开关。模拟厂商 CLI 的渠道会自行设置身份请求头，客户端无法覆盖。

以下各节说明个别渠道的专有选项。

### Claude 模型 fallback

`fallback_mode` 可取 `off`（默认）、`default` 或 `models`；`fallback_models` 是按顺序排列的上游模型 ID 列表。控制台根据渠道描述渲染这两个字段。列表中的空值、重复项和主模型会被跳过，最多使用三个 fallback 模型。

不同渠道的执行方式不同：

- Claude API、Claude Code 和自定义 Claude 端点：发送 Anthropic 的 `fallbacks` 字段及对应的 beta 头。`default` 模式由 Anthropic 选择 fallback 模型。
- OpenRouter：Claude Messages 请求发送 `fallbacks`，Chat Completions 请求发送 `models`，由 OpenRouter 执行 fallback。这不影响 `provider.allow_fallbacks`，后者控制的是同一模型在不同供应方之间的路由。客户端已经带了 `fallbacks` 或 `models` 时以客户端的值为准。Responses 请求不添加 fallback 参数，因为 OpenRouter 没有为它提供公开参数。
- Vercel、Azure、Vertex 和 AWS Bedrock：由 GPROXY 自己在同一凭证上用下一个配置的模型重试 Claude `refusal`，每次重新准备请求并重新签名。`default` 模式选择主模型命名空间下的 `claude-opus-4-8`。云厂商专用的模型 ID 请按该上游接受的完整 ID 配置。

网关 fallback 对从其他协议转换为 Claude 的请求同样生效。它只处理 refusal，不重试任意 HTTP 错误。流式内容到达即下发；一旦已经有输出，只有上游签发了带 prefill 声明的 credit 才能继续，没有可兑现的 credit 时绝不重放服务端工具。每次实际尝试分别记录，并按各自的模型计价；报告零输出的 refusal 不计费。最终响应保留最后一次尝试的顶层 usage。

### Claude Code 额度续用模式

`claudecode` 渠道有两个开关，决定订阅额度用尽时的行为，默认都是 `false`。

- `low_priority: true`：5 小时额度被拒绝后，接受服务端给出的低优先级方案。此后同一会话发送 `anthropic-usage-limit: slow`，直到该窗口重置或服务端结束这一模式。周额度和单独的低优先级额度仍然有效。
- `extended_usage: true`：在未确认已开通付费额外用量时，为工具结果续轮发送 `anthropic-usage-limit: extended`。是否给予宽限由服务端决定，订阅额度不会因此重置。

即使两个开关都关闭，客户端自己发送的 `slow` 或 `extended` 也会保留，两者互斥。CountTokens 和控制类请求不带这个请求头。对 Claude Code 以外的客户端，以工具结果消息判断续轮；官方 CLI 内部的任务深度和实验开关，网关拿不到。

发送 `slow` 期间，GPROXY 遇到 `429 slot_busy` 和过载响应时会等待，然后在同一凭证上重试缓冲好的原始请求。与 CLI 2.1.302 一致，默认间隔 20 秒，随机浮动 30%，默认最长等待 20 分钟；服务端给出的提示值被限制在每次 5–600 秒、总计 1–360 分钟之内。宿主的截止时间或取消信号可以提前结束等待。预算耗尽、周额度耗尽和资格拒绝直接返回，不做这种重试；已经开始的响应流、无法重放的请求体和不透明的 fallback credit 兑换请求都不会重放。

额度视图还会记录服务端报告的低优先级额度和宽限额度，这些额度不会拦截普通请求。显式模式只对当前请求放行它所适用的订阅窗口；本地预算、模型专属额度以及上游失败或限流的冷却仍然生效。

### Claude Code 客户端身份

`client_identity` 决定 `claudecode` 渠道以哪个官方客户端的身份发出请求。两种身份都是同一个 CLI 二进制、同一个 OAuth 令牌。

- `cli`（默认）：交互式 CLI，`claude-cli/2.1.318 (external, cli)`。客户端自带的合法 CLI User-Agent 和计费块中的 `cc_entrypoint` 会保留。
- `agent_sdk`：Claude Agent SDK 0.3.318，`claude-cli/2.1.318 (external, sdk-ts, agent-sdk/0.3.318)`。只保留客户端自带的 Agent SDK User-Agent（`sdk-ts` 或 `sdk-py` 且带 `agent-sdk/…`），其他一律替换。计费块的 `cc_entrypoint` 跟随 User-Agent，回合按 SDK 回合填写（`cc_turn_origin=sdk`、`cc_prompt_index=0`）。

`identity_system_block: true`（默认 `false`）会在计费块之后紧接着放入与计费 `cc_entrypoint` 对应的身份 system 块：`cli` 使用 `You are Claude Code, Anthropic's official CLI for Claude.`，`sdk-*` 使用 `You are a Claude agent, built on Anthropic's Claude Agent SDK.`。客户端自带的 SDK 身份（包括 `running within the Claude Agent SDK` 变体）会保留；另一类身份块会被改写；客户端没有发送时则插入一个。关闭此开关时，客户端的 system 块原样保留。

计费校验和（`cch`）、`cc_version` 后缀和 `metadata.user_id` 在两种身份下的计算方式相同。Anthropic 可能对订阅下的 Agent SDK 流量与交互式使用分开计量，区分依据就是 entrypoint。

### 按操作覆盖 URL

`operation_endpoints` 为某个供应商的某个 `(操作, 方言, 传输)` 整体替换方法 URL。URL 按原样使用，不会在后面再拼接渠道的默认路径；渠道自己的路径参数由该方法解析：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/operation-endpoints \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","operation":"generate_content","dialect":"openai_chat",
       "url":"https://elsewhere.example/v1/chat/completions"}'
```

对于把模型名写在路径里的接口，URL 中的 `{model}` 会被替换成上游模型名，并作为单个路径段做百分号编码，例如 `https://relay.example/v1beta/models/{model}:generateContent`。

`operation_rules` 则按供应商覆盖渠道对某个操作的处理方式。渠道默认值保留在代码里，不会复制到每个新建的供应商中，所以没有覆盖项的供应商会跟随默认值的后续变化。`POST /admin/api/providers/{id}/routing-defaults/reset` 在一次提交中清除这两类覆盖。

### Gemini Interactions

`aistudio` 渠道支持两种 Gemini 协议：`gemini`（GenerateContent）和 `gemini_interactions`（Interactions API）。两者都对应 `generate_content` 和 `stream_generate_content` 操作，但 Interactions 有自己的请求格式、步骤事件和响应类型。

客户端请求 `POST /v1beta/interactions` 或 `POST /v1/interactions`，前面可以加供应商挂载前缀。设置 `stream: true` 即为原生 SSE。`GET /interactions/{id}`、`POST /interactions/{id}/cancel` 和 `DELETE /interactions/{id}` 使用相同的版本前缀；`stream`、`last_event_id` 等查询参数会原样转发，客户端可以据此读取或续传。Interaction 的 id 以及引用它的 `previous_interaction_id` 只对创建它的网关调用方有效，并且一直使用创建时的那份凭证。`agent` 目标和模型名一样经过路由与权限检查，转发给上游时保留 `agent` 字段。

Responses、Chat Completions 和 Claude Messages 都可以与 Interactions 直接互相转换，不依赖保存的状态。使用方法是在供应商的操作映射里把目标协议设为 `gemini_interactions`，或者建一个只支持 Interactions 的 `custom` 供应商：

```json
{ "channel": "custom", "baseUrl": "https://generativelanguage.googleapis.com",
  "config": { "dialects": ["gemini_interactions"] } }
```

转换覆盖函数调用与结果、带签名的思考历史、内联图片，以及文本和 JSON 输出 schema。Interactions 的步骤签名与 GenerateContent 的签名分开保存。无法转换的可选字段会记入转换诊断。文件 id 需要事先换成内联数据或 URL。

以下功能需要原生支持 Interactions 的上游：agent、后台执行、续接保存在其他协议中的对话，以及显式的 `store: true`。把 Interactions 客户端转换到其他协议的上游时，请发送完整历史并设置 `store: false`；这时拿到的响应 id 并不对应上游保存的 Interaction。

原生流式是增量返回的。跨协议的流式请求会先从上游收齐完整结果，再按客户端协议重新生成事件，因此不会缩短首个 token 的等待时间。轮询和续传读取不会重复计费累计用量；创建响应中没有用量信息的后台任务，网关不会上报其用量。

### GLM

`glm` 使用按量付费 API，`glmcode` 使用 GLM Coding Plan，两者都填写 `api_key` 凭证。默认地址是国内的 `https://open.bigmodel.cn`；国际账号把 `baseUrl` 设为 `https://api.z.ai`。`glmcode` 使用 Coding Plan 专用的 Chat、Claude Messages 和 Responses 入口，额度用尽后不会转用普通付费 API。

两个渠道的模型列表都取自 ZCode 官方动态目录：先请求 `/api/v1/client/configs`，下载返回的 `builtin_provider_config_json`，再选取对应地区的普通 API 或 Coding Plan 模板。没有内置的固定模型名单，下载失败时也不会退回旧名单。这份目录是官方的产品列表，不代表某个 Key 对其中每个模型都有权限。

`glmcode` 通过 `/api/monitor/usage/quota/limit` 读取服务端报告的用量百分比、各个独立窗口及其重置时间。普通 `glm` 尚未接入账户余额查询。

### MiniMax

`minimax` 默认地址为 `https://api.minimax.io`；国内平台的账号按平台文档填写国内 API 地址。OpenAI Chat 和 Claude Messages 均可使用 Subscription Key（Coding Plan / Token Plan）或按量付费 API Key，都填入 `api_key`。模型列表和模型详情使用官方的 `/v1/models` 与 `/v1/models/{id}`。两类 Key 可以放在不同的供应商中，分别为订阅文本和付费视频配置路由。

额度查询沿用官方 CLI 的做法，按 Key 类型读取 `/v1/token_plan/remains` 或 `/account/query_balance`。这些读数（以及 `glmcode` 的读数）目前只用于展示，凭证是否耗尽仍以上游的请求结果为准。

视频支持 H3 V2（`MiniMax-H3`、`MiniMax-H3-Max`），需要按量付费 API Key。向 `/v1/videos` 提交 GPROXY 的 OpenAI 视频扩展 JSON：

```json
{
  "model": "MiniMax-H3",
  "prompt": "一只猫在花园里奔跑",
  "duration": 5,
  "resolution": "2K",
  "aspect_ratio": "16:9"
}
```

用返回的 `id` 查询 `/v1/videos/{id}`，完成后从 `/v1/videos/{id}/content` 下载。`frame_images` 用于指定首尾帧，`input_references` 用于提供图像、视频和音频参考；也可以直接传 MiniMax 原生的 `content`。不支持 Sora multipart、`seconds` 和 `size` 参数，也不支持旧版 Hailuo 2.x V1 接口。

列表使用 `page_num` 和 `page_size`（`limit` 映射为 `page_size`），不支持 `after`、`order` 游标。删除接口返回上游的 `action`：`cancelled` 表示取消了排队中的任务，`deleted` 表示删除了任务记录。渠道不会自动轮询，也不保存视频文件。

接口依据：[ZCode 动态目录实现](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/packages/provider-node/src/zcode-builtin-download.ts)、[MiniMax 官方 CLI](https://github.com/MiniMax-AI/cli)、[GLM Coding Plan](https://docs.bigmodel.cn/cn/coding-plan/tool/others)、[MiniMax 文本](https://platform.minimax.io/docs/api-reference/text-anthropic-api)、[MiniMax H3 V2](https://platform.minimax.io/docs/api-reference/video-generation-v2-create)。

### OrcaTerm

`orcaterm` 使用桌面端的 LightAI 协议，支持图文对话和模型专属的思考参数。新建供应商后，通过浏览器 OAuth 登录或导入 OAuth 凭证。国际站设置 `international=true`，账号地址为 `https://orcaterm.ai`，LightAI 地址为 `https://lightai.tencentcloud.com`。

图片以 Base64 data URL 发送（PNG、JPEG、WebP 或 GIF），历史消息中的图片和只含图片的用户消息都支持。过大的静态图片在上传前自动缩放和压缩；同一张图片在预览链接有效期内复用该凭证下已有的上传结果。可用模型和思考档位来自动态模型目录。上游不支持的请求选项会被忽略。token 数量是本地按字符估算的，在计量中标记为估算值和不完整用量；账号额度返回的是 AI 问答次数。

GPROXY 能识别的客户端终端、文件和网页抓取工具会映射到 OrcaTerm 原生的 review/reportToolResult 协议，每次调用仍由原客户端按自己的权限规则执行。工具续轮使用同一个供应商、凭证和模型；不支持注册任意函数。正文和工具参数在 Agent 完成响应修订后才输出。Codex 的独立网络请求使用 OrcaTerm 服务端的搜索和抓取工具，返回的是真实结果。

### 火山方舟

`volcengine_agent`（Agent Plan）和 `volcengine_coding`（Coding Plan）共用一套实现，分别走各自产品的路径（`/api/plan` 和 `/api/coding`），不会退回按量付费的 `/api/v3` 接口。Agent Plan 需要其专用 API Key；Coding Plan 个人版使用已开通 Coding Plan 的平台 API Key，企业版使用席位专用 API Key。

只做推理时，凭证只需要 `{"api_key"}`。模型发现、额度和套餐信息还需要在同一份 secret 中填写 IAM 密钥对（`access_key_id`、`secret_access_key`，临时凭证可加 `session_token`）。密钥对只发往控制面，API Key 只发往推理接口。没有密钥对时，推理照常可用，模型需手动配置。

`config.edition` 取 `personal`（默认）或 `enterprise`；企业版额度需要在凭证 metadata 中设置 `seat_id`。各个源地址可以覆盖：供应商的 base URL（默认 `https://ark.cn-beijing.volces.com`）、`config.control_base_url`（默认 `https://ark.cn-beijing.volcengineapi.com`），以及 Agent Plan 语音使用的 `config.speech_base_url`（默认 `https://openspeech.bytedance.com`）。账号在上游开通了后付费用量时，Agent 凭证可以在 metadata 中设置 `allow_paid_usage: true`，让订阅窗口用尽后继续路由到该凭证。

## 凭证

凭证是供应商凭证池中的一份密钥：API key、一组 OAuth 令牌或一个浏览器会话。在控制台中打开供应商，进入 **凭证** 标签页管理；通过 API 时，`POST /admin/api/credentials` 创建一条，批量接口可一次创建多条。

| 字段 | 含义 |
| --- | --- |
| `label` | 可选。通过登录创建时，根据渠道和账号自动生成。 |
| `authKind` | `api_key`、`oauth` 或 `cookie`，表示保存的凭证类型，与获取方式无关。 |
| `secret` | 渠道声明的字段。永远不会返回；列表中只显示 `hasSecret`。 |
| `organizationId` / `teamId` / `userId` | 归属者：三者恰好填一个，或都不填（共享凭证）。 |
| `connectionProfileId` | 覆盖供应商的连接配置。 |
| `expiresAtMs` | 密钥需要刷新的时间。 |
| `status` | `active` 或 `dead`。`dead` 的凭证不再被使用。 |
| `version` | 刷新写回时使用的 CAS 版本号。 |

密钥用主密钥以 AES-256-GCM 加密封装，并且封装与该行自己的 id 绑定，所以把密文复制到另一行上是解不开的。读取明文需要单独调用，并会记入审计：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/reveal \
  -H "Authorization: Bearer $GPROXY_KEY"
```

没有配置主密钥时，密钥以明文存储。这是受支持的部署方式，程序会在启动时提示一次。

### 凭证可见性

凭证在以下情况下对调用方可见：凭证没有归属者，或者归属者与调用方所用 key 的绑定一致，即该 key 的用户、团队或有效组织。

判断依据是 key 的绑定，而不是用户的成员关系，因为一个用户可以属于两个组织，而一把 key 只属于一个。如果按成员关系判断，多组织用户的每一把 key 都能用到所有这些组织的订阅，也就不可能有比持有人权限更窄的 key。

可见性只会从可用凭证中排除一部分，不会增加凭证。

## 通过登录获取凭证

持有账号而不是 key 的渠道，可以通过登录上游来创建凭证。

1. 打开供应商的 **凭证** 标签页，选择 **登录添加凭证**。
2. 浏览器授权（授权码）方式：打开授权链接并登录，然后把浏览器地址栏中完整的回调 URL 粘贴回对话框。
3. 设备码方式：在厂商页面输入显示的验证码，控制台会自动轮询，直到登录完成。

完成后新凭证出现在列表中。另见[控制台管理](/zh-cn/guides/console#凭证与上游登录)。

每个渠道提供下面一种或两种流程，在 `GET /admin/api/channels` 中以 `loginModes` 列出。请求渠道未提供的方式会被拒绝。

| 流程 | 步骤 | 适用场景 |
| --- | --- | --- |
| 授权码 | start → complete | 带 PKCE 的浏览器跳转 |
| 设备码 | start → 反复 poll | 在另一台设备上输入验证码 |

四个 POST 操作位于 `/admin/api/credential-login` 下。待完成的登录会话与发起它的用户及其管理范围绑定。

### 导入已有凭证

已经有令牌或 cookie 时，用 `POST /admin/api/credentials`（或批量接口）导入，再调用 `POST /admin/api/credentials/{id}/refresh` 完成初始化。控制台保存后会自动刷新待初始化的记录；初始化失败时已保存的记录仍然保留，可以在详情中重试。Claude Web 使用 `authKind: "cookie"`；Claude Code 和 OrcaTerm 使用 `authKind: "oauth"`，以 `secret: {"cookie": "..."}` 形式导入时也一样。旧的类型标签仍可读取。初始化和刷新会把 secret、到期时间和可选的公开 metadata 一起按版本号 CAS 保存，不需要数据库迁移或历史数据回填。

### 登录的安全措施

凡是不属于上游的环节都由 GPROXY 自己生成和校验。PKCE verifier 是本地生成的 32 个随机字节，从不外发，只有它的 S256 摘要会写进授权 URL，因此授权码即使被截获也无法使用。CSRF state 同样在本地生成和比对；state 不匹配时请求被拒绝，同时销毁该登录会话，攻击者无法反复重放直到成功。

待完成的会话保存在共享缓存中，而不是进程内存里。因此一个实例发起的登录可以由另一个实例完成（在负载均衡后面这是常态）；放弃的登录也不会留下任何东西：缓存键到期后，与从未签发过的 id 没有区别。

设备码轮询每次只执行一步就返回，服务端不会休眠或循环，轮询由调用方负责。每次应答都带有下次轮询前应等待的间隔，上游返回 `slow_down` 时会调大这个间隔，并对之后的所有轮询生效。

登录成功后，凭证的写入与普通管理写入走同一条提交路径。密钥在构造 SQL 语句之前就已加密封装，渠道到数据库之间的任何环节都看不到明文，应答中也只有新凭证的 id。

### 刷新凭证

持有 OAuth 令牌的渠道会声明密钥何时到期。刷新返回一份完整的新密钥，而不是需要合并的部分更新。宿主以 `version` 做 CAS 写回，并发布凭证变更通知。手动刷新：

```sh
curl -s -X POST 'http://127.0.0.1:8787/admin/api/credentials/{id}/refresh?force=true' \
  -H "Authorization: Bearer $GPROXY_KEY"
```

上游明确拒绝凭证时（`invalid_grant`、令牌已撤销），凭证被标记为 `dead`。临时的传输错误或 5xx 不会让凭证失效，只作为传输错误报告，宿主稍后重试。

使用版本号校验是因为 Claude 每次刷新都会轮换 refresh token。如果两次刷新并发而丢失了其中一次写入，数据库里保存的 refresh token 就已经失效了。

## 凭证健康与额度窗口

解析请求时，已禁用、已退役和 `dead` 的凭证直接排除。被上游限流的凭证处于封禁状态：只要该供应商还有未封禁的凭证，它就被排除；如果供应商的凭证全部被封禁，则保留这些凭证，但该供应商排在所有健康供应商之后，只在没有其他选择时才会被使用。

管理 API 可以按凭证查询和重置这些状态：

```sh
# 查看上游记录的这份凭证的额度窗口
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/quota -H "Authorization: Bearer $GPROXY_KEY"
# 立即向上游查询
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-probe -H "Authorization: Bearer $GPROXY_KEY"
# 兑换一次额度重置（仅限提供此服务的厂商）
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-reset -H "Authorization: Bearer $GPROXY_KEY"
# 清除已记录的健康状态
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/health-reset -H "Authorization: Bearer $GPROXY_KEY"
# 查看适用于这份凭证的运维限额
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/limits -H "Authorization: Bearer $GPROXY_KEY"
```

`POST /admin/api/credentials/{id}/status` 可以手动设置为 `active` 或 `dead`，需附带原因。

## 连接配置

连接配置是一次调用使用的出站栈：代理，以及对外呈现的 TLS 和 HTTP/2 指纹。选择顺序依次是凭证、供应商、渠道自己的默认值，最后是实例默认值。

身份预设可以直接保存为连接配置的 `emulation`：

```sh
curl -s http://127.0.0.1:8787/admin/api/tls-presets -H "Authorization: Bearer $GPROXY_KEY"
```

其中六个预设模拟厂商 CLI：

```text
claude / Claude CLI    codex / Codex CLI       gemini / Gemini CLI
antigravity            kiro / Kiro CLI         copilot / GitHub Copilot CLI
```

列表中还包含模拟库自带的每个浏览器和 HTTP 客户端指纹（Chrome、Edge、Firefox、Safari、Opera、OkHttp），id 形如 `wreq:{profile}`。

只有 `wreq` 传输会呈现模拟指纹。模拟 CLI 的渠道会提供自己的默认连接配置；凭证或供应商上显式指定的配置仍然优先。

## 测试供应商

管理调用中只有两类会访问进程外部：连通性测试，以及模型测试与发现。

### 连通性测试

连通性测试经由 scope 指定的客户端链路访问 Cloudflare 的 trace 端点，查看本部署从外部看是什么样子：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/connectivity/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"scope":"global"}'
```

```json
{"ok":true,"latencyMs":803,"ip":"223.166.167.192","colo":"LAX","error":null}
```

scope 可以是 `global`、`{"scope":"provider","provider_id":"…"}`、`{"scope":"credential","credential_id":"…"}`（与该凭证的调用使用同一条传输），或 `{"scope":"proxy","url":"…"}`，用于测试尚未配置到任何地方的代理。网络不通时返回 `ok: false` 和原因，而不是 HTTP 错误，因为“上游不可达”本身就是测试的有效结果。

### 模型测试与发现

模型测试和模型发现与调用方的请求一样完整地经过引擎：

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","model":"gpt-4o-mini"}'

curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

<Warning>
这两个调用使用真实凭证：会消耗上游额度，计入该凭证适用的预算，并写入一条用量记录。没有 dry run 模式，因为不真正调用上游的测试什么也测不出来。
</Warning>

模型发现使用供应商自己的协议查询，所以返回的是上游的模型名。每个结果都会标明该供应商是否已有这个模型，以及内置目录能否为它定价。`POST /admin/api/models/discover/apply` 插入你选中的模型，已存在的会跳过。

## 请求头白名单

默认情况下，客户端的请求头不会转发给上游。全局请求头白名单在“设置 → 网络”中配置，每个供应商还可以通过 `config.allowed_headers` 追加。最终生效的集合是全局白名单、供应商白名单和渠道默认头的并集，另外始终保留 `content-type`。未配置或为空的列表不增加任何条目。

原始鉴权头和逐跳头即使列入白名单也会被移除。渠道注入的鉴权信息和 `config` 中的静态 `headers` 不受此规则影响。修改在下一次配置重新加载时生效，合并结果不会写回供应商保存的列表。

## 迁移配置

```sh
gproxy export --out config.json --include-secrets
gproxy import --in  config.json --mode merge --source-master-key '…'
```

导出内容是部署本身的配置：连接配置、供应商、凭证、模型目录、路由、操作覆盖、改写规则、配额、价格和 settings 行。身份数据不导出（用户、key、组织、团队、权限和订阅属于产品层），用量和 capture 也不导出，否则目标实例上会出现它从未产生过的历史。主密钥相关规则见[配置](/zh-cn/reference/configuration#导出与导入配置)。
