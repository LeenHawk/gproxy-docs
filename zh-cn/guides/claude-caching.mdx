本页介绍 GPROXY 如何为 Claude 和 OpenAI 上游放置提示缓存标记（通过缓存断点规则，或通过写在提示中的魔法字符串），以及缓存 token 如何记录和计价。

缓存本身由上游提供，能否命中取决于模型、提示前缀和有效期（TTL）。添加标记不保证命中，也不能让不支持缓存的上游获得缓存能力。

## 缓存断点规则

在供应商的“重写规则”页面新增“缓存断点”规则，选择上游协议和位置。位置包括全局、系统和消息，Claude 还支持工具。局部位置可以填写索引：正数从 1 开始，负数从末尾倒数，留空则选择最后一个可用位置。

Claude 可选默认、5 分钟或 1 小时 TTL；OpenAI 局部断点可选默认、30 分钟或 12 小时，OpenAI 全局规则可选默认或 30 分钟。TTL 实际如何生效由上游决定。规则中的协议指转换后的上游协议。Gemini 不支持这种规则。

通过 API 配置时，使用 `action: "cache_breakpoint"`，并在 `replacement` 中填写配置对象的 JSON 字符串，例如：

```json
{"dialect":"claude","target":"message","index":-1,"ttl":"5m"}
```

```json
{"dialect":"openai","target":"message","index":-1,"ttl":"12h"}
```

这条规则作用于请求正文，与其他[重写规则](/zh-cn/guides/rules)按同一顺序执行。正文中已有四个标记时，规则不再添加，这与下文魔法字符串的上限相同。能够自行设置原生缓存字段的客户端，也可以直接发送上游支持的字段。

## 魔法字符串

无法设置缓存字段的客户端，可以在提示文本中写入以下字符串之一。供应商为目标协议开启 magic cache 选项后，GPROXY 会去掉该字符串，并在原位置放置一个断点。

```text
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_7D9ASD7A98SD7A9S8D79ASC98A7FNKJBVV80SCMSHDSIUCH
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_49VA1S5V19GR4G89W2V695G9W9GV52W95V198WV5W2FC9DF
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_1FAS5GV9R5H29T5Y2J9584K6O95M2NBVW52C95CX984FRJY
```

| 字符串 | Claude 目标 | OpenAI 目标 |
| --- | --- | --- |
| …`7D9ASD…` | `cache_control`，使用 API 默认 TTL | 显式断点 |
| …`49VA1S…` | `cache_control`，`"ttl": "5m"` | `prompt_cache_breakpoint` (`"ttl": "30m"`) |
| …`1FAS5G…` | `cache_control`，`"ttl": "1h"` | `prompt_cache_breakpoint` (`"ttl": "12h"`) |

同一个字符串按目标协议选择短期或长期缓存：Claude 的 `5m`、`1h` 分别对应 OpenAI 的 `30m`、`12h`，默认字符串不设置 TTL。TTL 写在断点本身上，不修改整个请求的缓存选项。

这些字符串属于客户端与 GPROXY 之间的协议，不会随版本变化。

### 开启 magic cache

供应商 `config` 中有两个开关，每个协议族一个：

```json
{ "config": { "enable_claude_magic_cache": true,
              "enable_openai_magic_cache": true } }
```

| 开关 | 提供该开关的渠道 |
| --- | --- |
| `enable_claude_magic_cache` | `aws_bedrock`、`azure`、`claudeapi`、`claudecode`、`custom`、`opencodego`、`opencodezen`、`openrouter`、`vercel` |
| `enable_openai_magic_cache` | `aws_bedrock`、`azure`、`openai`、`codex`、`custom`、`opencodego`、`opencodezen`、`openrouter`、`vercel` |

控制台中这两个开关显示为“Claude 魔法缓存”和“OpenAI 魔法缓存”。

起作用的是目标协议对应的开关，而不是客户端协议的开关。OpenAI 格式的客户端请求路由到 Claude 供应商时，会先转换为 Claude Messages，因此由 Claude 开关决定，写入的标记是 `cache_control`。客户端收到的响应仍是它自己的格式。

### 字符串的移除

上表中的渠道无论是否开启 magic cache，都会移除这些字符串，因为残留在提示中的标记对上游没有任何用处。

开关只决定是否在字符串原来的位置放置断点。magic cache 关闭时，只移除字符串，其他内容都不变：客户端自己的 `cache_control` 或 `prompt_cache_breakpoint` 原样保留；不含字符串的正文按原字节转发，不解析，也不重新序列化。

`claudeweb` 渠道同样只移除字符串而不放置断点，因为浏览器会话没有缓存控制。

## 标记的位置

开启 magic cache 后，魔法字符串对应的标记按目标协议放置在以下位置。

### Claude Messages

先对正文做规范化：字符串形式的 content 转为块数组，空文本块被删除，删除的块上若带有 `cache_control`，会移到最近的可缓存块上。因此，单独占一行的字符串也能正常生效。thinking 块只在 assistant 轮次中保留。

随后先处理 `system`，再处理 `messages`，断点名额因此按提示顺序分配，而不是按 JSON 键的顺序。每个包含字符串的文本块都会加上标记：

```json
{ "cache_control": { "type": "ephemeral", "ttl": "1h" } }
```

已经带有 `cache_control` 的块保持不变。

### OpenAI Chat Completions

除 `function` 角色以外的消息都可以加标记。纯字符串的 `content` 会拆成一个带标记的 `text` part，因为标记必须放在某个 part 上；数组形式的 content 则直接在原有 part 上加标记。

```json
{ "type": "text", "text": "…", "prompt_cache_breakpoint": { "mode": "explicit" } }
```

### OpenAI Responses

依次在三个位置放置标记：

1. `instructions`。其中的字符串被移除，并在 `input` 开头插入一条带标记的 developer 消息，因为 `instructions` 是纯字符串，无法携带标记。
2. `prompt.variables`，标记方式与 Chat 的 part 相同。
3. `input`。裸字符串会变成一条带标记的 user 消息；如果是 item 数组，则用 `input_text` 和 `output_text` 类型标记其中的 `content` 与 `output`。

### Gemini

Gemini 没有断点。字符串被移除，不做其他处理。

## 四个断点的上限

离开代理的断点最多四个，客户端自己设置的也计算在内。可用名额等于四减去正文中已有的标记数，所以客户端已经放了三个时，只剩一个名额。

超出上限的字符串仍会被移除，只是不再变成标记。

## 协议转换中的原生缓存字段

在 Claude 与 OpenAI Chat/Responses 之间转换时，原生缓存字段按同样的 TTL 对应关系双向映射。带标记的系统提示、消息、图片/文档和工具结果块保留各自的边界。Claude 的自动缓存策略会转换为对应末尾块上的显式断点，前提是该块在目标协议中有对应表示。没有 OpenAI 对应字段的工具定义级标记会列在转换报告中。

从 OpenAI 转换到 Claude 时，只有明确传入 `prompt_cache_options.mode: "implicit"` 才会生成顶层 `cache_control`。省略整个选项对象或省略 `mode`（包括空对象、只传 TTL）都不会开启 Claude 自动缓存。块上的显式标记不受此影响，单独转换。

OpenAI Responses 和 Chat 的显式断点支持 `prompt_cache_breakpoint: {"mode":"explicit","ttl":"12h"}`（也支持 `"30m"`），Chat 与 Responses 互相转换时保留这个 TTL。当前的[官方 OpenAPI](https://github.com/openai/openai-openapi/blob/master/openapi.json) 中，请求级的 `prompt_cache_options.ttl` 仍只允许 `"30m"`；`prompt_cache_retention` 是另一套较早的策略。

## 用量与计价

缓存 token 作为独立的指标记录，并按你配置的费率行计价：

| 上游报告的内容 | 指标 |
| --- | --- |
| 缓存读取 | `cached_input_tokens` |
| 缓存写入，按 TTL 分桶 | `cache_creation_tokens` + `ttl_seconds` |
| 缓存写入，TTL 未知 | `cache_creation_tokens` |

缓存写入统一使用 `cache_creation_tokens`。费率条件 `{"ttl_seconds":43200}` 匹配 12 小时写入的价格，不带该条件的费率作为默认价格；上游报告的每个写入桶分别计费。缓存读取是单一的 `cached_input_tokens` 计数，没有 TTL。阶梯价格使用 `cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]`，其中 `ttlSeconds: null` 的条目是默认价格。价格按每百万 token 计，不再乘以 TTL。

OpenAI 单次调用的 usage 只报告 `cache_write_tokens` 总量，因此 GPROXY 把这些写入的 TTL 记为未知，不去猜测它们在不同 TTL 的断点之间如何分配。

`cached_input_tokens` 以 `input_tokens` 为上限。未命中的部分按输入价格计费，命中的部分按缓存读取价格计费；没有设置缓存读取价格时按输入价格计费。没有单独费率的缓存写入不计费。参见[价格与分层](/zh-cn/reference/pricing)。

用量记录中的各项 token 数可以为空，因为上游没有报告某个字段，不代表它测得的是 0。合计值则总是普通数值，因为对“没有报告”的字段求和，结果就是 0。

## 避免缓存未命中

重写规则在协议转换之后、渠道发送之前执行，因此修改提示文本的规则可能把本应命中的请求变成未命中。把稳定的内容放在最前面，标记放在它后面，每次请求都会变化的内容放在标记之后。同时检查是否有 `paths` 范围过宽的重写规则改动了缓存前缀。
