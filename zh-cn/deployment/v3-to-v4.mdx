本文供管理员把 v3 部署升级到 v4 时参考。v4 启动时会识别 v3 数据库并原地转换，支持 SQLite、PostgreSQL、MySQL 和 D1。数据目录或连接串、`GPROXY_MASTER_KEY` 都沿用原值，不需要导出数据，也不需要重设密码。

## 变化内容

数据库 schema 整体更换。v4 读取 v3 的表，写入新的 v4 表，全部完成后才开始处理请求。各类数据的处理方式如下：

- 供应商与凭证：转换已知的渠道名称及其配置，凭证按当前主密钥重新加密。
- 模型路由与成员：路由原有的公开模型名成为路由名；其余每个名称展开为一条独立路由，并复制成员。
- 用户、密码、API key、组织与团队：全部迁移。密码哈希（Argon2）和 API key 摘要原样保留，原有用户名、密码和密钥继续可用。
- 价格与预算：换算为 v4 的单位。v4 金额保留 9 位小数，超出部分按“四舍六入五成双”舍入，并在报告中列出。
- 权限、限流与改写规则：迁移支持的写法；含义有变化或无法映射的内容在报告中列出。
- 团队和组织权限：展开为每位已迁移成员（包括已禁用用户）各自的用户规则。规则按升级时的成员关系生成，之后成员变动不会同步。没有已迁移成员的组在报告中记为跳过。早期版本升级时没有展开这类权限，已经升级过的实例丢失的权限不会被后续版本补回。
- 历史用量：分批导入原始 token 数、归属和已结算费用，不重新计价，也不重新结算配额。v4 没有对应列的 v3 字段保存在 `metrics.v3` 中。
- 抓包、请求日志、会话和审计历史：不转换，保留在 v3 备份中。所有人都需要重新登录控制台。

渠道或配置无法转换的供应商会连同依赖它的行一起跳过，并在报告中注明。跳过只针对无法转换的内容；数据库读写错误或主密钥不对，升级仍会中止。

原有的 v3 启动参数继续有效，v4 仍接受 `--persistence db` 和 `sqlite://` 形式的 DSN。Docker 镜像的目录结构与 v3 相同（数据在 `/app/data`，用户为 `65532:65532`），但 v3 标签运行的仍是 v3，需要换成 v4 标签。

## 准备工作

1. 确认 `GPROXY_MASTER_KEY` 设置在哪里（`.env` 文件、服务单元或容器环境变量），并另存一份。v4 必须用同一个密钥解开凭证；密钥不对时，升级会在改动任何数据之前停止。
2. 保留 v3 可执行文件，或记下 v3 镜像标签，回退时需要。
3. 安排停掉所有 v3 实例。升级期间只能有一个进程写数据库。如果 v3 和 v4 分别使用不同的数据库同时运行，不要让它们共用同一份 OAuth 凭证，否则双方刷新 token 时会让对方的 token 失效。
4. CLI 部署使用 PostgreSQL 或 MySQL 时，确认 v4 构建包含对应的数据库驱动。

然后在 v3 停止的状态下备份数据库：

<Tabs>
  <Tab title="SQLite">
    复制整个数据目录。目录中有 `gproxy.db`，可能还有 `gproxy.db-wal` 和 `gproxy.db-shm`；WAL 文件里可能有尚未写回 `gproxy.db` 的已提交数据，三个文件要一起复制。

    ```sh
    cp -a data data.v3-backup
    ```

    升级过程中 v4 还会在数据库旁边另写一份备份（见下文），因此要预留相当于两份数据库大小的空闲空间：一份备份，一份转换后的新库。
  </Tab>
  <Tab title="PostgreSQL">
    ```sh
    pg_dump --format=custom --file=gproxy-v3.dump "$GPROXY_DSN"
    ```
  </Tab>
  <Tab title="MySQL">
    ```sh
    mysqldump --single-transaction --databases gproxy > gproxy-v3.sql
    ```
  </Tab>
  <Tab title="D1">
    ```sh
    wrangler d1 export gproxy --remote --output=gproxy-v3.sql
    ```
  </Tab>
</Tabs>

## 升级步骤

1. 停止所有 v3 实例。
2. 用 v4 可执行文件替换 v3，或把容器镜像换成 v4 标签。Workers 部署则用原有的 D1 binding 和 Secrets 部署 v4 Worker。
3. 用原来的数据目录或连接串、原来的 `GPROXY_MASTER_KEY` 启动 v4。也可以先单独运行 `gproxy migrate`，它走同样的升级流程，完成后退出。
4. 观察日志。SQLite 部署依次会看到 `migrating v3 database to v4`、每张表一行 `migrated`、带有行数、丢弃数和警告数的 `v3 import complete`，最后是带备份路径的 `v3 migration complete`。含义发生变化的内容列在 `Changed on the way in` 下，没有 v4 对应形式的行列在 `NOT migrated` 下。
5. 日志显示服务开始监听后，登录控制台。

Worker 在部署后的第一个请求中转换数据库。转换未完成的实例不处理请求，也不会创建新的管理员，因此转换结束前请求都会失败。

## 迁移过程

### SQLite

在打开 HTTP 端口之前，v4 先用 `VACUUM INTO` 生成 v3 数据库的一致快照（包含 WAL 中已提交的内容），作为 `gproxy.db.v3-*.bak` 保存在数据库旁边。随后在原库旁的临时目录中把这份快照转换成新数据库，用现有主密钥解密凭证。只有导入成功后，才把新数据库重命名到原路径上。

转换失败时原文件保持不变，按日志指出的原因修正（例如恢复原来的主密钥）后重新启动即可。如果在重命名之前中断，原路径上仍是 v3 数据库，下次启动会重新尝试；重命名之后，原路径上是 v4 数据库，其迁移账本表明它已是当前版本，之后的启动都是普通的 v4 启动，不会重复导入。

### PostgreSQL、MySQL 与 D1

v4 先读取并检查 v3 数据，包括主密钥能否解开凭证，确认无误后才把每张 v3 表改名为 `gproxy_v3_<原表名>`，并用原来的表名创建 v4 表。配置、身份数据和历史用量从改名后的表中转换，最后一步完成后实例才开始处理请求。

进度记录在 `gproxy_v3_upgrade` 表中，其 `report_json` 列保存跳过的行和含义变化的警告。身份数据和用量分批写入，每批之后记录检查点；升级中断后，下次启动（Workers 上是下一个请求）会从中断处继续。

各数据库用不同方式防止第二个进程同时迁移：

- PostgreSQL 在整个升级期间持有会话级 advisory lock，并在一个事务中完成所有 v3 表的改名。
- MySQL 持有会话锁（`GET_LOCK`），锁在 DDL 语句隐式提交后依然有效；所有 v3 表用一条 `RENAME TABLE` 语句改名。
- D1 用事务性 batch 改名。迁移租约在每批写入时都会检查，防止另一个 isolate 同时写入；升级中断后，租约最多 60 秒后失效。

第二个 PostgreSQL 或 MySQL 实例拿不到锁时，会以 `another instance is migrating this database; retry after it finishes` 退出。Workers 上的提示则是等租约释放后重试。

失败后，v3 数据仍在归档表中，v4 表里可能已有部分导入的数据。修正报告的错误后重新启动，升级会继续进行。升级完成之前，不要删除 `gproxy_v3_upgrade`，也不要改名归档表。

## 检查升级结果

1. 阅读迁移报告：SQLite 在启动日志中，其他数据库在 `gproxy_v3_upgrade.report_json` 中。重点看被跳过的供应商和权限变化。
2. 运行 `gproxy migrate --status`。它列出本版本的每个 schema 迁移以及数据库是否已应用，只读不写，也不会执行 v3 升级。
3. 在控制台中确认供应商、凭证、模型路由、用户和 API key 都在，用量统计中的历史总数与原来一致。
4. 用一个原有的 API key 发送请求，参照[第一个请求](/zh-cn/getting-started/first-request)。

确认无误后，可以删除 `gproxy.db.v3-*.bak`（SQLite），或删除 `gproxy_v3_<表名>` 归档表（其他数据库）。如需保留报告，留下 `gproxy_v3_upgrade`。此后 v4 的 schema 变更记录在 SeaORM 的 `seaql_migrations` 表中。

## 回退

v3 无法读取 v4 数据库，转换到一半的数据库两个版本都用不了，所以回退只能恢复 v3 数据。升级之后写入的内容（新用量、配置修改）都会丢失。

<Tabs>
  <Tab title="SQLite">
    1. 停止 v4。
    2. 把 `gproxy.db` 以及可能存在的 `gproxy.db-wal`、`gproxy.db-shm` 移到别处。
    3. 把 `gproxy.db.v3-*.bak`（或自己备份中的 `gproxy.db`）复制为 `gproxy.db`。
    4. 重新安装 v3 可执行文件或换回 v3 镜像标签，用原来的参数和主密钥启动。
  </Tab>
  <Tab title="PostgreSQL、MySQL 与 D1">
    1. 停止所有实例。
    2. 把升级前的备份恢复到一个空数据库中。
    3. 用原来的主密钥让 v3 连接恢复后的数据库并启动。

    不要让 v3 连接已部分或全部转换过的数据库。
  </Tab>
</Tabs>

## 导入到另一个实例

上面的流程是原地转换。如果要把 v3 数据库或导出文件导入另一个 v4 实例，使用 `import --from-v3`：

```sh
gproxy --data-dir ./other-instance migrate
gproxy --data-dir ./other-instance import --from-v3 /path/to/v3-backup.db
```

目标必须为空，或者只包含同一导入此前未完成的那次运行。源数据中的密钥已加密时，用 `--source-master-key` 或 `GPROXY_IMPORT_SOURCE_MASTER_KEY` 提供 v3 的主密钥。加上 `--skip-unmappable-providers` 会像自动升级一样跳过无法转换的供应商；不加时，遇到这样的供应商导入会停止。

输入也可以是 v3 `POST /admin/api/export` 导出的 JSON，导出时需带上 `{"include_secrets": true}`。这种导出不含密码哈希、权限、限流和供应商模型，而 SQLite 数据库中都有。导入不含哈希的导出文件时，用 `--admin-password` 设置控制台密码；导入 SQLite 不需要。
