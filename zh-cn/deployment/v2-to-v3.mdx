本文供管理员把使用 SQLite 的 v2 部署升级到 v3 时参考。原生 v3 服务（v3.0.22）启动时会识别 v2 SQLite 数据库，并在打开 v3 存储之前完成转换。如果最终目标是 v4，可以跳过 v3，直接使用 [v2 升级到 v4](/zh-cn/deployment/v2-to-v4)，它同样支持 PostgreSQL 和 MySQL。

## 变化内容

会迁移的内容：

- 支持的配置，以及可以恢复的密钥。
- 组织、团队和用户对全部路由（`*`）的授权。
- 历史用量：`usages` 中仍保留的明细行。v3 据此重建小时聚合。
- 请求日志：`downstream_requests` 迁入 `request_logs`，`upstream_requests` 迁入 `wire_logs`。请求 ID、时间、方法、路径或 URL、状态、请求头以及请求和响应体都会保留，同一请求的多次上游尝试也一并保留。v2 中为 0 的状态码变为未知响应状态。供应商和凭证引用会重新映射，已删除的对象用禁用的占位对象代替。
- 可以恢复的 API key。

不迁移的内容（数据仍保留在 v2 备份中）：

- v2 用量汇总、每日凭证统计和历史配额周期。因此，明细已被 v2 保留策略删除的用量不会出现在 v3 统计中。
- 凭证健康快照、tokenizer 缓存和 Codex 任务绑定。
- v2 限流规则、针对特定路由的授权、未知的权限范围，以及主体已不存在的授权。这些策略在 v3 中不生效，需要升级后重新配置。
- 未知的表，无论其中是否有数据。
- v2 特有的日志创建、更新时间和每次尝试的 `latency_ms`。v3 从用量明细推算请求时长。
- 审计日志。浏览器和客户端可能需要重新登录。

每个被跳过的非空表都会连同行数和原因列在 `report.txt` 中。

## 准备工作

1. 保存当前使用的 v2 可执行文件及其启动参数。v2 自更新替换程序时不保留旧版本，v3 的迁移也无法找回它，而回退时需要用到。
2. 确认数据库类型。只有 v2 SQLite 数据库会自动升级，即默认数据库或文件型的 `--dsn sqlite://PATH?mode=rwc`。PostgreSQL、MySQL、远程 libSQL、v1 数据库和其他 SQLite DSN 都不在此列，需要另行迁移，例如使用 [v2 升级到 v4](/zh-cn/deployment/v2-to-v4)。
3. 如果数据库已加密，记下 `GPROXY_MASTER_KEY`。升级时不要同时轮换主密钥；开启轮换时，v3 会以 `disable master-key rotation during the v2 upgrade; rotate after the upgrade completes` 拒绝启动。
4. 确认磁盘有足够空间，容纳一份完整的数据库副本、转换用的工作库，以及用于切换的独立副本。
5. 安排停掉其他所有使用该数据库的进程。升级需要 SQLite 独占锁；v3 服务在接触数据库之前先占用监听端口，因此期间无法再启动第二个实例。

## 升级步骤

1. 停止 v2。
2. 用 [v3.0.22](https://github.com/LeenHawk/gproxy/releases/tag/v3.0.22) 可执行文件替换 v2。
3. 用原来的 v2 启动命令启动。v3 接受 `--persistence db`、`--data-dir`、文件型 `--dsn sqlite://PATH?mode=rwc` 和 `--update-channel staging`。`GPROXY_MASTER_KEY` 保持不变。
4. 观察日志。依次会看到 `checking v2 configuration before database copy`、`configuration preflight passed; copying the v2 database`、`importing v2 configuration, usage, and request logs` 和 `validating the migrated database before cutover`，最后是一条注明备份目录的警告：`v2 database upgraded; retain this backup to roll back with a v2 executable`。

启动时，v3 按以下顺序处理：

1. 获取迁移锁（数据库旁的 `.gproxy-v2-upgrade.lock`），保证只有一个进程执行升级。
2. 在数据库旁创建私有目录 `gproxy-v2-backup-TIMESTAMP-PID`。
3. 在复制之前检查 v2 配置。
4. 独占锁定 SQLite 数据库，执行 WAL checkpoint，再把数据库复制为该目录中的 `gproxy-v2.db`。
5. 从副本中把配置、密钥、用量和请求日志导入 `candidate/` 下的新 v3 数据库，日志按有界批次读写。
6. 校验导入数量、SQLite 完整性、引用关系、运行时控制状态、用量行数以及精确的结算费用总额。
7. 全部通过后，才刷新新数据库并原子替换配置所指向的数据库。

备份目录及其中的 `report.txt` 会保留下来。重新启动 v3 不会再次导入。

## 检查升级结果

1. 阅读备份目录中的 `report.txt`，其中列出了被跳过的表和策略。
2. 登录控制台，检查供应商、凭证、用户和 API key。
3. 与 v2 对比用量统计。注意只有仍保留的明细行被导入。
4. 重新配置报告中列为跳过的限流规则和特定路由授权。

## 升级失败时

在替换之前失败，v2 数据库保持原样。v3 会把 `migration failed:` 和错误信息追加到本次工作目录的 `report.txt` 中，并把同样的错误连同目录路径写入数据库旁的 `.gproxy-v2-upgrade-blocked`。

只要这个标记文件存在，v3 就不会重试，而是以 `automatic migration previously failed; inspect … and remove that marker only after resolving the failure` 停止。这样可以避免进程管理器反复复制一个注定失败的数据库，把磁盘写满。修正原因后，只删除这个标记文件，再启动 v3。不要靠删除备份来触发重试。

## 回退

1. 停止 v3。
2. 把当前的 v3 数据库连同 `-wal`、`-shm` 文件一起移到别处，留作排查。
3. 把备份目录中的 `gproxy-v2.db` 复制到配置的数据库路径。
4. 重新安装保存的 v2 可执行文件，或相同版本的官方 v2 发布。
5. 用原来的启动参数和主密钥启动 v2。

不要让 v2 打开已转换的 v3 数据库。切换后记录的用量留在保存下来的 v3 数据库中，不会合并回 v2。
