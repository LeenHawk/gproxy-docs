GPROXY is a self-hosted gateway for LLM APIs. You register your upstream
accounts with it (API keys, OAuth logins such as Codex or Claude Code, browser
cookies), and your clients are given one base URL, a GPROXY API key and model
names that you define.

For every request GPROXY works out which provider and credential should serve
the model name, converts between the OpenAI, Claude and Gemini formats when
the client and the upstream use different ones, checks the caller's
permissions, rate limits and budget, and records the tokens and cost. When a
credential or provider fails, the request is retried on the next one.

GPROXY does not run models; the upstream service does the inference. It also
cannot add features an upstream lacks: converting a request to another format
does not give a model tool calling or image input it does not have.

It runs as a native server (the CLI, or a container) with a web console, as a
desktop or mobile application with the console built in, or on Cloudflare
Workers, Netlify and Vercel with a hosted database. Rust programs can embed it
as a library.

## An example

Suppose a provider named `openai-main` holds an OpenAI API key, and a model
route named `fast` points at its `gpt-4o-mini` model. A client then sends:

```sh
curl http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"Hello"}]}'
```

The client never sees the OpenAI key. If you later add a second provider to
`fast`, or replace the model behind it, nothing changes on the client side.
The same route can be called in Claude format at `/v1/messages` or in Gemini
format at `/v1beta/models/fast:generateContent`.
