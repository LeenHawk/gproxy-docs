This page covers two different containers. The Docker image runs the ordinary `gproxy` CLI with a SQLite database in a volume, for a host you manage yourself. The Render and Heroku templates build a separate image that runs the native PostgreSQL build behind a small Node.js entry point, for platforms whose local disk does not survive a restart. For Cloudflare Workers, Netlify and Vercel, see [Cloudflare Workers, Netlify, and Vercel](/deployment/edge).

## Docker

The same images are published to four registries for amd64, arm64 and riscv64. Use whichever is closest to you:

| Registry | Image |
| --- | --- |
| Docker Hub | `gproxy2/gproxy` |
| GitHub | `ghcr.io/leenhawk/gproxy` |
| GitLab | `registry.gitlab.com/leenhawk1/gproxy` |
| CNB | `docker.cnb.cool/leenhawk/gproxy` |

Stable releases are tagged `vX.Y.Z`, the beta channel is `staging`, and development snapshots are `nightly`. Append `-musl` to any tag for the musl build. Images with v3 tags run v3, not v4.

Start a container with a named volume for the data directory and your master key in the environment:

```sh
export GPROXY_IMAGE='gproxy2/gproxy:<tag>'
# Set GPROXY_MASTER_KEY to your saved 32-byte key (64 hex digits or base64).
docker run -d --name gproxy --restart unless-stopped \
  -p 127.0.0.1:8787:8787 \
  -v gproxy-data:/app/data \
  -e GPROXY_MASTER_KEY \
  "$GPROXY_IMAGE"
docker logs gproxy
```

On the first start, GPROXY creates an administrator and an API key and prints the generated credentials to the log. Save them, then open `http://127.0.0.1:8787/console/`. The log is the only place they appear, so protect it.

The image listens on port 8787, keeps its SQLite database in `/app/data`, and runs as user `65532:65532`. If you bind-mount a host directory instead of using a named volume, that user must be able to write to it.

To move to a new version, stop and remove the container and start a new one from the new tag with the same volume and the same `GPROXY_MASTER_KEY`. The database is in the volume, so removing the container does not touch it.

## Render

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)][render-deploy]

The Render template is the `render.yaml` Blueprint in the repository root. It creates one web service on the free plan and no database: you supply an external PostgreSQL database.

1. Use the button above and review the Blueprint.
2. Set `GPROXY_DATABASE_URL` to your PostgreSQL connection URL and deploy. The database must accept connections from Render; keep any SSL parameters your provider requires in the URL.
3. Render generates `GPROXY_ADMIN_PASSWORD` and `GPROXY_MASTER_KEY`. Open the service's **Environment** settings and save a copy of both.
4. Open the service URL followed by `/console/` and sign in as `admin`.

The service's health check is `/healthz` on port `8787`. Free web services sleep when idle, so the first request after a pause is slow while the service wakes up. Pricing and limits of the external database are your provider's.

## Heroku

[![Deploy to Heroku](https://www.herokucdn.com/deploy/button.svg)][heroku-deploy]

The Heroku template is `app.json` and `heroku.yml` in the repository root. It creates one Basic web dyno and a `heroku-postgresql:essential-0` add-on. Both are paid; review the plans before you deploy.

1. Generate a master key with `openssl rand -hex 32` and save it.
2. Use the button above, choose an app name and region, and enter the key as `GPROXY_MASTER_KEY`.
3. Review the dyno and the add-on, then deploy. Heroku generates `GPROXY_ADMIN_PASSWORD`.
4. Read the password under **Settings → Reveal Config Vars**, then sign in as `admin` at `/console/`.

The image is built from `deploy/serverless/Dockerfile`. The Node.js entry point listens on the `PORT` Heroku assigns and works under the user ID Heroku runs it as; the gateway reads the add-on's `DATABASE_URL`. A dyno's local files are temporary, and everything that matters (configuration, credentials, usage, cache state) is kept in PostgreSQL.

## Running the Render and Heroku templates

Both templates build the same image. At build time it downloads the release's `gproxy-serverless` executables for x86_64 and aarch64, checks them against the release's `SHA256SUMS`, and packages them with the Node.js entry point. Nothing is compiled. The ordinary Docker image above includes only the SQLite driver, so it cannot take this image's place.

### Database

The gateway reads `GPROXY_DATABASE_URL`, or the platform's `DATABASE_URL` when that is unset. Keep the database and `GPROXY_MASTER_KEY` across updates and back up both.

### Updates

The build downloads the latest stable release by default (`GPROXY_RELEASE_VERSION=latest`). To upgrade, clear the platform's build cache and redeploy. To stay on one version, set the Docker build argument `GPROXY_RELEASE_VERSION` to a release tag; that release must contain both serverless Linux archives and `SHA256SUMS`.

### Instances

The templates start one application instance. The shared cache is kept in PostgreSQL.

### Public address

Set `GPROXY_PUBLIC_BASE_URL` to the service's public HTTPS origin if you use OAuth or published file links. The templates do not configure file storage; for a filesystem or object storage, run a native CLI build instead.

### Client addresses

The client IP is taken from the TCP peer, which may be the platform's router. Forwarded client-IP headers are not trusted.

### Connections

The entry point serves HTTP, SSE and WebSocket. The platform's router timeouts, idle limits and restarts still apply. On shutdown it stops accepting connections and gives open SSE and WebSocket connections up to 25 seconds before it exits.
