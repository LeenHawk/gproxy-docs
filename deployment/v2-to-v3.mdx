These notes are for administrators moving a v2 deployment on SQLite to v3. The native v3 server, v3.0.22, recognizes a v2 SQLite database when it starts and converts it before opening the v3 store. If you are going on to v4, you can skip v3 and use the [v2 to v4 migration](/deployment/v2-to-v4), which also handles PostgreSQL and MySQL.

## What changes

Converted:

- Supported configuration and the secrets that can be recovered.
- Organization, team and user grants on all routes (`*`).
- Usage history: the detail rows still present in `usages`. v3 rebuilds its hourly aggregates from them.
- Request logs: `downstream_requests` becomes `request_logs` and `upstream_requests` becomes `wire_logs`. Request IDs, timestamps, methods, paths and URLs, status, request headers and request and response bodies are kept, including several upstream attempts for one request. A v2 status of zero becomes an unknown response status. Provider and credential references are remapped; entities that were deleted get disabled placeholders.
- API keys that can be recovered.

Not converted (the data stays in the v2 backup):

- v2 usage rollups, daily credential statistics and historical quota cycles. Usage whose detail rows v2 retention had already deleted therefore does not appear in v3 statistics.
- Credential health snapshots, tokenizer caches and Codex task bindings.
- v2 rate-limit rules, route-specific grants, unknown permission scopes and grants whose subject no longer exists. These are not enforced in v3; configure them again after the upgrade.
- Unknown tables, whether or not they hold rows.
- The v2-only log creation and update timestamps and the per-attempt `latency_ms`. v3 derives request duration from usage details.
- Audit logs. Browser and client sessions may have to sign in again.

Every non-empty table that was skipped is listed in `report.txt` with its row count and the reason.

## Before you start

1. Keep a copy of the v2 executable you run now, and its launch settings. The v2 self-updater replaces the executable without keeping the old one, and the v3 migration cannot bring it back. You need it to roll back.
2. Check the database. Only a v2 SQLite database is upgraded automatically: the default database, or a file-backed `--dsn sqlite://PATH?mode=rwc`. PostgreSQL, MySQL, remote libSQL, v1 databases and other SQLite DSNs are not; migrate them explicitly, for example with the [v2 to v4 migration](/deployment/v2-to-v4).
3. Note your `GPROXY_MASTER_KEY` if the database is encrypted. Do not rotate the key as part of this upgrade; with rotation enabled, v3 refuses to start with `disable master-key rotation during the v2 upgrade; rotate after the upgrade completes`.
4. Make sure there is free disk space for a full copy of the database, the converted working database, and its standalone copy for the cutover.
5. Plan to stop every other process that uses the database. The upgrade needs an exclusive SQLite lock, and the v3 server takes its listening port before it touches the database, so a second instance cannot start in the meantime.

## Upgrading

1. Stop v2.
2. Install the [v3.0.22](https://github.com/LeenHawk/gproxy/releases/tag/v3.0.22) executable in place of v2.
3. Start it with your v2 launch command. v3 accepts `--persistence db`, `--data-dir`, a file-backed `--dsn sqlite://PATH?mode=rwc` and `--update-channel staging`. Keep the same `GPROXY_MASTER_KEY`.
4. Watch the log. You should see `checking v2 configuration before database copy`, `configuration preflight passed; copying the v2 database`, `importing v2 configuration, usage, and request logs` and `validating the migrated database before cutover`, and at the end a warning naming the backup directory: `v2 database upgraded; retain this backup to roll back with a v2 executable`.

On startup, v3 does the following:

1. Takes a migration lock (`.gproxy-v2-upgrade.lock` beside the database), so only one process upgrades the database.
2. Creates a private directory `gproxy-v2-backup-TIMESTAMP-PID` beside the database.
3. Checks the v2 configuration before copying anything.
4. Locks the SQLite database exclusively, checkpoints the WAL, and copies the database to `gproxy-v2.db` in that directory.
5. Imports configuration, secrets, usage and request logs from the copy into a new v3 database under `candidate/`, reading and writing logs in bounded batches.
6. Checks import counts, SQLite integrity, references, runtime control state, the number of usage rows and the exact total settled cost.
7. Only then flushes the new database and atomically replaces the configured database with it.

The backup directory and its `report.txt` are kept. Restarting v3 does not import again.

## Verifying the upgrade

1. Read `report.txt` in the backup directory. It lists the skipped tables and policies.
2. Sign in to the console and check providers, credentials, users and API keys.
3. Compare usage statistics with v2, keeping in mind that only retained detail rows were imported.
4. Configure again any rate limits and route-specific grants the report lists as skipped.

## If the upgrade fails

A failure before the replacement leaves the v2 database where it was. v3 appends `migration failed:` and the error to `report.txt` in the attempt directory, and writes the same error, with the directory's path, to `.gproxy-v2-upgrade-blocked` beside the database.

While that marker exists, v3 does not try again; it stops with `automatic migration previously failed; inspect … and remove that marker only after resolving the failure`. This keeps a process supervisor from copying a failing database over and over until the disk is full. Fix the cause, then delete only the marker and start v3 again. Do not delete the backup to force a retry.

## Rolling back

1. Stop v3.
2. Move the current v3 database aside, together with its `-wal` and `-shm` files, and keep them for investigation.
3. Copy `gproxy-v2.db` from the backup directory to the configured database path.
4. Reinstall the v2 executable you saved, or the same official v2 release.
5. Start v2 with the old launch settings and master key.

Do not run v2 against the converted v3 database. Usage recorded after the cutover stays in the saved v3 database; it is not merged back into v2.
