Rewrite rules change a request on its way to the upstream, or a response on
its way back: adding system text, placing cache breakpoints, editing JSON
fields, replacing text and setting headers. The last section of this page
covers protocol and endpoint overrides, which decide which upstream protocol
and URL a provider uses for an operation.

## Adding a rule

Open the provider's **Rewrite rules** page, add a rule, choose its type and
fill in its settings. Every new provider gets a default rule set with the same
name, already bound to it, so for a single provider you do not need to manage
bindings. Use the advanced binding settings when several providers should
share one rule set.

| Console type | Purpose | API `action` |
| --- | --- | --- |
| System text | Prepend or append text to system instructions | `system_text` |
| Cache breakpoint | Add protocol-specific global, system, message, or tool cache markers | `cache_breakpoint` |
| Rewrite | Set or delete a field, or merge an object | `set`, `delete`, `merge` |
| Transform | Apply a regular expression to body text, headers, or query values | `replace` |
| Request header | Set a value or merge comma-separated values | `header_set`, `header_merge` |

System text supports Claude, OpenAI Chat, Responses (including WebSocket) and
Gemini. Cache breakpoints support Claude and OpenAI formats; positions and TTLs
are described in [Prompt caching](/guides/claude-caching).

Each rule has a `phase` (`request`, `response` or `both`) and a `target`
(`body`, `header` or `query`).

## Execution order

A request is first converted to the upstream protocol, then the request rules
run, then the channel sends it. A response goes through the response rules
first and is converted back to the client's protocol afterwards. Rule paths
therefore use the upstream format. For example, when an OpenAI Chat request is
routed to a Claude provider, request rules already see Claude's `system` and
`messages` fields.

Enabled rule-set bindings run in `sortOrder` and then ID order, and so do the
enabled rules inside each set. Each rule sees the output of the one before it.
System text and cache breakpoint rules are ordered the same way as every other
rule.

## Paths, regular expressions and headers

JSON edits need a path such as `temperature` or `messages.*.content`; a `*`
segment selects every element. `set` takes any valid JSON value, `merge` takes
a JSON object, and `delete` takes no value.

Text transforms use Rust regular expressions, including `(?i)`, `(?s)`, and
`$1` and `${name}` in the replacement. With body paths, they replace inside
the selected JSON string values. Without paths, they operate on the whole body
text, so make sure the result is still valid JSON.

Header and query rules require `targetName`. `header_set` replaces the header
value. `header_merge` merges comma-separated values and removes duplicates.
Do not put upstream secrets in rules that other providers share.

## Filters

Filters restrict when a rule runs. A rule runs only when every filter it has
matches; a filter you leave out imposes no restriction.

| Filter | API field | Matches |
| --- | --- | --- |
| Operation and protocol | `filterOperationKeys` | The converted operation executed on the provider |
| Model | `filterModelPattern` | Either the upstream or requested model name, with `*` and `?` wildcards |
| Request headers | `filterHeaderPattern` | A regular expression tested against each inbound header as `name: value` |
| Stream event | `filterEventPattern` | An SSE event name or JSON `type`, for body rules |

To add a compatibility rule for one client, filter it by request headers so it
does not affect other clients.

The model filter's suggestions come only from saved provider models and their
variants. On a provider's page they list that provider's models; on a
standalone rule-set page they combine the models of the attached providers. A
set with no attached providers has no suggestions, but you can still type a
model name or a pattern such as `gpt-*`. Suggestions never query upstream model
directories.

## Body and header conditions

`filterBody` and `filterHeader` run a rule only when a body field or a request
header has a given value. They can be used separately or together, and both
must match along with every other filter:

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "service_tier"
  ],
  "pattern": "",
  "replacement": "\"priority\"",
  "filterBody": {
    "path": "reasoning.effort",
    "op": "eq",
    "value": "high"
  },
  "filterHeader": {
    "name": "x-client-mode",
    "op": "eq",
    "value": "fast"
  }
}
```

`filterBody` reads the current JSON payload, including changes made by earlier
rules, and is supported only on body targets. Its path takes dot-separated keys
and array indexes such as `reasoning.effort` or `messages.0.role`, without
wildcards. Equality compares JSON types, so `"1"` does not equal `1`, and a
missing field is different from `null`. A body that is not valid JSON never
matches a body condition, not even `not_exists`.

`filterHeader` reads the original inbound request headers and works for any
target and phase. Header names are case-insensitive. Values are compared as
exact, case-sensitive strings and are not split at commas. When a header is
repeated, `eq` matches if any value is equal, and `ne` requires the header to
be present with no equal value.

The operators are `eq`, `ne`, `exists` and `not_exists`. `eq` and `ne` require
`value`; `exists` and `not_exists` reject it. A missing field does not satisfy
`ne`.

In a stream, conditions are evaluated separately for each complete SSE event,
NDJSON record, JSON-array element or WebSocket message, with no state carried
between them; a plain HTTP body is evaluated as a whole. To remove a condition,
clear it in the form or set the API field to `null`. A PATCH that omits the
field keeps the existing condition.

### JMESPath expressions

`filterBody` also accepts a JMESPath expression as a string. The expression is
evaluated against the current body, and the action runs only when the result
is boolean `true`. Type errors, unknown functions, other evaluation errors and
non-boolean results do not match. Syntax is checked when the rule is saved. The
`{ "path", "op", "value" }` object form is still supported.

This rule sets `max_tokens` to 0 only when a text block in the last message
contains the keepalive marker; the marker in an earlier message does not
trigger it:

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "max_tokens"
  ],
  "replacement": "0",
  "filterBody": "length(messages[-1].content[?type(text) == 'string' && contains(text, '[cache-keepalive]')]) > `0`"
}
```

Negative indexes such as `[-1]`, projections, `contains()`, comparisons and
boolean operators follow the
[JMESPath specification](https://jmespath.org/specification.html). Missing
fields evaluate to `null` and can be tested explicitly; non-JSON payloads never
match. The action's `paths` still use the dot-path syntax described above,
independently of the expression.

Expressions are compiled once. While the payload is unchanged, all expressions
share one converted JMESPath document; when an earlier rule actually edits the
body, the document is rebuilt so no rule sees stale values. Rules without
expressions do not create this extra copy. Each stream unit is evaluated on its
own, and a query that walks the whole document still costs time proportional to
its size.

## Streaming responses

Body rewrites operate on complete events, such as an SSE event or a JSON array
element, not on network chunks. An event larger than
`settings.maxStreamEventBytes` fails. Use an event filter to rewrite only
particular event types.

## Editing a rule as JSON

When you create or edit a rule, either inside a rule set or on a provider's
**Rewrite rules** page, select **Advanced JSON** to paste one v4 rule object.
You can switch between the form and JSON and format the JSON. Invalid input
stays in the editor with an error message, and saving also checks that the
rule can execute.

For example, to replace `"type":"function"}` in the body with
`"type":"function","strict":false}`:

```json
{
  "action": "replace",
  "phase": "request",
  "target": "body",
  "pattern": "\"type\":\"function\"\\}",
  "replacement": "\"type\":\"function\",\"strict\":false}"
}
```

Use the v4 `action`, `pattern` and `replacement` fields. The page manages the
rule set, ID and order, so leave those out. You may include optional filters
and `enabled`; omitted filters impose no restriction and `enabled` defaults to
true. The editor takes one rule object at a time, not an array.

## Managing rules through the API

This example replaces `widget` with `gadget` in the selected strings. Use your
own rule-set ID.

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"ruleSetId":"your-rule-set-id","action":"replace",
       "phase":"request","target":"body","paths":["messages.*.content"],
       "pattern":"(?i)\\bwidget\\b","replacement":"gadget",
       "filterOperationKeys":[{"operation":"generate_content","dialect":"openai_chat"}]}'
```

`PUT /admin/api/rule-sets/{id}/rules` replaces the whole rule list of a set.
For system text and cache breakpoints, `replacement` holds a JSON-encoded
configuration string; the console builds it for you.

## Compatibility presets

`GET /admin/api/rule-presets` returns the built-in OpenCode, pi-mono,
Aider, Cline, Continue and Cursor presets. The endpoint's answer is the
authoritative list of rules in each.

<Warning>
`POST /admin/api/rule-sets/{id}/rule-presets/{preset}` replaces all existing
rules in the set. To keep them, read or export them first and save a merged
list.
</Warning>

## Protocol and endpoint overrides

A provider's **Routing rules** choose which upstream protocol it uses for an
operation. They are separate from model routes, which choose the provider.

- `operation_rules` overrides a provider's protocol list for an operation. If
  the client's protocol is in the list, the request passes through unchanged;
  otherwise it is converted to the first protocol in the list.
- `operation_endpoints` overrides the full endpoint URL for an operation,
  protocol and transport.

For example, to change the protocols used for generation:

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/operation-rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"providerId":"your-provider-id","operation":"generate_content",
       "action":"dialects","target":["claude","openai_chat"]}'
```

Without overrides, the channel's defaults apply.
`POST /admin/api/providers/{id}/routing-defaults/reset` removes the provider's
operation and endpoint overrides.

The `custom` channel also needs a `dialects` list in the provider
configuration, for example `["openai_chat", "openai"]`. If an operation fails,
check that the upstream supports it, then check this list and the operation
overrides.
