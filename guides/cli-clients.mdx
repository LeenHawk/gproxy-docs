## Vendor service routes

Some vendor CLIs need more than an inference endpoint. They fetch account
profiles, usage windows, plugins, tasks and files from the vendor's control
plane, and they stop working when those requests fail.

A channel can therefore declare a service route table: the control-plane paths
it knows and what each one returns. The host matches an incoming path against
that table before it tries the data plane.

Control-plane paths are vendor-specific, so they are matched only on a provider
or namespace mount. The aggregated mount names no channel, and without a
channel there is no table to match against:

```text
https://gproxy.example/codex/backend-api/wham/profiles/me
                       ^^^^^ the provider (or namespace) named "codex"
```

A path that is not in the table returns `404`, unless the view is
`credential:{id}` (see below).

### Choosing a view

The `x-gproxy-view` request header says what the caller wants back. Without
the header the view is `caller`, and `caller` is the only view an ordinary
member may request.

| Header | What it answers |
| --- | --- |
| `x-gproxy-view: caller` | This caller's own facts: their usage windows, their budget chain, the resources their own calls created. Identity, usage and settings requests do not reach the vendor. |
| `x-gproxy-view: pool` | The same, aggregated over every credential in the target. |
| `x-gproxy-view: credential:{id}` | Raw passthrough. The named credential's own authentication goes upstream and the vendor's answer is returned unchanged. |

Which views a caller may request follows from credential ownership. The
target is the set of credentials of that provider the caller can see, which
is the same set a model call with the same key could use. The caller
administers the target when they are an instance administrator, or an `Admin`
member of the organization or team that owns every credential in the set.
Anyone else is a member and may only request `caller`; `pool` and
`credential:{id}` return `403`.

The condition is "every credential" so that administering one organization
never shows a pool that also contains another organization's credentials. An
unowned credential has no owner whose admin you could be, so on a
single-tenant instance where all credentials are shared, only an instance
administrator can use `pool` and `credential`.

Key minting is refused under every view. A long-lived API key on a shared
subscription is the kind of credential a pooling gateway is meant to keep from
being handed out.

### Metering and cancellation

A vendor service call takes no rate-limit lease, because charging a window for
a profile fetch would use up allowance the caller needs for paid traffic. It
also writes no capture record: the engine writes no upstream record for a
service call, so a downstream capture would have nothing to link to and would
look like a request that never reached an upstream.

Service calls do pass through the budget chain, because the `caller` view
reports the caller's own windows from it. Reading a quota does not spend any of
it.

Service calls carry the same cancellation token as model requests. A
cancellation stops credential preparation, upstream dispatch and streaming of
the HTTP response. For WebSocket services the token covers the handshake; once
the socket is established, the host manages it. Service calls still take no
rate-limit lease and produce no model usage.

## Codex CLI

The `codex` channel declares the ChatGPT backend calls the CLI makes besides
Responses. The wire details follow the CLI's own source under `samples/codex`.

| Family | Paths |
| --- | --- |
| plugins and MCP | `/backend-api/ps/**` |
| account, settings, usage, tasks, environments, remote control | `/backend-api/wham/**` |
| uploads | `/backend-api/files/**` |
| workspace plugin sharing | `/backend-api/public/plugins/**` |
| the start-up identity probe | `GET /v1/user-auth-credential/whoami` |

The CLI addresses the same endpoints in two ways: `/backend-api/wham/**` on
ChatGPT hosts and `/api/codex/**` on Codex API hosts. Both spellings, and the
bare `/codex/**` and `/ps/**` mounts, are normalized to `/backend-api/**`
before the table is consulted, so it does not matter which host style the
client is configured for.

`/backend-api/wham/remote/control/server` is a WebSocket, and it is the only
service route that upgrades. Codex rejects a synthesized view for it, so the
only way through is `x-gproxy-view: credential:{id}`, sent by an administrator
of that credential.

Paths the table does not classify fall through to the `/backend-api/{*path}`
prefix rows and are forwarded unchanged, non-2xx answers included.

## Claude Code

The `claudecode` channel declares the OAuth-scoped `/api/**` calls the CLI
makes besides Messages: profile, validate, roles, bootstrap, usage, policy
limits, account settings, file upload and download, organization connectors,
plugins and skills, onboarding and billing controls, desktop update redirects
and the Claude Design surface.

All of them resolve against `api.anthropic.com`. `claude.ai` is used only for
cookie initialization of a credential, so the channel does not contact it for
these calls.

Under the `caller` and `pool` views, the identity, usage and settings answers
are synthesized from what this instance knows, and their ids are a stable hash
of the provider and the caller's identity. The account, organization and plan
the CLI displays are GPROXY's synthetic values; nothing is invented about the
shared upstream account, and nothing about it is exposed.

## GPROXY as an OAuth issuer

A CLI that logs in with OAuth can log in to this GPROXY instance instead of to
the vendor. This is separate from the SDK's `login()`, in which GPROXY is the
OAuth client of somebody else's authorization server:

```text
  Claude Code ──authorize/token──▶ gproxy   (the authorization server)
                                     │
                                     └──login()──▶ OpenAI   (the client)
```

The endpoints exist under every mount, so a client discovers the issuer of the
mount it is talking to:

```text
GET  {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/token
POST {mount}/v1/oauth/device/code
POST {mount}/v1/oauth/revoke
GET  {mount}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{mount}/v1
```

```sh
curl -s http://127.0.0.1:8787/v1/.well-known/oauth-authorization-server
```

```json
{"issuer":"http://127.0.0.1:8787/v1",
 "authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/authorize",
 "token_endpoint":"http://127.0.0.1:8787/v1/oauth/token",
 "device_authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/device/code",
 "revocation_endpoint":"http://127.0.0.1:8787/v1/oauth/revoke",
 "response_types_supported":["code"],
 "grant_types_supported":["authorization_code","refresh_token",
   "urn:ietf:params:oauth:grant-type:device_code"],
 "code_challenge_methods_supported":["S256"]}
```

v3 served these endpoints at the root. v4 moved them under `/v1` so that they
follow the same prefix rule as `/v1/messages` and share its implementation.

### Issuer security rules

- PKCE with S256 is required. `plain` is refused, and so is a request without
  a challenge. Every registered client is public and has no secret to prove
  itself with, so the verifier is the only thing that keeps a leaked code from
  being exchanged for a token.
- Redirect URIs must match exactly. Prefixes, wildcards and "same origin" are
  not accepted, because each looser rule admits some URL an attacker controls.
- Authorization codes, refresh tokens and device codes are single-use. Each is
  consumed and replaced in one atomic batch, so two redemptions cannot both
  succeed, however they interleave.
- Replaying a code or refresh token revokes the whole family: the grant, its
  internal key and every token it has issued. A lost response cannot be told
  apart from a stolen credential, so a replay is treated as a leak. The
  legitimate client logs in again; the thief cannot. The device flow is
  exempt, because a polling client resends its code by design.

### What an OAuth caller may do

An access token is a credential the user has handed to somebody else's
program. Unless the client is listed in the instance's `oauth.cliClientIds`,
the token may only list models, get a model, count tokens, generate, stream
and compact. Any other operation returns `403`. The limit applies to an
instance administrator's account as well; that is the account where a
third-party token must least be allowed to act as an administrative
credential.

Listing a client in `cliClientIds` means the operator accepts that the client
acts for the user across the whole API. The scopes the user consented to still
bound the token: every operation requires the matching `gproxy:{operation}`
scope in the grant, for listed clients too.

An OAuth caller also cannot mint, rotate, reveal or delete keys, and cannot
change the account password.

## Session affinity

A multi-turn CLI works best when one conversation stays on one credential.
GPROXY reads the conversation identity in the format of the client that sent
the request, not of the upstream it is forwarded to: a Claude Code request
routed to another channel is still read for Claude Code's fields.

The first non-empty source in this list is used:

1. `x-gproxy-session-id`, the gateway's own header.
2. The clients' native headers, in this order: `x-opencode-session`,
   `thread-id`, `session-id`, `x-claude-code-session-id`, `x-conversation-id`,
   `x-grok-session-id`, `x-session-id`, `x-session-affinity`, `session_id`.
3. The session field of the inbound body format: Responses'
   `client_metadata.thread_id` or `session_id`; Claude's `session_id` inside
   the JSON-encoded `metadata.user_id`; Gemini's `request.session_id` or
   `request.sessionId`. Chat Completions defines no such field.
4. A sha256 fingerprint of the conversation's stable prefix.
5. The request id, recorded as a fallback rather than as a session.

Only these fields are read; GPROXY does not search arbitrary JSON for a field
named `session_id`. Request, turn and cache identifiers such as
`x-grok-req-id`, `user_prompt_id`, `prompt_cache_key` and
`previous_response_id` are not treated as sessions.

The gateway header is never forwarded upstream, including when the client
sent it: a client must not be able to pick another caller's conversation by
sending the header the gateway uses to name one. A request without any session
header is never refused.
