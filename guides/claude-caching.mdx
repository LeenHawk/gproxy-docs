This page describes how GPROXY places prompt-cache markers for Claude and
OpenAI upstreams, either through cache breakpoint rules or through magic
strings embedded in the prompt, and how cached tokens are recorded and priced.

Caching itself is done by the upstream. Whether a request hits depends on the
model, the prompt prefix and the TTL. A marker does not guarantee a hit, and it
cannot add caching to an upstream that does not support it.

## Cache breakpoint rules

On the provider's **Rewrite rules** page, add a **Cache breakpoint** rule.
Choose the upstream protocol and a target: global, system or message, and for
Claude also tools. For a local target you can give an index: positive indexes
start at 1, negative indexes count from the end, and an empty index selects the
last available position.

Claude offers default, 5-minute and 1-hour TTLs. OpenAI local breakpoints offer
default, 30-minute and 12-hour TTLs; OpenAI global rules offer default and
30-minute. What the upstream does with the TTL is up to the upstream. The
protocol in the rule is the one used after conversion. Gemini is not supported
by this rule type.

Through the API, use `action: "cache_breakpoint"` with a JSON-encoded
configuration string in `replacement`, for example:

```json
{"dialect":"claude","target":"message","index":-1,"ttl":"5m"}
```

```json
{"dialect":"openai","target":"message","index":-1,"ttl":"12h"}
```

The rule runs on the request body, in the same order as the other
[rewrite rules](/guides/rules). It adds nothing when the body already carries
four markers, the same limit that applies to magic strings below. Clients that
can set native cache fields themselves can also send the upstream's own fields
directly.

## Magic strings

A client that has no cache controls can put one of the following strings in
its prompt text. When the provider's magic cache option for the target
protocol is on, GPROXY removes the string and places a breakpoint where it was.

```text
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_7D9ASD7A98SD7A9S8D79ASC98A7FNKJBVV80SCMSHDSIUCH
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_49VA1S5V19GR4G89W2V695G9W9GV52W95V198WV5W2FC9DF
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_1FAS5GV9R5H29T5Y2J9584K6O95M2NBVW52C95CX984FRJY
```

| String | On a Claude target | On an OpenAI target |
| --- | --- | --- |
| …`7D9ASD…` | `cache_control` with the API's default TTL | an explicit breakpoint |
| …`49VA1S…` | `cache_control` with `"ttl": "5m"` | `prompt_cache_breakpoint` (`"ttl": "30m"`) |
| …`1FAS5G…` | `cache_control` with `"ttl": "1h"` | `prompt_cache_breakpoint` (`"ttl": "12h"`) |

The same string selects short or long retention according to the target
protocol: Claude `5m` and `1h` correspond to OpenAI `30m` and `12h`. The
default string leaves the TTL unset. The TTL is written on the breakpoint
itself; the request-wide cache options are not changed.

The strings are part of the protocol between clients and GPROXY and do not
change between releases.

### Enabling magic cache

There are two provider `config` switches, one for each protocol family:

```json
{ "config": { "enable_claude_magic_cache": true,
              "enable_openai_magic_cache": true } }
```

| Switch | Channels that offer it |
| --- | --- |
| `enable_claude_magic_cache` | `aws_bedrock`, `azure`, `claudeapi`, `claudecode`, `custom`, `opencodego`, `opencodezen`, `openrouter`, `vercel` |
| `enable_openai_magic_cache` | `aws_bedrock`, `azure`, `openai`, `codex`, `custom`, `opencodego`, `opencodezen`, `openrouter`, `vercel` |

In the console they appear as **Enable claude magic cache** and
**Enable openai magic cache**.

The switch that applies is the one for the target protocol, not the client's.
A request from an OpenAI-style client routed to a Claude provider is first
converted to Claude Messages, so the Claude switch decides, and the marker
written is `cache_control`. The client still receives responses in its own
format.

### Stripping

The channels in the table above always remove the strings, whether or not
magic cache is enabled, because a leftover marker in a prompt is never useful
to the upstream.

The switch only decides whether a breakpoint is placed where the string was.
With magic cache off, the strings are removed and nothing else changes: the
client's own `cache_control` or `prompt_cache_breakpoint` stays as it is, and
a body that contains no string is forwarded byte for byte without being parsed
and re-serialized.

The `claudeweb` channel applies the same strip without placing anything,
because a browser session has no cache control.

## Where markers are placed

With magic cache enabled, markers for magic strings are placed as follows for
each target protocol.

### Claude Messages

The body is normalized first: string content becomes block arrays, empty text
blocks are dropped, and a `cache_control` on a dropped block moves to the
nearest cacheable block. This is what makes a string on a line by itself work.
Thinking blocks are kept only on assistant turns.

`system` is then processed before `messages`, so the breakpoint budget is spent
in prompt order rather than in JSON key order. Every text block that contains a
string is marked:

```json
{ "cache_control": { "type": "ephemeral", "ttl": "1h" } }
```

A block that already has `cache_control` is left alone.

### OpenAI Chat Completions

Every message except those with the `function` role can be marked. A
plain-string `content` is split into a marked `text` part, since the marker
needs a part to sit on; array content has its parts marked in place.

```json
{ "type": "text", "text": "…", "prompt_cache_breakpoint": { "mode": "explicit" } }
```

### OpenAI Responses

Markers are placed in three places, in this order:

1. `instructions`. A string found there is removed and a marked developer
   message is inserted at the start of `input`, because `instructions` is a
   plain string and cannot carry a marker.
2. `prompt.variables`, marked the same way as Chat parts.
3. `input`. A bare string becomes one marked user message; in an array of
   items, `content` and `output` are marked using the `input_text` and
   `output_text` kinds.

### Gemini

Gemini has no breakpoints. The strings are removed and nothing else happens.

## Four-breakpoint limit

At most four breakpoints leave the proxy, counting the ones the client set
itself. The budget is the number of markers already in the body subtracted
from four, so a client that placed three of its own leaves room for one more.

Strings beyond the limit are still removed; they just do not become markers.

## Native cache fields in protocol conversion

When a request is converted between Claude and OpenAI Chat or Responses, native
cache fields are mapped in both directions using the same TTL correspondence.
Marked system, message, image or document, and tool-result blocks keep their
boundaries. A Claude automatic cache policy becomes an explicit breakpoint on
the corresponding final block, as long as that block has a representation in
the target protocol. Per-tool definition markers that have no OpenAI equivalent
are listed in the conversion report.

When converting from OpenAI to Claude, only an explicitly supplied
`prompt_cache_options.mode: "implicit"` produces a top-level `cache_control`.
Omitting the options object or its `mode` (including an empty object, or a TTL
on its own) does not turn on Claude automatic caching. Explicit block markers
are converted independently of this.

OpenAI Responses and Chat explicit breakpoints accept
`prompt_cache_breakpoint: {"mode":"explicit","ttl":"12h"}` (or `"30m"`), and
the TTL is kept across Chat and Responses conversion. The current
[OpenAPI schema](https://github.com/openai/openai-openapi/blob/master/openapi.json)
still limits the request-wide `prompt_cache_options.ttl` to `"30m"`.
`prompt_cache_retention` is a separate, older policy.

## Usage and pricing

Cached tokens are recorded as their own metrics and priced from your rate rows:

| What the upstream reports | Metric |
| --- | --- |
| cache read | `cached_input_tokens` |
| cache write, by retention | `cache_creation_tokens` + `ttl_seconds` |
| cache write, unknown retention | `cache_creation_tokens` |

All cache writes use `cache_creation_tokens`. A rate condition such as
`{"ttl_seconds":43200}` selects the 12-hour write price; a rate without the
condition is the fallback price. Each reported write bucket is priced
separately. Cache reads are a single `cached_input_tokens` count with no TTL.
Tier overrides use `cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]`,
where an entry with `ttlSeconds: null` is the fallback. Prices are per million
tokens; the TTL does not multiply them.

OpenAI's per-call usage reports only a total `cache_write_tokens`, so GPROXY
records the TTL of those writes as unknown instead of guessing how they split
across breakpoints with different TTLs.

`cached_input_tokens` is capped at `input_tokens`. The uncached remainder is
priced at the input rate and the cached part at the cache-read rate; if no
cache-read rate exists, the input rate is used instead. Cache writes with no
rate of their own are charged nothing. See [Pricing](/reference/pricing).

Token counts on a usage record are optional, because an upstream that did not
report a field did not measure zero. Totals are plain numbers, since a sum over
fields that were not reported is zero.

## Avoiding cache misses

Rewrite rules run after protocol conversion and before the channel sends the
request, so a rule that edits prompt text can turn an expected hit into a
miss. Put stable content first, the marker after it, and anything that changes
per request after that boundary. Check that no rewrite rule with a broad
`paths` selector edits the cached prefix.
