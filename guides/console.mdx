The console is GPROXY's web interface for both personal use and
administration. This page describes what each part of it does and how scoped
administrators use it.

The CLI and container builds serve the console at `/console`. Sign in with an
account configured for the deployment. The console signs in through
`/portal/api/login` and keeps the session in an HttpOnly cookie.

## First startup

CLI and container instances create an administrator on first startup; open
`/console/` in a browser and sign in with it. There is no setup wizard in this
case.

A new Application instance instead opens a setup wizard before the in-app
console. Its steps are **Instance**, **Administrator** and **Upstreams**; the
providers created there are then given credentials in **Add credentials**,
after sign-in. See [Download & Install](/download#setup).

## Language

The console is available in English, Simplified Chinese, Traditional Chinese
and Russian (Русский). On first use it picks a supported language from the
browser or system settings; regional Russian tags such as `ru-RU` use the
Russian translation. A language you choose by hand takes priority and is saved
on the device. Numbers and dates are formatted for the selected language;
amounts stay in the configured billing currency.

## Management scope

The console combines personal pages, from `/portal/api/context`, with the
management sections returned by `/admin/api/context`. What you see depends on
your role:

- Instance administrators manage the whole gateway.
- Organization and team administrators manage their own credentials through
  the same **Providers** entry. Their **Organizations** and **Teams** pages
  show only the objects they are admitted to and their cost budgets, with no
  identity create/edit/delete and no provider configuration.

If you administer more than one organization or team, choose the scope in the
account menu. Management requests then carry the server-provided scope
selector in the `x-gproxy-admin-scope` header. Switching scope closes open
editors and login flows and replaces the cached data for the scope. A write
that is still being submitted must finish before you can switch. Personal
pages do not depend on the management scope.

Personal cost budgets appear read-only on **Overview**, next to usage. There is
no separate personal quota page; administrators edit budgets on the user, API
key, organization or team they belong to.

## Pages

The configuration pages, with their menu labels:

| Console path | Menu label | Contents |
| --- | --- | --- |
| `/console/providers` | **Providers** | provider configuration, credentials, models, protocol conversion, rewrite rule bindings, endpoint overrides |
| `/console/model-routes` | **Model routes** | cross-provider routes, members, weights, fallback tiers and public model names |
| `/console/rule-sets` | **Rule sets** | rewrite rules, their order, and saving a whole set at once |
| `/console/model-catalog` | **Models** | the global model catalogue and global prices |
| `/console/settings` | **Global settings** | instance and logging settings |
| `/console/settings/transfer` | **Configuration transfer** (a tab of **Global settings**) | configuration export and import; `/console/transfer` opens the same panel |
| `/console/clients` | **HTTP client configuration** | reusable connection profiles |
| `/console/tokenizer` | **Vocabularies** | vocabulary downloads and model vocabulary bindings |
| `/console/update` | **Updates** | the update operations this host supports |

A provider page has the tabs **Credentials**, **Models**, **Rules**,
**Routing rules** and **Settings**. **Routing rules** controls operation and
protocol conversion for that provider. **Model routes** chooses between
upstream providers. The two are configured separately.

Configuration tables let you select rows on the current page and delete them
in one batch; tables whose rows have an enabled switch also allow batch enable
and disable. Changing the filter or page, or switching management scope,
clears the selection. Each batch goes through the existing transactional
configuration API.

## Credentials and upstream sign-in

A provider's credentials are managed on its **Credentials** tab. New
credentials and sign-in flows started there belong to that provider. The
ownership you can choose is limited to the current management scope. Tenant
directories show provider labels and the actions available, not gateway
configuration.

Editing a credential opens one panel with three tabs: **Basic settings**,
**Local limits** and **Upstream allowance**. From the credential row you can
also open **Upstream allowance**, run a test, or delete the credential.

- Revealing and refreshing the secret are below the secret field in **Basic
  settings**.
- Changing the lifecycle status and **Reset health state** are in the status
  area.
- The test dialog loads the available models and shows the result, the latency
  and the reply. **Test generation** sends a real request upstream.
- Upstream readings are shown as amounts, counts and reset times.

### Signing in to an upstream

**Add by signing in** offers the sign-in methods the channel supports.

For browser authorization:

1. Click **Start sign-in** and open the authorization link.
2. Complete the authorization with the upstream.
3. Copy the full callback URL, including `code` and `state`, and paste it into
   the console. If the callback is a registered loopback address, the page may
   fail to load in the browser; copy the address from the address bar anyway.
   The console does not run a local callback listener.
4. Click **Complete sign-in**.

For a device code, open the verification link and enter the code the console
shows. The console polls at the interval the backend returns and stops on
success, denial, expiry, or when you close the window.

A login session is bound to the user who started it, the management scope and
the credential owner. Completing it returns the credential ID, never the
secret. Closing an unfinished flow stops the UI only; the cached session
expires on its own. Reloading the page does not restore the login wizard.

The upstream login routes are POST requests under
`/admin/api/credential-login`: `/authcode/start`, `/authcode/complete`,
`/device/start` and `/device/poll`. They use the same scope checks as the
credentials section. Model discovery and testing for a credential use
`/admin/api/credentials/{id}/models/discover` and `/models/test`.

## Quotas and prices

### Key budgets

Administrators can set a budget for a key directly in the **New key** form,
below the key name (**Set a budget for this key**). This works both in **Personal
→ Your keys** and in **Access control → User keys**. The key and its first budget are saved in one
transaction; if the budget is invalid, no key is created. Editing an existing
key opens one panel with **Basic settings** and **Cost budget** tabs.

Ordinary users create and manage their own keys as before, but only
administrators set budgets on them.

### Cost budgets

Users, API keys, organizations and teams each have a **Cost budget** entry.
Rules are added and edited inside that panel, without a second dialog. Costs
are decimal strings in USD. Request-count limits on providers and credentials
use the unit `count`.

### Default credential limits

A provider's **Settings → Default credential limits** apply each rule to each
credential separately; they are not a budget shared by the provider. That page
shows the configuration; usage and reset times are shown on each credential.

An enabled credential rule with the same name overrides the provider default.
**Restore inheritance** deletes the credential's override. Disabling an
override also lets an enabled default apply again; it does not remove the
limit.

Credential limit cards show the source of the rule, the configured cap, the
actual usage and the next reset. Organization and team administrators can see
the effective limits; instance administrators configure them. Period, amount
or count, model pattern and enabled state are edited in place. A custom
duration and the anchor of a fixed period are under the advanced options.

### Resetting limits

Resetting a provider default affects every credential that currently inherits
it, and the confirmation says so. An inherited card has no reset button of its
own. Resetting a credential override or a caller budget resets only that rule.
None of these actions resets the upstream account's allowance.

### Prices

Global prices are edited on the **Models** page, and provider-specific prices on
a provider's **Models** tab. The model dialog manages the price rule, its rates
for each dimension, and its context and service tiers together.

A price rule applies to all providers or to one provider, and its model
pattern accepts `*` and `?`. One model can have several rules for different
operations. For how a price is computed, see
[Pricing and tiers](/reference/pricing).

## Import and export

The transfer document contains gateway configuration. It does not contain
identities, usage or request logs.

- **Export configuration** leaves credential secrets out unless you tick
  **Include stored credential secrets**. Included secrets are exported in
  their stored, sealed form.
- **Import configuration** accepts the current v4 document format. The summary
  shown after you choose a file lists the format version and record counts; it
  is not a server-side dry run.

The import mode decides what happens to existing records:

- **Merge** updates records with matching IDs and keeps records the file does
  not mention.
- **Replace configuration** also deletes records the file does not mention,
  within the configuration kinds that are exported.

Encrypted secrets from an instance with a different master key can only be
read if you enter that key in **Source master key (optional, Hex or Base64)**,
so the backend can reseal them. Without it, the destination must use the same
master key. The console clears the field after submitting.

The import runs in one transaction, and after it commits the host reloads its
runtime settings. Read the returned warnings and skipped counts. If the reload
fails, the result reports a configuration that has been imported plus a
runtime warning; the import has not been rolled back.

## Fonts

In CLI and Application builds the console uses system fonts by default. You
can download Noto Sans, Noto Sans SC/TC and Noto Sans Mono during application
setup or later under **Interface fonts** in settings (**Download interface
fonts**). GPROXY downloads about 9.2 MiB from
`https://gproxy.leenhawk.com/fonts/`, verifies the files and stores them in
its local data directory, so they work offline. No font requests are made
until you choose to download. **Delete fonts and use system fonts** goes back
to system fonts.

Edge deployments serve bundled static fonts from the same origin. Headless
packages contain neither the console nor fonts.

## Building the console

Run `pnpm --dir console lint`, `pnpm --dir console test` and
`pnpm --dir console build`. The build type-checks the code, bundles it with
Vite and copies the assets into the embedded console directory. A native
binary built afterwards serves that bundle at `/console`; Edge deployments
serve the same bundle as static assets in front of the gateway. See
[Building](/development/building).
