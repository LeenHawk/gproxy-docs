This page explains how GPROXY turns the `model` a client sends into a provider,
a credential and an upstream model name, and how to set up the routes and the
model catalogue that drive it. To change request parameters rather than where a
request goes, use [rewrite rules](/guides/rules).

## Resolving a model name

The client's model name is usually not an upstream model id. GPROXY resolves it
before the request reaches the engine, so the engine only ever receives a
target that has already been chosen:

```text
request model
  → the first matching form: route name · provider/model
  → candidates, narrowed by channel, allowed providers, allowed credentials
  → ordered by (tier, health, descending weight, stable id)
  → the leading run balanced by the route's strategy
  → one (provider, credential, upstream model) per attempt
```

The name is matched against the following forms, in order, and the first one
that applies wins:

| Name | Resolves to | Attempt budget |
| --- | --- | --- |
| absent | every enabled provider, no upstream model | `settings.max_attempts` |
| a model route name | that route's enabled members | the route's own |
| `provider/model` | that one provider | `settings.max_attempts` |
| anything else | `404 unknown_model` | — |

Route names are compared exactly, and before the prefix form. A disabled route
is not a name at all, so a request for it falls through to the next form. The
prefix in `provider/model` is always a provider name, never a channel id: a
provider named `openai` on the `codex` channel is reached as `openai/…`, the
same way its mount `/openai/v1` reaches it.

The candidates are then narrowed by the ingress mount's channel, by the
providers the caller's key may use and by the credentials it may spend. A name
that matched a form but has nothing left after narrowing returns
`503 no_usable_target`. That is a configuration problem (no member is enabled,
no credential is usable, or the key is not allowed any of them), which is why it
is reported differently from an unknown model.

In practice, give clients route names as their model names.

## Creating a route

A route is a public model name with a list of provider/model members, a
balancing strategy and an attempt budget. After you create a route named
`main`, clients can send `model: "main"`.

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/routes \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"main","strategy":"round_robin","maxAttempts":6}'
```

```json
{"id":"33a88261f571347c7f0408c3bd2e2164","name":"main","strategy":"round_robin",
 "maxAttempts":6,"enabled":true}
```

| Field | Meaning |
| --- | --- |
| `name` | Globally unique. Clients send this exact name as `model`. |
| `sessionAffinity` | Reuse a successful provider/model target for the session; defaults off. Credential selection remains the provider's responsibility. |
| `strategy` | `round_robin`, `weighted` or `failover`. |
| `maxAttempts` | The total attempt budget including the first call; must be positive. `settings.maxAttempts` (default 6) is a hard ceiling on it at execution time. |

In the console, routes are under **Model routes**.

## Adding members

Each member sends traffic to one provider under one upstream model name:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/route-members \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"routeId":"…","providerId":"…","upstreamModel":"gpt-4o-mini",
       "tier":0,"weight":100}'
```

| Field | Meaning |
| --- | --- |
| `providerId`, `upstreamModel` | Where this member sends traffic. The model name is an explicit string, not a catalogue foreign key. |
| `tier` | Lower is preferred. Tier 0 is exhausted before tier 1 sees any traffic. |
| `weight` | Positive, default 100. Splits traffic inside a tier, and orders failover candidates. |
| `enabled` | A disabled member leaves the plan. |

A member of a disabled or deleted provider is skipped. If `upstreamModel`
matches a variant name of one of the provider's enabled models, the request is
sent under that model's upstream name.

A member does not name a credential. The engine picks a credential inside the
chosen provider, and it fails over between that provider's credentials before
the plan moves on to the next member.

## Ordering and strategies

Candidates are sorted by `(tier, health, descending weight, stable id)`. The
stable id is the member id, so two candidates never compare equal and the order
is the same on every request.

Tier is a strict preference: a later tier is never balanced against an earlier
one. Only the leading run (the candidates that share the first candidate's tier
and health) is reordered, according to the route's strategy:

- `round_robin` rotates the leading run using a counter kept per route.
- `weighted` moves the smooth weighted round-robin pick to the front. Over a
  full cycle each member is picked in proportion to its weight, and the picks
  are spread out rather than batched.
- `failover` leaves the sorted order as it is.

Rotation uses a counter rather than a random draw, so native and wasm builds
behave the same and a sequence can be reproduced. The counters are kept in
process memory and are not shared between instances; a restart starts the
rotation again from the first candidate.

Health comes from the provider's credentials. Disabled, retired and dead
credentials are removed. Blocked credentials (for example after a rate limit)
are removed while the provider still has an unblocked one. If every credential
of a provider is blocked, the provider stays in the plan with its blocked
credentials and is sorted behind every healthy provider, so a rate-limited
provider is tried last instead of being treated as down.

With `sessionAffinity` on, a session's previous successful target is preferred,
but only within that same leading tier and health group.

## Route names and namespaces

You create and edit the public names directly on routes; there is no separate
public-name mapping.

### Namespaces

A route name that contains `/` defines a namespace at runtime. Creating route
`acme/fast` makes `acme` a mount, and a request to `/acme/v1/chat/completions`
with `{"model":"fast"}` resolves `acme/fast`:

```sh
curl -s http://127.0.0.1:8787/acme/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"hi"}]}'
```

A namespace is only an index over route names. It is not stored anywhere, it
does not group or own routes, and nothing is created when it appears.

### Reserved first segments

If a route name's first segment is the name of an existing provider (compared
case-insensitively), management refuses it, because `name/…` already means
`provider/model` for that provider:

```json
{"error":{"code":"invalid_request","message":"invalid request: `codex/` is reserved:
 a first segment naming a provider already means `provider/model` narrowing;
 choose a distinct model route name"}}
```

Any other first segment is allowed; `coding/fast` is a valid public name.

## Model lists for callers

`GET /v1/models` returns the configured names (route names and
`provider/model`), filtered to the names the caller may use. It does not proxy
any single upstream's model directory. Provider models appear here once you add
or import them, prefixed with the provider's name.

These two requests are equivalent: base URL `/provider-A/v1` with model
`gpt-5`, or base URL `/v1` with model `provider-A/gpt-5`.
`GET /provider-A/v1/models` lists only provider A and keeps its original model
names.

The prefix is the provider's display name, so renaming a provider changes both
its model prefix and its base URL.

The portal list also includes names the caller cannot use, marked with
`permitted`:

```sh
curl -s http://127.0.0.1:8787/portal/api/models -H "Authorization: Bearer $GPROXY_KEY"
```

```json
[{"name":"provider-A/gpt-4o-mini","providerCount":1,"channelIds":["custom"],"permitted":true},
 {"name":"fast","providerCount":1,"channelIds":["custom"],"permitted":true}]
```

A name the caller's rules do not reach stays in the list with
`permitted: false`. v3 removed such rows. v4 keeps them because a list that
silently omits names makes "this model returns 404" look the same as "you are
not allowed to use this model", and the names are instance configuration that
the operator publishes anyway.

The provider ids behind a name are not shown. Each entry reports a provider
count and the channel ids, which tell the caller how redundant a name is
without exposing the providers themselves.

## The model catalogue

The catalogue consists of two tables. Routing needs neither of them: a route
member names its upstream model as a plain string, so routing works for names
that appear in neither table. Catalogue rows are used for model lists,
documentation, metadata and pricing.

- `provider_models` records which upstream names a provider serves.
  Discovery writes here.
- `models` is the global catalogue that a `provider_models` row may point at:
  one name, its metadata, and the tokenizer vocabulary that token estimation
  should use for it.

To add a provider model by hand:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/provider-models \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","upstreamName":"gpt-4o-mini"}'
```

```json
{"id":"f32df0bb6378c03e70f7c3aa6315a3b8","providerId":"5a45fd807be0…",
 "upstreamName":"gpt-4o-mini","modelId":null,"metadata":{},"enabled":true}
```

### Discovering models from the upstream

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

Discovery queries the upstream in the provider's own protocol, so nothing is
converted and the names are the upstream's. Each entry in the answer says
whether the provider already has a row for it and whether the bundled catalogue
can price it. `POST /admin/api/models/discover/apply` inserts the entries you
name and skips those that already exist, so applying the same discovery twice
has the same effect as applying it once.

When discovery fills in metadata, it matches the full model id first and then a
unique basename; an ambiguous name gets no defaults. Fields are merged in this
order: bundled defaults, then non-null upstream fields, then local overrides.
Importing into an existing provider model from the console fills only missing
fields.

<Warning>
Discovery and `POST /admin/api/models/test` both spend a real credential and
write a real usage row. See [Testing a provider](/guides/providers#testing-a-provider).
</Warning>

### The bundled catalogue

Each release bundles a catalogue of model names, context windows and default
prices. It is a snapshot taken when the asset was generated, not a live
directory:

```sh
curl -s http://127.0.0.1:8787/admin/api/default-model-catalog -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

With `overwrite: false`, re-applying is safe: a rule that an operator has
edited keeps the edit and is reported as skipped.

Bundled model ids are unqualified names such as `claude-sonnet-4`, not
`anthropic/claude-sonnet-4`; the source URLs and raw prices keep their
provenance. Qualified upstream names still match by basename. Default price
matching prefers the longest matching model fragment, while importing a
provider's prices keeps the provider's actual upstream name as the rule
pattern.

The default prices are an OpenRouter snapshot and do not reflect every
provider's contract. Applying them creates global pricing rules and does not
replace an existing rule with the same pattern. Provider-specific rules take
precedence over global rules. Prices are edited in the existing global-model
and provider-model dialogs, whose price editor handles rates, context tiers and
service tiers. See [Pricing](/reference/pricing).

### The Models page

The console's **Models** page (`/console/model-catalog`) lists the models saved
in the database. It uses the same `/admin/api/models` endpoint as the
permission selectors, and an empty database gives an empty list. The page shows
saved capabilities and limits, provider associations, and bundled reference
prices where one matches.

**Load default models** imports the entries you select from the bundled table
and leaves existing models unchanged. Loading model metadata does not change
pricing rules. You can also add models by hand. A deleted model is removed from
the list and is not restored from the bundled data when the list is read.

Metadata is copied at import time. Editing a global model later does not change
provider models that were imported from it earlier.

### Refreshing the bundled catalogue

Regenerate the bundled asset with:

```sh
node scripts/update-openrouter-model-catalog.mjs
```

Pass `--input response.json` to build it offline from a saved response. The
public model endpoint needs no key; an optional credential is read only from
`OPENROUTER_API_KEY`. The generator keeps the raw `source_pricing` for review
and maps only the billing units it supports. After unit conversion, billing
prices are rounded to nine decimal places (round half to even), and importing
default prices uses the same rule.

A missing or dynamic price does not mean the model is free. Before adding a
price from an official price page, check the exact model version, region, unit
and threshold; do not guess a missing rate.
