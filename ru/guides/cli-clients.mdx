<a id="vendor-service-routes"></a>

## Сервисные маршруты поставщиков

Некоторым CLI поставщиков нужна не только конечная точка инференса. Они загружают профили аккаунтов, окна использования, плагины, задачи и файлы из плоскости управления поставщика и перестают работать, если эти запросы не выполняются.

Поэтому канал может объявить таблицу сервисных маршрутов: известные ему пути плоскости управления и то, что возвращает каждый из них. Хост сопоставляет входящий путь с этой таблицей, прежде чем обратиться к плоскости данных.

Пути плоскости управления зависят от поставщика, поэтому сопоставляются только на точке монтирования провайдера или namespace. Агрегированная точка монтирования не называет канал, а без канала нет и таблицы:

```text
https://gproxy.example/codex/backend-api/wham/profiles/me
                       ^^^^^ the provider (or namespace) named "codex"
```

Путь, которого нет в таблице, возвращает `404`, кроме случая, когда представление — `credential:{id}` (см. ниже).

<a id="choosing-a-view"></a>

### Выбор представления

Заголовок запроса `x-gproxy-view` указывает, что вызывающий хочет получить. Без заголовка используется представление `caller`, и это единственное представление, доступное обычному участнику.

| Заголовок | Что возвращается |
| --- | --- |
| `x-gproxy-view: caller` | Собственные данные вызывающего: его окна использования, цепочка бюджетов, ресурсы, созданные его собственными вызовами. Запросы идентичности, использования и настроек к поставщику не обращаются. |
| `x-gproxy-view: pool` | То же самое, но в сумме по всем учётным данным цели. |
| `x-gproxy-view: credential:{id}` | Прямая передача. К вышестоящему сервису идёт собственная аутентификация указанных учётных данных, а ответ поставщика возвращается без изменений. |

Какие представления доступны вызывающему, определяется владением учётными данными. Цель — набор учётных данных этого провайдера, видимых вызывающему, то есть тот же набор, который мог бы использовать вызов модели с тем же ключом. Вызывающий администрирует цель, если он администратор экземпляра или участник с ролью `Admin` в организации или команде, которой принадлежат все учётные данные набора. Все остальные — участники и могут запрашивать только `caller`; `pool` и `credential:{id}` возвращают `403`.

Условие «все учётные данные» нужно для того, чтобы администрирование одной организации никогда не показывало пул, содержащий учётные данные другой. У учётных данных без владельца нет никого, чьим администратором можно быть, поэтому на однопользовательском экземпляре, где все учётные данные общие, `pool` и `credential` доступны только администратору экземпляра.

Выпуск ключей отклоняется в любом представлении. Долгоживущий API-ключ на общей подписке — именно тот вид учётных данных, выдачи которых шлюз-пул должен избегать.

<a id="metering-and-cancellation"></a>

### Учёт и отмена

Вызов сервиса поставщика не берёт аренду ограничения скорости, потому что списание окна за загрузку профиля расходовало бы квоту, нужную вызывающему для платного трафика. Он также не пишет запись захвата: движок не создаёт вышестоящей записи для сервисного вызова, поэтому нижестоящему захвату не на что было бы ссылаться и он выглядел бы как запрос, не дошедший ни до какого вышестоящего сервиса.

Сервисные вызовы проходят через цепочку бюджетов, потому что представление `caller` показывает по ней собственные окна вызывающего. Чтение квоты её не расходует.

Сервисные вызовы несут тот же токен отмены, что и запросы моделей. Отмена прерывает подготовку учётных данных, отправку вышестоящему сервису и потоковую передачу HTTP-ответа. Для сервисов WebSocket токен охватывает рукопожатие; установленным сокетом управляет хост. Сервисные вызовы по-прежнему не берут аренду ограничения скорости и не создают использования моделей.

<a id="codex-cli"></a>

## Codex CLI

Канал `codex` объявляет вызовы бэкенда ChatGPT, которые CLI делает помимо Responses. Детали протокола соответствуют собственному исходному коду CLI в `samples/codex`.

| Группа | Пути |
| --- | --- |
| плагины и MCP | `/backend-api/ps/**` |
| аккаунт, настройки, использование, задачи, окружения, удалённое управление | `/backend-api/wham/**` |
| загрузки файлов | `/backend-api/files/**` |
| общий доступ к плагинам рабочего пространства | `/backend-api/public/plugins/**` |
| проверка идентичности при запуске | `GET /v1/user-auth-credential/whoami` |

CLI обращается к одним и тем же конечным точкам двумя способами: `/backend-api/wham/**` на хостах ChatGPT и `/api/codex/**` на хостах Codex API. Оба написания, а также голые точки монтирования `/codex/**` и `/ps/**`, перед поиском в таблице приводятся к `/backend-api/**`, поэтому неважно, на какой стиль хоста настроен клиент.

`/backend-api/wham/remote/control/server` — это WebSocket и единственный сервисный маршрут с повышением протокола. Codex не принимает для него синтезированное представление, поэтому пройти можно только с `x-gproxy-view: credential:{id}`, отправленным администратором этих учётных данных.

Пути, которые таблица не классифицирует, попадают в префиксные строки `/backend-api/{*path}` и пересылаются без изменений, включая ответы не 2xx.

<a id="claude-code"></a>

## Claude Code

Канал `claudecode` объявляет вызовы `/api/**` в рамках области OAuth, которые CLI делает помимо Messages: profile, validate, roles, bootstrap, использование, лимиты политик, настройки аккаунта, загрузка и скачивание файлов, коннекторы организации, плагины и skills, онбординг и управление биллингом, перенаправления обновлений настольного приложения и интерфейс Claude Design.

Все они разрешаются на `api.anthropic.com`. `claude.ai` используется только для инициализации учётных данных по cookie, поэтому для этих вызовов канал к нему не обращается.

В представлениях `caller` и `pool` ответы об идентичности, использовании и настройках синтезируются из того, что знает этот экземпляр, а их id — стабильный хэш провайдера и идентичности вызывающего. Аккаунт, организация и план, которые показывает CLI, — синтетические значения GPROXY; об общем вышестоящем аккаунте ничего не выдумывается и ничего не раскрывается.

<a id="gproxy-as-an-oauth-issuer"></a>

## GPROXY как OAuth-сервер авторизации

CLI, входящий через OAuth, может входить в этот экземпляр GPROXY вместо поставщика. Это не то же самое, что `login()` в SDK, где GPROXY выступает OAuth-клиентом чужого сервера авторизации:

```text
  Claude Code ──authorize/token──▶ gproxy   (the authorization server)
                                     │
                                     └──login()──▶ OpenAI   (the client)
```

Конечные точки есть под каждой точкой монтирования, поэтому клиент обнаруживает сервер авторизации той точки, с которой работает:

```text
GET  {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/authorize
POST {mount}/v1/oauth/token
POST {mount}/v1/oauth/device/code
POST {mount}/v1/oauth/revoke
GET  {mount}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{mount}/v1
```

```sh
curl -s http://127.0.0.1:8787/v1/.well-known/oauth-authorization-server
```

```json
{"issuer":"http://127.0.0.1:8787/v1",
 "authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/authorize",
 "token_endpoint":"http://127.0.0.1:8787/v1/oauth/token",
 "device_authorization_endpoint":"http://127.0.0.1:8787/v1/oauth/device/code",
 "revocation_endpoint":"http://127.0.0.1:8787/v1/oauth/revoke",
 "response_types_supported":["code"],
 "grant_types_supported":["authorization_code","refresh_token",
   "urn:ietf:params:oauth:grant-type:device_code"],
 "code_challenge_methods_supported":["S256"]}
```

В v3 эти конечные точки находились в корне. В v4 они перенесены под `/v1`, чтобы подчиняться тому же правилу префикса, что и `/v1/messages`, и использовать ту же реализацию.

<a id="issuer-security-rules"></a>

### Правила безопасности сервера авторизации

- PKCE с S256 обязателен. `plain` отклоняется, как и запрос без challenge. Все зарегистрированные клиенты публичные и не имеют секрета для подтверждения, поэтому только верификатор не даёт обменять утёкший код на токен.
- Redirect URI должны совпадать точно. Префиксы, шаблоны и «тот же источник» не принимаются, потому что любое более мягкое правило пропускает какой-нибудь URL, контролируемый злоумышленником.
- Коды авторизации, refresh token и коды устройств одноразовые. Каждый расходуется и заменяется в одном атомарном пакете, так что два погашения не могут оба пройти, как бы они ни чередовались.
- Повторное использование кода или refresh token отзывает всё семейство: грант, его внутренний ключ и все выданные им токены. Потерянный ответ невозможно отличить от украденных учётных данных, поэтому повтор считается утечкой. Законный клиент входит заново; похититель — нет. Поток с кодом устройства — исключение, потому что опрашивающий клиент по замыслу повторно отправляет свой код.

<a id="what-an-oauth-caller-may-do"></a>

### Что разрешено OAuth-клиенту

Токен доступа — это учётные данные, которые пользователь передал чужой программе. Если клиент не указан в `oauth.cliClientIds` экземпляра, токен может только получать список моделей, получать модель, считать токены, генерировать, генерировать потоково и сжимать. Любая другая операция возвращает `403`. Ограничение действует и для аккаунта администратора экземпляра: именно его стороннему токену нельзя позволить стать административными учётными данными.

Включая клиента в `cliClientIds`, оператор соглашается, что клиент действует от имени пользователя во всём API. Токен при этом по-прежнему ограничен областями, на которые согласился пользователь: каждая операция требует в гранте соответствующую область `gproxy:{operation}`, в том числе для клиентов из списка.

OAuth-клиент также не может выпускать, ротировать, раскрывать или удалять ключи и не может менять пароль аккаунта.

<a id="session-affinity"></a>

## Привязка сессии

Многоходовому CLI лучше всего, когда один разговор остаётся на одних учётных данных. GPROXY читает идентификатор разговора в формате клиента, отправившего запрос, а не вышестоящего сервиса, которому запрос будет переслан: запрос Claude Code, направленный в другой канал, по-прежнему читается по полям Claude Code.

Используется первый непустой источник из списка:

1. `x-gproxy-session-id`, собственный заголовок шлюза.
2. Нативные заголовки клиентов в таком порядке: `x-opencode-session`, `thread-id`, `session-id`, `x-claude-code-session-id`, `x-conversation-id`, `x-grok-session-id`, `x-session-id`, `x-session-affinity`, `session_id`.
3. Поле сессии во входящем формате тела: `client_metadata.thread_id` или `session_id` в Responses; `session_id` внутри JSON-строки `metadata.user_id` в Claude; `request.session_id` или `request.sessionId` в Gemini. В Chat Completions такого поля нет.
4. Отпечаток sha256 стабильного префикса разговора.
5. Идентификатор запроса, записанный как запасной вариант, а не как сессия.

Читаются только эти поля; GPROXY не ищет в произвольном JSON поле с именем `session_id`. Идентификаторы запросов, ходов и кэша, такие как `x-grok-req-id`, `user_prompt_id`, `prompt_cache_key` и `previous_response_id`, сессиями не считаются.

Заголовок шлюза никогда не передаётся вышестоящему сервису, в том числе если его прислал клиент: клиент не должен иметь возможности выбрать чужой разговор, отправив заголовок, которым шлюз обозначает разговоры. Запрос без заголовка сессии никогда не отклоняется.
