GPROXY работает с MCP-серверами (Model Context Protocol, streamable HTTP) так же, как с провайдерами моделей. Администратор экземпляра регистрирует сервер как провайдера; пользователи, команды и организации входят в него; после этого любой MCP-клиент обращается к серверу через GPROXY, имея только API-ключ шлюза. Клиент, который сам не умеет работать с OAuth, менять не нужно.

Шлюз понимает инструменты: перечисляет их, фильтрует по областям, направляет вызовы нужному серверу и записывает каждый вызов в аудит. Проксируются только инструменты; prompts и resources не проксируются.

## Регистрация сервера

Сервер — это провайдер, у которого `channel` равен `mcp`. В `GET /admin/api/channels` он отображается как «MCP server».

| Поле | Значение |
| --- | --- |
| `name` | Имя сервера. Оно входит в URL и служит префиксом имён инструментов, поэтому используйте только `[A-Za-z0-9_-]`. |
| `baseUrl` | MCP-эндпоинт сервера, например `https://mcp.deepwiki.com/mcp`. Обязательно. |
| `config.headers` | Необязательно. Объект с фиксированными заголовками, которые отправляются в каждом запросе, например `{"X-Tenant":"acme"}`. |
| `config.auth_header` | Необязательно. Заголовок, в котором вставленный секрет отправляется как есть. Если он не задан, секрет отправляется как `Authorization: Bearer <secret>`. |

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/providers \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"deepwiki","channel":"mcp",
       "baseUrl":"https://mcp.deepwiki.com/mcp"}'
```

Прокси и профиль подключения провайдера действуют так же, как для любого провайдера. Модели, маршруты, правила операций и правила перезаписи к MCP-серверу не применяются.

## Вход

Учётные данные MCP-сервера бывают трёх видов:

| Вид | Секрет | Назначение |
| --- | --- | --- |
| `oauth` | Получается при входе | Серверы, требующие OAuth |
| `api_key` | `{"api_key": "..."}` | Секрет, который вы вставляете вручную |
| `none` | `{}` | Серверы без аутентификации |

OAuth использует тот же вход по коду авторизации, что и остальные учётные данные: `POST /admin/api/credential-login/authcode/start`, затем `/complete`. См. [Получение учётных данных через вход](/ru/guides/providers#получение-учётных-данных-через-вход). GPROXY находит сервер авторизации по метаданным защищённого ресурса (RFC 9728, в том числе из запроса `WWW-Authenticate`) и метаданным сервера авторизации (RFC 8414 или OIDC), регистрируется динамически (RFC 7591) и использует PKCE S256 и параметр `resource` (RFC 8707). Токен обновляется до истечения срока действия и ещё один раз после ответа `401`.

После подтверждения браузер переходит на `http://127.0.0.1:47821/callback`. По этому адресу ничего не слушает, поэтому страница не откроется; скопируйте адрес из адресной строки и вставьте его в диалог.

<Warning>
Если сервер авторизации не поддерживает динамическую регистрацию клиентов, войти на такой сервер через OAuth в этой версии нельзя.
</Warning>

### Кто может использовать сервер

Вызывающий может использовать сервер, только если его ключу видны действующие учётные данные этого провайдера. Это обычное правило [видимости учётных данных](/ru/guides/permissions#видимость-учётных-данных): всё решает привязка ключа.

Если видно несколько учётных данных, сначала выбираются собственные учётные данные вызывающего, затем учётные данные его команды, затем организации, затем общие. Сеанс сохраняет те учётные данные, с которыми он начался.

## Два адреса

| Адрес | Что он обслуживает |
| --- | --- |
| `https://<gproxy>/connect/mcp/<name>` | Один сервер. Инструменты сохраняют свои имена. `https://<gproxy>/<name>/connect/mcp` — тот же адрес. |
| `https://<gproxy>/connect/mcp` | Все серверы, доступные вызывающему, в агрегированном виде. `?servers=a,b` сужает набор. |

На агрегированном адресе инструмент называется `<server>__<tool>`. Имя длиннее 64 символов или с символами вне `[A-Za-z0-9_-]` там не предлагается; обращайтесь к такому инструменту по адресу самого сервера.

## Настройка клиента

Клиенту нужны только URL и ключ шлюза: транспорт — streamable HTTP, ключ передаётся как `Authorization: Bearer <key>` или в `x-api-key`.

Claude Code:

```sh
claude mcp add --transport http deepwiki https://gproxy.example/connect/mcp/deepwiki \
  --header "Authorization: Bearer sk-..."
```

Codex, в `~/.codex/config.toml`:

```toml
[mcp_servers.deepwiki]
url = "https://gproxy.example/connect/mcp/deepwiki"
bearer_token_env_var = "GPROXY_API_KEY"
```

Клиенту, который входит в GPROXY через OAuth, а не по ключу, нужен токен с областью OAuth `gproxy:mcp`.

## Области

MCP разрешён по умолчанию: пользователь или ключ без правил MCP может использовать любой сервер, учётные данные которого ему видны. [Правила разрешений](/ru/guides/permissions#правила-разрешений) для моделей к MCP не применяются.

У правила есть субъект, область, действие и приоритет. Субъект — один пользователь или один API-ключ, но не оба сразу.

### Синтаксис областей

| Область | Что охватывает |
| --- | --- |
| `mcp:*` | Всё |
| `mcp:<server>:*` | Все инструменты одного сервера |
| `mcp:<server>:<tool>` | Один инструмент |
| `mcp:*:<tool>` | Инструмент с таким именем на любом сервере |
| `mcp:<server>:@read` | Инструменты сервера с характером `read` |
| `mcp:<server>:@write` | Инструменты сервера с характером `write` |
| `mcp:<server>:@destructive` | Инструменты сервера с характером `destructive` |

`*` заменяет всю часть с сервером или всю часть с инструментом; внутри имени это не шаблон. В формах с характером сервером тоже может быть `*`: `mcp:*:@destructive`.

### Порядок оценки

- Субъекту без правил разрешено всё.
- Иначе правила проверяются от высшего приоритета к низшему, и решает первое подходящее. При равном приоритете побеждает `deny`.
- Инструмент, которому не подошло ни одно правило, запрещён.
- Правила ключа только сужают правила его пользователя: сначала оцениваются правила пользователя, затем правила ключа, и разрешить должны оба набора.
- Правила действуют для всех вызывающих, включая администраторов экземпляра.

Инструмент, который вызывающему нельзя вызывать, не попадает в список инструментов, а его вызов возвращает «Unknown tool».

### Примеры

Только чтение на одном сервере и больше ничего:

| Область | Действие | Приоритет |
| --- | --- | --- |
| `mcp:deepwiki:@read` | `allow` | 0 |

Всё, кроме разрушительных инструментов:

| Область | Действие | Приоритет |
| --- | --- | --- |
| `mcp:*` | `allow` | 0 |
| `mcp:*:@destructive` | `deny` | 10 |

Один сервер без одного инструмента:

| Область | Действие | Приоритет |
| --- | --- | --- |
| `mcp:notion:*` | `allow` | 0 |
| `mcp:notion:delete_page` | `deny` | 10 |

### Управление правилами

Правила — это семейство `mcp-scopes` API управления, доступное администраторам экземпляра: список, создание, пакетная операция, а также чтение, изменение и удаление по ID в `/admin/api/mcp-scopes`. Список принимает `userId`, `apiKeyId`, `ownerUserId`, `search`, `page` и `pageSize`.

| Поле API | Значение |
| --- | --- |
| `userId` / `apiKeyId` | Субъект: ровно одно из двух полей. Изменить его потом нельзя. |
| `scope` | Область в описанном выше синтаксисе |
| `action` | `allow` или `deny` |
| `priority` | Большие значения проверяются первыми; по умолчанию `0` |

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/mcp-scopes \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"userId":"<user id>","scope":"mcp:deepwiki:@read","action":"allow"}'
```

## Характер инструмента

Каждый инструмент имеет характер `read`, `write` или `destructive`. Он определяется по аннотациям MCP с консервативными значениями по умолчанию из спецификации:

| Аннотации | Характер |
| --- | --- |
| `readOnlyHint: true` | `read` |
| иначе `destructiveHint: false` | `write`: что-то изменяет, но не разрушает |
| иначе | `destructive` |

Поэтому инструмент, который ничего не объявил, считается `destructive`.

Администратор может переопределить характер инструмента. Список инструментов, который получают вызывающие, содержит подсказки, соответствующие итоговому характеру. Переопределения — это семейство `mcp-tool-natures` (`/admin/api/mcp-tool-natures`) с полями `providerId`, `tool` и `nature`; после создания изменить можно только `nature`.

`GET /admin/api/mcp-tools/{providerId}` возвращает инструменты сервера с объявленным характером, действующим характером и ID переопределения, если оно есть. Запрос обращается к серверу напрямую, поэтому провайдеру нужны базовый URL и действующие учётные данные; если сервер недоступен, ответ — `502`.

## Аудит

Каждый вызов инструмента создаёт одну запись в журнале аудита с действием `mcp.tools.call`:

```text
GET /admin/api/audit?action=mcp.tools.call
```

| Поле | Содержимое |
| --- | --- |
| `actorUserId`, `actorApiKeyId`, `sourceIp` | Кто вызвал |
| `entityKind`, `entityId` | `provider` и ID провайдера сервера |
| `outcome` | `ok` или `error` |
| `detail.server`, `detail.tool` | Имя сервера и инструмент |
| `detail.credentialId` | Использованные учётные данные или `null` |
| `detail.durationMs` | Длительность вызова |
| `detail.outcome` | `ok`, `tool_error`, `input_required`, `refused` или `failed` |
| `detail.arguments`, `detail.result` | Присутствуют, только когда включено журналирование тел нисходящих запросов (настройка `enableDownstreamLogBody`). Поля с чувствительными именами скрываются. |

См. [Использование, журналы и аудит](/ru/guides/observability).

## Поведение протокола и ограничения

- С клиентами GPROXY работает по ревизии MCP 2026-07-28 (без состояния, без `initialize`) и по сеансовым ревизиям с 2024-11-05 по 2025-11-25.
- С серверами он предпочитает 2026-07-28, а иначе переходит на `initialize` и сеанс; так сегодня работают DeepWiki, Notion и другие серверы (2025-11-25).
- Для сеансового сервера соответствие «сеанс вызывающего → сеанс сервера и учётные данные» хранится долговременно, поэтому продолжить сеанс может любой экземпляр.
- Каждый ответ — одно тело JSON. Потока SSE в сторону клиентов и потока GET нет, уведомления о ходе выполнения отбрасываются.
- Запросы по инициативе сервера (sampling, elicitation) работают только в виде результатов `input_required`, когда и клиент, и сервер используют 2026-07-28; они передаются без изменений. Сеансовый сервер открывается без клиентских возможностей и запрашивать ничего не может.
- Если сервер отвечает `401`, GPROXY один раз обновляет учётные данные и повторяет запрос. Если сервер снова отказывает, клиент получает обычный ответ `502` с ошибкой JSON-RPC. Заголовок `WWW-Authenticate` сервера никогда не пересылается, поэтому клиент не начинает OAuth с сервером сам.
- Список инструментов сервера кэшируется на 5 минут, отдельно для каждого сервера и учётных данных. Добавленный или удалённый сервером инструмент может появиться или исчезнуть с такой задержкой.
- Prompts и resources не проксируются.
