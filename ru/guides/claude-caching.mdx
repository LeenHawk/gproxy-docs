Здесь описано, как GPROXY расставляет маркеры кэша промптов для провайдеров
Claude и OpenAI — с помощью правил точек кэширования или магических строк в
тексте промпта, — и как учитываются и тарифицируются кэшированные токены.

Само кэширование выполняет провайдер. Будет ли попадание, зависит от модели,
префикса промпта и TTL. Маркер не гарантирует попадания и не добавляет
кэширование провайдеру, который его не поддерживает.

## Правила точек кэширования

На странице **Правила перезаписи** провайдера добавьте правило типа
**Точка кэширования**. Выберите протокол провайдера и цель: глобальную,
системную или сообщение, а для Claude также инструменты. Для локальной цели
можно указать индекс: положительные индексы начинаются с 1, отрицательные
отсчитываются с конца, пустой индекс выбирает последнюю доступную позицию.

Для Claude доступны TTL по умолчанию, 5 минут и 1 час. Для локальных точек
OpenAI — по умолчанию, 30 минут и 12 часов; для глобальных правил OpenAI — по
умолчанию и 30 минут. Как TTL действует на самом деле, решает провайдер.
Протокол в правиле — это протокол после преобразования. Gemini этим типом
правил не поддерживается.

В API используйте `action: "cache_breakpoint"` и строку конфигурации в
кодировке JSON в `replacement`, например:

```json
{"dialect":"claude","target":"message","index":-1,"ttl":"5m"}
```

```json
{"dialect":"openai","target":"message","index":-1,"ttl":"12h"}
```

Правило применяется к телу запроса в общем порядке
[правил перезаписи](/ru/guides/rules). Если в теле уже четыре маркера, оно
ничего не добавляет — это тот же предел, что и для магических строк ниже.
Клиенты, которые умеют сами задавать нативные поля кэша, могут отправлять поля
провайдера напрямую.

## Магические строки

Клиент без управления кэшем может вставить в текст промпта одну из следующих
строк. Если у провайдера включён magic cache для целевого протокола, GPROXY
удаляет строку и ставит на её месте точку кэширования.

```text
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_7D9ASD7A98SD7A9S8D79ASC98A7FNKJBVV80SCMSHDSIUCH
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_49VA1S5V19GR4G89W2V695G9W9GV52W95V198WV5W2FC9DF
GPROXY_MAGIC_STRING_TRIGGER_CACHING_CREATE_1FAS5GV9R5H29T5Y2J9584K6O95M2NBVW52C95CX984FRJY
```

| Строка | Для цели Claude | Для цели OpenAI |
| --- | --- | --- |
| …`7D9ASD…` | `cache_control` с TTL API по умолчанию | явная точка кэширования |
| …`49VA1S…` | `cache_control` с `"ttl": "5m"` | `prompt_cache_breakpoint` (`"ttl": "30m"`) |
| …`1FAS5G…` | `cache_control` с `"ttl": "1h"` | `prompt_cache_breakpoint` (`"ttl": "12h"`) |

Одна и та же строка выбирает короткое или длинное хранение в зависимости от
целевого протокола: `5m` и `1h` у Claude соответствуют `30m` и `12h` у OpenAI.
Строка по умолчанию TTL не задаёт. TTL записывается на саму точку кэширования;
параметры кэша всего запроса не меняются.

Строки входят в протокол между клиентом и GPROXY и не меняются от выпуска к
выпуску.

### Включение magic cache

В `config` провайдера есть два переключателя, по одному на семейство
протоколов:

```json
{ "config": { "enable_claude_magic_cache": true,
              "enable_openai_magic_cache": true } }
```

| Переключатель | Каналы, которые его предлагают |
| --- | --- |
| `enable_claude_magic_cache` | `aws_bedrock`, `azure`, `claudeapi`, `claudecode`, `custom`, `opencodego`, `opencodezen`, `openrouter`, `vercel` |
| `enable_openai_magic_cache` | `aws_bedrock`, `azure`, `openai`, `codex`, `custom`, `opencodego`, `opencodezen`, `openrouter`, `vercel` |

В консоли они называются **Включить magic cache для Claude** и
**Включить magic cache для OpenAI**.

Действует переключатель целевого протокола, а не протокола клиента. Запрос от
клиента в формате OpenAI, направленный провайдеру Claude, сначала
преобразуется в Claude Messages, поэтому решает переключатель Claude, а
записывается маркер `cache_control`. Клиент по-прежнему получает ответы в
своём формате.

### Удаление строк

Каналы из таблицы выше всегда удаляют эти строки, независимо от того, включён
ли magic cache: оставшийся в промпте маркер провайдеру ни к чему.

Переключатель решает только, ставить ли точку кэширования на месте строки. При
выключенном magic cache строки удаляются, а всё остальное не меняется:
собственные `cache_control` или `prompt_cache_breakpoint` клиента остаются как
есть, а тело без строк пересылается байт в байт, без разбора и повторной
сериализации.

Канал `claudeweb` тоже только удаляет строки, ничего не ставя, потому что у
браузерной сессии нет управления кэшем.

## Куда ставятся маркеры

При включённом magic cache маркеры для магических строк ставятся так, в
зависимости от целевого протокола.

### Claude Messages

Сначала тело нормализуется: строковое содержимое превращается в массивы
блоков, пустые текстовые блоки удаляются, а `cache_control` с удалённого блока
переносится на ближайший кэшируемый блок. Благодаря этому работает строка,
стоящая на отдельной строке текста. Блоки thinking сохраняются только в ходах
assistant.

Затем `system` обрабатывается раньше `messages`, так что лимит точек
расходуется в порядке промпта, а не в порядке ключей JSON. Каждый текстовый
блок, содержащий строку, получает маркер:

```json
{ "cache_control": { "type": "ephemeral", "ttl": "1h" } }
```

Блок, у которого уже есть `cache_control`, не трогается.

### OpenAI Chat Completions

Маркер можно поставить на любое сообщение, кроме сообщений с ролью `function`.
Строковое `content` разбивается на отмеченную часть `text`, потому что маркеру
нужна часть, на которой он будет стоять; в массиве `content` части отмечаются на
месте.

```json
{ "type": "text", "text": "…", "prompt_cache_breakpoint": { "mode": "explicit" } }
```

### OpenAI Responses

Маркеры ставятся в трёх местах, в таком порядке:

1. `instructions`. Найденная там строка удаляется, а в начало `input`
   вставляется отмеченное сообщение developer, потому что `instructions` —
   обычная строка и не может нести маркер.
2. `prompt.variables` — так же, как части в Chat.
3. `input`. Простая строка превращается в одно отмеченное сообщение user; в
   массиве элементов `content` и `output` отмечаются через типы `input_text` и
   `output_text`.

### Gemini

У Gemini нет точек кэширования. Строки удаляются, больше ничего не происходит.

## Предел в четыре точки

Из прокси уходит не больше четырёх точек кэширования, включая поставленные
самим клиентом. Доступный лимит — это четыре минус число маркеров, уже
имеющихся в теле, поэтому клиенту, поставившему три своих, остаётся одна.

Строки сверх предела всё равно удаляются, просто маркерами они не становятся.

## Нативные поля кэша при преобразовании протоколов

При преобразовании между Claude и OpenAI Chat/Responses нативные поля кэша
переносятся в обе стороны с тем же соответствием TTL. Отмеченные системные
блоки, сообщения, изображения или документы и результаты инструментов
сохраняют свои границы. Политика автоматического кэширования Claude
превращается в явную точку на соответствующем последнем блоке, если у этого
блока есть представление в целевом протоколе. Маркеры отдельных определений
инструментов, у которых нет аналога в OpenAI, перечисляются в отчёте о
преобразовании.

При преобразовании из OpenAI в Claude верхнеуровневый `cache_control` создаёт
только явно переданный `prompt_cache_options.mode: "implicit"`. Если объект
параметров или его `mode` опущен (в том числе пустой объект или только TTL),
автоматическое кэширование Claude не включается. Явные маркеры на блоках
преобразуются независимо от этого.

Явные точки кэширования OpenAI Responses и Chat принимают
`prompt_cache_breakpoint: {"mode":"explicit","ttl":"12h"}` (или `"30m"`), и
TTL сохраняется при преобразовании между Chat и Responses. Текущая
[схема OpenAPI](https://github.com/openai/openai-openapi/blob/master/openapi.json)
по-прежнему допускает для `prompt_cache_options.ttl` всего запроса только
`"30m"`. `prompt_cache_retention` — отдельная, более старая политика.

## Использование и стоимость

Кэшированные токены учитываются как отдельные метрики и тарифицируются по
вашим строкам тарифов:

| Что сообщает провайдер | Метрика |
| --- | --- |
| чтение из кэша | `cached_input_tokens` |
| запись в кэш с известным сроком хранения | `cache_creation_tokens` + `ttl_seconds` |
| запись в кэш с неизвестным сроком хранения | `cache_creation_tokens` |

Все записи в кэш используют `cache_creation_tokens`. Условие тарифа вроде
`{"ttl_seconds":43200}` выбирает цену 12-часовой записи; тариф без условия
служит резервной ценой. Каждая сообщённая группа записей тарифицируется
отдельно. Чтения из кэша — это единый счётчик `cached_input_tokens` без TTL.
Переопределения уровней используют
`cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]`, где запись с
`ttlSeconds: null` — резервная. Цены указываются за миллион токенов; TTL на них
не умножается.

Использование одного вызова у OpenAI сообщает только общий
`cache_write_tokens`, поэтому GPROXY записывает TTL этих записей как
неизвестный и не пытается угадать, как они делятся между точками с разными
TTL.

`cached_input_tokens` ограничен значением `input_tokens`. Некэшированный
остаток тарифицируется по цене ввода, кэшированная часть — по цене чтения из
кэша; если цены чтения нет, используется цена ввода. Записи в кэш без
собственного тарифа ничего не стоят. См.
[Цены и уровни тарификации](/ru/reference/pricing).

Счётчики токенов в записи использования необязательны: если провайдер не
сообщил поле, это не значит, что он намерил ноль. Итоги же — обычные числа,
потому что сумма по несообщённым полям действительно равна нулю.

## Как избежать промахов кэша

Правила перезаписи выполняются после преобразования протокола и до отправки
запроса каналом, поэтому правило, меняющее текст промпта, может превратить
ожидаемое попадание в промах. Ставьте стабильное содержимое первым, маркер —
после него, а всё, что меняется от запроса к запросу, — за этой границей.
Проверьте, что ни одно правило перезаписи с широким селектором `paths` не
правит кэшируемый префикс.
