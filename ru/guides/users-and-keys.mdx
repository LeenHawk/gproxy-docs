На этой странице описаны учётные записи, которые работают с GPROXY, и API-ключи шлюза, с которыми они вызывают модели: первый администратор, пользователи, организации и команды, а также создание, передача, ротация и отзыв ключей.

<VideoTutorial topic="users" locale="ru" title="Видеоруководство по пользователям и ключам API" />

В GPROXY есть два способа входа. Люди входят в консоль по имени пользователя и паролю. Клиенты вызывают модели с API-ключом шлюза. Учётные данные вышестоящих сервисов принадлежат провайдерам: они используются только при обращении к вышестоящему сервису и не позволяют войти в GPROXY.

## Первый администратор

Приложение создаёт администратора в мастере первого запуска.

CLI создаёт администратора при запуске на пустом экземпляре и выводит сгенерированные пароль и API-ключ. Чтобы задать их самостоятельно, установите эти переменные до первого запуска:

```sh
export GPROXY_ADMIN_USER='admin'
export GPROXY_ADMIN_PASSWORD='your-initial-password'
export GPROXY_BOOTSTRAP_ADMIN_API_KEY='your-initial-gateway-key'
./gproxy serve
```

На новом экземпляре любую из переменных пароля и ключа можно не задавать; недостающие значения будут сгенерированы. `GPROXY_BOOTSTRAP_ADMIN_API_KEY` читается только при первой инициализации.

<Warning>
`GPROXY_ADMIN_PASSWORD` применяется при каждом запуске, а не только при первом. Если существует пользователь с именем `GPROXY_ADMIN_USER`, его пароль заменяется этим значением. Если пользователя с таким именем нет, восстанавливается встроенный администратор `0`: он переименовывается, снова включается с ролью `admin`, получает этот пароль, а его текущие сеансы в консоли завершаются. Удалите переменную, когда она больше не нужна, иначе перезапуск отменит пароль, изменённый в консоли.
</Warning>

Провайдеры добавляются в консоли. Старая переменная `GPROXY_BOOTSTRAP_CHANNELS` их больше не создаёт.

Пользователи CLI и контейнера входят по адресу `/console/`. Личные страницы и страницы управления используют один сеанс, который хранится в HTTP-cookie `gproxy_session`; срок его действия задаёт `session_ttl_secs`. В приложении вместо этого используется встроенная консоль.

## Пользователи, организации и команды

Администраторы экземпляра создают пользователей в разделе **Пользователи и команды → Пользователи**. У каждого пользователя роль `admin` или `user`. Пользователь без пароля не может войти в консоль, но может пользоваться выданными ему API-ключами в пределах своих разрешений.

Организации и команды распределяют пользователей по группам через членство, и у каждого членства есть роль внутри группы. Администраторы организаций и команд управляют только тем, что доступно в их области; администраторами экземпляра они не являются. Что доступно в каждой области, описано в разделе [Консоль и администрирование по областям](/ru/guides/console).

Ключ можно привязать к организации или команде. Привязка определяет, какие общие учётные данные доступны ключу и с бюджетов каких групп списывается его стоимость. Привязка хранится в самом ключе: клиент не может изменить её, отправив заголовки организации или команды.

## Создание ключа

Пользователи управляют своими ключами в разделе **Ваши ключи** в представлении **Личный кабинет** консоли. Администраторы экземпляра могут управлять ключами любого пользователя в разделе **Управление доступом → Ключи пользователей**.

У ключа есть следующие настройки:

- **Название**: обозначает приложение или устройство, которое использует ключ.
- Владелец: пользователь и, при необходимости, организация или команда, к которой привязан ключ.
- **Истекает** и **Включено**: истёкший или отключённый ключ не может выполнять новые запросы.
- **Доступ к управлению**: разрешает ключу вызывать API управления в пределах разрешений его пользователя и области. По умолчанию выключен; включает его администратор в разделе **Ключи пользователей**.
- **Хранить секрет**: сохраняет ключ целиком, чтобы его можно было показать позже. По умолчанию выключено, выбирается только при создании ключа.
- **Бюджет расходов**: администраторы могут задать для ключа сумму, период и фильтр моделей.

Скопируйте ключ целиком, когда он показан после создания. Ключ, секрет которого не сохранялся, повторно показать нельзя; это относится и к ключам, импортированным из другого экземпляра только в виде дайджестов. Для показа сохранённого ключа также нужно соответствующее разрешение.

Новый ключ и его начальный бюджет сохраняются вместе. Если бюджет не проходит проверку, ключ тоже не создаётся.

## Передача ключа

```text
Authorization: Bearer <gateway-key>
x-api-key: <gateway-key>
x-goog-api-key: <gateway-key>
```

Используйте заголовок, привычный для протокола вашего клиента, и передавайте только один ключ. Если присутствует несколько таких заголовков, первым читается `Authorization`, затем `x-api-key`, затем `x-goog-api-key`.

Для вызовов API управления нужен ключ с доступом к управлению. Обычный ключ для инференса не получает доступа к управлению оттого, что его пользователь — администратор.

## Ротация и отзыв ключа

При ротации ключ получает новое значение. Старое значение сразу перестаёт работать, поэтому все клиенты, которые его используют, нужно обновить. Чтобы переводить клиентов по одному, вместо ротации создайте второй ключ, переключите клиентов, а затем отключите или удалите старый ключ.

В API управления есть те же операции:

- `POST /admin/api/api-keys/{id}/rotate`: перевыпустить ключ.
- `GET /admin/api/api-keys/{id}/secret`: показать сохранённый секрет.
- В личном API им соответствуют `/portal/api/keys/{id}/rotate` и `/portal/api/keys/{id}/secret`.

Отзыв вступает в силу сразу на том экземпляре, который его записал. Другие экземпляры в многоэкземплярном развёртывании проверяют аутентификацию по снимку в памяти и перестают принимать ключ, когда перезагружают его: в течение миллисекунд через инвалидацию общего кэша, а если это сообщение потеряется, то не позднее чем через 30 секунд при опросе ревизии. См. [Архитектура](/ru/development/architecture).

Исключение участника из организации или команды в той же транзакции отключает ключи этого пользователя, привязанные к ней, включая внутренние ключи OAuth.

## Сеансы OAuth

GPROXY может работать как сервер авторизации OAuth: клиент просит пользователя выдать ему доступ и получает токен доступа. За каждым выданным доступом стоит внутренний ключ. Внутренние ключи не являются обычными пользовательскими ключами: их нельзя создать вручную, показать или использовать как Bearer-ключ.

Пользователи видят и отзывают авторизованные ими программы в разделе **Учётная запись → Авторизованные приложения**. Вывод клиента из использования в разделе **Управление доступом → OAuth-клиенты** отзывает выданные ему доступы и токены.

Настройка клиентов и процесс авторизации описаны в разделе [CLI-клиенты](/ru/guides/cli-clients). Области и операции, доступные токену OAuth, перечислены в разделе [Разрешения, лимиты запросов и бюджеты](/ru/guides/permissions#токены-доступа-oauth).
