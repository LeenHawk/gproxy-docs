Правила перезаписи изменяют запрос по пути к провайдеру или ответ по пути
обратно: добавляют системный текст, расставляют точки кэширования, правят поля
JSON, заменяют текст и задают заголовки. Последний раздел страницы посвящён
переопределению протоколов и конечных точек — тому, какой протокол и URL
провайдер использует для операции.

## Добавление правила

Откройте страницу **Правила перезаписи** провайдера, добавьте правило,
выберите его тип и заполните параметры. Каждый новый провайдер получает
одноимённый набор правил по умолчанию, уже привязанный к нему, поэтому для
одного провайдера управлять привязками не нужно. Расширенные настройки привязки
нужны, когда один набор правил должны использовать несколько провайдеров.

| Тип в консоли | Назначение | `action` в API |
| --- | --- | --- |
| Системный текст | Добавить текст в начало или конец системных инструкций | `system_text` |
| Точка кэширования | Добавить маркеры кэша для протокола: глобальный, системный, сообщения или инструмента | `cache_breakpoint` |
| Перезапись | Установить или удалить поле либо объединить объект | `set`, `delete`, `merge` |
| Преобразование | Применить регулярное выражение к тексту тела, заголовкам или параметрам запроса | `replace` |
| Заголовок запроса | Установить значение или объединить значения через запятую | `header_set`, `header_merge` |

Системный текст поддерживается для Claude, OpenAI Chat, Responses (включая
WebSocket) и Gemini. Точки кэширования поддерживаются для форматов Claude и
OpenAI; позиции и TTL описаны в разделе
[Кэширование промптов](/ru/guides/claude-caching).

У каждого правила есть `phase` (`request`, `response` или `both`) и `target`
(`body`, `header` или `query`).

## Порядок выполнения

Запрос сначала преобразуется в протокол провайдера, затем выполняются правила
запроса, и только потом канал отправляет его. Ответ сначала проходит через
правила ответа и лишь затем преобразуется обратно в протокол клиента. Поэтому
пути в правилах указываются в формате провайдера. Например, если запрос OpenAI
Chat направлен провайдеру Claude, правила запроса уже видят поля Claude
`system` и `messages`.

Включённые привязки наборов правил выполняются в порядке `sortOrder`, затем по
ID; так же упорядочены включённые правила внутри каждого набора. Каждое правило
видит результат предыдущего. Правила системного текста и точек кэширования
упорядочиваются так же, как все остальные.

## Пути, регулярные выражения и заголовки

Правкам JSON нужен путь, например `temperature` или `messages.*.content`;
сегмент `*` выбирает все элементы. `set` принимает любое корректное значение
JSON, `merge` — объект JSON, а `delete` значения не требует.

Преобразования используют регулярные выражения Rust, включая `(?i)`, `(?s)`, а
также `$1` и `${name}` в замене. С путями по телу замена выполняется внутри
выбранных строковых значений JSON. Без путей обрабатывается весь текст тела,
поэтому следите, чтобы результат оставался корректным JSON.

Правилам для заголовков и параметров запроса нужен `targetName`. `header_set`
заменяет значение заголовка. `header_merge` объединяет значения, разделённые
запятыми, и убирает повторы. Не храните секреты провайдеров в правилах, общих
для нескольких провайдеров.

## Фильтры

Фильтры ограничивают, когда выполняется правило. Правило срабатывает, только
если совпадают все заданные фильтры; незаданный фильтр ничего не ограничивает.

| Фильтр | Поле API | Что сопоставляется |
| --- | --- | --- |
| Операция и протокол | `filterOperationKeys` | Преобразованная операция, выполняемая у провайдера |
| Модель | `filterModelPattern` | Имя модели у провайдера или запрошенное имя, с подстановками `*` и `?` |
| Заголовки запроса | `filterHeaderPattern` | Регулярное выражение, проверяемое по каждому входящему заголовку в виде `name: value` |
| Событие потока | `filterEventPattern` | Имя события SSE или JSON `type`, для правил тела |

Правила совместимости для конкретного клиента ограничивайте фильтром по
заголовкам запроса, чтобы они не затрагивали других клиентов.

Подсказки фильтра модели берутся только из сохранённых моделей провайдеров и
их вариантов. На странице провайдера показываются модели этого провайдера; на
отдельной странице набора правил — объединение моделей привязанных
провайдеров. У набора без привязанных провайдеров подсказок нет, но можно
ввести имя модели или шаблон вроде `gpt-*`. Подсказки никогда не запрашивают
каталоги моделей у провайдеров.

## Условия по телу и заголовкам

`filterBody` и `filterHeader` запускают правило, только когда поле тела или
заголовок запроса имеет определённое значение. Их можно использовать по
отдельности или вместе; оба должны совпасть вместе со всеми остальными
фильтрами:

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "service_tier"
  ],
  "pattern": "",
  "replacement": "\"priority\"",
  "filterBody": {
    "path": "reasoning.effort",
    "op": "eq",
    "value": "high"
  },
  "filterHeader": {
    "name": "x-client-mode",
    "op": "eq",
    "value": "fast"
  }
}
```

`filterBody` читает текущее тело JSON, включая изменения предыдущих правил, и
поддерживается только для целей типа тело. Путь состоит из ключей и индексов
массивов через точку, например `reasoning.effort` или `messages.0.role`, без
подстановок. Сравнение учитывает типы JSON: `"1"` не равно `1`, а
отсутствующее поле — не то же самое, что `null`. Тело, не являющееся корректным
JSON, не удовлетворяет ни одному условию по телу, даже `not_exists`.

`filterHeader` читает исходные входящие заголовки запроса и работает для любой
цели и фазы. Имена заголовков не зависят от регистра. Значения сравниваются как
точные строки с учётом регистра и не разбиваются по запятым. Если заголовок
повторяется, `eq` срабатывает при совпадении любого значения, а `ne` требует,
чтобы заголовок присутствовал и ни одно значение не совпадало.

Операторы: `eq`, `ne`, `exists` и `not_exists`. Для `eq` и `ne` нужен
`value`; `exists` и `not_exists` его не принимают. Отсутствующее поле не
удовлетворяет `ne`.

В потоке условия проверяются отдельно для каждого полного события SSE, записи
NDJSON, элемента JSON-массива или сообщения WebSocket, без состояния между
ними; обычное тело HTTP проверяется целиком. Чтобы убрать условие, очистите его
в форме или передайте `null` в поле API. PATCH без этого поля сохраняет
существующее условие.

### Выражения JMESPath

`filterBody` также принимает выражение JMESPath в виде строки. Оно вычисляется
над текущим телом, и действие выполняется, только если результат — логическое
`true`. Ошибки типов, неизвестные функции, прочие ошибки вычисления и
нелогические результаты считаются несовпадением. Синтаксис проверяется при
сохранении правила. Объектная форма `{ "path", "op", "value" }` по-прежнему
поддерживается.

Это правило устанавливает `max_tokens` в 0, только если текстовый блок
последнего сообщения содержит маркер keepalive; маркер в более раннем
сообщении правило не запускает:

```json
{
  "action": "set",
  "phase": "request",
  "target": "body",
  "paths": [
    "max_tokens"
  ],
  "replacement": "0",
  "filterBody": "length(messages[-1].content[?type(text) == 'string' && contains(text, '[cache-keepalive]')]) > `0`"
}
```

Отрицательные индексы вроде `[-1]`, проекции, `contains()`, сравнения и
логические операции работают по
[спецификации JMESPath](https://jmespath.org/specification.html).
Отсутствующие поля дают `null`, и это можно проверить явно; тела не в формате
JSON никогда не совпадают. `paths` действия по-прежнему используют описанный
выше синтаксис путей через точку, независимо от выражения.

Выражения компилируются один раз. Пока тело не меняется, все выражения
используют один преобразованный документ JMESPath; если предыдущее правило
действительно изменило тело, документ строится заново, чтобы никто не увидел
устаревшие значения. Правила без выражений эту дополнительную копию не
создают. Каждая единица потока проверяется отдельно, а запрос, обходящий весь
документ, по-прежнему занимает время, пропорциональное его размеру.

## Потоковые ответы

Перезапись тела работает с полными событиями, например событием SSE или
элементом JSON-массива, а не с сетевыми фрагментами. Событие больше
`settings.maxStreamEventBytes` приводит к ошибке. Чтобы перезаписывать только
определённые типы событий, используйте фильтр событий.

## Редактирование правила в JSON

При создании или изменении правила в наборе или на странице
**Правила перезаписи** провайдера выберите **Редактор JSON** и вставьте один
объект правила v4. Можно переключаться между формой и JSON и форматировать
JSON. Некорректный ввод остаётся в редакторе с сообщением об ошибке, а при
сохранении дополнительно проверяется, что правило может выполняться.

Например, чтобы заменить в теле `"type":"function"}` на
`"type":"function","strict":false}`:

```json
{
  "action": "replace",
  "phase": "request",
  "target": "body",
  "pattern": "\"type\":\"function\"\\}",
  "replacement": "\"type\":\"function\",\"strict\":false}"
}
```

Используйте поля v4 `action`, `pattern` и `replacement`. Набор правил, ID и
порядок задаёт страница, поэтому их в JSON не указывают. Можно добавить
необязательные фильтры и `enabled`; пропущенные фильтры ничего не ограничивают,
а `enabled` по умолчанию равно true. Редактор принимает один объект правила, а
не массив.

## Управление через API

Этот пример заменяет `widget` на `gadget` в выбранных строках. Подставьте ID
своего набора правил.

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"ruleSetId":"your-rule-set-id","action":"replace",
       "phase":"request","target":"body","paths":["messages.*.content"],
       "pattern":"(?i)\\bwidget\\b","replacement":"gadget",
       "filterOperationKeys":[{"operation":"generate_content","dialect":"openai_chat"}]}'
```

`PUT /admin/api/rule-sets/{id}/rules` заменяет весь список правил набора. Для
системного текста и точек кэширования `replacement` содержит строку
конфигурации в кодировке JSON; консоль формирует её сама.

## Пресеты совместимости

`GET /admin/api/rule-presets` возвращает встроенные пресеты OpenCode, pi-mono,
Aider, Cline, Continue и Cursor. Точный состав правил каждого
пресета смотрите в ответе этой конечной точки.

<Warning>
`POST /admin/api/rule-sets/{id}/rule-presets/{preset}` заменяет все
существующие правила набора. Чтобы их сохранить, сначала прочитайте или
экспортируйте их и сохраните объединённый список.
</Warning>

## Переопределение протокола и конечной точки

**Правила маршрутизации** провайдера определяют, какой протокол провайдера
используется для операции. Это отдельная настройка от маршрутов моделей,
которые выбирают провайдера.

- `operation_rules` переопределяет список протоколов провайдера для операции.
  Если протокол клиента есть в списке, запрос проходит без преобразования;
  иначе он преобразуется в первый протокол списка.
- `operation_endpoints` переопределяет полный URL конечной точки для операции,
  протокола и транспорта.

Например, чтобы изменить протоколы для генерации:

```sh
curl -sS -X POST http://127.0.0.1:8787/admin/api/operation-rules \
  -H "Authorization: Bearer $GPROXY_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"providerId":"your-provider-id","operation":"generate_content",
       "action":"dialects","target":["claude","openai_chat"]}'
```

Без переопределений действуют значения канала по умолчанию.
`POST /admin/api/providers/{id}/routing-defaults/reset` удаляет
переопределения операций и конечных точек провайдера.

Каналу `custom` дополнительно нужен список `dialects` в конфигурации
провайдера, например `["openai_chat", "openai"]`. Если операция не работает,
проверьте, поддерживает ли её провайдер, затем этот список и переопределения
операций.
