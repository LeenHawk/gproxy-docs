Здесь описано, как GPROXY превращает `model` из запроса клиента в провайдера,
учётные данные и имя модели у провайдера, и как настроить маршруты и каталог
моделей, от которых это зависит. Чтобы изменить параметры запроса, а не то,
куда он уйдёт, используйте [правила перезаписи](/ru/guides/rules).

## Разрешение имени модели

Имя модели, которое присылает клиент, обычно не совпадает с идентификатором
модели у провайдера. GPROXY разрешает его до того, как запрос попадает в
движок, поэтому движок всегда получает уже выбранную цель:

```text
request model
  → the first matching form: route name · provider/model
  → candidates, narrowed by channel, allowed providers, allowed credentials
  → ordered by (tier, health, descending weight, stable id)
  → the leading run balanced by the route's strategy
  → one (provider, credential, upstream model) per attempt
```

Имя сверяется со следующими формами по порядку; применяется первая подходящая:

| Имя | Во что разрешается | Бюджет попыток |
| --- | --- | --- |
| отсутствует | все включённые провайдеры, без модели провайдера | `settings.max_attempts` |
| имя маршрута модели | включённые элементы этого маршрута | собственный бюджет маршрута |
| `provider/model` | один этот провайдер | `settings.max_attempts` |
| что-либо другое | `404 unknown_model` | — |

Имена маршрутов сравниваются точно и проверяются раньше префиксной формы.
Отключённый маршрут не считается именем, и запрос к нему переходит к следующей
форме. Префикс в `provider/model` всегда является именем провайдера, а не
идентификатором канала: провайдер с именем `openai` на канале `codex`
вызывается как `openai/…`, так же как через его точку монтирования
`/openai/v1`.

Затем кандидаты сужаются по каналу точки монтирования, по провайдерам,
доступным ключу вызывающей стороны, и по учётным данным, которые ему разрешено
использовать. Если имя подошло к одной из форм, но после сужения не осталось ни
одной цели, возвращается `503 no_usable_target`. Это ошибка конфигурации (нет
включённых элементов, нет пригодных учётных данных или ключу не разрешён ни
один из них), поэтому она отличается от неизвестной модели.

На практике выдавайте клиентам в качестве имён моделей имена маршрутов.

## Создание маршрута

Маршрут — это публичное имя модели со списком элементов «провайдер/модель»,
стратегией балансировки и бюджетом попыток. После создания маршрута `main`
клиенты могут отправлять `model: "main"`.

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/routes \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"main","strategy":"round_robin","maxAttempts":6}'
```

```json
{"id":"33a88261f571347c7f0408c3bd2e2164","name":"main","strategy":"round_robin",
 "maxAttempts":6,"enabled":true}
```

| Поле | Значение |
| --- | --- |
| `name` | Глобально уникально. Клиенты отправляют именно это имя в `model`. |
| `sessionAffinity` | Повторно использовать успешную цель «провайдер/модель» в рамках сессии; по умолчанию выключено. Выбор учётных данных остаётся за провайдером. |
| `strategy` | `round_robin`, `weighted` или `failover`. |
| `maxAttempts` | Общий бюджет попыток, включая первый вызов; должен быть положительным. При выполнении его жёстко ограничивает `settings.maxAttempts` (по умолчанию 6). |

В консоли маршруты находятся в разделе **Маршруты моделей**.

## Добавление элементов

Каждый элемент направляет трафик одному провайдеру под одним именем модели:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/route-members \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"routeId":"…","providerId":"…","upstreamModel":"gpt-4o-mini",
       "tier":0,"weight":100}'
```

| Поле | Значение |
| --- | --- |
| `providerId`, `upstreamModel` | Куда элемент направляет трафик. Имя модели — явная строка, а не внешний ключ на каталог. |
| `tier` | Меньшее значение предпочтительнее. Пока уровень 0 не исчерпан, уровень 1 не получает трафика. |
| `weight` | Положительное число, по умолчанию 100. Делит трафик внутри уровня и задаёт порядок кандидатов при переключении. |
| `enabled` | Отключённый элемент исключается из плана. |

Элементы отключённого или удалённого провайдера пропускаются. Если
`upstreamModel` совпадает с именем варианта одной из включённых моделей
провайдера, запрос уходит под именем этой модели у провайдера.

Элемент не указывает учётные данные. Движок сам выбирает учётные данные внутри
выбранного провайдера и сначала переключается между учётными данными этого
провайдера, а уже потом план переходит к следующему элементу.

## Порядок и стратегии

Кандидаты сортируются по `(tier, health, descending weight, stable id)`.
Стабильный идентификатор — это идентификатор элемента, поэтому два кандидата
никогда не равны, и порядок одинаков для каждого запроса.

Уровень — строгий приоритет: более поздний уровень никогда не балансируется
вместе с более ранним. Переупорядочивается только ведущая группа (кандидаты с
тем же уровнем и состоянием, что и у первого), согласно стратегии маршрута:

- `round_robin` вращает ведущую группу по счётчику, который ведётся для каждого
  маршрута.
- `weighted` выдвигает вперёд выбор плавного взвешенного round-robin. За полный
  цикл каждый элемент выбирается пропорционально своему весу, причём выборы
  распределены равномерно, а не идут подряд.
- `failover` оставляет отсортированный порядок без изменений.

Вращение использует счётчик, а не случайное число, поэтому нативная сборка и
wasm ведут себя одинаково, а последовательность воспроизводима. Счётчики
хранятся в памяти процесса и не разделяются между экземплярами; после
перезапуска вращение снова начинается с первого кандидата.

Состояние провайдера определяется его учётными данными. Отключённые, выведенные
из использования и «мёртвые» учётные данные исключаются. Заблокированные
учётные данные (например, после ограничения частоты) исключаются, пока у
провайдера остаются незаблокированные. Если заблокированы все учётные данные
провайдера, он остаётся в плане с ними и ставится после всех исправных
провайдеров, поэтому провайдер с ограничением частоты пробуется последним, а не
считается недоступным.

При включённом `sessionAffinity` предыдущая успешная цель сессии
предпочитается, но только внутри той же ведущей группы по уровню и состоянию.

## Имена маршрутов и пространства имён

Публичные имена создаются и редактируются прямо на маршрутах; отдельного
сопоставления публичных имён нет.

### Пространства имён

Имя маршрута, содержащее `/`, во время работы задаёт пространство имён.
Создание маршрута `acme/fast` делает `acme` точкой монтирования, и запрос к
`/acme/v1/chat/completions` с `{"model":"fast"}` разрешается в `acme/fast`:

```sh
curl -s http://127.0.0.1:8787/acme/v1/chat/completions \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"hi"}]}'
```

Пространство имён — это лишь индекс по именам маршрутов. Оно нигде не
хранится, не группирует маршруты и не владеет ими, и при его появлении ничего
не создаётся.

### Зарезервированные первые сегменты

Если первый сегмент имени маршрута совпадает с именем существующего провайдера
(без учёта регистра), API управления отклоняет его, потому что `имя/…` уже
означает форму `provider/model` для этого провайдера:

```json
{"error":{"code":"invalid_request","message":"invalid request: `codex/` is reserved:
 a first segment naming a provider already means `provider/model` narrowing;
 choose a distinct model route name"}}
```

Любой другой первый сегмент допустим; `coding/fast` — корректное публичное имя.

## Списки моделей для клиентов

`GET /v1/models` возвращает настроенные имена (имена маршрутов и
`provider/model`), отфильтрованные по тем, которые доступны вызывающей
стороне. Он не проксирует каталог моделей какого-либо одного провайдера.
Модели провайдера появляются в списке после того, как вы их добавите или
импортируете, с именем провайдера в качестве префикса.

Эти два запроса эквивалентны: базовый URL `/provider-A/v1` с моделью `gpt-5`
или базовый URL `/v1` с моделью `provider-A/gpt-5`. `GET /provider-A/v1/models`
перечисляет только провайдера A и сохраняет исходные имена его моделей.

Префикс — это отображаемое имя провайдера, поэтому переименование провайдера
меняет и префикс его моделей, и его базовый URL.

Список в портале включает и имена, которые вызывающая сторона использовать не
может; они отмечены полем `permitted`:

```sh
curl -s http://127.0.0.1:8787/portal/api/models -H "Authorization: Bearer $GPROXY_KEY"
```

```json
[{"name":"provider-A/gpt-4o-mini","providerCount":1,"channelIds":["custom"],"permitted":true},
 {"name":"fast","providerCount":1,"channelIds":["custom"],"permitted":true}]
```

Имя, недоступное по правилам вызывающей стороны, остаётся в списке с
`permitted: false`. v3 удаляла такие строки. v4 их сохраняет: список, молча
пропускающий имена, делает «модель возвращает 404» неотличимым от «вам не
разрешена эта модель», а сами имена — это конфигурация экземпляра, которую
оператор и так публикует.

Идентификаторы провайдеров за именем не показываются. Каждая запись содержит
число провайдеров и идентификаторы каналов: по ним видно, насколько имя
резервировано, но не видно, какие именно провайдеры за ним стоят.

## Каталог моделей

Каталог состоит из двух таблиц, и маршрутизации не нужна ни одна из них:
элемент маршрута задаёт модель провайдера обычной строкой, поэтому
маршрутизация работает и для имён, которых нет ни в одной таблице. Строки
каталога используются для списков моделей, документации, метаданных и цен.

- `provider_models` хранит, какие имена моделей обслуживает провайдер. Сюда
  записываются результаты обнаружения моделей.
- `models` — глобальный каталог, на который может ссылаться строка
  `provider_models`: одно имя, его метаданные и словарь токенизатора, который
  следует использовать для оценки числа токенов.

Чтобы добавить модель провайдера вручную:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/provider-models \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","upstreamName":"gpt-4o-mini"}'
```

```json
{"id":"f32df0bb6378c03e70f7c3aa6315a3b8","providerId":"5a45fd807be0…",
 "upstreamName":"gpt-4o-mini","modelId":null,"metadata":{},"enabled":true}
```

### Обнаружение моделей у провайдера

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

Обнаружение запрашивает провайдера на его собственном протоколе, поэтому
ничего не преобразуется и имена остаются такими, как у провайдера. Для каждой
записи в ответе указано, есть ли уже у провайдера такая строка и может ли
встроенный каталог назначить ей цену. `POST /admin/api/models/discover/apply`
вставляет указанные вами записи и пропускает уже существующие, так что
повторное применение одного и того же результата равносильно однократному.

При заполнении метаданных сначала ищется совпадение по полному идентификатору
модели, затем по уникальному базовому имени; неоднозначные имена значений по
умолчанию не получают. Поля сливаются в таком порядке: встроенные значения по
умолчанию, затем непустые поля провайдера, затем локальные переопределения.
Импорт в существующую модель провайдера из консоли заполняет только
недостающие поля.

<Warning>
Обнаружение и `POST /admin/api/models/test` расходуют настоящие учётные данные
и записывают настоящую строку использования. См.
[проверку провайдера](/ru/guides/providers#testing-a-provider).
</Warning>

### Встроенный каталог

Каждый выпуск содержит встроенный каталог с именами моделей, контекстными
окнами и ценами по умолчанию. Это снимок, сделанный при генерации ресурса, а не
живой справочник:

```sh
curl -s http://127.0.0.1:8787/admin/api/default-model-catalog -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

С `overwrite: false` повторное применение безопасно: правило, отредактированное
оператором, сохраняет правку и попадает в отчёт как пропущенное.

Встроенные идентификаторы моделей — неквалифицированные имена вроде
`claude-sonnet-4`, а не `anthropic/claude-sonnet-4`; URL источников и исходные
цены сохраняют своё происхождение. Квалифицированные имена моделей провайдера
по-прежнему сопоставляются по базовому имени. При подборе цены по умолчанию
предпочитается самый длинный совпавший фрагмент имени модели, а импорт цен
провайдера использует в качестве шаблона правила фактическое имя модели у
провайдера.

Цены по умолчанию — снимок цен OpenRouter, они не отражают договор с каждым
провайдером. Применение цен по умолчанию создаёт глобальные правила тарификации
и не заменяет существующее правило с тем же шаблоном. Правила конкретного
провайдера имеют приоритет над глобальными. Цены редактируются в диалогах
глобальной модели и модели провайдера; редактор цен поддерживает тарифы,
контекстные уровни и уровни обслуживания. См.
[Цены и уровни тарификации](/ru/reference/pricing).

### Страница «Модели»

Страница **Модели** в консоли (`/console/model-catalog`) показывает модели,
сохранённые в базе данных. Она использует ту же конечную точку
`/admin/api/models`, что и селекторы разрешений; при пустой базе список пуст.
На странице видны сохранённые возможности и ограничения, связи с провайдерами
и справочные встроенные цены, если они нашлись.

**Загрузить стандартные модели** импортирует выбранные записи из встроенной
таблицы и не трогает существующие модели. Загрузка метаданных не меняет
правила тарификации. Модели можно добавлять и вручную. Удалённая модель
исчезает из списка и не восстанавливается из встроенных данных при чтении.

Метаданные копируются в момент импорта. Последующее редактирование глобальной
модели не меняет модели провайдеров, импортированные из неё ранее.

### Обновление встроенного каталога

Встроенный ресурс пересоздаётся командой:

```sh
node scripts/update-openrouter-model-catalog.mjs
```

С `--input response.json` его можно собрать офлайн из сохранённого ответа.
Публичная конечная точка моделей не требует ключа; необязательные учётные
данные читаются только из `OPENROUTER_API_KEY`. Генератор сохраняет исходный
`source_pricing` для проверки и переносит только поддерживаемые единицы
тарификации. После пересчёта единиц цены округляются до девяти знаков после
запятой (к ближайшему, при равенстве — к чётному); импорт цен по умолчанию
использует то же правило.

Отсутствующая или динамическая цена не означает, что модель бесплатна. Прежде
чем добавлять цену с официальной страницы, проверьте точную версию модели,
регион, единицу и порог; не угадывайте недостающий тариф.
