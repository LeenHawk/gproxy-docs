Эта глава предназначена для администратора, который подключает GPROXY к вышестоящим сервисам: выбор канала, создание провайдеров, добавление и обслуживание учётных данных, настройки исходящих подключений.

*Канал* — это встроенный в бинарный файл адаптер для одного семейства вышестоящих сервисов. *Провайдер* — одно сохранённое подключение на канале: имя, необязательный базовый URL, собственный JSON `config` канала и пул учётных данных. На одном канале может быть сколько угодно провайдеров: `openai-main` и `openai-eu` могут оба использовать канал `openai`.

<a id="choosing-a-channel"></a>

## Выбор канала

Сборка по умолчанию включает все каналы репозитория; бинарный файл, собранный с отдельными feature каналов, содержит только их. `GET /admin/api/channels` отвечает на основе бинарного файла, а не базы данных. Каждая запись перечисляет способы входа канала, его возможности и ключи `config`, которые должна показывать форма провайдера; [каталог каналов](/ru/reference/channel-catalog) содержит те же данные для текущего выпуска.

<a id="compatible-vendors"></a>

### Совместимые сервисы

Сервису, который отличается от стандартного API только источником и заголовками, отдельный канал не нужен. Настройте его как провайдера `custom` и перечислите форматы протоколов, на которых он работает:

```json
{ "name": "example-vendor", "channel": "custom",
  "baseUrl": "https://api.example-vendor.com",
  "config": { "dialects": ["openai_chat"] } }
```

Отдельный канал пишется только тогда, когда строка провайдера не может выразить то, что нужно сервису. NVIDIA NIM, Vercel AI Gateway и Cloudflare AI Gateway раньше настраивались как провайдеры `custom`; теперь у каждого есть свой канал с собственной аутентификацией и запросом баланса, и его следует предпочитать.

<a id="creating-a-provider"></a>

## Создание провайдера

В Console откройте **Провайдеры**, выберите **Новый провайдер**, укажите канал, заполните имя и поля, которые показывает форма канала, и нажмите **Сохранить**. Затем добавьте учётные данные (см. [Учётные данные](#credentials)) и проверьте одни из них, прежде чем включать провайдера в маршрут модели.

То же самое через API администрирования:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/providers \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"name":"example-vendor","channel":"custom",
       "baseUrl":"https://api.example-vendor.com",
       "config":{"dialects":["openai_chat"]}}'
```

Перезапуск не нужен. Запись провайдера или учётных данных фиксируется в той же транзакции, что и увеличение ревизии конфигурации, а экземпляр перечитывает свою конфигурацию до того, как оповестить остальные экземпляры, поэтому следующий запрос уже видит изменение.

<a id="provider-configuration"></a>

## Конфигурация провайдера

| Поле | Значение |
| --- | --- |
| `name` | Метка, которую задаёт оператор; уникальна. Это также точка монтирования провайдера (`/{name}/...`) и левая часть формы `provider/model`. |
| `channel` | Один из идентификаторов каналов выше. |
| `baseUrl` | Источник вышестоящего сервиса, для каналов, которые его принимают. |
| `config` | Собственный JSON канала. Каждый канал объявляет, какие ключи он читает; `GET /admin/api/channels` их перечисляет. |
| `connectionProfileId` | Исходящий стек (прокси, эмуляция TLS) для вызовов этого провайдера. См. [Профили подключения](#connection-profiles). |
| `enabled` | Отключённый провайдер не участвует в разрешении. |

Для `custom` в `config` задаются `dialects` (форматы протоколов, на которых говорит конечная точка), статические `headers`, `allowed_headers` и два переключателя magic cache. Каналы, имитирующие CLI поставщика, сами выставляют свои заголовки идентификации и не дают клиенту их переопределить.

Далее описаны параметры отдельных каналов.

<a id="claude-model-fallback"></a>

### Резервные модели Claude

`fallback_mode` принимает значения `off` (по умолчанию), `default` или `models`. `fallback_models` — упорядоченный список идентификаторов моделей вышестоящего сервиса. Console строит оба поля по дескриптору канала. Пустые значения, дубликаты и основная модель пропускаются; используется не более трёх резервных моделей.

Как выполняется переключение, зависит от канала:

- Claude API, Claude Code и пользовательские конечные точки Claude получают поле `fallbacks` Anthropic с соответствующим beta-заголовком. В режиме `default` резервную модель выбирает Anthropic.
- OpenRouter получает `fallbacks` для Claude Messages или `models` для Chat Completions и выполняет переключение сам. Это не меняет `provider.allow_fallbacks`, который управляет выбором поставщика для одной и той же модели. Если клиент уже прислал `fallbacks` или `models`, используется значение клиента. Запросы Responses не получают параметра переключения, потому что OpenRouter не документирует его для них.
- Vercel, Azure, Vertex и AWS Bedrock: GPROXY сам повторяет запрос после `refusal` Claude на следующей настроенной модели через те же учётные данные, заново подготавливая и подписывая запрос. Режим `default` выбирает `claude-opus-4-8` в пространстве имён основной модели. Для облачных идентификаторов моделей укажите полные идентификаторы, которые принимает этот сервис.

Переключение на стороне шлюза работает и для запросов, преобразованных в Claude из другого протокола. Оно реагирует только на отказы (refusal), а не на произвольные ошибки HTTP. Потоковое содержимое передаётся по мере поступления; после того как вывод уже отправлен, запрос может продолжиться, только если вышестоящий сервис выдал кредит с заявкой на prefill, и серверный инструмент никогда не повторяется без погашаемого кредита. Каждая физическая попытка учитывается и тарифицируется отдельно по своей модели, а отказ с нулевым выводом не оплачивается. Итоговый ответ сохраняет usage верхнего уровня последней попытки.

<a id="claude-code-usage-limit-modes"></a>

### Режимы лимитов использования Claude Code

Два переключателя `claudecode` определяют поведение, когда подписка упирается в лимиты. Оба по умолчанию `false`.

- `low_priority: true`: после отказа из-за пятичасового лимита принять предложение сервера о низком приоритете. Сессия затем отправляет `anthropic-usage-limit: slow`, пока окно не сбросится или сервер не завершит режим. Недельные лимиты и отдельная квота низкого приоритета продолжают действовать.
- `extended_usage: true`: отправлять `anthropic-usage-limit: extended` в продолжениях с результатами инструментов, если не известно, что платное дополнительное использование включено. Предоставлять ли льготу, решает сервер; квота подписки при этом не сбрасывается.

Если клиент сам отправляет `slow` или `extended`, это значение сохраняется даже при выключенных переключателях; два значения взаимоисключающие. Запросы CountTokens и управляющие запросы этот заголовок не несут. Для клиентов, отличных от Claude Code, продолжение распознаётся по сообщению с результатом инструмента: внутренние флаги глубины задачи и экспериментов CLI шлюзу не видны.

Пока отправляется `slow`, GPROXY при ответах `429 slot_busy` и о перегрузке ждёт и повторяет тот же буферизованный запрос на тех же учётных данных. Как в CLI 2.1.302, задержка по умолчанию — 20 секунд с разбросом 30%, максимальное ожидание по умолчанию — 20 минут. Подсказки сервера ограничиваются диапазоном 5–600 секунд на одну задержку и 1–360 минут суммарно. Срок хоста или отмена могут прервать ожидание раньше. Отказы из-за бюджета, недельного лимита и права на использование возвращаются без повторов; уже начавшийся поток ответа, тело, которое нельзя воспроизвести, и непрозрачное погашение резервного кредита никогда не повторяются.

Представление квот также записывает квоты низкого приоритета и льготного использования, которые сообщает сервер. Обычный трафик они не блокируют. Явный режим освобождает только те окна подписки, к которым он относится, и только для данного запроса; локальные бюджеты, ограничения для отдельных моделей и периоды охлаждения после сбоев или ограничения скорости вышестоящего сервиса продолжают действовать.

<a id="claude-code-client-identity"></a>

### Идентификация клиента Claude Code

`client_identity` выбирает, каким официальным клиентом представляется канал `claudecode`. Обе идентичности — один и тот же бинарный файл CLI с одним и тем же OAuth-токеном.

- `cli` (по умолчанию): интерактивный CLI, `claude-cli/2.1.318 (external, cli)`. Корректный user agent CLI и `cc_entrypoint` блока биллинга, присланные клиентом, сохраняются.
- `agent_sdk`: Claude Agent SDK 0.3.318, `claude-cli/2.1.318 (external, sdk-ts, agent-sdk/0.3.318)`. Собственный user agent Agent SDK клиента (`sdk-ts` или `sdk-py` с `agent-sdk/…`) сохраняется, любой другой заменяется. `cc_entrypoint` блока биллинга следует за user agent, а ход помечается как ход SDK (`cc_turn_origin=sdk`, `cc_prompt_index=0`).

`identity_system_block: true` (по умолчанию `false`) помещает системный блок идентичности сразу после блока биллинга, в соответствии с `cc_entrypoint` биллинга: `You are Claude Code, Anthropic's official CLI for Claude.` для `cli` и `You are a Claude agent, built on Anthropic's Claude Agent SDK.` для `sdk-*`. Собственная SDK-идентичность клиента, включая вариант `running within the Claude Agent SDK`, сохраняется. Блок идентичности другого вида переписывается, а если клиент не прислал никакого, он вставляется. При выключенном переключателе системные блоки клиента остаются как есть.

Контрольная сумма биллинга (`cch`), суффикс `cc_version` и `metadata.user_id` вычисляются одинаково для обеих идентичностей. Anthropic может учитывать трафик Agent SDK в подписке отдельно от интерактивного использования; различает их он по entrypoint.

<a id="per-operation-url-overrides"></a>

### Переопределение URL для отдельных операций

`operation_endpoints` заменяет полный URL метода для одной тройки `(operation, dialect, transport)` у одного провайдера. URL используется как есть: это не базовый URL, к которому дописывается путь канала по умолчанию. Собственные параметры пути канал подставляет для этого метода сам:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/operation-endpoints \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","operation":"generate_content","dialect":"openai_chat",
       "url":"https://elsewhere.example/v1/chat/completions"}'
```

Для интерфейсов, в которых модель указывается в пути, `{model}` в URL заменяется именем модели вышестоящего сервиса, закодированным как один сегмент пути: `https://relay.example/v1beta/models/{model}:generateContent`.

`operation_rules` переопределяет для конкретного провайдера то, что канал делает для операции. Значения канала по умолчанию остаются в коде и не копируются в каждый новый провайдер, поэтому провайдер без переопределений следует за последующими изменениями умолчаний. `POST /admin/api/providers/{id}/routing-defaults/reset` удаляет оба вида переопределений одной фиксацией.

<a id="gemini-interactions"></a>

### Gemini Interactions

Канал `aistudio` поддерживает два диалекта Gemini: `gemini` (GenerateContent)
и `gemini_interactions` (Interactions API). Оба обслуживают операции
`generate_content` и `stream_generate_content`, но у Interactions свой формат
запроса, события шагов и тип ответа.

Клиент обращается к `POST /v1beta/interactions` или `POST /v1/interactions`,
при желании через префикс провайдера. `stream: true` включает нативный SSE.
`GET /interactions/{id}`, `POST /interactions/{id}/cancel` и
`DELETE /interactions/{id}` используют тот же префикс версии, а параметры
запроса вроде `stream` и `last_event_id` передаются дальше, чтобы клиент мог
получить или возобновить поток. Идентификатор interaction и ссылающийся на него
`previous_interaction_id` действительны только для того вызывающего, который
его создал, и всегда обслуживаются теми же учётными данными. Цель `agent`
проходит маршрутизацию и проверку прав так же, как имя модели, а поле `agent`
сохраняется в запросе к провайдеру.

Responses, Chat Completions и Claude Messages преобразуются в Interactions и
обратно напрямую, без хранимого состояния. Для этого укажите
`gemini_interactions` целевым диалектом в сопоставлении операций провайдера
или создайте провайдера `custom`, который поддерживает только Interactions:

```json
{ "channel": "custom", "baseUrl": "https://generativelanguage.googleapis.com",
  "config": { "dialects": ["gemini_interactions"] } }
```

Преобразуются вызовы функций и их результаты, подписанная история рассуждений,
встроенные изображения, а также текстовые и JSON-схемы вывода. Подписи шагов
Interactions хранятся отдельно от подписей GenerateContent. Необязательные
поля, которые нельзя преобразовать, попадают в диагностику преобразования.
Идентификаторы файлов нужно заранее заменить встроенными данными или URL.

Некоторым возможностям нужен провайдер с нативной поддержкой Interactions:
агентам, фоновому выполнению, продолжению диалога, сохранённого в другом
диалекте, и явному `store: true`. Когда клиент Interactions обслуживается
провайдером с другим протоколом, отправляйте полную историю и `store: false`;
полученный идентификатор ответа не соответствует interaction, сохранённому у
провайдера.

Нативный поток передаётся по частям. Поток со сменой протокола сначала
полностью собирается у провайдера, а затем воспроизводится как события
клиентского протокола, поэтому время до первого токена не сокращается.
Опрос и возобновлённое получение не тарифицируют накопленное использование
повторно. Фоновая работа, в ответе на создание которой нет данных об
использовании, шлюзом не учитывается.

<a id="glm"></a>

### GLM

`glm` — API с оплатой по факту, `glmcode` — GLM Coding Plan. Оба принимают учётные данные `api_key` и по умолчанию используют `https://open.bigmodel.cn`; глобальные аккаунты задают `baseUrl: "https://api.z.ai"`. `glmcode` использует выделенные конечные точки плана для Chat, Claude Messages и Responses и не переходит на платный API, когда план исчерпан.

Оба списка моделей берутся из живого официального каталога ZCode: канал запрашивает `/api/v1/client/configs`, загружает возвращённый `builtin_provider_config_json` и выбирает региональный шаблон платформенного API или Coding Plan. Встроенного списка моделей нет, и при неудачной загрузке устаревший список не используется. Каталог — это продуктовый список поставщика; он не доказывает, что конкретному ключу доступна каждая модель из него.

`glmcode` читает `/api/monitor/usage/quota/limit`: сообщаемые проценты, независимые окна и время их сброса. Платформенный `glm` пока не запрашивает баланс аккаунта.

<a id="minimax"></a>

### MiniMax

`minimax` по умолчанию использует `https://api.minimax.io`; аккаунты китайской платформы указывают источник API этой платформы. OpenAI Chat и Claude Messages принимают в `api_key` либо Subscription Key (Coding Plan / Token Plan), либо API-ключ с оплатой по факту. Обнаружение моделей и сведения о модели используют официальные `/v1/models` и `/v1/models/{id}`. Два вида ключей можно разнести по разным провайдерам, чтобы маршрутизировать текст по подписке и платное видео независимо.

Вслед за официальным CLI запрос квоты читает `/v1/token_plan/remains` или `/account/query_balance` в зависимости от типа ключа. Эти показания (как и у `glmcode`) служат для отображения; исчерпаны ли учётные данные, определяют ответы вышестоящего сервиса.

Видео поддерживает H3 V2 (`MiniMax-H3`, `MiniMax-H3-Max`) и требует API-ключа с оплатой по факту. Отправьте JSON видеорасширения OpenAI от GPROXY на `/v1/videos`:

```json
{
  "model": "MiniMax-H3",
  "prompt": "A cat running through a garden",
  "duration": 5,
  "resolution": "2K",
  "aspect_ratio": "16:9"
}
```

Запрашивайте `/v1/videos/{id}` по возвращённому ID и загружайте готовое видео с `/v1/videos/{id}/content`. `frame_images` задаёт первый и последний кадры; `input_references` передаёт изображения, видео и аудио в качестве референсов. Принимается и нативное поле MiniMax `content`. Sora multipart, `seconds`, `size` и устаревшие конечные точки Hailuo 2.x V1 не поддерживаются.

Список использует `page_num` и `page_size` (`limit` отображается на `page_size`); курсоры `after` и `order` не поддерживаются. Удаление возвращает `action` вышестоящего сервиса: `cancelled` означает, что задача в очереди отменена, `deleted` — что запись задачи удалена. Канал не опрашивает задачи сам и не хранит видеофайлы.

Источники: [реализация каталога ZCode](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/packages/provider-node/src/zcode-builtin-download.ts), [официальный CLI MiniMax](https://github.com/MiniMax-AI/cli), [GLM Coding Plan](https://docs.z.ai/devpack/tool/others), [текстовый API MiniMax](https://platform.minimax.io/docs/api-reference/text-anthropic-api), [MiniMax H3 V2](https://platform.minimax.io/docs/api-reference/video-generation-v2-create).

<a id="orcaterm"></a>

### OrcaTerm

`orcaterm` использует настольный протокол LightAI для текстовых и графических диалогов с параметрами рассуждения, зависящими от модели. Создайте провайдера, затем войдите через браузер или импортируйте учётные данные OAuth. Для международного сервиса задайте `international=true`; его источник аккаунта — `https://orcaterm.ai`, источник LightAI — `https://lightai.tencentcloud.com`.

Изображения передаются как Base64 data URL (PNG, JPEG, WebP или GIF), в том числе в истории и в пользовательских сообщениях, состоящих только из изображения. Слишком большие статичные изображения перед загрузкой уменьшаются и сжимаются, а одинаковое изображение повторно использует прежнюю загрузку тех же учётных данных, пока её URL предпросмотра действителен. Доступные модели и уровни рассуждения берутся из живого каталога моделей. Параметры запроса, которые сервис не поддерживает, игнорируются. Число токенов — локальная оценка по символам, помеченная в учёте как оценочная и неполная; квота аккаунта показывает число AI-вопросов.

Распознанные GPROXY клиентские инструменты терминала, файлов и загрузки веб-страниц отображаются на нативный протокол review/reportToolResult OrcaTerm. Каждый вызов по-прежнему выполняет исходный клиент со своими проверками разрешений. Продолжения с инструментами используют тот же провайдер, учётные данные и модель; регистрация произвольных функций не поддерживается. Текст ответа и аргументы инструментов выдаются после того, как агент закончит редактировать свой ответ. Отдельные веб-запросы Codex используют серверные инструменты поиска и загрузки OrcaTerm и возвращают их настоящие результаты.

<a id="volcengine-ark"></a>

### Volcengine Ark

`volcengine_agent` (Agent Plan) и `volcengine_coding` (Coding Plan) используют одну реализацию и собственные пути продуктов (`/api/plan` и `/api/coding`); на конечную точку `/api/v3` с оплатой по факту они не переходят. Agent Plan требует собственного выделенного API-ключа. Coding Plan personal использует API-ключ платформы с включённым Coding Plan, Coding Plan enterprise — API-ключ места (seat).

Для инференса достаточно `{"api_key"}`. Для обнаружения моделей, квоты и сведений о плане в том же секрете нужна ещё пара ключей IAM (`access_key_id`, `secret_access_key`, при необходимости `session_token`). Пара ключей отправляется только в плоскость управления, API-ключ — только на инференс. Без пары ключей инференс работает с вручную настроенными строками моделей.

`config.edition` — `personal` (по умолчанию) или `enterprise`; для квоты enterprise в метаданных учётных данных нужен `seat_id`. Источники можно переопределить базовым URL провайдера (по умолчанию `https://ark.cn-beijing.volces.com`), `config.control_base_url` (`https://ark.cn-beijing.volcengineapi.com`) и, для речи Agent Plan, `config.speech_base_url` (`https://openspeech.bytedance.com`). Учётные данные Agent могут задать в метаданных `allow_paid_usage: true`, чтобы маршрутизация продолжалась после исчерпания окон подписки, если в аккаунте у поставщика включено постоплатное использование.

<a id="credentials"></a>

## Учётные данные

Учётные данные — один секрет в пуле провайдера: API-ключ, набор OAuth-токенов или браузерная сессия. В Console откройте провайдера и перейдите на вкладку **Учётные данные**; через API запись создаёт `POST /admin/api/credentials`, а его пакетная конечная точка создаёт несколько.

| Поле | Значение |
| --- | --- |
| `label` | Необязательно. Если учётные данные созданы входом, метка выводится из канала и аккаунта. |
| `authKind` | `api_key`, `oauth` или `cookie`: тип сохранённых учётных данных, независимо от способа их получения. |
| `secret` | Поля, объявленные каналом. Никогда не возвращается; список сообщает только `hasSecret`. |
| `organizationId` / `teamId` / `userId` | Владелец: ровно одно из полей или ни одного для общих учётных данных. |
| `connectionProfileId` | Переопределяет исходящий стек провайдера. |
| `expiresAtMs` | Когда секрет нужно обновить. |
| `status` | `active` или `dead`. Учётные данные `dead` больше не используются. |
| `version` | Защита compare-and-swap, под которой записывается обновление. |

Секреты запечатываются AES-256-GCM под мастер-ключом. Печать привязана к собственному id строки, поэтому запечатанный блок, скопированный в другую строку, не открывается. Чтение секрета — отдельный вызов, и он попадает в аудит:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/reveal \
  -H "Authorization: Bearer $GPROXY_KEY"
```

Без мастер-ключа секреты хранятся незашифрованными. Это поддерживаемый вариант развёртывания; бинарный файл один раз сообщает о нём при запуске.

<a id="credential-visibility"></a>

### Видимость учётных данных

Учётные данные видны вызывающему, если у них нет владельца или если владелец совпадает с привязкой ключа, которым выполнен вызов: собственным пользователем, командой или действующей организацией ключа. Используется привязка ключа, а не членство пользователя, потому что пользователь может состоять в двух организациях, а ключ принадлежит одной. Если бы решало членство, каждый ключ пользователя из нескольких организаций получал бы доступ к подпискам всех этих организаций, и ни один ключ не мог бы быть уже, чем его владелец.

Видимость только исключает учётные данные из набора, доступного запросу, и никогда не добавляет новые.

<a id="logging-in-to-obtain-a-credential"></a>

## Получение учётных данных через вход

Каналы, работающие с аккаунтом, а не с ключом, позволяют создать учётные данные входом в вышестоящий сервис.

1. Откройте вкладку **Учётные данные** провайдера и выберите **Добавить через вход**.
2. Для входа через браузер (код авторизации) откройте ссылку авторизации, войдите и вставьте в диалог полный URL обратного вызова из адресной строки браузера.
3. Для входа по коду устройства введите показанный код на странице поставщика; Console опрашивает сервер, пока вход не завершится.

Новые учётные данные появляются в списке. См. также [администрирование в Console](/ru/guides/console#credentials-and-upstream-sign-in).

Канал предлагает один или оба способа; они перечислены в поле `loginModes` ответа `GET /admin/api/channels`. Запрос способа, которого канал не предлагает, отклоняется.

| Способ | Шаги | Для чего |
| --- | --- | --- |
| Код авторизации | start → complete | Перенаправление в браузере с PKCE |
| Код устройства | start → poll, многократно | Код вводится на другом устройстве |

Четыре операции POST находятся под `/admin/api/credential-login`. Незавершённый вход привязан к пользователю, который его начал, и к его административной области.

<a id="importing-an-existing-credential"></a>

### Импорт существующих учётных данных

Если токен или cookie у вас уже есть, импортируйте их через `POST /admin/api/credentials` (или пакетную конечную точку) и инициализируйте через `POST /admin/api/credentials/{id}/refresh`. Console после сохранения обновляет ожидающие импорта записи; если инициализация не удалась, сохранённая строка остаётся, и её можно повторить из подробностей. Claude Web использует `authKind: "cookie"`; Claude Code и OrcaTerm — `authKind: "oauth"`, в том числе при импорте в виде `secret: {"cookie": "..."}`. Старые метки видов по-прежнему читаются. Инициализация и обновление сохраняют секрет, срок действия и необязательные публичные метаданные вместе под проверкой версии, поэтому миграция базы данных или заполнение старых данных не требуются.

<a id="how-a-login-is-protected"></a>

### Защита входа

GPROXY сам генерирует и проверяет всё, что не относится к вышестоящему сервису. Верификатор PKCE — 32 случайных байта, сгенерированных локально и никогда не отправляемых; в URL авторизации попадает только его дайджест S256, поэтому перехваченный код без него бесполезен. Состояние CSRF тоже генерируется и сравнивается локально. Несовпадающее состояние отклоняется и уничтожает незавершённую сессию, так что повтор нельзя перебирать до успеха.

Незавершённая сессия хранится в общем кэше, а не в процессе. Поэтому любой экземпляр может завершить вход, начатый другим (за балансировщиком нагрузки это обычный случай), а брошенный вход ничего не оставляет: его ключ истекает, а истёкший ключ неотличим от никогда не выданного.

Опрос по коду устройства выполняет один шаг и возвращается; сервер не засыпает и не крутится в цикле, опрашивает вызывающая сторона. Каждый ответ содержит интервал ожидания, а `slow_down` от вышестоящего сервиса увеличивает его для всех последующих опросов.

Успешный вход — обычная вставка учётных данных через тот же путь фиксации, что и запись управления. Секрет запечатывается до построения SQL-запроса, так что ничто между каналом и базой данных не видит его в открытом виде, а ответ содержит только id новых учётных данных.

<a id="refreshing-a-credential"></a>

### Обновление учётных данных

Каналы, хранящие OAuth-токены, объявляют, когда секрет нужно обновить. Обновление возвращает полный заменяющий секрет, а не частичное обновление для слияния. Хост записывает его с compare-and-swap по `version` и публикует уведомление об изменении учётных данных. Обновить вручную:

```sh
curl -s -X POST 'http://127.0.0.1:8787/admin/api/credentials/{id}/refresh?force=true' \
  -H "Authorization: Bearer $GPROXY_KEY"
```

Если вышестоящий сервис окончательно отвергает учётные данные (`invalid_grant`, отозванный токен), они помечаются как `dead`. Временная транспортная ошибка или 5xx этого не делают: они сообщаются как транспортная ошибка, и хост повторяет попытку позже.

Проверка версии важна, потому что Claude меняет refresh token при каждом обновлении. Если бы два обновления выполнялись одновременно и одна запись потерялась, сохранённый refresh token был бы уже недействителен.

<a id="credential-health-and-quota-windows"></a>

## Состояние учётных данных и окна квот

При разрешении запроса отключённые, выведенные из эксплуатации и `dead` учётные данные исключаются. Заблокированные учётные данные (те, для которых вышестоящий сервис ограничил скорость) исключаются, пока у провайдера есть незаблокированные. Если заблокированы все учётные данные провайдера, они сохраняются, а провайдер ставится после всех исправных, так что его пробуют, только когда больше ничего нет.

API администрирования показывает и сбрасывает это состояние для каждых учётных данных:

```sh
# окна квот, которые провайдер сообщает для этих учётных данных
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/quota -H "Authorization: Bearer $GPROXY_KEY"
# запросить провайдера прямо сейчас
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-probe -H "Authorization: Bearer $GPROXY_KEY"
# использовать сброс квоты (если провайдер их продаёт)
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/quota-reset -H "Authorization: Bearer $GPROXY_KEY"
# сбросить записанное состояние
curl -s -X POST http://127.0.0.1:8787/admin/api/credentials/{id}/health-reset -H "Authorization: Bearer $GPROXY_KEY"
# ограничения оператора, действующие для этих учётных данных
curl -s http://127.0.0.1:8787/admin/api/credentials/{id}/limits -H "Authorization: Bearer $GPROXY_KEY"
```

`POST /admin/api/credentials/{id}/status` вручную устанавливает `active` или `dead` с указанием причины.

<a id="connection-profiles"></a>

## Профили подключения

Профиль подключения — исходящий стек, которым идёт вызов: прокси, а также предъявляемые отпечатки TLS и HTTP/2. Профиль выбирается сначала из учётных данных, затем из провайдера, затем из умолчания канала и, наконец, из умолчания экземпляра.

Пресеты идентичности можно сохранить как `emulation` профиля:

```sh
curl -s http://127.0.0.1:8787/admin/api/tls-presets -H "Authorization: Bearer $GPROXY_KEY"
```

Шесть пресетов воспроизводят CLI поставщиков:

```text
claude / Claude CLI    codex / Codex CLI       gemini / Gemini CLI
antigravity            kiro / Kiro CLI         copilot / GitHub Copilot CLI
```

Кроме того, список содержит по одному пресету `wreq:{profile}` для каждого профиля браузера и HTTP-клиента, поставляемого библиотекой эмуляции (Chrome, Edge, Firefox, Safari, Opera, OkHttp).

Эмулированную идентичность предъявляет только транспорт `wreq`. Канал, имитирующий CLI, предоставляет собственный профиль по умолчанию; явный профиль в учётных данных или провайдере всё равно имеет приоритет.

<a id="testing-a-provider"></a>

## Проверка провайдера

Только два вида вызовов управления выходят за пределы процесса: проверка связности и проверка моделей с обнаружением.

<a id="connectivity-test"></a>

### Проверка связности

Проверка связности обращается к trace-конечной точке Cloudflare через выбранную областью цепочку клиента и показывает, как развёртывание выглядит снаружи:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/connectivity/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"scope":"global"}'
```

```json
{"ok":true,"latencyMs":803,"ip":"223.166.167.192","colo":"LAX","error":null}
```

Область — `global`, `{"scope":"provider","provider_id":"…"}`, `{"scope":"credential","credential_id":"…"}` (тот же транспорт, что используют вызовы этих учётных данных) или `{"scope":"proxy","url":"…"}` для прокси, который ещё нигде не настроен. Сетевой сбой возвращается как `ok: false` с причиной, а не как ошибка HTTP: недоступный вышестоящий сервис — допустимый результат проверки.

<a id="model-test-and-discovery"></a>

### Проверка и обнаружение моделей

Проверка и обнаружение моделей проходят через движок так же, как запрос вызывающего:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/models/test \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","model":"gpt-4o-mini"}'

curl -s -X POST http://127.0.0.1:8787/admin/api/models/discover \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…"}'
```

<Warning>
Оба вызова используют настоящие учётные данные: они расходуют квоту вышестоящего сервиса, учитываются в любом бюджете, который распространяется на эти учётные данные, и записывают строку использования. Режима пробного запуска нет, потому что проверка, не обращающаяся к вышестоящему сервису, ничего бы не проверила.
</Warning>

Обнаружение запрашивает модели на собственном диалекте провайдера, поэтому имена моделей — те, что у вышестоящего сервиса. Каждый результат показывает, есть ли у провайдера уже строка для этой модели и может ли встроенный каталог её тарифицировать. `POST /admin/api/models/discover/apply` добавляет выбранные модели и пропускает уже существующие.

<a id="request-header-allow-lists"></a>

## Списки разрешённых заголовков запроса

По умолчанию заголовки запроса клиента вышестоящему сервису не передаются. В разделе «Общие настройки → Сеть» задаётся глобальный список разрешённых заголовков, а каждый провайдер может добавить имена через `config.allowed_headers`. Итоговый набор — объединение глобального списка, списка провайдера и заголовков канала по умолчанию, плюс `content-type`. Отсутствующий или пустой список ничего не добавляет.

Исходные учётные данные и hop-by-hop заголовки удаляются, даже если они перечислены. Аутентификация, которую добавляет канал, и статические `headers` в `config` этой политикой не затрагиваются. Изменения вступают в силу при следующей перезагрузке конфигурации; сохранённый список провайдера объединённым результатом не перезаписывается.

<a id="moving-configuration"></a>

## Перенос конфигурации

```sh
gproxy export --out config.json --include-secrets
gproxy import --in  config.json --mode merge --source-master-key '…'
```

Экспорт содержит конфигурацию развёртывания: профили подключения, провайдеров, учётные данные, каталог моделей, маршрутизацию, переопределения операций, правила перезаписи, квоты, цены и строку настроек. Идентичность он не переносит (пользователи, ключи, организации, команды, разрешения и подписки относятся к продуктовому уровню), как и использование и захваты, которые иначе выглядели бы как история, которой у целевого экземпляра никогда не было. Правила для мастер-ключа описаны в разделе [Конфигурация](/ru/reference/configuration#moving-a-configuration).
