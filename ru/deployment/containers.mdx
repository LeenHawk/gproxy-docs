На этой странице описаны два разных контейнера. Образ Docker запускает обычный CLI `gproxy` с базой данных SQLite в томе и предназначен для сервера, которым вы управляете сами. Шаблоны Render и Heroku собирают отдельный образ, в котором нативная сборка с PostgreSQL работает за небольшой точкой входа на Node.js; он предназначен для платформ, где локальный диск не сохраняется после перезапуска. О Cloudflare Workers, Netlify и Vercel см. [Cloudflare Workers, Netlify и Vercel](/ru/deployment/edge).

## Docker

Одни и те же образы для amd64, arm64 и riscv64 публикуются в четырёх реестрах. Используйте ближайший к вам:

| Реестр | Образ |
| --- | --- |
| Docker Hub | `gproxy2/gproxy` |
| GitHub | `ghcr.io/leenhawk/gproxy` |
| GitLab | `registry.gitlab.com/leenhawk1/gproxy` |
| CNB | `docker.cnb.cool/leenhawk/gproxy` |

Стабильные релизы помечаются тегом `vX.Y.Z`, бета-канал — тегом `staging`, снимки разработки — тегом `nightly`. Чтобы получить сборку с musl, добавьте к любому тегу `-musl`. Образы с тегами v3 запускают v3, а не v4.

Запустите контейнер с именованным томом для каталога данных и мастер-ключом в переменной среды:

```sh
export GPROXY_IMAGE='gproxy2/gproxy:<tag>'
# Set GPROXY_MASTER_KEY to your saved 32-byte key (64 hex digits or base64).
docker run -d --name gproxy --restart unless-stopped \
  -p 127.0.0.1:8787:8787 \
  -v gproxy-data:/app/data \
  -e GPROXY_MASTER_KEY \
  "$GPROXY_IMAGE"
docker logs gproxy
```

При первом запуске GPROXY создаёт администратора и ключ API и выводит сгенерированные учётные данные в журнал. Сохраните их и откройте `http://127.0.0.1:8787/console/`. Больше нигде эти данные не появляются, поэтому защитите журнал.

Образ слушает порт 8787, хранит базу данных SQLite в `/app/data` и работает от имени пользователя `65532:65532`. Если вместо именованного тома вы монтируете каталог хоста, у этого пользователя должно быть право записи в него.

Чтобы перейти на новую версию, остановите и удалите контейнер и запустите новый из нового тега с тем же томом и тем же `GPROXY_MASTER_KEY`. База данных находится в томе, поэтому удаление контейнера её не затрагивает.

## Render

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)][render-deploy]

Шаблон Render — это Blueprint `render.yaml` в корне репозитория. Он создаёт один веб-сервис на бесплатном тарифе и не создаёт базу данных: внешнюю базу PostgreSQL вы предоставляете сами.

1. Нажмите кнопку выше и просмотрите Blueprint.
2. Укажите в `GPROXY_DATABASE_URL` URL подключения к PostgreSQL и запустите развёртывание. База данных должна принимать подключения из Render; если поставщик требует параметры SSL, оставьте их в URL.
3. Render сгенерирует `GPROXY_ADMIN_PASSWORD` и `GPROXY_MASTER_KEY`. Откройте настройки сервиса **Environment** и сохраните копию обоих значений.
4. Откройте URL сервиса с путём `/console/` и войдите как `admin`.

Проверка работоспособности сервиса — `/healthz` на порту `8787`. Бесплатные веб-сервисы засыпают при простое, поэтому первый запрос после паузы выполняется медленно, пока сервис просыпается. Цены и ограничения внешней базы данных определяет её поставщик.

## Heroku

[![Deploy to Heroku](https://www.herokucdn.com/deploy/button.svg)][heroku-deploy]

Шаблон Heroku состоит из `app.json` и `heroku.yml` в корне репозитория. Он создаёт один веб-дино Basic и дополнение `heroku-postgresql:essential-0`. Оба платные; перед развёртыванием ознакомьтесь с тарифами.

1. Сгенерируйте мастер-ключ командой `openssl rand -hex 32` и сохраните его.
2. Нажмите кнопку выше, выберите имя приложения и регион и введите ключ в `GPROXY_MASTER_KEY`.
3. Проверьте дино и дополнение и запустите развёртывание. Heroku сгенерирует `GPROXY_ADMIN_PASSWORD`.
4. Посмотрите пароль в **Settings → Reveal Config Vars** и войдите как `admin` по пути `/console/`.

Образ собирается из `deploy/serverless/Dockerfile`. Точка входа на Node.js слушает порт `PORT`, назначенный Heroku, и работает под тем идентификатором пользователя, с которым её запускает Heroku; шлюз читает `DATABASE_URL` дополнения. Локальные файлы дино временные, а всё важное (конфигурация, учётные данные, данные об использовании, состояние кеша) хранится в PostgreSQL.

## Работа шаблонов Render и Heroku

Оба шаблона собирают один и тот же образ. Во время сборки он скачивает исполняемые файлы релиза `gproxy-serverless` для x86_64 и aarch64, сверяет их с `SHA256SUMS` релиза и упаковывает вместе с точкой входа на Node.js. Ничего не компилируется. Обычный образ Docker, описанный выше, содержит только драйвер SQLite, поэтому заменить этот образ он не может.

### База данных

Шлюз читает `GPROXY_DATABASE_URL`, а если она не задана — `DATABASE_URL` платформы. При обновлениях сохраняйте базу данных и `GPROXY_MASTER_KEY` и делайте резервные копии обоих.

### Обновления

По умолчанию сборка скачивает последний стабильный релиз (`GPROXY_RELEASE_VERSION=latest`). Чтобы обновиться, очистите кеш сборки платформы и разверните заново. Чтобы закрепить версию, задайте аргументу сборки Docker `GPROXY_RELEASE_VERSION` тег релиза; в этом релизе должны быть оба архива serverless для Linux и `SHA256SUMS`.

### Экземпляры

Шаблоны запускают один экземпляр приложения. Общий кеш хранится в PostgreSQL.

### Публичный адрес

Если вы используете OAuth или опубликованные ссылки на файлы, задайте в `GPROXY_PUBLIC_BASE_URL` публичный HTTPS-адрес (origin) сервиса. Шаблоны не настраивают хранилище файлов; для файловой системы или объектного хранилища запустите нативную сборку CLI.

### Адреса клиентов

IP-адрес клиента берётся из TCP-соединения, а на другом его конце может оказаться маршрутизатор платформы. Заголовкам с переданным IP-адресом клиента шлюз не доверяет.

### Соединения

Точка входа обслуживает HTTP, SSE и WebSocket. Тайм-ауты маршрутизатора платформы, ограничения на простой и перезапуски по-прежнему действуют. При завершении работы она перестаёт принимать соединения и даёт открытым соединениям SSE и WebSocket до 25 секунд, прежде чем завершиться.
