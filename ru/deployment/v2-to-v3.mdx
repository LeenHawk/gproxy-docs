Эти указания предназначены для администраторов, переводящих развёртывание v2 на SQLite на v3. Нативный сервер v3 версии v3.0.22 при запуске распознаёт базу данных SQLite v2 и преобразует её, прежде чем открыть хранилище v3. Если вы собираетесь перейти дальше на v4, v3 можно пропустить и воспользоваться [миграцией с v2 на v4](/ru/deployment/v2-to-v4), которая также поддерживает PostgreSQL и MySQL.

## Что меняется

Преобразуется:

- Поддерживаемая конфигурация и секреты, которые удаётся восстановить.
- Права организаций, команд и пользователей на все маршруты (`*`).
- История использования: подробные строки, ещё оставшиеся в `usages`. По ним v3 заново строит почасовые агрегаты.
- Журналы запросов: `downstream_requests` превращается в `request_logs`, а `upstream_requests` — в `wire_logs`. Сохраняются идентификаторы запросов, метки времени, методы, пути и URL, статус, заголовки запросов, тела запросов и ответов, в том числе несколько попыток обращения к провайдеру для одного запроса. Нулевой статус v2 становится неизвестным статусом ответа. Ссылки на провайдеров и учётные данные переназначаются; вместо удалённых сущностей создаются отключённые заглушки.
- Ключи API, которые удаётся восстановить.

Не преобразуется (данные остаются в резервной копии v2):

- Свёртки использования v2, ежедневная статистика по учётным данным и исторические циклы квот. Поэтому использование, подробные строки которого уже удалила политика хранения v2, не попадает в статистику v3.
- Снимки состояния учётных данных, кеши токенизатора и привязки задач Codex.
- Правила лимитов запросов v2, права на отдельные маршруты, неизвестные области разрешений и права, субъект которых больше не существует. В v3 они не применяются; настройте их заново после обновления.
- Неизвестные таблицы, независимо от того, есть ли в них строки.
- Метки времени создания и обновления журналов, существовавшие только в v2, и `latency_ms` для каждой попытки. Длительность запроса v3 определяет по подробным данным об использовании.
- Журналы аудита. Браузерам и клиентам, возможно, придётся снова войти.

Каждая пропущенная непустая таблица указывается в `report.txt` с числом строк и причиной.

## Подготовка

1. Сохраните копию используемого сейчас исполняемого файла v2 и его параметры запуска. Механизм самообновления v2 заменяет исполняемый файл, не сохраняя старый, а миграция v3 не может его вернуть. Копия понадобится для отката.
2. Проверьте базу данных. Автоматически обновляется только база данных SQLite v2: база по умолчанию или файловая база, заданная как `--dsn sqlite://PATH?mode=rwc`. PostgreSQL, MySQL, удалённый libSQL, базы данных v1 и другие DSN SQLite автоматически не обновляются; мигрируйте их явно, например с помощью [миграции с v2 на v4](/ru/deployment/v2-to-v4).
3. Если база данных зашифрована, запишите ваш `GPROXY_MASTER_KEY`. Не меняйте ключ в рамках этого обновления: при включённой ротации v3 откажется запускаться с сообщением `disable master-key rotation during the v2 upgrade; rotate after the upgrade completes`.
4. Убедитесь, что на диске достаточно места для полной копии базы данных, преобразованной рабочей базы и её отдельной копии для переключения.
5. Запланируйте остановку всех остальных процессов, работающих с базой данных. Обновлению нужна монопольная блокировка SQLite, а сервер v3 занимает порт для прослушивания до того, как обратится к базе данных, поэтому второй экземпляр в это время запуститься не сможет.

## Обновление

1. Остановите v2.
2. Установите исполняемый файл [v3.0.22](https://github.com/LeenHawk/gproxy/releases/tag/v3.0.22) вместо v2.
3. Запустите его той же командой, что и v2. v3 принимает `--persistence db`, `--data-dir`, файловый `--dsn sqlite://PATH?mode=rwc` и `--update-channel staging`. Оставьте прежний `GPROXY_MASTER_KEY`.
4. Следите за журналом. Вы должны увидеть `checking v2 configuration before database copy`, `configuration preflight passed; copying the v2 database`, `importing v2 configuration, usage, and request logs` и `validating the migrated database before cutover`, а в конце — предупреждение с именем каталога резервной копии: `v2 database upgraded; retain this backup to roll back with a v2 executable`.

При запуске v3 выполняет следующее:

1. Захватывает блокировку миграции (`.gproxy-v2-upgrade.lock` рядом с базой данных), чтобы базу обновлял только один процесс.
2. Создаёт рядом с базой данных закрытый каталог `gproxy-v2-backup-TIMESTAMP-PID`.
3. Проверяет конфигурацию v2, прежде чем что-либо копировать.
4. Устанавливает монопольную блокировку базы данных SQLite, выполняет контрольную точку WAL и копирует базу в этот каталог как `gproxy-v2.db`.
5. Импортирует конфигурацию, секреты, данные об использовании и журналы запросов из копии в новую базу данных v3 в `candidate/`, читая и записывая журналы ограниченными пакетами.
6. Проверяет число импортированных записей, целостность SQLite, ссылки, состояние управления во время выполнения, число строк использования и точную итоговую рассчитанную стоимость.
7. Только после этого сбрасывает новую базу данных на диск и атомарно заменяет ею настроенную базу.

Каталог резервной копии и его `report.txt` сохраняются. При перезапуске v3 повторный импорт не выполняется.

## Проверка обновления

1. Прочитайте `report.txt` в каталоге резервной копии. В нём перечислены пропущенные таблицы и политики.
2. Войдите в консоль и проверьте провайдеров, учётные данные, пользователей и ключи API.
3. Сравните статистику использования с v2, учитывая, что импортированы только сохранившиеся подробные строки.
4. Заново настройте лимиты запросов и права на отдельные маршруты, которые отчёт указывает как пропущенные.

## Если обновление завершилось ошибкой

Сбой до замены оставляет базу данных v2 на прежнем месте. v3 дописывает `migration failed:` и текст ошибки в `report.txt` в каталоге этой попытки и записывает ту же ошибку вместе с путём к каталогу в `.gproxy-v2-upgrade-blocked` рядом с базой данных.

Пока этот маркер существует, v3 не повторяет попытку и останавливается с сообщением `automatic migration previously failed; inspect … and remove that marker only after resolving the failure`. Так диспетчер процессов не будет снова и снова копировать проблемную базу данных, пока не закончится место на диске. Устраните причину, затем удалите только маркер и снова запустите v3. Не удаляйте резервную копию, чтобы принудительно повторить попытку.

## Откат

1. Остановите v3.
2. Переместите в сторону текущую базу данных v3 вместе с её файлами `-wal` и `-shm` и сохраните их для анализа.
3. Скопируйте `gproxy-v2.db` из каталога резервной копии по настроенному пути базы данных.
4. Снова установите сохранённый исполняемый файл v2 или тот же официальный релиз v2.
5. Запустите v2 с прежними параметрами запуска и мастер-ключом.

Не запускайте v2 с преобразованной базой данных v3. Данные об использовании, записанные после переключения, остаются в сохранённой базе данных v3 и обратно в v2 не переносятся.
