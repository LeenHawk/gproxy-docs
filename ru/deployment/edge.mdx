Для GPROXY есть готовые шаблоны развёртывания в Cloudflare Workers, Netlify Functions и Vercel Functions. Этот раздел пригодится, если нужен размещённый шлюз без собственного сервера; о Docker, Render и Heroku см. [Docker, Render и Heroku](/ru/deployment/containers).

Шаблоны скачивают готовые архивы релиза во время сборки, поэтому инструментарий Rust не нужен. Консоль и API работают на домене развёртывания, консоль доступна по пути `/console/`.

## Выбор платформы

| Платформа | База данных платформы | Существующая база данных | WebSocket / Realtime |
| --- | --- | --- | --- |
| [Cloudflare Workers](#cloudflare-workers) | D1, создаётся при развёртывании | libSQL / Turso | Поддерживается |
| [Netlify Functions](#netlify) | Netlify Database | PostgreSQL | Не поддерживается |
| [Vercel Functions](#vercel) | Продукт PostgreSQL, выбранный при развёртывании | PostgreSQL | Поддерживается (бета-версия платформы) |

Все три платформы обслуживают HTTP и потоковую передачу SSE. Если клиентам нужны WebSocket или Realtime, выберите Cloudflare Workers или Vercel либо запустите [CLI или контейнер](/ru/download).

В Cloudflare шлюз работает внутри Worker как WebAssembly. В Netlify и Vercel небольшая функция на Node.js запускает нативный исполняемый файл `gproxy-serverless` и перенаправляет ему запросы. API управления и консоль на всех трёх платформах одинаковы; типы баз данных, допустимая длительность выполнения функции и ограничения на размер запроса определяются платформой.

## Перед развёртыванием

Каждый шаблон запрашивает два секрета. Подготовьте их заранее и сохраните копию.

- `GPROXY_ADMIN_PASSWORD`: пароль консоли, не короче 8 символов.
- `GPROXY_MASTER_KEY`: 32-байтовый ключ, которым шифруются учётные данные провайдеров в базе данных; записывается как 64 шестнадцатеричных символа или в base64. Сгенерировать его можно командой `openssl rand -hex 32`.

Имя пользователя — `admin`, если не задана также переменная `GPROXY_ADMIN_USER`. Пароль применяется при каждом запуске: если пользователь с таким именем существует, меняется только его пароль; если нет, администратор `0` снова включается и получает заданные имя и пароль. Полные правила описаны в разделе [Первоначальная настройка](/ru/reference/configuration#bootstrap) справочника по конфигурации.

<Warning>
При каждом обновлении и повторном развёртывании используйте один и тот же `GPROXY_MASTER_KEY`. Учётные данные, зашифрованные одним ключом, нельзя расшифровать другим, поэтому с новым ключом все сохранённые учётные данные провайдеров станут нечитаемыми.
</Warning>

Если вы подключаете существующую базу данных, а не базу платформы, подготовьте и параметры подключения к ней. Какие значения нужны, указано в разделе каждой платформы.

## Cloudflare Workers

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)][cloudflare-auto]

[Использовать внешнюю базу данных libSQL / Turso][cloudflare-external]

Кнопка развёртывания создаёт базу данных D1. Вторая ссылка развёртывает вариант, который подключается к существующей базе libSQL или Turso и не создаёт D1.

1. Откройте нужный вариант и подключите учётную запись GitHub или GitLab.
2. Для D1 выберите имя базы данных; Cloudflare создаст базу и привяжет её под именем `DB`. Для внешней базы данных введите `GPROXY_DATABASE_URL` и `GPROXY_LIBSQL_TOKEN`.
3. Введите пароль администратора и мастер-ключ. Оставьте команду сборки `npm run build` и команду развёртывания `npm run deploy` без изменений и запустите развёртывание.

URL Turso можно записать как `libsql://your-db.turso.io` или как равнозначный адрес HTTPS. Worker обращается к libSQL через его HTTP-интерфейс, поэтому строка подключения PostgreSQL здесь не подойдёт.

Развёртывание с D1 можно позже переключить на libSQL, задав те же две переменные; `GPROXY_DATABASE_URL` имеет приоритет над привязкой D1. При смене подключения выбирается другая база данных. Из D1 ничего не копируется.

О том, как развернуть Worker самостоятельно с помощью Wrangler или изменить его конфигурацию, см. [Ручное развёртывание в Cloudflare](#ручное-развёртывание-в-cloudflare).

## Netlify

[![Deploy to Netlify](https://www.netlify.com/img/deploy/button.svg)][netlify-auto]

[Использовать существующую базу данных PostgreSQL][netlify-external]

Кнопка развёртывания использует Netlify Database. Вторая ссылка открывает тот же шаблон с полем для подключения к внешней базе PostgreSQL.

1. Откройте нужный вариант, разрешите доступ к репозиторию и введите пароль администратора и мастер-ключ.
2. С Netlify Database функция сама читает строку подключения платформы, вводить ничего не нужно. Для существующей базы данных укажите её строку подключения PostgreSQL в `GPROXY_DATABASE_URL`.
3. Оставьте команду сборки и конфигурацию Functions из шаблона без изменений и запустите развёртывание.

Строка подключения к внешней базе выглядит как `postgresql://user:password@db.example.com/gproxy?sslmode=require`; подставьте значения, которые выдал поставщик базы данных.

Netlify может создать базу данных платформы, даже если указано внешнее подключение. Это ничему не мешает: `GPROXY_DATABASE_URL` проверяется первой.

## Vercel

[![Deploy with Vercel](https://vercel.com/button)][vercel-auto]

[Использовать существующую базу данных PostgreSQL][vercel-external]

Кнопка развёртывания предлагает подключить новый продукт PostgreSQL. Вторая ссылка пропускает этот шаг и вместо этого запрашивает `GPROXY_DATABASE_URL`.

1. Откройте нужный вариант. При использовании кнопки развёртывания выберите и подключите продукт PostgreSQL, когда появится запрос.
2. Введите пароль администратора и мастер-ключ, а для существующей базы данных — ещё и `GPROXY_DATABASE_URL`.
3. Оставьте команду сборки и `vercel.json` из шаблона без изменений и запустите развёртывание.

Функция ищет строку подключения в `GPROXY_DATABASE_URL`, затем в `DATABASE_URL`, затем в `POSTGRES_URL`. Если подключённый продукт задаёт переменную с другим именем, скопируйте её значение в `GPROXY_DATABASE_URL`.

Шаблон использует Node.js Functions. Не переключайте его на Edge Runtime: функция запускает нативный исполняемый файл, а Edge Runtime этого не умеет.

## Вход в консоль

1. Откройте `https://your-domain/console/`. Туда же ведёт и сам домен без пути.
2. Войдите как `admin` (или под именем, заданным в `GPROXY_ADMIN_USER`) с настроенным паролем.
3. Добавьте провайдер и учётные данные и проверьте учётные данные.
4. Создайте маршрут модели и ключ API, затем отправьте запрос, как описано в разделе [Первый запрос](/ru/getting-started/first-request).

Клиенты используют URL развёртывания как базовый URL, например `https://gateway.example.com/v1`, и проходят аутентификацию с созданным ключом API.

Если шлюз в Netlify или Vercel не может запуститься, на запросы приходит ответ с кодом 503 и сообщением `GPROXY is unavailable. Check the deployment database and secrets in the platform console.` Изучите журналы функции. Обычные причины: база данных не подключена, строка подключения не начинается с `postgres://` или `postgresql://`, не задан пароль или мастер-ключ. Исполняемый файл должен сообщить о готовности в течение 45 секунд; недоступная база данных проявляется как превышение времени ожидания запуска. Кроме того, учётной записи PostgreSQL нужно право создавать схему `gproxy` и таблицы приложения.

## Обновление

Конфигурация, учётные записи и данные об использовании хранятся в базе данных, поэтому при обновлении заменяется только код. Сохраните базу данных и мастер-ключ.

Шаблон с D1, а также шаблоны Netlify и Vercel во время сборки скачивают последний стабильный релиз и сверяют его контрольную сумму SHA-256 с файлом `SHA256SUMS` релиза. Чтобы обновиться, очистите кеш сборки платформы и разверните заново. Чтобы закрепить версию, задайте переменной среды сборки `GPROXY_RELEASE_VERSION` тег релиза; в этом релизе должен быть архив для вашей платформы.

Шаблон Cloudflare с внешней базой данных устроен иначе: в его `prepare-release.mjs` указан фиксированный тег релиза (сейчас `v4.2.0`), а `GPROXY_RELEASE_VERSION` игнорируется. Чтобы обновить его, измените тег в этом файле в репозитории, созданном при развёртывании, и разверните заново.

Размещённые развёртывания не используют встроенное в консоль обновление исполняемого файла.

## Ограничения среды выполнения

Все шаблоны обрабатывают HTTP и SSE. Netlify Functions не принимают переход на WebSocket; на такие запросы шлюз отвечает кодом 501. Vercel поддерживает WebSocket через [WebSocket Beta](https://vercel.com/docs/functions/websockets). На любой платформе соединение WebSocket всё равно может закрыться из-за ограничений длительности функции и перезапуска экземпляров, поэтому клиенты должны переподключаться.

Шаблон Vercel задаёт `maxDuration` равным 300 секундам в `vercel.json`. Долгие запросы к моделям, большие файлы и высокая параллельность по-прежнему упираются в ограничения каждой платформы; сверьте актуальные лимиты [Netlify Functions](https://docs.netlify.com/build/functions/overview/) и [Vercel Functions](https://vercel.com/docs/functions/limitations) со своей нагрузкой.

Шаблоны Netlify и Vercel не настраивают хранилище файлов. Для S3 или R2, а также для файлов, которые клиенты скачивают по публичной ссылке, соберите собственный Worker, как описано ниже, или запустите CLI.

Конечным точкам OAuth и опубликованным ссылкам на файлы нужен публичный адрес шлюза. В Netlify и Vercel задайте его в `GPROXY_PUBLIC_BASE_URL`; без этой переменной функция использует production URL, который сообщает платформа. Если публичный адрес неизвестен, конечные точки OAuth используют `Host` каждого запроса, а ссылки для публикации остаются отключёнными. В Workers задайте `public_base_url` в `GPROXY_CONFIG` (см. ниже).

## Ручное развёртывание в Cloudflare

### Из архива релиза

Скачайте `gproxy-edge-cloudflare.zip` из релиза, распакуйте его и перейдите в каталог `cloudflare`. В нём находятся собранный Worker, консоль и `wrangler.toml`.

Для D1 установите зависимости и создайте базу данных:

```sh
pnpm install
pnpm exec wrangler d1 create gproxy
```

Скопируйте идентификатор базы данных, который выведет Wrangler, в `wrangler.toml`. Имя привязки `DB` не меняйте:

```toml
[[d1_databases]]
binding = "DB"
database_name = "gproxy"
database_id = "replace-with-your-database-id"
```

Сохраните мастер-ключ и пароль администратора как секреты, проверьте развёртывание и разверните Worker:

```sh
pnpm exec wrangler secret put GPROXY_MASTER_KEY
pnpm exec wrangler secret put GPROXY_ADMIN_PASSWORD
pnpm exec wrangler deploy --dry-run
pnpm exec wrangler deploy
```

Чтобы использовать libSQL вместо D1, задайте `GPROXY_DATABASE_URL` и `GPROXY_LIBSQL_TOKEN` и удалите неиспользуемую привязку D1. Архив релиза собран с поддержкой libSQL; при собственной сборке не отключайте эту функцию.

GPROXY создаёт таблицы при первом запуске. Выполнять миграции SQL через Wrangler не нужно.

### Конфигурация Worker

`GPROXY_CONFIG` содержит конфигурацию в виде документа JSON. Секреты с собственными именами, например `GPROXY_MASTER_KEY`, переопределяют соответствующие поля. В этом примере используется D1 и задаётся публичный адрес:

```toml
[vars]
GPROXY_CONFIG = '{"store":{"kind":"d1","binding":"DB"},"cache":{"kind":"store"},"public_base_url":"https://gateway.example.workers.dev"}'
```

Консоль отдаётся через Workers Assets, поэтому при её загрузке Worker не запускается. Сохраните маршрутизацию из шаблона, чтобы `/console/` обслуживался из ресурсов, а все остальные пути попадали в шлюз:

```toml
[assets]
directory = "./public"
binding = "ASSETS"
not_found_handling = "single-page-application"
run_worker_first = ["/*", "!/", "!/console", "!/console/*"]
```

Worker может использовать D1 или libSQL. В нём нет локального SQLite, TCP-подключений к базам данных и локального каталога для файлов. Для хранения файлов в S3 или R2 соберите Worker с функцией `s3`, задайте `GPROXY_S3_ACCESS_KEY_ID` и `GPROXY_S3_SECRET_ACCESS_KEY` и добавьте в конфигурацию поля хранилища файлов; они перечислены в [справочнике по конфигурации](/ru/reference/configuration).

### Сборка из исходного кода

Из корня репозитория:

```sh
rustup target add wasm32-unknown-unknown
cargo install worker-build
pnpm --dir console install --frozen-lockfile
pnpm --dir deploy/cloudflare install
pnpm --dir deploy/cloudflare build
pnpm --dir deploy/cloudflare check
```

`build` компилирует Worker в `deploy/cloudflare/build/`, а консоль — в `deploy/cloudflare/public/`; `check` выполняет пробный запуск Wrangler. Другие варианты сборки и упаковки описаны в разделе [Сборка из исходного кода](/ru/development/building).
