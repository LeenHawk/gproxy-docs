Эти указания предназначены для администраторов, переводящих развёртывание v3 на v4. При запуске v4 распознаёт базу данных v3 и преобразует её на месте; поддерживаются SQLite, PostgreSQL, MySQL и D1. Каталог данных или строка подключения и `GPROXY_MASTER_KEY` остаются прежними; ничего экспортировать не нужно, сбрасывать пароли тоже.

## Что меняется

Схема базы данных заменяется. Прежде чем обслуживать запросы, v4 читает таблицы v3 и записывает на их место таблицы v4. Вот что происходит с каждым видом данных:

- Провайдеры и учётные данные: известные имена каналов и их конфигурация переводятся, а секреты заново шифруются заданным мастер-ключом.
- Маршруты и участники: публичное имя модели маршрута становится именем маршрута. Каждое дополнительное имя становится отдельным маршрутом с копией участников.
- Пользователи, пароли, ключи API, организации и команды: переносятся. Хеши паролей (Argon2) и дайджесты ключей API сохраняются, поэтому существующие имена пользователей, пароли и ключи продолжают работать.
- Цены и бюджеты: пересчитываются в единицы v4. v4 хранит суммы с точностью до 9 знаков после запятой; значение с большим числом знаков округляется до ближайшего чётного, и это изменение указывается в отчёте.
- Разрешения, лимиты запросов и правила перезаписи: поддерживаемые формы переносятся. Изменившиеся значения и формы, которые нельзя сопоставить, перечисляются в отчёте.
- Разрешения команд и организаций: разворачиваются в отдельное пользовательское правило для каждого импортированного участника, включая отключённых пользователей. Правила отражают состав на момент обновления и не следуют за его последующими изменениями. Группа без импортированных участников указывается в отчёте как пропущенная. Экземпляры, обновлённые релизом, который ещё не разворачивал эти разрешения, их потеряли, и более поздний релиз их не восстанавливает.
- История использования: импортируется ограниченными пакетами с исходным числом токенов, атрибуцией и рассчитанной стоимостью. Ничего не переоценивается, квоты повторно не рассчитываются. Поля v3, для которых в v4 нет столбца, сохраняются в `metrics.v3`.
- Перехваченные запросы, журналы запросов, сеансы и история аудита: не преобразуются. Они остаются в резервной копии v3. Всем пользователям придётся снова войти в консоль.

Провайдер, канал или конфигурацию которого не удаётся перевести, пропускается вместе с зависящими от него строками, и отчёт об этом сообщает. Это касается только перевода: ошибка чтения базы данных или неверный мастер-ключ по-прежнему останавливают обновление.

Параметры запуска v3 продолжают работать. v4 по-прежнему принимает `--persistence db` и DSN `sqlite://`. Образ Docker устроен так же, как в v3 (данные в `/app/data`, пользователь `65532:65532`), но теги образов v3 запускают v3; переключитесь на тег v4.

## Подготовка

1. Найдите, где задан ваш `GPROXY_MASTER_KEY` (файл `.env`, unit-файл службы, переменные среды контейнера), и сохраните копию. Чтобы расшифровать учётные данные, v4 нужен тот же ключ; с другим ключом обновление остановится, ничего не изменив.
2. Сохраните копию исполняемого файла v3 или запишите тег образа v3. Они понадобятся для отката.
3. Запланируйте остановку всех экземпляров v3. Во время обновления писать в базу данных может только один процесс. Если вы запускаете v3 и v4 параллельно на разных базах данных, не давайте им одни и те же учётные данные OAuth: каждый из них обновляет токены и тем самым делает недействительными токены другого.
4. Если CLI работает с PostgreSQL или MySQL, убедитесь, что ваша сборка v4 содержит драйвер этой базы данных.

Затем, при остановленной v3, сделайте резервную копию базы данных:

<Tabs>
  <Tab title="SQLite">
    Скопируйте весь каталог данных. В нём находятся `gproxy.db` и, если есть, `gproxy.db-wal` и `gproxy.db-shm`; в файле WAL могут быть зафиксированные данные, которых ещё нет в `gproxy.db`, поэтому копируйте все три файла вместе.

    ```sh
    cp -a data data.v3-backup
    ```

    Во время обновления v4 также записывает собственную резервную копию рядом с базой данных (см. ниже), поэтому оставьте свободное место ещё на две копии базы: резервную и преобразованную.
  </Tab>
  <Tab title="PostgreSQL">
    ```sh
    pg_dump --format=custom --file=gproxy-v3.dump "$GPROXY_DSN"
    ```
  </Tab>
  <Tab title="MySQL">
    ```sh
    mysqldump --single-transaction --databases gproxy > gproxy-v3.sql
    ```
  </Tab>
  <Tab title="D1">
    ```sh
    wrangler d1 export gproxy --remote --output=gproxy-v3.sql
    ```
  </Tab>
</Tabs>

## Обновление

1. Остановите все экземпляры v3.
2. Установите исполняемый файл v4 вместо v3 или смените образ контейнера на тег v4. Для Workers разверните Worker v4 с той же привязкой D1 и теми же секретами.
3. Запустите v4 с тем же каталогом данных или строкой подключения и тем же `GPROXY_MASTER_KEY`. Преобразование можно также выполнить отдельным шагом командой `gproxy migrate`: она работает с тем же путём и затем завершается.
4. Следите за журналом. Для SQLite вы увидите `migrating v3 database to v4`, строку `migrated` для каждой таблицы, `v3 import complete` с числом строк, отброшенных строк и предупреждений и в конце `v3 migration complete` с путём к резервной копии. Всё, что изменило смысл, выводится под заголовком `Changed on the way in`, а строки, для которых нет формы в v4, — под заголовком `NOT migrated`.
5. Когда в журнале появится сообщение о том, что сервер слушает порт, войдите в консоль.

Worker преобразует свою базу данных при первом запросе после развёртывания. Частично преобразованный экземпляр не обслуживает запросы и не создаёт нового администратора, поэтому до окончания преобразования запросы завершаются ошибкой.

## Как выполняется преобразование

### SQLite

Прежде чем открыть HTTP-порт, v4 делает согласованный снимок базы данных v3 командой `VACUUM INTO`, которая учитывает зафиксированное содержимое WAL, и сохраняет его рядом с базой как `gproxy.db.v3-*.bak`. Этот снимок преобразуется в новую базу данных во временном каталоге рядом с исходной; учётные данные расшифровываются существующим мастер-ключом. Только после успешного импорта новая база данных переименовывается поверх исходного пути.

Если преобразование не удалось, исходный файл остаётся нетронутым: устраните причину, названную в журнале (например, верните исходный мастер-ключ), и запустите заново. Если процесс прерван до переименования, по этому пути по-прежнему лежит база данных v3, и при следующем запуске попытка повторяется. После переименования по этому пути находится база данных v4, журнал миграций которой отмечает её как актуальную, и последующие запуски проходят как обычные запуски v4. Повторно ничего не импортируется.

### PostgreSQL, MySQL и D1

Сначала v4 читает и проверяет данные v3, в том числе то, что мастер-ключ расшифровывает учётные данные. Только после этого все таблицы v3 переименовываются в `gproxy_v3_<original name>`, а таблицы v4 создаются под исходными именами. Конфигурация, учётные записи и история использования преобразуются из переименованных таблиц, и экземпляр начинает принимать запросы только после последнего шага.

Ход обновления хранится в таблице `gproxy_v3_upgrade`. В её столбце `report_json` перечислены пропущенные строки и предупреждения об изменившемся смысле. Учётные записи и данные об использовании записываются пакетами с контрольной точкой после каждого, поэтому прерванное обновление продолжается с места остановки при следующем запуске (а в Workers — при следующем запросе).

Каждая СУБД по-своему не допускает второй процесс:

- PostgreSQL удерживает сеансовую рекомендательную блокировку (advisory lock) на всё время обновления и переименовывает таблицы v3 в одной транзакции.
- MySQL удерживает сеансовую блокировку (`GET_LOCK`) на протяжении операторов DDL, которые фиксируются неявно, и переименовывает все таблицы v3 одним оператором `RENAME TABLE`.
- D1 переименовывает таблицы транзакционными пакетами. Аренда миграции, проверяемая при каждом пакете записи, не позволяет писать второму изоляту. Аренда прерванного обновления истекает в течение 60 секунд.

Второй экземпляр PostgreSQL или MySQL, обнаружив занятую блокировку, останавливается с сообщением `another instance is migrating this database; retry after it finishes`. В Workers сообщение предлагает повторить попытку после освобождения аренды.

После сбоя данные v3 по-прежнему находятся в архивных таблицах, а в таблицах v4 уже может быть часть импортированных данных. Устраните указанную ошибку и перезапустите экземпляр; обновление продолжится. Пока обновление не завершено, не удаляйте `gproxy_v3_upgrade` и не переименовывайте архивные таблицы.

## Проверка обновления

1. Прочитайте отчёт о преобразовании: для SQLite — в журнале запуска, для остальных СУБД — в `gproxy_v3_upgrade.report_json`. Особенно внимательно проверьте пропущенных провайдеров и изменения разрешений.
2. Выполните `gproxy migrate --status`. Команда перечисляет все миграции схемы этой сборки и показывает, применены ли они к базе данных. Она только читает данные и никогда не выполняет преобразование v3.
3. В консоли убедитесь, что провайдеры, учётные данные, маршруты, пользователи и ключи API на месте, а история использования показывает прежние итоги.
4. Отправьте запрос с существующим ключом API, как описано в разделе [Первый запрос](/ru/getting-started/first-request).

Убедившись, что всё в порядке, можно удалить `gproxy.db.v3-*.bak` (SQLite) или архивные таблицы `gproxy_v3_<name>` (остальные СУБД). Если отчёт нужно сохранить, оставьте `gproxy_v3_upgrade`. В дальнейшем изменения схемы v4 записываются в таблицу SeaORM `seaql_migrations`.

## Откат

v3 не может прочитать базу данных v4, а частично преобразованная база не является ни той, ни другой. Откат всегда означает восстановление данных v3. Всё, что записано после обновления (новые данные об использовании, изменения конфигурации), будет потеряно.

<Tabs>
  <Tab title="SQLite">
    1. Остановите v4.
    2. Переместите в сторону `gproxy.db` и, если есть, `gproxy.db-wal` и `gproxy.db-shm`.
    3. Скопируйте `gproxy.db.v3-*.bak` (или `gproxy.db` из собственной резервной копии) в `gproxy.db`.
    4. Снова установите исполняемый файл или тег образа v3 и запустите его с исходными параметрами и мастер-ключом.
  </Tab>
  <Tab title="PostgreSQL, MySQL и D1">
    1. Остановите все экземпляры.
    2. Восстановите резервную копию, сделанную перед обновлением, в пустую базу данных.
    3. Запустите v3 с восстановленной базой данных и исходным мастер-ключом.

    Не направляйте v3 на частично или полностью преобразованную базу данных.
  </Tab>
</Tabs>

## Импорт в отдельный экземпляр

Описанное выше обновление преобразует базу данных на месте. Чтобы вместо этого перенести базу данных или экспорт v3 в другой экземпляр v4, используйте `import --from-v3`:

```sh
gproxy --data-dir ./other-instance migrate
gproxy --data-dir ./other-instance import --from-v3 /path/to/v3-backup.db
```

Целевая база должна быть пустой или содержать только незавершённый предыдущий запуск того же импорта. Если секреты источника зашифрованы, передайте мастер-ключ v3 в `--source-master-key` или `GPROXY_IMPORT_SOURCE_MASTER_KEY`. Параметр `--skip-unmappable-providers` пропускает провайдеров, которых не удаётся перевести, как это делает автоматическое обновление; без него такой провайдер останавливает импорт.

На вход можно также подать документ JSON, полученный из `POST /admin/api/export` в v3 с `{"include_secrets": true}`. В таком экспорте нет хешей паролей, разрешений, лимитов запросов и моделей провайдеров, которые есть в базе данных SQLite. При импорте экспорта без хешей задайте пароль консоли параметром `--admin-password`; при импорте из SQLite он не нужен.
