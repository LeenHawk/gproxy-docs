Полному шлюзу нужны процесс и база данных, поэтому он работает нативно или в контейнере. На serverless-платформах вместо него работает `gproxy-lite`: отдельный тонкий движок с теми же каналами и тем же преобразованием протоколов, собранный в один модуль WebAssembly с небольшой оболочкой на JavaScript для каждой платформы.

## Что в нём есть и чего нет

`gproxy-lite` обслуживает одного оператора. В нём есть:

- все каналы полного шлюза, включая те, где вход выполняется через OAuth;
- все операции по HTTP во всех диалектах: генерация содержимого (потоковая и обычная), подсчёт токенов, эмбеддинги, изображения, список моделей, сжатие, файлы и видео. Запрос передаётся как есть, если апстрим говорит на диалекте клиента, и преобразуется, если нет;
- операции WebSocket на Cloudflare, которые пересылаются апстриму, поддерживающему WebSocket.

В нём нет:

- пользователей, организаций, команд, API-ключей и прав: один ключ доступа пропускает любой запрос;
- бюджетов, квот, цен, записей об использовании, лимитов запросов и записей аудита;
- нескольких учётных данных на провайдера, выбора учётных данных и повтора с другими учётными данными;
- маршрутов, псевдонимов и уровней: запрос сам называет провайдера;
- правил перезаписи и правил маршрутизации по операциям: маршрутизация задаётся значениями канала по умолчанию;
- консоли, API управления и синхронизации между экземплярами;
- MCP-серверов и служебных маршрутов каналов (страницы использования, запросы квот);
- локального каталога моделей и токенизатора: операция, которой нет у апстрима, отклоняется, а не оценивается;
- хранения файлов: на преобразованный запрос изображения нельзя ответить URL, только `b64_json`;
- преобразования клиента Responses WebSocket в HTTP-апстрим.

Если вам нужно что-либо из этого, используйте [контейнер](/ru/deployment/containers).

## Конфигурация

Вся конфигурация — один документ JSON в переменной среды `GPROXY_LITE_CONFIG`. В нём находятся ключ доступа и учётные данные апстримов, поэтому храните его как секрет.

```json
{
  "access_key": "what clients send as their API key",
  "providers": [
    { "name": "openai", "channel": "openai", "credential": "sk-..." },
    {
      "name": "local",
      "channel": "custom",
      "base_url": "https://llm.example.com",
      "config": { "dialects": ["openai_chat"] },
      "credential": "upstream-key"
    },
    {
      "name": "vertex",
      "channel": "vertex",
      "credential": { "kind": "service_account", "secret": { "type": "service_account" } }
    },
    { "name": "codex", "channel": "codex" }
  ]
}
```

| Поле | Значение |
| --- | --- |
| `access_key` | Ключ, который предъявляют клиенты: как bearer-токен, в `x-api-key`, в `x-goog-api-key` или в `?key=`. |
| `providers[].name` | Буквы, цифры, `.`, `_` и `-`. Это префикс пути и префикс модели. Имя `lite` зарезервировано. |
| `providers[].channel` | Идентификатор канала, как в [каталоге каналов](/ru/reference/channel-catalog). |
| `providers[].base_url`, `config` | Собственные настройки канала, те же, что у провайдера в полном шлюзе. |
| `providers[].credential` | Вставленный API-ключ в виде строки или `{ "kind", "secret" }` для секрета в формате самого канала. Для канала, в который выполняется вход, поле не указывается. |

Конфигурация, которую движок не может использовать (неизвестный канал, повторяющееся имя, учётные данные, которые канал не принимает), отклоняется при запуске, и на каждый запрос возвращается `500` с указанием причины.

## Обращение к провайдеру

- `/{provider}/v1/...` отправляет запрос этому провайдеру. Модель указывается под именем апстрима.
- Без префикса поле модели имеет вид `provider/model`.
- Если настроен один провайдер, префикс можно не указывать.

Если настроено несколько провайдеров, `GET /v1/models` без префикса перечисляет модели всех провайдеров, и каждый идентификатор начинается с имени провайдера.

```sh
curl https://your-deployment.example/v1/chat/completions \
  -H "Authorization: Bearer $ACCESS_KEY" -H "Content-Type: application/json" \
  -d '{"model":"openai/gpt-5.5","messages":[{"role":"user","content":"Hi"}]}'
```

## Вход в канал с OAuth

Вход в провайдера без `credential` выполняется через три пути, и все они защищены ключом доступа. Перенаправление браузера не должно попадать в само развёртывание.

<Steps>
  <Step title="Начало">
    ```sh
    curl -X POST https://your-deployment.example/lite/login/start \
      -H "Authorization: Bearer $ACCESS_KEY" -H "Content-Type: application/json" \
      -d '{"provider":"codex"}'
    ```

    В ответе приходит `session` и либо `authorize_url`, который нужно открыть в браузере, либо, при входе по коду устройства, `user_code` и `verification_uri`. Канал с обоими способами принимает `"mode": "authorization_code"` или `"device_code"`.
  </Step>
  <Step title="Авторизация">
    Откройте URL и подтвердите доступ. Вход по коду авторизации заканчивается на странице, которая не загружается (адрес `localhost`) или показывает код: скопируйте адрес целиком или код.
  </Step>
  <Step title="Завершение">
    ```sh
    curl -X POST https://your-deployment.example/lite/login/complete \
      -H "Authorization: Bearer $ACCESS_KEY" -H "Content-Type: application/json" \
      -d '{"session":"...","callback_url":"http://localhost:1455/auth/callback?code=...&state=..."}'
    ```

    Отправьте либо `callback_url`, либо `code`, но не оба. При входе по коду устройства отправьте только `session` и повторяйте запрос, пока ответ равен `{"status":"pending"}`, выжидая `interval_secs` секунд между запросами. `{"status":"ready"}` означает, что учётные данные сохранены.
  </Step>
</Steps>

`GET /lite/status` перечисляет всех провайдеров с состоянием их учётных данных: `none`, `configured`, `signed_in` или `dead`. `dead` означает, что upstream отказался продлевать учётные данные; причина указана в `reason`, и заменить их можно только новым входом.

## Как не потерять вход

Учётные данные с ограниченным сроком продлеваются, когда запрос обнаруживает, что срок истекает, ещё раз при ответе upstream `401` и по расписанию, чтобы вход пережил период без запросов. Каждый шаблон запускает расписание раз в сутки, в 04:00 UTC. `POST /lite/renew` (нужен ключ доступа) делает то же самое по требованию и отвечает, что произошло с каждым провайдером, у которого есть что продлевать:

```json
{
  "renewals": [
    { "provider": "codex", "outcome": "renewed" },
    { "provider": "claude", "outcome": "not_due" },
    { "provider": "kiro", "outcome": "no_credential" },
    { "provider": "gemini", "outcome": "failed", "reason": "..." }
  ]
}
```

Запуск, в котором хотя бы одно продление не удалось, записывается в журналах платформы как неудачный.

| Платформа | Что запускает | Где задано расписание | Ограничения |
| --- | --- | --- | --- |
| Cloudflare Workers | Cron Trigger и обработчик `scheduled` в Worker | `[triggers] crons` в `wrangler.toml` | Любой интервал от одной минуты на любом тарифе. На тарифе Free не больше пяти Cron Trigger на аккаунт. |
| Netlify | Scheduled Function `renew` | `[functions."renew"] schedule` в `netlify.toml` | Любой тариф. Запускается только на опубликованном развёртывании, не дольше 30 секунд, и не имеет URL. |
| Vercel | Cron Job, запрашивающий `GET /lite/renew` | `crons` в `vercel.json` | Hobby: не чаще раза в сутки, запуск в пределах указанного часа; более частое выражение приводит к ошибке развёртывания. Pro: от одной минуты. |

На Vercel задайте переменную окружения `CRON_SECRET` со случайной строкой не короче 16 символов и разверните проект заново. Vercel отправляет её как Bearer-токен запроса по расписанию, и функция принимает такой запрос только с ней. Без `CRON_SECRET` запрос по расписанию отклоняется, и по расписанию ничего не продлевается.

Раза в сутки достаточно для refresh token: он действует несколько дней или дольше. Если расписание не запускается или интервал длиннее срока жизни сессии (канал `playground` меняет cookie каждые десять минут), учётные данные по-прежнему продлеваются запросами, а после слишком долгого простоя нужно войти заново.

Продления одних и тех же учётных данных не пересекаются: некоторые upstream отзывают все токены входа, если refresh token предъявлен дважды. Перед продлением берётся аренда: запись в хранилище, создаваемая только при отсутствии и истекающая через 30 секунд. Другой экземпляр, обнаружив занятую аренду, ждёт до 10 секунд и использует продлённые учётные данные. Если владелец аренды завершился, она истекает, и её берёт следующее продление. Продление, которое длится дольше аренды, всё же может пересечься со следующим; тогда сохраняемый результат определяет сравнение с обменом.

## Состояние

Всё, что помнит движок, находится в одном хранилище «ключ — значение» на развёртывание: учётные данные, полученные при входе или обновлённые, незавершённые входы и состояние, которое преобразование протоколов хранит между запросами. Вставленные учётные данные остаются в конфигурации и записываются в хранилище, только когда канал их обновляет. Учётные данные хранятся в том виде, в каком их выдал провайдер, без шифрования мастер-ключом, как в полном шлюзе, поэтому ограничьте доступ к хранилищу на чтение.

| Платформа | Хранилище | Сравнение с обменом |
| --- | --- | --- |
| Cloudflare Workers | Один Durable Object с хранилищем SQLite | Атомарно: объект выполняет по одному вызову за раз, а его хранилище строго согласовано. |
| Netlify | Netlify Blobs, чтение со строгой согласованностью | Атомарно для записи (`onlyIfMatch`, `onlyIfNew`). В Blobs нет условного удаления, поэтому при удалении записывается отметка об удалении, а ключ остаётся; освобождённая аренда — такая же отметка, которую перезаписывает следующее продление. |
| Vercel | Upstash Redis из Marketplace | Атомарно: один скрипт Lua на единственном первичном узле. |

## Развёртывание

Шаблоны находятся в каталоге `deploy/lite` [репозитория](https://github.com/LeenHawk/gproxy). Сначала соберите модуль. Для этого нужен Rust с целью `wasm32-unknown-unknown` и `wasm-bindgen-cli` той версии, что указана в `Cargo.lock`:

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.130
sh deploy/lite/build.sh
```

В сборку попадают все каналы. Модуль занимает 10.7 MB, в сжатом виде (gzip) — 4.0 MB.

<Tabs>
  <Tab title="Cloudflare Workers">
    ```sh
    cd deploy/lite/cloudflare
    wrangler secret put GPROXY_LITE_CONFIG
    wrangler deploy
    ```

    Worker объявляет свой Durable Object в `wrangler.toml`, заранее ничего создавать не нужно. Для локального запуска скопируйте `dev.vars.example` в `.dev.vars` и запустите `wrangler dev`.
  </Tab>
  <Tab title="Netlify">
    ```sh
    cd deploy/lite/netlify
    npm install
    netlify env:set GPROXY_LITE_CONFIG '{"access_key":"..."}' --secret
    netlify deploy --prod
    ```

    Движок работает как Netlify Function. Функция выполняется не дольше 60 секунд, включая потоковую передачу, поэтому более долгая генерация обрывается. На запросы WebSocket возвращается `501`.
  </Tab>
  <Tab title="Vercel">
    Добавьте в проект Upstash Redis из Marketplace: он задаёт `KV_REST_API_URL` и `KV_REST_API_TOKEN`. Затем:

    ```sh
    cd deploy/lite/vercel
    vercel env add GPROXY_LITE_CONFIG
    vercel env add CRON_SECRET
    vercel deploy --prod
    ```

    Движок работает как функция Node.js с максимальной длительностью 300 секунд. На запросы WebSocket возвращается `501`.
  </Tab>
</Tabs>
