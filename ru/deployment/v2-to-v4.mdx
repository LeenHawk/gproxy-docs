Эти указания предназначены для администраторов, переводящих развёртывание v2 сразу на v4. В отличие от [обновления с v3 до v4](/ru/deployment/v3-to-v4), эта миграция выполняется офлайн: скрипт [migrate-v2-to-v4.py](https://github.com/LeenHawk/gproxy/blob/main/scripts/migrate-v2-to-v4.py) читает базу данных v2 и записывает новую базу данных v4, а исходная база не изменяется.

## Что меняется

За один запуск скрипт выполняет четыре этапа:

1. Снимок источника v2 в файл SQLite.
2. Обновление этого файла до v3 исполняемым файлом v3.0.22.
3. Импорт файла v3 в базу данных SQLite v4 исполняемым файлом v4.
4. Копирование базы данных v4 в целевую базу.

На этапах 2 и 3 используются те же преобразования, что и в самих исполняемых файлах v3 и v4, поэтому здесь действуют и их ограничения (см. [С v2 на v3](/ru/deployment/v2-to-v3) и [С v3 на v4](/ru/deployment/v3-to-v4)):

- Учётные записи, учётные данные, ключи API и история использования преобразуются.
- Некоторые разрешения и правила v2 сопоставить нельзя, и их придётся настроить заново.
- Подробные данные об использовании, которые ещё хранятся в v2, переносятся. Данные, уже удалённые политикой хранения v2, восстановить по агрегатам нельзя.
- Старые журналы запросов, сеансы, записи аудита и кеши не превращаются в записи v4.
- v4 хранит стоимость с точностью до 9 знаков после запятой. Точное историческое значение сохраняется в `metrics.v3.cost`.

Источником и целевой базой может быть SQLite, PostgreSQL или MySQL, причём они не обязаны быть одного типа.

## Подготовка

1. Остановите экземпляр v2 и сделайте резервную копию его базы данных. Скрипт открывает источник только для чтения, но резервную копию всё равно сделайте.
2. Подготовьте целевую базу: путь к ещё не существующему файлу SQLite или пустую базу данных PostgreSQL или MySQL. Это не должна быть база данных v2; если в целевой базе уже есть таблицы, скрипт откажется с ней работать. Целевая база PostgreSQL должна использовать схему `public`.
3. Если база данных v2 зашифрована, подготовьте её `GPROXY_MASTER_KEY`. Скрипт ожидает формат v2 — 32 байта в base64 — и при любом другом формате останавливается. v4 принимает то же значение.
4. Установите Python 3.10 или новее и скачайте два исполняемых файла: [v3.0.22](https://github.com/LeenHawk/gproxy/releases/tag/v3.0.22) и [v4](https://github.com/LeenHawk/gproxy/releases/latest). Скрипт проверяет их версии. Сборка v4 должна содержать драйвер целевой базы данных.
5. Если на какой-либо стороне используется PostgreSQL или MySQL, установите драйвер Python для неё (для SQLite ничего дополнительно не нужно) и скачайте скрипт:

```sh
python3 -m pip install 'psycopg[binary]>=3,<4'  # PostgreSQL
python3 -m pip install 'PyMySQL[rsa]>=1,<2'     # MySQL
curl -fL https://raw.githubusercontent.com/LeenHawk/gproxy/main/scripts/migrate-v2-to-v4.py -o migrate-v2-to-v4.py
```

Источник MySQL должен использовать таблицы InnoDB: они нужны скрипту для согласованного снимка. Для источника PostgreSQL вне схемы `public` передайте параметр `--source-schema`.

## Запуск миграции

Если на обеих сторонах SQLite:

```sh
python3 migrate-v2-to-v4.py \
  --source ./old-data/gproxy.db \
  --target ./new-data/gproxy.db \
  --v3-bin ./v3/gproxy \
  --v4-bin ./v4/gproxy
```

Для сервера баз данных укажите вместо любого из путей строку подключения, например `postgresql://user:password@host/database` или `mysql://user:password@host/database`. Строки подключения MySQL принимают параметры TLS `ssl-mode`, `ssl-ca`, `ssl-cert` и `ssl-key`.

Чтобы пароли не попадали в список процессов и историю командной оболочки, передайте строки подключения в `GPROXY_SOURCE_DSN` и `GPROXY_TARGET_DSN` и не указывайте `--source` и `--target`. Мастер-ключ читается из `GPROXY_MASTER_KEY`:

```sh
read -rsp 'Source database DSN: ' GPROXY_SOURCE_DSN; echo; export GPROXY_SOURCE_DSN
read -rsp 'Empty destination DSN: ' GPROXY_TARGET_DSN; echo; export GPROXY_TARGET_DSN
read -rsp 'Original master key (empty for plaintext): ' GPROXY_MASTER_KEY; echo; export GPROXY_MASTER_KEY
python3 migrate-v2-to-v4.py --v3-bin ./v3/gproxy --v4-bin ./v4/gproxy
```

Без `--v3-bin` и `--v4-bin` скрипт ищет `gproxy-v3` и `gproxy` в `PATH`. В текущем каталоге он создаёт закрытый рабочий каталог с именем `gproxy-v2-to-v4-*`; параметр `--work-dir` позволяет задать другой каталог, который ещё не должен существовать. Скрипт выводит начало каждого этапа:

```text
1/4 Snapshot v2 -> SQLite. Work directory: /srv/gproxy-v2-to-v4-k3j2x1
2/4 Upgrade SQLite -> v3
3/4 Upgrade SQLite -> v4
4/4 Copy v4 SQLite -> sqlite
Migration complete. Review reports in /srv/gproxy-v2-to-v4-k3j2x1; start v4 against the target with the same master key.
```

## Проверка результата

Все промежуточные базы данных (`v2.db`, `v3/gproxy.db`, `v4/gproxy.db`) и все отчёты остаются в рабочем каталоге:

| Файл | Содержимое |
| --- | --- |
| `snapshot-report.json` | Тип источника, число строк в каждой таблице и исправления, внесённые в снимок на этапе 1 |
| `v3-preflight.log`, `v3-import.log` | Вывод проверки и импорта v3.0.22 |
| `v3-verification.json` | Сравнение числа строк, хешей паролей и рассчитанной стоимости использования в v3 с v2 |
| `v4-import.log` | Вывод импорта v4, включая его отчёт о преобразовании |
| `v4-verification.json` | Проверки базы данных v4 |
| `target-schema.log` | Создание схемы в целевой базе PostgreSQL или MySQL |
| `target-verification.json` | Проверки целевой базы |

Проверки сравнивают между этапами учётные записи, дайджесты ключей API и историческую стоимость. Для целевой базы PostgreSQL или MySQL при финальном копировании также сравниваются число строк и контрольная сумма содержимого строк в каждой таблице.

1. Прочитайте `v3-import.log`, `v4-import.log` и файлы `*-verification.json`, особенно списки пропущенных строк и изменённых разрешений.
2. Запустите v4 с целевой базой и тем же мастер-ключом, например `gproxy --data-dir ./new-data` для приведённого выше примера с SQLite или с `GPROXY_DSN`, в которой задана строка подключения к целевой базе.
3. Войдите в консоль, проверьте провайдеров, пользователей и историю использования и отправьте тестовый запрос, прежде чем переключать клиентов.

В рабочем каталоге находятся базы данных и секреты. Закройте к нему доступ и удалите его, когда он станет не нужен.

## Если миграция завершилась ошибкой

Скрипт останавливается на первой ошибке и выводит `Migration failed:` с причиной; пароли и мастер-ключ в выводе скрыты. Источник он не трогает, а целевую базу не очищает. Найдите причину ошибки по журналам в рабочем каталоге и запустите скрипт снова с новым рабочим каталогом и пустой целевой базой.

На время этапа 2 v3.0.22 получает мастер-ключ как аргумент командной строки, поэтому ключ ненадолго виден в списке процессов. Не запускайте скрипт с включённой трассировкой оболочки (`set -x`).

## Откат

В базу данных v2 ничего не записывается. Чтобы вернуться, удалите целевую базу и снова запустите v2 с исходной базой данных и исходными параметрами.
