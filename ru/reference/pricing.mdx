На этой странице описано, как GPROXY вычисляет стоимость обмена по таблицам
цен и как эти таблицы редактировать. Она понадобится при вводе цен, при разборе
неожиданной стоимости и при настройке бюджетов расходов.

<a id="overview"></a>

## Общая схема

Движок рассчитывает стоимость каждого обмена при расчёте (settlement) по трём
данным: провайдер, модель провайдера и нормализованное использование, которое
канал извлёк из ответа. Бюджеты и наблюдатель (observer) видят одно и то же
вычисленное значение. (В v3 движок передавал использование наверх, а уровень
приложения вычислял стоимость повторно; в результате было два механизма
сопоставления моделей и два разных ответа на вопрос, что делать с моделью без
цены. В v4 стоимость считается в одном месте.)

Цены хранятся в трёх таблицах:

- `price_rules` — строка выбирает модель, при необходимости только для одного
  провайдера и одной операции;
- `price_rates` — базовая цена каждой метрики в рамках правила;
- `price_tiers` — переопределения цен токенов правила по длине промпта и по
  уровню обслуживания.

Все цены и расчёты ведутся в USD.

<a id="rule-selection"></a>

## Выбор правила

Правило применяется к обмену, если выполнены все условия:

- провайдер правила совпадает с провайдером обмена, или провайдер не задан
  (глобальное правило);
- glob-шаблон `modelPattern` совпадает с именем модели у провайдера;
- `operation` правила совпадает с операцией запроса или не задана (все
  операции).

Правила провайдера проверяются раньше глобальных. Внутри каждой группы
выигрывает правило с наименьшей парой `(priority, id)`.

| Поле | Значение |
| --- | --- |
| `providerId` | `null` — глобальное правило |
| `modelPattern` | glob с `*` / `?`, сопоставляется с именем модели у провайдера |
| `operation` | `null` — все операции выбранной модели |
| `priority` | меньшее значение проверяется раньше; при равенстве решает id |
| `currency` | должна быть `USD` |
| `enabled` | отключённые правила не учитываются |

Правило с валютой, отличной от `USD`, с недопустимым шаблоном или с
неизвестной операцией пропускается при сборке снимка конфигурации (см.
[Недопустимые строки](#invalid-rows)).

Если использование обмена передаётся по отдельным попыткам, каждая оплачиваемая
попытка оценивается по правилу для её собственной модели, и суммы складываются.
Попытки, помеченные как неоплачиваемые, пропускаются.

<a id="exchanges-with-no-matching-rule"></a>

### Обмен без подходящего правила

Если ни одно правило не подошло, обмен остаётся без цены: он ничего не стоит,
расчёт проходит как обычно, а в использовании появляется измерение

```json
{"dimensions": {"unpriced": "true"}}
```

Запрос при этом не отклоняется. Отсутствующая цена — пробел в конфигурации, и
по этому измерению можно найти модели, которые обслуживаются бесплатно, не
отказывая в обслуживании, пока кто-нибудь не введёт цену.

<a id="rate-rows"></a>

## Строки ставок

Строка ставки задаёт базовую цену одной метрики в рамках одного правила.

| Поле | Значение |
| --- | --- |
| `metric` | встроенный ключ метрики или любой собственный ключ, который выдаёт канал |
| `unit` | `token`, `count`, `second` или `character` |
| `unitQuantity` | положительный знаменатель: 1 000 000 токенов, 1 изображение, 60 секунд |
| `value` | неотрицательная цена `unitQuantity` единиц в USD |
| `conditions` | `null` — резервная строка; иначе непустой объект «имя измерения → скалярное значение», совпасть должны все условия |
| `priority` | среди строк одной метрики меньшее значение проверяется раньше |

Для каждой метрики строки с условиями проверяются в порядке `(priority, id)`.
Используется первая строка, все условия которой совпадают с измерениями
расчёта; если таких нет, используется резервная строка. Совпавшая строка с
условиями заменяет резервную цену, а не добавляется к ней.

```json
[{"metric":"input_tokens",  "unit":"token","unitQuantity":"1000000","value":"0.40"},
 {"metric":"output_tokens", "unit":"token","unitQuantity":"1000000","value":"1.60"},
 {"metric":"image_outputs", "unit":"count","unitQuantity":"1","value":"0.04",
  "conditions":{"quality":"hd","size":"1024x1024"},"priority":0}]
```

<a id="avoiding-double-billing"></a>

### Как избежать двойного списания

Каждая ставка должна оценивать количество, которое не оценивает никакая другая
ставка. В частности:

- кэшированный ввод считается отдельно от обычного ввода;
- подмножество токенов рассуждения или медиа, уже оплаченное в составе
  агрегата, нельзя оценивать ещё раз;
- цены вывода за изображение и за токен — взаимоисключающие варианты; задавайте
  обе, только если провайдер действительно берёт оба вида платы;
- общая строка `tool_calls` и конкретная строка `web_searches` не должны обе
  оплачивать один и тот же вызов;
- инструмент, который клиент объявил в запросе, не является выполнением на
  стороне сервера и не оплачивается.

<a id="metrics"></a>

## Метрики

Метрики токенов обычно оцениваются за 1 000 000 токенов:

```text
input_tokens          output_tokens           cached_input_tokens
cache_creation_tokens
reasoning_tokens      image_input_tokens      image_output_tokens
audio_input_tokens    cached_audio_input_tokens  audio_output_tokens
video_input_tokens    video_tokens
```

Метрики количества, длительности и символов:

```text
image_outputs   video_outputs   audio_seconds   video_seconds   audio_characters
search_units    web_searches    web_fetches     file_searches
code_interpreter_sessions       tool_calls      requests
```

Это список встроенных ключей, а не ограничение: метрика, которой в нём нет,
тоже оценивается, если на неё ссылается строка ставки.

Метрика, не относящаяся к токенам, оплачивается как

```text
amount × value / unitQuantity
```

Множители уровней обслуживания к таким метрикам не применяются.

`requests` — плата за запрос: за каждый оценённый обмен начисляется один
запрос.

<a id="cache-writes"></a>

### Запись в кэш

Запись в кэш учитывается как `cache_creation_tokens`. В использовании может быть
несколько групп записей с разным временем хранения, и каждая оценивается
отдельно. Чтобы задать цену для конкретного времени хранения, добавьте строку
ставки с условием `ttl_seconds`: `{"ttl_seconds":43200}` выбирает цену записи
на 12 часов, а строка без этого условия задаёт цену по умолчанию.

В уровне цены записи задаются списком, где `ttlSeconds: null` — запись по
умолчанию:

```text
cacheCreationPerMillion: [{"ttlSeconds":43200,"price":"5"}]
```

Цены указываются за миллион токенов. Время хранения только выбирает цену и не
участвует в умножении.

Чтение из кэша — одно значение `cached_input_tokens` без TTL.

<a id="tiers"></a>

## Уровни

Строка `price_tiers` переопределяет только цены токенов и всегда за миллион
токенов.

| Поле | Значение |
| --- | --- |
| `serviceTier` | `null` — уровень контекста; иначе уровень обслуживания, например `standard`, `priority`, `flex`, `batch` |
| `minPromptTokens` | неотрицательный порог включительно; по умолчанию 0 |
| `multiplier` | только для уровней обслуживания: множитель унаследованной цены. В уровнях контекста не задаётся |
| `*_per_million` | явная цена для одного вида токенов |

Столбцы явных цен: `input`, `output`, `cache_read`, `cache_creation`,
`reasoning`, `image_input`, `image_output`, `audio_input`, `cached_audio_input`,
`audio_output`, `video_input` и `video`, все с суффиксом `_per_million`.
`cache_creation_per_million` — список, описанный в разделе
[Запись в кэш](#cache-writes).

Для сравнения с порогом длина промпта равна сумме входных токенов, чтений из
кэша и записей в кэш, каждое учитывается один раз.

<a id="how-a-token-price-is-computed"></a>

### Как вычисляется цена токена

Цена каждого вида токенов определяется в три шага:

1. Базовая ставка: строка `price_rates` для этой метрики, строки с условиями
   проверяются первыми.
2. Уровень контекста: среди строк без уровня обслуживания берётся строка с
   наибольшим достигнутым `minPromptTokens`. Её явные цены заменяют базовую
   цену для тех видов, которые в ней заданы.
3. Уровень обслуживания: среди строк, указывающих фактически предоставленный
   уровень обслуживания, берётся строка с наибольшим достигнутым порогом. Явная
   цена в ней используется как есть. Иначе цена после второго шага умножается
   на `multiplier` этой строки (по умолчанию 1).

При одинаковых порогах выигрывает строка с меньшей парой `(priority, id)`.
Цена `null` наследуется с предыдущего шага; `0` означает, что вид токенов
бесплатен.

<Warning>
Явная цена уровня обслуживания заменяет всю лестницу под ним, включая уровень
контекста. Пусть базовая цена ввода равна 1, ступень контекста `≥ 200 000 → 2`,
а промпт содержит 300 000 токенов:

| Строка `batch` | Итоговая ставка ввода |
| --- | --- |
| `{"serviceTier":"batch","multiplier":"0.5"}` | `2 × 0.5 = 1` |
| `{"serviceTier":"batch","inputPerMillion":"0.5"}` | `0.5` (ступень 200k теряется) |
| `{"serviceTier":"batch","minPromptTokens":200000,"inputPerMillion":"1"}` | `1` |

Либо повторяйте явную цену уровня на каждом пороге, который она должна
покрывать, либо используйте множитель.
</Warning>

<a id="reasoning-tokens-and-cache-reads"></a>

### Токены рассуждения и чтение из кэша

Токены рассуждения — подмножество выходных токенов. Если в правиле есть цена
рассуждения, токены рассуждения вычитаются из `output_tokens` и оплачиваются
по этой цене. Если её нет, они остаются в выводе и оплачиваются один раз по
цене вывода.

Чтение из кэша без собственной цены наследует цену ввода. Все остальные виды
токенов без цены бесплатны. Чтение из кэша — это всегда входные токены, поэтому
цена ввода здесь безопасное значение по умолчанию. Отсутствующая цена аудио или
видео, напротив, означает пробел в конфигурации, и нулевая стоимость делает
этот пробел заметным в расходах.

<a id="requested-and-served-service-tier"></a>

### Запрошенный и предоставленный уровень обслуживания

Для расчёта используется уровень обслуживания, указанный в ответе, а не тот,
что был запрошен. Запрос `priority`, который провайдер понизил, оплачивается по
строке пониженного уровня. Имена уровней сравниваются без учёта регистра.

<a id="editing-prices"></a>

## Редактирование цен

У каждой таблицы своё семейство маршрутов администрирования:

```sh
curl -s http://127.0.0.1:8787/admin/api/price-rules  -H "Authorization: Bearer $GPROXY_KEY"
curl -s http://127.0.0.1:8787/admin/api/price-rates  -H "Authorization: Bearer $GPROXY_KEY"
curl -s http://127.0.0.1:8787/admin/api/price-tiers  -H "Authorization: Bearer $GPROXY_KEY"
```

В каждом семействе есть обычные пять маршрутов и пакетный маршрут. Пакет
фиксируется одной ревизией, сколько бы строк он ни содержал. В консоли
глобальные цены редактируются на странице **Модели**, а цены провайдера — на
его вкладке **Модели**; см. [Консоль](/ru/guides/console#quotas-and-prices).

<a id="applying-catalogue-prices"></a>

### Применение цен из каталога

Встроенный каталог моделей содержит цены моделей, известных на момент выпуска.
Чтобы создать правила из каталога:

```sh
curl -s -X POST http://127.0.0.1:8787/admin/api/default-model-catalog/apply-prices \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"providerId":"…","modelIds":["gpt-4o-mini"],"overwrite":false}'
```

Без `providerId` правило получает glob и приоритет из каталога, так что одно
глобальное правило оценивает модель у любого провайдера, который её
обслуживает. С `providerId` шаблоном становится буквальное имя модели, а
приоритет равен 0.

С `"overwrite": false` каталог можно применять повторно в любой момент:
существующее правило, например изменённое вами, остаётся без изменений и
учитывается в ответе как пропущенное.

<a id="invalid-rows"></a>

### Недопустимые строки

Строка цен, которую нельзя использовать (правило не в USD, недопустимый
шаблон, неизвестная операция, ставка с неположительным `unitQuantity`, условия,
не являющиеся непустым объектом скалярных значений), отбрасывается с
предупреждением при сборке снимка конфигурации. Остальная часть снимка
загружается как обычно, поэтому одна опечатка не останавливает экземпляр,
который в остальном обслуживает трафик. После правки цен проверьте журнал на
такие предупреждения.

<a id="budgets"></a>

## Бюджеты

Бюджет расходов — строка `quotas` с метрикой `cost` в USD. При допуске запроса
движок получает цепочку вызывающего, `[api_key?, user, team?, org?]`, и к
запросу применяется каждый включённый бюджет каждого владельца в этой цепочке.

Стоимость рассчитывается после ответа провайдера, поэтому выполняющиеся и
параллельные запросы могут вывести бюджет за предел. Владение бюджетами и сами
проверки описаны в разделе
[Разрешения, лимиты запросов и бюджеты](/ru/guides/permissions).

<a id="token-estimation"></a>

## Оценка токенов

Если оплачиваемый ответ совсем не содержит использования, движок сам считает
токены и помечает запись `estimated = true`. Подсчёт ведётся по локальному
словарю, который выбирается в таком порядке:

1. кодировки tiktoken для моделей семейства GPT;
2. словарь, указанный в строке каталога для модели;
3. встроенный словарь DeepSeek.

Чтобы получить список сохранённых словарей или загрузить словарь с Hugging Face
и назначить его модели и экземпляру по умолчанию:

```sh
curl -s http://127.0.0.1:8787/admin/api/tokenizer-vocabs -H "Authorization: Bearer $GPROXY_KEY"
curl -s -X POST http://127.0.0.1:8787/admin/api/tokenizer-vocabs \
  -H "Authorization: Bearer $GPROXY_KEY" -H 'content-type: application/json' \
  -d '{"repo":"…","filename":"tokenizer.json","modelId":"…","setAsDefault":true}'
```

Загруженный файл сначала записывается в настроенное файловое хранилище. Затем
одной ревизией записываются строка словаря, ссылка модели и ссылка по
умолчанию. Порядок важен: строка, указывающая на файл, который так и не был
записан, ломала бы каждую последующую перезагрузку, а файл без строки лишь
занимает место.

Словарям нужно файловое хранилище. Без него все маршруты словарей отвечают
«не поддерживается». См. [Файловое хранилище](/ru/reference/database#file-storage).
