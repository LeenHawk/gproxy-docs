В GPROXY три компонента хранения, и каждый настраивается отдельно: база данных,
кэш и необязательное файловое хранилище. На этой странице описаны бэкенды
каждого из них, способ выбора и то, что нужно учесть при запуске нескольких
экземпляров и планировании резервного копирования.

<a id="database"></a>

## База данных

База данных хранит всю конфигурацию, учётные записи, использование и журналы.
Нативный бинарный файл (`gproxy`) работает с SQLite, PostgreSQL и MySQL; хост
Cloudflare Workers — с D1 и libSQL.

| Бэкенд | Подключение | Где доступен |
| --- | --- | --- |
| SQLite (по умолчанию) | `<data-dir>/gproxy.db`, либо путь к файлу или URL `sqlite://` в `--dsn` | нативный бинарный файл, встроен всегда |
| PostgreSQL | `postgres://…` в `--dsn` | нативный бинарный файл, feature `postgres` (включена по умолчанию) |
| MySQL | `mysql://…` в `--dsn` | нативный бинарный файл, feature `mysql` (включена по умолчанию) |
| D1 | привязка D1 воркера (по умолчанию `DB`) | хост Workers |
| libSQL / Turso | URL `libsql://` или `https://` в `GPROXY_DATABASE_URL`, токен в `GPROXY_LIBSQL_TOKEN` | хост Workers |

MySQL нужна версии 8.0.13 или новее: это первая версия, допускающая выражения
по умолчанию для JSON. Драйверы PostgreSQL и MySQL собраны с поддержкой TLS.

<a id="selecting-a-backend"></a>

### Выбор бэкенда

Для нативного бинарного файла обычно достаточно `--dsn` (`GPROXY_DSN`): если
`--persistence` (`GPROXY_PERSISTENCE`) не задан, бэкенд определяется по схеме
URL.

```sh
gproxy serve --dsn 'postgres://gproxy:…@db.internal:5432/gproxy'
```

`GPROXY_PERSISTENCE` принимает `sqlite`, `postgres` или `mysql`. DSN вида
`sqlite://`, оставшийся от развёртываний v2 или v3, принимается, и
используется путь к файлу из него. `:memory:` отклоняется: экземпляр, чья база
исчезает вместе с процессом, создал бы администратора, обслуживал бы трафик и
затем всё это потерял.

Бэкенд, которого нет в сборке, отклоняется при запуске с ошибкой, где названа
нужная feature. Проблема обнаруживается при старте процесса, а не на первом
запросе. Нативный бинарный файл также отклоняет D1 и libSQL — их открывает
только хост Workers; его привязки описаны в разделе
[Cloudflare Workers](/ru/deployment/edge). В хосте Workers
`GPROXY_DATABASE_URL` имеет приоритет над привязкой D1. libSQL обращается к
базе по HTTP через тот же транспорт fetch, которым воркер вызывает провайдеров.

<a id="schema-synchronization"></a>

### Синхронизация схемы

```text
$ gproxy migrate --data-dir ./data
INFO gproxy::instance: schema is up to date warnings=0
```

Схема выводится из определений сущностей, а не из пронумерованной
последовательности миграций. Таблицы описаны в одном реестре. Синхронизация
создаёт недостающие таблицы в новой базе, а в существующей добавляет
недостающие столбцы и индексы там, где бэкенд это поддерживает. Повторный
запуск сохраняет все строки.

`gproxy serve` тоже синхронизирует схему при запуске. `gproxy migrate` нужен
развёртываниям, которые выполняют синхронизацию отдельным шагом, одним
процессом-писателем, до запуска экземпляров. Так и следует делать, когда
несколько экземпляров работают с одной базой, чтобы они не меняли схему
одновременно.

Синхронизация не делает следующего:

- не создаёт настройки по умолчанию и администраторов;
- не выполняет версионированные миграции;
- не меняет тип столбца, не преобразует его данные и не меняет существующие
  внешние ключи.

Для таких изменений нужна явная миграция, и GPROXY не гарантирует, что она
выполнится одной транзакцией на каждом нативном бэкенде.

Отчёт синхронизации содержит предупреждения, например о различиях типов в D1.
Пустой список не доказывает, что все изменения применены. Прежде чем считать
запуск завершённым, прочитайте диагностику в журнале.

<a id="store-api-and-batches"></a>

### API хранилища и пакеты

Нативные соединения SeaORM и Cloudflare D1 используются через один и тот же
API хранилища. Все методы доступа к сущностям проходят через один обобщённый
репозиторий, поэтому обычный CRUD не пишется отдельно для каждой таблицы, а
каждый метод выполняется одним атомарным пакетом. Создание хранилища не
открывает базу и не меняет схему.

На следующие свойства этого API можно полагаться:

- чтение возвращает результаты в порядке входных данных, сохраняет дубликаты и
  возвращает `None` для отсутствующего id, так что каждый результат можно
  сопоставить с запросом;
- предикат по ключам разбивается так, чтобы каждый оператор укладывался в
  ограничение D1 в 100 связанных параметров; части по-прежнему выполняются в
  одном пакете. SQL, написанный вызывающей стороной, не разбивается, и
  собственные ограничения базы на число и размер запросов продолжают
  действовать;
- ошибка SQL откатывает транзакционную запись. Условная запись, не затронувшая
  ни одной строки, возвращает конфликт и не откатывает остальную часть пакета;
- автоматических повторов нет. Если результат фиксации неизвестен (например,
  оборвалось соединение), проверьте сохранённое состояние, прежде чем
  повторять запись.

<a id="exact-amounts"></a>

### Точные суммы

Деньги и лимиты хранятся как масштабированные целые числа, а не числа с
плавающей точкой. Одна единица равна `0.000000001`, представимый диапазон —
примерно ±9,2 миллиарда.

Столбцы SQL имеют тип `BIGINT`. Сущности передают эти значения через границу
JavaScript в D1 как текст, чтобы сравнение, сортировка и сложение внутри базы
оставались числовыми; в JSON по той же причине используются десятичные строки.

Вычисления выполняются в десятичном типе с однократным округлением всего
расчёта, половины округляются к чётному. Перед увеличением счётчика расчёт
проверяет отрицательные значения и знаковое переполнение.

<a id="the-cache"></a>

## Кэш

Кэш хранит кратковременное состояние: значения с TTL, точные счётчики,
разрешения и аренды, а также топик инвалидации. Бизнес-сущностей и
долговременного учёта в нём нет; всё, что должно сохраняться, пишется в базу
данных.

| Бэкенд | Как выбирается | Общий для |
| --- | --- | --- |
| Память | по умолчанию в нативном бинарном файле (feature `memory`) | никого; один процесс |
| Redis / Valkey | `GPROXY_REDIS_URL`; бинарный файл должен быть собран с feature `redis` | всех экземпляров с одним Redis |
| База данных | по умолчанию в хосте Workers | всех изолятов с одной базой |

Нативный бинарный файл подключается к Redis при запуске и завершается, если
подключиться не удалось. Лимиты запросов считаются в кэше, поэтому экземпляр
без доступа к Redis принимал бы трафик лишь для того, чтобы отклонять каждый
запрос с лимитом. Кэш в базе данных предназначен только для хоста Workers;
нативный бинарный файл такую настройку отклоняет. Набор feature по умолчанию,
с которым собираются выпускные бинарные файлы, не включает `redis` и `s3`;
если они нужны, соберите бинарный файл сами (см.
[Сборка](/ru/development/building)).

<a id="operations"></a>

### Операции

| Операция | Поведение |
| --- | --- |
| `get` / `put` / `delete` | непрозрачные байты; положительный TTL обязателен; каждый put создаёт новую версию |
| `compare_exchange` | замена или удаление, если текущая версия совпадает с ожидаемой или ключ отсутствует |
| `counter` / `increment` / `decrement` | точные неотрицательные целые с атомарной проверкой верхней границы |
| `acquire_permit` | не более N живых владельцев, у каждого свой TTL |
| `acquire_lease` | разрешение с лимитом 1, используется как аренда на обновление |
| `publish` / `subscribe` | подсказки об инвалидации; доставка не гарантируется |

Каждая операция атомарна в пределах одного ключа; между ключами атомарности
нет. Пары ключ/значение, счётчики, разрешения и топики — отдельные
пространства имён, и одно и то же имя может существовать в каждом.

Счётчик использует фиксированное окно. TTL задаёт только вызов, создающий
счётчик, поэтому каждый экземпляр вычисляет границу окна по одним лишь часам.
У разрешения окна нет: оно считает запросы, которые выполняются в данный
момент, а граница окна их не делит. Его TTL лишь ограничивает время, через
которое кэш заберёт разрешение у запроса, завершившегося без освобождения.

<a id="cache-failures"></a>

### Сбои кэша

При сбое Redis GPROXY не переходит на кэш в памяти процесса. Два экземпляра,
каждый из которых откатился бы на локальное состояние, держали бы
конфликтующие блокировки и считали бы один и тот же лимит по отдельности, а
это хуже ошибки.

Запрос, на который распространяется лимит запросов и который кэш не может
проверить, отклоняется с кодом `429` без подсказки `Retry-After`. Если бы такие
запросы пропускались, сбой кэша незаметно отключал бы все лимиты на
экземпляре, и оператор бы этого не увидел.

<a id="running-more-than-one-instance"></a>

### Несколько экземпляров

Нескольким экземплярам нужен общий кэш: Redis для нативных экземпляров или кэш
в базе данных в Workers. С кэшем на процесс каждый экземпляр считает свои
лимиты запросов, каждый обновляет один и тот же токен OAuth, и ни один не
видит инвалидаций конфигурации от других.

Сеансы входа тоже хранятся в кэше, поэтому вход, начатый на одном экземпляре,
можно завершить на другом. За балансировщиком нагрузки так обычно и бывает.

Если один сервер Redis используют несколько развёртываний или окружений,
задайте каждому своё пространство имён (по умолчанию `gproxy`). Имя канала
уведомлений включает номер базы данных, потому что Redis Pub/Sub игнорирует
`SELECT`.

<a id="database-backed-cache"></a>

### Кэш в базе данных

У изолята Workers нет долгоживущего процесса и нет Redis, поэтому хост Workers
держит кэш в трёх таблицах своей базы D1 или libSQL. Срок действия
сравнивается в SQL, так что все изоляты на одной базе одинаково определяют,
какие записи ещё действительны.

У этого бэкенда нет транспорта уведомлений. Подписка выдаёт начальную
подсказку о повторной синхронизации, и больше ничего. Вместо этого хост
Workers читает ревизию конфигурации в начале каждого запроса; в этом и состоит
весь его механизм синхронизации.

<a id="configuration-synchronization"></a>

## Синхронизация конфигурации

Запись конфигурации проходит такие шаги:

```text
commit_revision([statements…, config_revision += 1, read back])   one transaction
      ↓
reload   this instance's snapshot
      ↓
publish  ConfigurationChanged { revision, scopes }
```

Строки и увеличение ревизии записываются одной транзакцией. Если бы они
записывались отдельно, другой экземпляр мог бы прочитать новую ревизию раньше,
чем появятся строки.

Остальные экземпляры узнают об изменении двумя способами, и нужны оба:

| Механизм | Что передаёт | Как отказывает |
| --- | --- | --- |
| инвалидация в общем кэше | «проверь снова», за миллисекунды | сообщения могут теряться |
| опрос `settings.config_revision` | сохранённую ревизию, каждые 30 секунд | медленно |

Уведомление никогда не несёт саму конфигурацию. Оно называет ревизию, и
экземпляр перезагружается, только если она новее той, что он обслуживает.
Нераспознанное содержимое уведомления вызывает перезагрузку.

Счётчик в кэше не может заменить ревизию в базе данных. Перезапуск Redis или
вытеснение могут его потерять, а фиксация в базе и последующая публикация в
топик — две отдельные операции, а не одна транзакция.

Перезагрузки выполняются по одной и только вперёд: старая ревизия никогда не
заменяет более новую, а при неудачной перезагрузке продолжает работать
предыдущий снимок.

<a id="file-storage"></a>

## Файловое хранилище

Файловое хранилище необязательно и выключено, пока не настроен бэкенд.

| Бэкенд | Как выбирается | Нативный бинарный файл | Хост Workers |
| --- | --- | --- | --- |
| Локальная файловая система | `--file-storage-dir` (feature `fs`, включена по умолчанию) | да | нет |
| S3-совместимое, включая R2 | блок `[file_storage]` (feature `s3`) | да | да |

В нём хранятся тела публикаций (байты, отдаваемые по `/publications/{id}`) и
загруженные словари токенизатора. Метаданные файлов и сведения о владельцах
хранятся в базе данных; бэкенд хранилища содержит только содержимое.

Без файлового хранилища публикация и загрузка словарей отвечают «не
поддерживается»: байты негде хранить.

Ссылке на публикацию также нужен `GPROXY_PUBLIC_BASE_URL`. Без него публикация
завершается ошибкой до записи тела, и вызывающей стороне предлагается запросить
байты inline. GPROXY не строит ссылку из заголовка `Host` запроса, потому что
его выбирает клиент: провайдер принял бы ответ, байты были бы сохранены, а
выданный URL мог бы указывать на хост, где он вернёт 404.

<a id="backups"></a>

## Резервные копии

- SQLite: остановите процесс и скопируйте `<data-dir>/gproxy.db` или
  используйте онлайн-резервное копирование SQLite. Храните мастер-ключ вместе
  с копией: без него секреты учётных данных в зашифрованной базе не прочитать.
- PostgreSQL и MySQL: штатные средства дампа базы.
- D1 и libSQL / Turso: снимки платформы.
- Логический экспорт: `gproxy export --out config.json --include-secrets`.
  Экспорт содержит конфигурацию, а не историю: учётные записи, использование и
  захваты в него не входят. См.
  [Конфигурация](/ru/reference/configuration#moving-a-configuration).

Каждый зашифрованный секрет привязан к id своей строки. Восстановить секрет
одной строки в другую строку нельзя. Это защищает от подмены секретов между
строками и не мешает восстановлению базы целиком.
