На этой странице перечислены все HTTP-маршруты экземпляра и порядок, в котором
разбирается путь запроса. Она пригодится, когда нужно понять, какой URL ведёт к
какой операции, что меняет префикс провайдера или пространства имён и как
запрос переключается между провайдерами при сбоях. Нативный хост и хост Workers
монтируют одну и ту же таблицу. Сам `gproxy-protocol` путей не объявляет:
соответствие URL и операций определяет описанный здесь входной слой.

Полные схемы запросов и ответов для каждого маршрута приведены в
[справочнике HTTP API](/ru/reference/http-api).

<a id="gateway-routes"></a>

## Собственные маршруты шлюза

Собственных маршрутов у шлюза немного; все остальные пути передаются
плоскости данных. Обычно бывает наоборот, но здесь собственные маршруты — это
короткий фиксированный список, а всё прочее — API upstream, которые экземпляр
пересылает. Поэтому поддержка нового API upstream не требует нового маршрута.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/healthz` | проверка работоспособности и опубликованная ревизия конфигурации; без аутентификации |
| `GET` | `/info` | имя экземпляра, версия и хеш сборки |
| `GET` | `/robots.txt` | запрет для всех поисковых роботов |
| `GET` | `/publications/{id}` | опубликованное тело. Сам id служит учётными данными, ключ не нужен |
| — | `/admin/api/…` | API управления |
| — | `/portal/api/…` | API личного кабинета пользователя |
| — | всё остальное | входная обработка (OAuth issuer, сервисы провайдеров, плоскость данных, консоль) |

```sh
curl -s http://127.0.0.1:8787/healthz
```

```json
{"revision":2,"status":"ok"}
```

`/healthz` читает опубликованный снимок и не обращается ни к базе данных, ни к
кешу, поэтому частый опрос балансировщиком нагрузки их не нагружает.

Каждый ответ содержит заголовок `x-robots-tag: noindex, nofollow`.

<a id="request-processing-order"></a>

## Порядок обработки запроса

Запрос, не попавший в собственные маршруты шлюза, обрабатывается в таком
порядке:

1. CORS и адрес клиента. Предварительный запрос CORS получает ответ здесь и
   никуда не пересылается: он спрашивает, что принимает этот экземпляр. Адрес
   клиента определяется по [правилу доверенных прокси](/ru/reference/configuration#trusted-proxies)
   до того, как что-либо попадёт в журнал.
2. Точка монтирования: какая начальная часть пути относится к шлюзу (см.
   [Точки монтирования](#mounts)).
3. OAuth issuer по адресу `{mount}/v1/oauth/…`. Эти пути принадлежат самому
   экземпляру, а не upstream, и отвечают ошибками в формате OAuth, поэтому
   сопоставляются раньше плоскости данных.
4. Сервисный маршрут канала, например `/backend-api/…` у Codex или `/api/…` у
   Claude Code. Только на точке монтирования провайдера или пространства имён:
   для сопоставления нужен канал, а агрегированная точка его не задаёт.
5. [Плоскость данных](#data-plane-endpoints).
6. Консоль с SPA-откатом, если она включена.

Запрос, не подошедший ни под один пункт, получает 404.

## Конечные точки плоскости данных

Прежде всего, ещё до аутентификации, размер тела запроса ограничивается
`settings.maxRequestBodyBytes` (по умолчанию 128 МиБ), а для загрузки файла —
`maxUploadBodyBytes` (512 МиБ).

<a id="dialect-selection-on-shared-paths"></a>

### Выбор диалекта на общих путях

`/v1/models`, `/v1/models/{id}` и `/v1/files` одинаково записываются в API v1
OpenAI, Claude и Gemini. От диалекта зависит, в какие типы протокола
выполняется преобразование, и ошибка даст клиенту тело, которое он не сможет
разобрать.

Шлюз решает по заголовкам аутентификации самого клиента: `x-goog-api-key`
означает Gemini, `anthropic-version` или `x-api-key` — Claude. SDK поставщиков
отправляют эти заголовки всегда. Если нет ни одного, выбирается первая строка
таблицы, то есть OpenAI.

<a id="file-and-video-ownership"></a>

### Владение файлами и видео

Идентификаторы файлов и видео выдаёт upstream, а одни учётные данные upstream
обычно используют многие клиенты, поэтому шлюз сам ведёт учёт того, кто что
создал. Успешная загрузка или создание видео записывается на клиента и на
учётные данные, которые обслужили запрос. Все ключи и сеансы консоли одного
пользователя считаются одним клиентом; каждая выдача OAuth — отдельным.

- Получение, скачивание, опрос или удаление по id возвращает 404, если только
  этот клиент не создал объект через шлюз. Ответ одинаков для чужого и
  несуществующего id. Запрос отправляется с учётными данными, у которых
  хранится ресурс.
- Список показывает только собственные объекты клиента. Курсоры страниц
  (`has_more`, `last_id`, `nextPageToken`) передаются без изменений, поэтому на
  странице может быть меньше объектов, чем `limit`, или ни одного, хотя
  страницы ещё есть. Листайте, пока upstream не сообщит, что больше нет.
- Файлы и видео, созданные до появления этой проверки или напрямую в upstream,
  через шлюз недоступны.
- Возобновляемая загрузка Gemini (режим по умолчанию в SDK google-genai)
  работает как обычно. `x-goog-upload-url`, который возвращает начальный
  запрос, — это URL шлюза, привязанный к клиенту; данные передаются в сеанс
  upstream с теми же учётными данными, а готовый файл принадлежит клиенту.
  Другой клиент с этим URL получит 404. За прокси задайте `public_base_url`
  (или передавайте `Host` и доверенный `X-Forwarded-Proto`), чтобы URL
  указывал на адрес, доступный клиентам.
- То же правило действует для файлов, на которые ссылаются другие запросы:
  `file_id` в сообщении Chat, Responses или Claude (включая `file_ids`
  контейнера code interpreter), `fileData.fileUri` Gemini, указывающий на файл
  Files API, и `input_reference` видео. На файл, загруженный не этим клиентом,
  ответ 404 приходит до отправки чего-либо; запрос выполняется с учётными
  данными, у которых хранятся файлы. Файлы, загруженные с двумя разными
  учётными данными, нельзя использовать в одном запросе (400). Формы multipart
  проверяются так же (поля `file_id`, `file_ids[]`, `input_reference[file_id]`).
- В WebSocket Responses новый ответ открывает соединение с upstream на учётных
  данных, у которых хранятся файлы, на которые он ссылается. Продолжение
  (`previous_response_id`) остаётся на своей учётной записи, поэтому файлы,
  загруженные в другом месте, отклоняются событием `error`; чтобы их
  использовать, начните новый ответ.
- В сокете Realtime или Gemini Live сообщение клиента со ссылкой на файл,
  который не принадлежит клиенту на учётных данных этого сокета, не
  пересылается: Realtime отвечает событием `error` (`file_not_found`), Gemini
  Live закрывает соединение с кодом `1008`.

<a id="realtime-and-websocket-sessions"></a>

### Сеансы Realtime и WebSocket

Стандартный Realtime и GPT-Live используют разные протоколы и разные права
учётной записи. Устаревшие маршруты `/v1/live` сохранены для совместимости.
Новые маршруты Live и создание собственных голосов доступны с API-ключом
OpenAI; канал Codex поддерживает стандартный Realtime, client secrets и явное
завершение вызова. Ответ 201 при создании сеанса означает лишь, что запрос
принят, а не что сеанс сможет работать.

Client secrets — это bearer-учётные данные upstream для прямого подключения.
Их тела никогда не попадают в захваты, а запросы, которые клиент затем
отправляет напрямую в upstream, обходят допуск и учёт шлюза. Явное завершение
и управляющие каналы используют область доступа клиента, создавшего вызов, и
исходные учётные данные. Привязанная модель восстанавливается до допуска, и
текущие права на модель проверяются заново.

`POST /v1/realtime/calls` — это HTTP-запрос multipart с SDP offer. Следующее
за ним рукопожатие WebSocket тела не содержит. Связывает их идентификатор
вызова — в пути или в `?call_id=`. По нему движок закрепляет сокет за учётными
данными, ответившими на offer, поэтому строка запроса пересылается без
изменений.

Сеанс realtime никогда не преобразуется между диалектами: поддерживается
только прямая передача в том же диалекте. Клиенту, который может продолжать
говорить во время ответа, нет соответствия в полудуплексном диалекте.

Запрос realtime проходит допуск до переключения протокола. Порядок такой:
аутентификация, проверка рукопожатия, допуск, рукопожатие с upstream и только
затем ответ `101`. Поэтому любой отказ — это обычный HTTP-ответ, который клиент
может прочитать; сокет, принятый и сразу закрытый, не несёт ни статуса, ни
тела, ни кода. Если upstream отклоняет рукопожатие, его ответ передаётся как
есть: `429 {"error":{"code":"insufficient_quota"}}` от поставщика сообщает
клиенту больше, чем 502 от шлюза.

Сокет realtime занимает слот параллельности до закрытия, а не только до
отправки `101`. Сеанс длиной в час держит слот этот час.

Responses использует один путь `/v1/responses` для HTTP POST и WebSocket GET.
Рукопожатие аутентифицирует клиента; затем каждый `response.create` задаёт
модель для проверки прав, маршрутизации и лимитов генерации. Независимые
потоки `stream_id` могут работать параллельно. Новая цепочка ответов может
выбрать новую цель, а продолжения с `previous_response_id` сохраняют исходную.
Простаивающие соединения Responses не занимают разрешений на параллельную
генерацию.

Нативные сокеты Responses пересылают управляющие события upstream. Мосты к HTTP
Responses, Chat, Claude и Gemini поддерживают локальный прогрев контекста,
прерывание, steering-продолжения и вставку входных данных между сегментами
HTTP-генерации. Локальный прогрев не заполняет кеш upstream. История
`store:false` живёт только пока открыто соединение клиента; сохранённые
продолжения хранят изолированную историю и привязки к цели. Начатая генерация
или генерация с неизвестным исходом не повторяется на другой цели.

<a id="codex-routes"></a>

### Маршруты Codex

Закрытые операции Codex доступны только на точке монтирования провайдера с
каналом Codex. Для провайдера с именем `codex` это
`POST /codex/v1/memories/trace_summarize`. Эти маршруты проходят обычный
допуск операций, маршрутизацию по модели и тарификацию; агрегированный `/v1`
их не предоставляет. Стандартный `/v1/moderations` сохраняет собственный
JSON-контракт `create_moderation`.

Сервисы учётной записи также доступны под `/codex/v1`, включая
`usage/thread_usage/query_v2` (POST), `usage/plan_limit_history` и ежедневные
отчёты по токенам, кредитам, рабочим пространствам, плагинам и навыкам (GET).
Нативные варианты `/codex/api/codex/**`, `/codex/backend-api/**` и
`/codex/ps/**` тоже работают. Администратор может прочитать отчёты upstream
конкретной учётной записи с заголовком `x-gproxy-view: credential:<id>`. В
представлениях по умолчанию (клиента и пула) исторические лимиты и кредиты
поставщика, которые нельзя восстановить из локальных записей, помечаются как
недоступные со значением null, а не заимствуются у другой учётной записи и не
показываются нулями.

<a id="mounts"></a>

## Точки монтирования

Один экземпляр предоставляет один и тот же API upstream на трёх видах точек
монтирования:

| Путь | Точка монтирования | Ограничивает разрешение |
| --- | --- | --- |
| `/v1/messages` | агрегированная | ничем |
| `/acme/v1/messages` | пространство имён `acme` | опубликованными именами под `acme/` |
| `/openai-prod/v1/messages` | провайдер `openai-prod` | этим провайдером |

Пространство имён — это первый сегмент опубликованного имени модели, содержащего
косую черту: публикация `acme/fast` создаёт пространство имён `acme`. Точка
монтирования провайдера использует его `name` — выбранную вами метку, а не id
строки, потому что сгенерированный id никто не станет вписывать в базовый URL
клиента. Если пространство имён и провайдер называются одинаково, побеждает
пространство имён.

Префикс отбрасывается, только если остаток пути — тоже маршрут шлюза. Без этой
проверки провайдер с именем `backend-api` поглотил бы
`/backend-api/codex/responses` — настоящий путь Codex — и превратил бы вызов
плоскости данных в несуществующую точку монтирования. Если первый сегмент
совпадает с пространством имён или провайдером, но остаток не является
известным маршрутом, путь остаётся целым и считается агрегированным.
Пропущенная точка монтирования даёт заметную 404; ошибочно распознанная
отправила бы запрос не тому upstream.

Точка монтирования сужает разрешение, добавляя префикс к имени модели — это
собственный синтаксис резолвера для провайдера или маршрута: `/acme/v1/messages`
с `{"model":"fast"}` разрешает `acme/fast`. Имя, у которого префикс уже есть,
не меняется, так что клиент может писать его любым способом. Точка
монтирования провайдера ограничивает этим провайдером и операции без модели,
например операции с файлами.

Сервисный маршрут на точке монтирования пространства имён обслуживает тот
единственный провайдер этого пространства, чей канал предлагает маршрут. Если
таких несколько, запрос отклоняется с 409; вызывайте его на точке
монтирования нужного провайдера.

<a id="oauth-issuer"></a>

## OAuth issuer

Конечные точки issuer задаются относительно префикса точки монтирования (`""`,
`/acme`, `/openai-prod`):

```text
GET  {prefix}/v1/oauth/authorize    consent handoff (302 to `/console/authorize` for a browser)
POST {prefix}/v1/oauth/authorize    the person's decision
POST {prefix}/v1/oauth/token        code, refresh and device grants
POST {prefix}/v1/oauth/device/code
POST {prefix}/v1/oauth/revoke
GET  {prefix}/v1/.well-known/oauth-authorization-server
GET  /.well-known/oauth-authorization-server{prefix}/v1   (RFC 8414 §3.1)
```

Идентификатор issuer — `{origin}{prefix}/v1`, так что для агрегированной точки
это `https://host/v1`, а не `https://host`. Так одно правило покрывает все три
вида точек монтирования. RFC 8414 требует, чтобы идентификатор совпадал с
адресом, по которому клиент получил метаданные, а знает, через какую точку
пришёл запрос, только хост, поэтому он и передаёт это значение.

Ошибки эти конечные точки возвращают в формате OAuth (RFC 6749 §5.2, `error` —
строка), а не в обычной обёртке ошибок шлюза. Страница подтверждения
устройства — это операция личного кабинета, `/portal/api/oauth/device`, её
вызывает страница консоли `/console/device`.

В v3 эти конечные точки находились в корне. После переноса под `/v1` они
подчиняются тому же правилу префикса, что и `/v1/messages`. Конечную точку
обнаружения v3 не реализовывал вовсе, так что клиенты всё равно прописывали
адреса вручную.

<a id="management-api"></a>

## API управления

У каждого семейства ресурсов управления одни и те же шесть маршрутов:

```text
GET    /admin/api/{family}           list      (page and filters in the query)
POST   /admin/api/{family}           create
GET    /admin/api/{family}/{id}      get
PATCH  /admin/api/{family}/{id}      update
DELETE /admin/api/{family}/{id}      delete    → 204
POST   /admin/api/{family}/batch     batch
       [{"create": …}, {"update": {"id": …, "patch": …}}, {"delete": "id"}]
```

Маршруты генерируются из одного объявления, так что ни одному семейству не
может недоставать какого-то из них. Пакет — это одна фиксация ревизии, сколько
бы строк он ни затрагивал: сохраняются либо все элементы, либо ни одного.

Семейства пользователей и доступа: `users`, `api-keys`, `organizations`,
`teams`, `permissions`, `rate-limits` и `oauth-clients`. Для членства в
организациях и командах есть отдельные конечные точки
(`organizations/{id}/members`, `teams/{id}/members`). Некоторые семейства
отличаются от шести маршрутов:

- У `oauth-clients` вместо удаления — `POST …/{id}/retire`, потому что выданные
  клиентом разрешения продолжают на него ссылаться. В пакете элемент delete
  выводит клиента из употребления, и пакет с такими элементами может содержать
  только delete: вывод выполняется в отдельной транзакции и не может делить
  фиксацию с созданием или изменением. Выведенный `client_id` можно
  зарегистрировать снова; новая регистрация использует ту же строку, а
  разрешения, отозванные при выводе, остаются отозванными.
- Пакет `api-keys` не принимает создание: при создании ключа возвращается его
  открытое значение, а пакету негде его вернуть.
- Пакет `users`, после которого не осталось бы ни одного включённого
  администратора, отклоняется целиком.

Семейства конфигурации: `providers`, `credentials`, `models`,
`provider-models`, `routes`, `route-members`, `connection-profiles`,
`rule-sets`, `rules`, `provider-rule-sets`, `operation-rules`,
`operation-endpoints`, `quotas`, `price-rules`, `price-rates`, `price-tiers`.

Другие конечные точки управления:

- Экземпляр: `settings`, `export`, `import`, `connectivity/test`, `audit`,
  `session`, `sessions`, `context` и `update` (если хост поддерживает
  самообновление).
- Учётные данные: `credentials/{id}/…` с `reveal`, `status`, `refresh`,
  `quota`, `quota-probe`, `quota-reset`, `quota-reset-credits`,
  `quota-diagnostics`, `quota-observations`, `health-reset`, `limits`,
  `models/discover` и `models/test`; `credentials/owners`,
  `credentials/providers`, а также входы по коду авторизации и по коду
  устройства в `credential-login/…`.
- Модели и маршрутизация: `models/discover`, `models/discover/apply`,
  `models/test`, `model-names`, `operation-keys`, `providers/{id}/routing`,
  `providers/{id}/routing-defaults/reset`, `providers/{id}/default-rule-set`.
- Правила: `rule-sets/{id}/rules`, `rule-sets/{id}/rule-presets/{preset}`,
  `rule-presets`.
- Квоты: `quotas/status`, `quotas/{id}/reset`, `quotas/{id}/limit-reset`.
- Каталоги: `channels`, `tls-presets`, `default-model-catalog`,
  `default-model-catalog/apply-prices`.
- Токенизатор: `tokenizer-vocabs`, `tokenizer-auth`.
- Пользователи: `users/{id}/password`, `users/{id}/sessions`,
  `users/{id}/allowlist`; API-ключи: `api-keys/{id}/rotate`,
  `api-keys/{id}/secret`.
- История: `usage`, `usage/records`, `logs/downstream`, `logs/upstream`,
  `logs/captures/{id}`; см. [Использование, журналы и аудит](/ru/guides/observability).

Полный список с параметрами — в [справочнике HTTP API](/ru/reference/http-api).
Форматы управления в v4 изменились, поэтому сверяйте с ним старые скрипты.

Каждый запрос управления проходит через одно промежуточное ПО:
аутентификация (для небезопасного метода с аутентификацией по cookie — ещё и
проверка того же origin), определение области управления клиента, выполнение
операции и запись в аудит. В аудит попадает каждый запрос, включая
отклонённые. Это промежуточное ПО — route layer, поэтому неизвестный путь
`/admin/api/…` даёт 404, не обращаясь к базе данных. Тело запроса управления
ограничено 50 МиБ — этого хватает для импорта конфигурации.

<a id="portal-api"></a>

## API личного кабинета

```text
POST   /portal/api/login             name + password → session cookie and token
POST   /portal/api/logout
GET    /portal/api/context           the caller, their memberships, their features
GET    /portal/api/models            every exposed name, each marked `permitted`
GET    /portal/api/usage             their own spend
GET    /portal/api/quota             their own budget windows
GET    /portal/api/requests          their recent requests, if enabled
GET    /portal/api/sessions
GET    /portal/api/keys              (+ POST, DELETE …/{id}, POST …/{id}/rotate, GET …/{id}/secret)
GET    /portal/api/oauth-sessions    (+ DELETE …/{id})
POST   /portal/api/password
GET    /portal/api/oauth/device      a pending device code (?userCode=), for `/console/device`
POST   /portal/api/oauth/device      approve or deny it; a session or a management key
```

Маршруты личного кабинета требуют только аутентифицированного клиента. Проверки
ролей нет, потому что каждая операция кабинета относится к тому клиенту, который
сделал запрос, и ни одна не принимает id пользователя. Забытая проверка роли
могла бы стать уязвимостью; параметр, которого нет, злоупотребить нельзя.

`login` и `logout` эту проверку не проходят. `login` выполняется, когда клиента
ещё нет, а `logout` должен работать и для уже истёкшего сеанса — иначе браузер
останется с cookie, от которого не сможет избавиться.

<a id="resolution-and-failover"></a>

## Разрешение имён и переключение при сбоях

Четыре формы имени модели и порядок их перебора описаны в разделе
[Модели, маршруты и опубликованные имена](/ru/guides/models). Бюджет
переключения при сбоях устроен так:

- Бюджет — это `maxAttempts` самого маршрута, ограниченный
  `settings.maxAttempts`.
- Бюджет общий для всех целей. Каждая цель получает не больше попыток, чем у
  неё учётных данных, и не больше остатка, так что план не может сделать
  больше вызовов upstream, чем позволяет бюджет.
- К следующему провайдеру запрос переходит, только если другой провайдер мог
  бы его обслужить: нет пригодных учётных данных, учётные данные недействительны,
  продолжение закреплено в другом месте, любая ошибка канала или транспорта
  либо ответ 401, 403, 429 или 5xx.
- Исчерпанный бюджет, запрещённый запрос, отмена, ошибка преобразования и сбой
  хранилища или кеша останавливают вызов на месте.
- Когда целей не осталось, последний ответ возвращается без изменений. 429 от
  последнего провайдера доходит до клиента как этот самый 429, а не как
  сгенерированная шлюзом ошибка.

Тело запроса буферизуется один раз, чтобы его можно было повторить на другой
цели. Потоковое тело больше `maxRequestBodyBytes` остаётся потоком, а план
сокращается до одной цели: читать большую загрузку в память ради переключения
при сбоях невыгодно.
